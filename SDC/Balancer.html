Load Balancer

Load balancing is the process of distributing traffic among different instances of the same application.

To create a fault-tolerant system, it’s common to run multiple instances of each application. Thus, whenever one service needs to communicate with another, it needs to pick a particular instance to send its request.

There are many algorithms when it comes to load balancing:

  • Random selection: Choosing an instance randomly
  • Round-robin: Choosing an instance in the same order each time
  • Least connections: Choosing the instance with the fewest current connections
  • Weighted metric: Using a weighted metric to choose the best instance (for example, CPU or memory usage)
  • IP hash: Using the hash of the client IP to map to an instance

A load balancer is the component that does this work. It sits between the callers and a pool of identical instances, receives every request, picks one healthy instance using its algorithm, and forwards the request there. Callers only know the balancer’s address, so instances can be added, removed, or replaced without the callers noticing.

Because no single instance has to absorb all the traffic, the system can scale horizontally by adding instances, and it keeps serving requests when one instance crashes, since the balancer simply stops sending traffic to it.

How It Works
ReceiveThe client sends its request to the balancer’s single address (a virtual IP or DNS name) instead of to any one instance.
Health CheckThe balancer continuously probes each instance (a TCP connect or an HTTP endpoint such as /health) and keeps only the healthy ones in the pool.
ChooseIt applies the configured algorithm to the healthy instances to pick the target for this request.
ForwardThe request is sent to the chosen instance, and the response travels back to the client through the balancer.
AdaptWhen an instance fails its checks it is taken out of rotation; when it recovers, or a new one is added, it starts receiving traffic again.
Load Balancing Algorithms
Round RobinSends each new request to the next instance in a fixed order, wrapping back to the first. Simple and fair when instances are identical and requests cost about the same.
Weighted Round RobinRound robin where each instance has a weight; an instance with weight 3 gets three requests for every one sent to an instance with weight 1. Useful when machines have different capacity.
RandomPicks an instance at random. Needs no shared state, and over many requests it spreads load evenly.
Least ConnectionsPicks the instance with the fewest active connections. Works well when request durations vary a lot, such as long-lived or streaming connections.
Weighted Least ConnectionsCompares active connections divided by weight, so bigger instances are allowed proportionally more open connections.
Least Response TimePicks the instance with the lowest recent response time (often combined with fewest connections), steering traffic away from slow instances.
Weighted MetricChooses using live resource metrics such as CPU or memory usage reported by each instance, sending work to the least loaded one.
IP HashHashes the client IP to pick an instance, so the same client keeps reaching the same instance. Gives simple session stickiness without cookies.
Consistent HashingPlaces instances and request keys on a hash ring; adding or removing an instance only moves the keys next to it. Common for caches and sharded data.
Types of Load Balancers
Layer 4 (Transport)Routes on IP address and TCP/UDP port without reading the request content. Very fast, but cannot route by URL, header, or cookie.
Layer 7 (Application)Reads the HTTP request and can route by path, host, header, or cookie, terminate TLS, and rewrite requests. More flexible, slightly more work per request.
HardwareDedicated appliances (for example F5 BIG-IP) with high throughput; expensive and less flexible to scale.
SoftwareRuns on ordinary servers or containers, such as NGINX, HAProxy, or Envoy; cheap and easy to automate.
Cloud ManagedProvided as a service, such as AWS ELB/ALB/NLB, Azure Load Balancer, or Google Cloud Load Balancing; scales and stays available without servers to manage.
Server-SideA separate balancer sits in front of the instances and every request passes through it; clients stay simple.
Client-SideThe caller fetches the instance list from service discovery (for example Eureka or Consul) and picks an instance itself, as Spring Cloud LoadBalancer does; no extra network hop.
Global (DNS / GSLB)Spreads users across regions or data centers by returning different addresses from DNS, often based on location or region health.
Key Features
Health ChecksActive probes and passive failure tracking remove unhealthy instances automatically and add them back once they recover.
Session PersistenceSticky sessions (cookie or IP based) keep a user on the same instance when session state lives in that instance’s memory.
TLS TerminationThe balancer decrypts HTTPS once, so instances handle plain HTTP and certificates are managed in one place.
Connection DrainingAn instance being removed stops getting new requests but finishes the ones in flight, which allows deployments without dropped requests.
Autoscaling IntegrationNew instances created by an autoscaler register with the balancer and start receiving traffic automatically.
Pros and Cons

Pros

  • High Availability
    When an instance fails its health checks, traffic goes to the remaining instances, so a single crash does not take the service down.
  • Horizontal Scalability
    Capacity grows by adding instances behind the balancer instead of buying a bigger machine.
  • Even Resource Use
    Spreading requests prevents one instance from overloading while others sit idle, keeping latency steady.
  • Zero-Downtime Deployments
    Instances can be drained, updated, and returned one at a time (rolling, blue-green, or canary releases) while users keep being served.
  • Single Entry Point
    Clients use one stable address; TLS, rate limiting, and routing rules can be applied in one place.
  • Flexibility
    Instances can be moved, resized, or replaced without changing any client configuration.

Cons

  • Single Point of Failure
    A lone balancer can itself go down; it needs a redundant pair or a managed service to avoid becoming the weakest link.
  • Extra Hop and Latency
    Every request passes through one more network component, adding a little latency and another place to troubleshoot.
  • Session State Problems
    If instances keep user sessions in memory, requests landing on a different instance lose that state unless sessions are sticky or shared.
  • Configuration Complexity
    Algorithms, health checks, timeouts, and TLS settings must be tuned correctly; mistakes can send traffic to broken instances or reject good ones.
  • Cost
    Hardware appliances and managed balancers add licensing or usage costs, and redundancy doubles them.
  • Uneven Load with Simple Algorithms
    Round robin or random can still overload an instance when some requests are much heavier than others.
Round Robin
public class RoundRobinBalancer {

    private List<String> instances;
    private AtomicInteger next = new AtomicInteger();

    public RoundRobinBalancer(List<String> instances) {
        this.instances = instances;
    }

    public String choose() {
        int index = Math.floorMod(next.getAndIncrement(), instances.size());
        return instances.get(index);
    }
}
How it works

next is a shared counter, so every call to choose() takes the following instance in order.

AtomicInteger keeps it correct when many threads pick instances at once.

floorMod wraps the counter back to the first instance, even after it overflows to a negative value.

Least Connections
public class LeastConnectionsBalancer {

    private Map<String, AtomicInteger> active = new ConcurrentHashMap<>();

    public LeastConnectionsBalancer(List<String> instances) {
        instances.forEach(i -> active.put(i,new AtomicInteger()));
    }

    public String acquire() {
        Comparator<String> load =
                Comparator.comparingInt(i -> active.get(i).get());
        String instance = Collections.min(active.keySet(), load);
        active.get(instance).incrementAndGet(); # one more open request
        return instance;
    }

    public void release(String instance) {
        active.get(instance).decrementAndGet(); # request finished
    }
}
How it works

active tracks how many requests each instance is currently handling.

acquire() picks the instance with the smallest count and increments it; the caller calls release() when the response arrives.

Slow instances hold their connections longer, so they naturally receive fewer new requests.

Spring Cloud LoadBalancer
@Configuration
public class ClientConfig {

    @Bean
    @LoadBalanced
    public RestClient.Builder restClientBuilder() {
        return RestClient.builder();
    }
}

@Service
public class PaymentClient {

    private RestClient client;

    public PaymentClient(RestClient.Builder builder) {
        this.client = builder.build();
    }

    public Payment getPayment(long id) {
        return client.get()
                .uri("http://payment-service/api/payments/{id}", id)
                .retrieve()
                .body(Payment.class);
    }
}
How it works

@LoadBalanced makes every client built from this builder resolve the host name through service discovery.

payment-service is a logical service name, not a real host; Spring replaces it with one of its registered instances on every call.

This is client-side load balancing: round robin by default, with no separate balancer in the request path.
