Docker

Docker is a containerization platform that provides a way to package an application and its dependencies into a single, self-contained unit called a container. Containers are isolated from each other and from the host operating system, which makes them an ideal solution for deploying applications in a consistent and predictable manner across different environments.

For example, using Docker, you can deploy Java and .NET Microservice in same way, unlike traditional way where you need JDK installed or CLR installed for .NET. Docker abstract that and allow you to deploy containers instead of JAR files or .NET executables.

On the other hand, Kubernetes, is an open-source platform for automating the deployment, scaling, and management of containerized applications. It provides a set of APIs and tools for deploying, scaling, and managing containers, including Docker containers.

In summary, Docker provides the containers, and Kubernetes provides the orchestration and management of those containers. The combination of Docker and Kubernetes allows organizations to manage and scale their applications more effectively and efficiently in a production environment.

It's also important to note that Kubernetes is not the only platform for orchestration and management of containers. There are many other alternatives available, such as Docker Swarm and OpenShift. However, Kubernetes is probably most popular solution in recent years due to its robust feature set, large community, and broad ecosystem.

A container is not a virtual machine. It is an ordinary process on the host that the Linux kernel isolates: namespaces give it its own view of processes, network, and file system, and cgroups limit how much CPU and memory it may use. All containers share the host’s kernel, which is why they start in milliseconds and take megabytes rather than gigabytes.

The famous “works on my machine” problem disappears because the image carries the exact runtime, libraries, and configuration the application was tested with. The same image runs unchanged on a laptop, a CI server, and production.

Core Concepts
ImageA read-only template containing the application, its runtime, libraries, and configuration. Built in layers, where each instruction in a Dockerfile adds one layer that can be cached and shared.
ContainerA running instance of an image. It adds a thin writable layer on top of the image; many containers can run from the same image.
DockerfileA text file of instructions (FROM, COPY, RUN, CMD, ...) that describes how to build an image.
RegistryA store for images, such as Docker Hub, Amazon ECR, or a private Harbor registry. Images are pushed after a build and pulled wherever they run.
Docker DaemonThe background service (dockerd) that builds images and creates, runs, and stops containers.
Docker ClientThe docker command-line tool; it sends each command to the daemon through its REST API.
VolumeStorage managed by Docker that lives outside the container’s writable layer, so data survives when the container is removed.
NetworkA virtual network that lets containers reach each other by container name; the default types are bridge, host, and none.
Docker ComposeA tool that defines and runs multi-container applications from a single compose.yaml file.
  • Virtual machines virtualize the entire hardware — including the operating system. Each VM has its own operational system (OS). This in turn requires more memory and resources.
  • Containers, on the other hand, share the host operating system and only virtualize the application layer. This makes them significantly lighter and faster.

Image Commands
docker build -t app:1.0 .Build an image from the Dockerfile in the current directory and tag it app:1.0.
docker imagesList local images.
docker pull nginx:1.27Download an image from a registry.
docker tag app:1.0 repo/app:1.0Give an image another name, usually the registry path before a push.
docker push repo/app:1.0Upload an image to a registry.
docker rmi app:1.0Remove a local image.
docker history app:1.0Show the layers an image is built from and their sizes.
docker image pruneDelete dangling (untagged) images to free disk space.
Container Commands
docker run -d -p 8080:8080 --name api app:1.0Start a container in the background, mapping host port 8080 to container port 8080.
docker run -it --rm ubuntu bashStart an interactive shell in a throwaway container that is deleted on exit.
docker psList running containers; add -a to include stopped ones.
docker logs -f apiStream a container’s standard output and error.
docker exec -it api shOpen a shell inside a running container.
docker stop apiStop a container gracefully (SIGTERM, then SIGKILL after a timeout).
docker start apiStart a stopped container again.
docker rm apiRemove a stopped container; add -f to stop and remove it.
docker inspect apiShow full configuration and state as JSON (IP address, mounts, environment).
docker statsShow live CPU, memory, and network usage per container.
docker cp api:/app/log.txt .Copy files between a container and the host.
Volume, Network and Compose Commands
docker volume create pgdataCreate a named volume.
docker run -v pgdata:/var/lib/postgresql/data postgresMount a volume into a container so its data outlives the container.
docker network create backendCreate a user-defined bridge network.
docker run --network backend --name db postgresAttach a container to a network; others on it can reach it as db.
docker compose up -dBuild if needed, then start every service in compose.yaml in the background.
docker compose downStop and remove the services and their network; add -v to remove volumes too.
docker compose logs -fFollow the combined logs of all services.
docker system pruneRemove stopped containers, unused networks, dangling images, and build cache.
Pros and Cons

Pros

  • Consistent Environments
    The image carries the exact runtime and libraries, so the application behaves the same in development, testing, and production.
  • Lightweight and Fast
    Containers share the host kernel, so they start in seconds and use far less memory and disk than virtual machines.
  • Isolation
    Each service gets its own file system, dependencies, and resource limits, so conflicting library versions can run side by side.
  • Portability
    The same image runs on any host with a container runtime: a laptop, an on-premise server, or any cloud.
  • Faster Delivery
    Images are versioned, immutable artifacts, which makes CI/CD pipelines, rollbacks, and blue-green releases straightforward.
  • Easy Scaling
    New instances are just new containers from the same image, which orchestrators such as Kubernetes start and stop automatically.

Cons

  • Weaker Isolation than VMs
    All containers share one kernel; a kernel vulnerability or a container running as root can put the whole host at risk.
  • Persistent Data Is Harder
    Container file systems are temporary; databases and other stateful services need carefully managed volumes and backups.
  • Operational Complexity
    Running many containers in production needs orchestration, service discovery, logging, and monitoring, which adds tools to learn and operate.
  • Image Sprawl and Size
    Careless Dockerfiles produce large images with outdated packages, slowing deployments and widening the attack surface.
  • Kernel Dependency
    Linux containers need a Linux kernel; on Windows and macOS Docker runs them inside a hidden virtual machine.
  • Networking and Debugging
    Port mappings, overlay networks, and short-lived containers make troubleshooting harder than on a plain server.
Dockerfile for a Spring Boot Service
# Stage 1: build the JAR with Maven
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline # cached until pom.xml changes
COPY src ./src
RUN mvn -q package -DskipTests

# Stage 2: small runtime image with only the JRE
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app
USER app # never run as root
COPY --from=build /src/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
How it works

A multi-stage build: the first stage has Maven and the full JDK, the second keeps only the JRE and the finished JAR.

Copying pom.xml before the source lets Docker reuse the cached dependency layer when only code changes.

The final image is small, contains no build tools, and runs as an unprivileged user.

Build, Run and Push
docker build -t order-service:1.0 . # build the image
docker run -d --name orders -p 8080:8080 \
    -e SPRING_PROFILES_ACTIVE=dev order-service:1.0
docker logs -f orders # follow startup logs
curl http://localhost:8080/actuator/health
docker tag order-service:1.0 registry.example.com/team/order-service:1.0
docker push registry.example.com/team/order-service:1.0
docker stop orders && docker rm orders # clean up
How it works

-d runs the container in the background, -p publishes its port on the host, and -e passes configuration as environment variables.

Tagging with the registry address and pushing makes the same image available to every other environment.

application.properties for the Container
spring.application.name=order-service
server.port=8080

# db is the database container's name on the shared network
spring.datasource.url=jdbc:postgresql://db:5432/orders
spring.datasource.username=orders
spring.datasource.password=${DB_PASSWORD}

management.endpoints.web.exposure.include=health
How it works

Inside a container, localhost is the container itself, so the database is addressed by its container name db.

The password is not baked into the image; Spring reads ${DB_PASSWORD} from an environment variable passed with docker run -e.

Any property can also be overridden at run time, for example -e SERVER_PORT=9090.

Running the Service with a Database
docker network create orders-net # containers find each other by name
docker volume create pgdata # database files outlive the container

docker run -d --name db --network orders-net \
    -e POSTGRES_DB=orders -e POSTGRES_USER=orders \
    -e POSTGRES_PASSWORD=$DB_PASSWORD \
    -v pgdata:/var/lib/postgresql/data postgres:16

docker run -d --name orders --network orders-net -p 8080:8080 \
    -e DB_PASSWORD=$DB_PASSWORD order-service:1.0
How it works

Both containers join the orders-net network, so the service reaches PostgreSQL at db:5432.

Only the service publishes a port to the host; the database stays reachable from the network alone.

Removing the db container keeps the data, because it lives in the pgdata volume.
