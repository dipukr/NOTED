Scalability

Scalability is a system's ability to handle growing amounts of work, traffic, or data efficiently without losing performance or quality. A system must be scalable in order to accommodate growing user traffic, data volumes, or computing demands without suffering a major performance hit or necessitating a total redesign.

For example, an online shopping application might initially serve 1,000 users. Later, it must serve 1 million users, store hundreds of millions of orders, and process thousands of payments per second.

A scalable design lets the system grow to meet that demand without requiring a complete redesign.

Scalability is not simply add more servers. If all those servers depend on one overloaded database, adding servers may achieve very little.

Key Techniques
Load Balancing

Spreads incoming traffic across many servers to prevent crashes.

Caching

Stores frequent data in fast memory to speed up response times.

Sharding

Splits large databases into smaller, easy-to-manage parts.

Replication

Copies data to read replicas so read traffic is spread across many nodes.

Stateless Services

Keeps user state out of app instances so any instance can serve any request.

Asynchronous Processing

Moves slow work to background workers through queues so requests return fast.

Message Queues

Buffer bursts of work and let producers and consumers scale independently.

CDN and Edge

Serve cacheable content from locations close to users to cut latency.

Database Indexing

Speeds up queries and reduces load by avoiding full table scans.

Partitioning

Divides a large table within one database to improve manageability and some queries.

Autoscaling

Adds and removes capacity automatically as demand rises and falls.

Rate Limiting

Caps request rates to protect the system from overload and abuse.

A system may scale well along one dimension and poorly along another.

  • A product catalog may support enormous read traffic through caching.
  • Same system may struggle with inventory updates because many transactions modify the same popular product.
  • A chat server may handle many idle connections but struggle when all users send messages simultaneously.

Always ask: Scalable for which workload?

Performance, scalability and availability

An application can be fast but not scalable. For example, an in-memory application on one machine might respond
in 2 ms, but its data cannot grow beyond that machine's memory. An application can also scale to high throughput while individual requests remain slow.

Vertical scalability: make one machine more powerful

Vertical scaling means increasing the resources (CPU, RAM or Storage) of an existing machine. Simple but limited by hardware maximums. This is also called scaling up. Reducing resources is scaling down.

ResourceBeforeAfter
CPU cores432
RAM16 GB128 GB
StorageLow-throughput diskHigh-throughput SSD storage
Network capacityLower bandwidthHigher bandwidth

Your application still runs on one machine, but that machine has more capacity. For a Java application this might allow:

  • More CPU-intensive tasks to run concurrently.
  • A larger heap for live application data.
  • More filesystem cache.
  • Higher disk throughput.
  • More concurrent requests, provided the application can use the additional resources.

Ways to scale vertically: increase CPU cores or speed, add RAM, use faster storage or more provisioned throughput, increase network bandwidth, and adjust application limits so it can use the new capacity.

Adding resources does not automatically remove every bottleneck. A single-threaded operation may not benefit much from additional CPU cores. A global lock can prevent multiple threads from doing useful work simultaneously.

Advantages: usually simpler to implement; often requires fewer architectural changes; keeps data and transactions within one machine; useful for databases and applications that are difficult to distribute.

Limitations: there is a maximum practical machine size; larger machines can become disproportionately expensive; resizing may require interruption; one machine remains a failure domain unless redundancy is added separately.

Example: If a database is slow because its working set does not fit in memory, adding RAM may be a highly effective first step.

Horizontal scalability: add more machines or instances

Horizontal scaling means increasing the number of machines or nodes or application instances. This is also called scaling out. Removing instances is scaling in. Adding more machines or nodes to share the workload. This handles massive growth well, but requires complex setup like load balancing.

Instead of one large application server, you run several servers and distribute work across them.

When one instance can sustainably process 500 requests/second, four instances might approach 2,000 requests/second if shared dependencies and workload distribution allow it. The diagram also reveals a possible limitation: all three instances still depend on the same database.

Ways to scale horizontally: run multiple instances behind a load balancer; add worker processes for background jobs; add database read replicas; shard data across nodes; partition event streams; distribute cache entries across cache nodes.

Advantages: capacity can grow incrementally; work spreads across many machines; supports redundancy across independent failure domains; often fits elastic workloads well.

Challenges: requests can reach different instances; data and sessions must be managed across instances; network calls add latency and partial failures; coordination and consistency become more complex; uneven distribution can overload individual nodes.

Horizontal scaling is easiest when work can be divided into relatively independent units. For example, processing 10,000 unrelated images is easier to distribute than coordinating 10,000 purchases of the last available concert ticket.

Diagonal scaling: combine vertical and horizontal

Diagonal scaling is a commonly used term for combining both approaches.

  1. Start with one instance containing 2 CPU cores and 4 GB RAM.
  2. Increase it to 8 CPU cores and 16 GB RAM.
  3. When further growth makes sense, run several instances of that size.
  4. Continue adjusting both instance size and instance count.

This is common in practice because the smallest possible instances are not always efficient and the largest possible machines are not always economical.

Scale copies, functions, or data

Vertical and horizontal describe how resources grow. Another classification describes how the application's work is divided.

ApproachWhat is divided?Example
X-axis scalingCopies of the same applicationRun 10 identical application instances
Y-axis scalingBusiness capabilities or functionsScale search separately from checkout
Z-axis scalingData or workload subsetsRoute different customers to different shards

X-axis: duplicate the application. Each instance runs the same code and can handle the same kinds of requests. For example, run five copies of a Spring Boot application behind a load balancer.

Y-axis: separate functions. Different capabilities receive independent resources:

  • Product search requires substantial read capacity.
  • Order processing requires transactional database capacity.
  • Video processing requires CPU or GPU capacity.
  • Email delivery requires background workers.

You do not need to scale all of them equally. Microservices can enable this, but microservices do not automatically make a system scalable. Poor boundaries and excessive synchronous calls can create additional bottlenecks.

Z-axis: divide the workload or data. Customer IDs in one group go to shard A, another group goes to shard B, and each shard handles only its assigned customers. This helps when one database or processing group cannot handle the full dataset or workload. The difficulty is selecting a partitioning strategy that avoids hotspots and supports your access patterns.

Stateless application design eases horizontal scaling

Suppose a user logs in through application instance A, and A stores the user's session only in its own memory. The next request reaches instance B. B does not have that session. This creates a problem because requests are distributed across instances.

A more scalable design keeps application instances stateless with respect to durable, user-specific state. That does not mean the entire system has no state — it means state is stored somewhere appropriate:

StatePossible location
Login sessionShared session store
Orders and paymentsDatabase
Uploaded filesShared object storage
Background job progressDurable job store
Temporary cached resultsLocal or distributed cache, depending on requirements

Now, any healthy instance can handle the next request.

Sticky sessions can route a user back to the same instance, but they can create uneven load and complicate failure handling. Similarly, storing uploaded files only on an application server's local disk makes it difficult for other instances to access them.

Database scalability: reads and writes

The database often becomes a bottleneck because many application instances share it. Before distributing the database, reduce unnecessary work:

  • Add appropriate indexes.
  • Examine expensive query plans.
  • Fetch only required columns and rows.
  • Avoid repeated queries and N+1 query patterns.
  • Keep transactions reasonably short.
  • Use suitable pagination.
  • Batch operations where appropriate.
  • Bound connection pools.

Read scalability — common approaches: caching frequently requested data; adding read replicas; precomputing summaries or materialized views; using a separate search system for search-heavy workloads; creating read models tailored to query patterns.

With read replicas, writes generally go to a primary, while eligible reads go to replicas. However, asynchronously replicated data may be temporarily stale. A user who updates an address may not immediately see the update if the next read goes to a lagging replica.

Write scalability — common approaches: reducing unnecessary writes; batching small writes; spreading independent writes across shards; reducing contention on frequently updated rows; using asynchronous processing where delayed completion is acceptable.

Adding read replicas usually does not increase the primary database's write capacity.

Also, partitioning a table inside one database can improve management and certain queries, but it does not necessarily distribute work across machines. Sharding specifically distributes subsets of data across database nodes. Sharding introduces trade-offs:

  • Cross-shard joins become harder.
  • Cross-shard transactions become more complex.
  • Rebalancing requires moving data.
  • Some shards may receive much more traffic than others.

For example, assigning tenants to shards works well until one tenant generates half of all traffic.

Caching: reduce repeated work

Suppose a product-details endpoint receives 20,000 requests/second. If 95% of those requests can be served from cache, the database receives approximately 1,000 read/second for that workload.

20,000 × (1 − 0.95) = 1,000 reads/second

Cache locationTypical use
BrowserStatic assets and cacheable responses
CDNImages, videos, scripts, and other cacheable content
Reverse proxyCacheable HTTP responses
Application memorySmall, frequently used local data
Distributed cacheData shared across application instances

Caching works best when data is reused enough to justify storing it. Its challenges include stale data, cache invalidation, memory limits and eviction, hot keys, and cache stampedes when many requests regenerate the same expired entry.

A cache reduces backend demand; it does not eliminate the need to plan backend capacity. A cold or unavailable cache can suddenly expose the database to much higher traffic.

Asynchronous processing: separate requests from background work

Consider an order workflow:

  1. Save the order.
  2. Send a confirmation email.
  3. Generate an invoice.
  4. Update analytics.
  5. Notify the warehouse.

If every action runs synchronously, the user waits for all of them, and downstream delays occupy request-handling capacity. Instead, the request can complete after the required durable order operation, while suitable follow-up work runs asynchronously.

An outbox can help reliably connect the database transaction to event publication. Each worker group can scale independently.

A queue absorbs bursts; it does not create processing capacity.

If jobs arrive at 10,000/second and workers process 8,000/second:

Backlog growth = 10,000 − 8,000 = 2,000 jobs/second

The backlog keeps growing until processing capacity increases or incoming work decreases. Queue-based systems also need retry handling, idempotent processing, backpressure, handling for repeatedly failing jobs, and ordering rules where required.

Geographic scalability: bring processing closer to users

When users are distributed worldwide, one region can create long network delays. Possible approaches include:

  • Serve static and cacheable content through a CDN.
  • Run application instances in multiple regions.
  • Route requests to suitable nearby regions.
  • Replicate data across regions.
  • Assign users or tenants a home region.

The difficult part is usually mutable data. For example, if two regions simultaneously update the same account balance, the system needs a clear coordination or conflict-resolution strategy. Synchronous cross-region coordination adds network latency. Asynchronous replication permits temporary differences between regions.

Geographic scaling involves decisions about latency, consistency, availability, and where writes are accepted.

The real limit is often the bottleneck

Consider a request path:

Load balancer → application → database → external payment provider

Increasing application capacity does little if the payment provider accepts only 1,000 requests/second.

A subtle example is database connection pools. If one application instance allows 50 database connections, then 100 instances could collectively attempt:

100 × 50 = 5,000 connections

Scaling the application may therefore overload the database unless pool sizes and concurrency are controlled.

Capacity planning must consider the whole request path.

Scaling is rarely perfectly linear

Ideally, doubling resources doubles throughput:

T(N) ≈ N × T(1)

where T(N) is throughput with N equivalent instances. Actual throughput is usually lower because of shared resources, network overhead, coordination, serial processing, lock contention, and uneven work distribution.

A useful theoretical model is Amdahl's law:

Speedup(N) = 1 / [s + (1 − s) / N]

Here s is the fraction of work that must remain serial, and N is the number of parallel workers. If 10% of a fixed workload is inherently serial, the theoretical maximum speedup is:

1 / 0.10 = 10×

Even an unlimited number of workers cannot remove that serial portion. Real distributed systems may perform worse because this model does not include all communication and coordination costs. This is why removing a global lock or a centralized sequencing step can matter more than adding servers.

Measure scalability against an explicit target

Handles 10,000 requests/second is incomplete. Useful measurements include:

Sustain 10,000 requests/second with p99 latency below 300 ms, errors below 0.1%, and enough spare capacity to tolerate one instance failure.

Concurrency also matters. For a stable system, Little's law relates average in-flight work, throughput, and average time in the system:

L = λW

At 2,000 requests/second and an average response time of 0.2 seconds:

L = 2,000 × 0.2 = 400 requests in flight

Approximately 400 requests are in flight on average. This does not necessarily mean 400 threads are required; that depends on the execution model. If response time increases, more requests remain in flight, which can create additional memory and connection pressure.

Autoscaling needs headroom and overload protection

Autoscaling is a mechanism for adjusting capacity as demand changes. It depends on the system already being able to scale. Common signals include:

  • CPU utilization.
  • Requests per instance.
  • Queue backlog.
  • Age of the oldest queued job.
  • Active connections.
  • Processing latency.

CPU is not always the right signal. An application waiting on a slow database may have low CPU while requests pile up. Scaling also takes time: instances must start, initialize, warm caches, and become healthy.

Useful protections include spare capacity, bounded queues, concurrency limits, rate limiting, timeouts, retries with backoff and jitter, and load shedding when capacity is exhausted.

Without these protections, retries and unbounded queues can turn a temporary overload into a larger failure.

The central design habit is to identify the workload, define acceptable service levels, measure the limiting resource, and choose a scaling approach that addresses that specific limit.
