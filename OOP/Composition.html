Composition

Composition is a stronger form of association where one object contains another object and the contained object cannot exist independently of the container.

The lifetime of the contained object depends on the lifetime of the container.

In composition if owning object is garbage collected the owned object will also be which is not the case in aggregation.

Composition means the child entity (order items) is part of a whole and cannot exist independently of the parent entity (order). The child entity is contained in the parent entity and can only be accessed via the parent entity.

Both composition and aggregation express a has-a relationship.

Composition expresses a strong has-a relationship (whole-part ownership).

Aggregation expresses a weak has-a relationship (association without ownership).

Both composition and inheritance used to solve the same problem that is code reuse.

Process of building complex objects from simpler ones is called object composition.

Use inheritance only when you want both hierarchical reuse of code and subtype polymorphism.

Code
public class Room {
    private String name;
    public Room(String name) {this.name = name;}
}

public class House {
    # House owns and creates its Rooms
    private List<Room> rooms = new ArrayList<>();

    public House() {
        rooms.add(new Room("Kitchen"));
        rooms.add(new Room("Bedroom"));
    }
}
How composition works

House creates its own Room objects internally.

The rooms belong to that house and are not shared.

When the house is garbage collected, its rooms go with it.

This models a strong part-of ownership relationship.

Composition vs Inheritance
AspectCompositionInheritance
Relationshiphas-a — an object holds a reference to anotheris-a — a subclass is a kind of its superclass
CouplingLoose — depends only on the other type's interfaceTight — subclass is bound to the parent's implementation
BindingDecided at runtime; behaviour can be swapped dynamicallyFixed at compile time by the class hierarchy
FlexibilityHigh — swap or add parts without touching the containerLow — changing the hierarchy affects all subclasses
Code reuseBy delegating to contained objectsBy inheriting fields and methods from the parent
PolymorphismVia interfaces the parts implementVia subtype substitution of the superclass
EncapsulationStrong — internals of the part stay hiddenWeaker — subclass sees protected members of the parent
Fragile base classNot affected — parts are independentProne — parent changes can silently break subclasses
Multiple sourcesCan compose many objects freelyJava allows only single class inheritance
When to useDefault choice for reuse; parts vary or change over timeOnly when you need both code reuse and subtype polymorphism
