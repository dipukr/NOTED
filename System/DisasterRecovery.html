Disaster Recovery

Disaster recovery (DR) is the plan and tooling to restore service after a major failure.

It targets events like region outages, data corruption, or catastrophic loss.

Two key objectives define it: RPO (data loss tolerance) and RTO (downtime tolerance).

Strategies range from cheap backups to costly active-active multi-region setups.

When to use / Key points
  • RPO sets how much recent data you can afford to lose; RTO sets how fast you must recover.
  • Common tiers: backup-restore, pilot light, warm standby, active-active.
  • Replicate data cross-region and test failover regularly.
  • An untested DR plan is not a real DR plan.
Advantages
  • Business continuity through catastrophic failures.
  • Bounded, predictable data loss and downtime.
  • Meets regulatory and contractual resilience requirements.
Disadvantages / Trade-offs
  • Lower RPO/RTO costs more in infrastructure and complexity.
  • Standby capacity is often idle, wasting spend.
  • Failover procedures can fail if not exercised often.
Code
// Health-based failover: fall back to the DR region on primary failure
@Service
public class FailoverClient {

    private final RegionClient primary;
    private final RegionClient secondary; // DR region

    public Response call(Request req) {
        try {
            if (primary.isHealthy()) {
                return primary.send(req);
            }
        } catch (RegionUnavailableException ex) {
            log.warn("Primary down, failing over to DR", ex);
        }
        return secondary.send(req); // warm standby serves traffic
    }
}
How it works

primary.isHealthy() gates traffic to the main region when it is up.

A failure or exception triggers failover to the DR region.

secondary is a warm standby kept in sync via cross-region replication.

The replication lag between regions determines the achievable RPO.
