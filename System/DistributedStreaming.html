Distributed Streaming

Distributed streaming continuously moves and processes unbounded event data across a cluster in near real time.

Producers publish events to durable, partitioned logs that consumers read at their own pace.

Platforms like Apache Kafka and Pulsar decouple producers from consumers and retain events for replay.

It underpins event-driven architectures, real-time analytics, and data pipelines.

When to use / Key points
  • Use for real-time pipelines, event sourcing, and decoupling services asynchronously.
  • Topics are split into partitions for parallelism; order is guaranteed within a partition.
  • Consumer groups let many consumers share partitions and scale horizontally.
  • Offsets track progress and enable replay from any point in the retained log.
  • Choose a partition key carefully to balance load and preserve per-key ordering.
Advantages
  • Decouples producers and consumers, improving resilience and flexibility.
  • High throughput with horizontal scaling via partitions.
  • Durable, replayable log enables reprocessing and multiple consumers.
Disadvantages / Trade-offs
  • Operationally complex to run and tune (brokers, partitions, retention).
  • Only per-partition ordering, not global ordering.
  • At-least-once delivery often requires idempotent consumers.
Code
# Kafka consumer in a group; key preserves per-order sequencing
@KafkaListener(topics = "orders", groupId = "billing")
public void onEvent(ConsumerRecord<String, String> rec) {
    String key = rec.key();      # same key => same partition => ordered
    long offset = rec.offset();  # position in the partition log
    try {
        billing.process(rec.value()); # make this idempotent
    } catch (Exception e) {
        log.error("failed at offset {}", offset, e);
        throw e; # let the framework retry / dead-letter
    }
}
How it works

groupId lets consumers in a group split partitions for parallelism.

The record key maps to a partition, preserving order per key.

offset records progress and allows replay from any point.

Processing should be idempotent because delivery is at-least-once.
