API Gateway

An API gateway acts as a single entry point for handling client requests to various backend services.

It acts as a reverse proxy, routing requests to the appropriate services.

It can also handle cross-cutting concerns like authentication, authorization, rate limiting, caching, logging, monitoring, protocol translation, and load balancing.

It accepts API requests, processes them based on defined policies, directs them to the right services, and combines responses for a simplified client experience.

When to use / Key points
  • Use in microservices to give clients one stable endpoint instead of many service URLs.
  • Centralizes auth, rate limiting, TLS termination, and logging out of each service.
  • Can aggregate/compose responses from several services into one payload.
  • Supports protocol translation (e.g. external REST to internal gRPC).
  • Distinct from a plain reverse proxy by adding API-aware policy and composition.
Pros and Cons
Single Entry Point

A single entry point simplifies clients and hides the internal service topology.

Removes Duplicated Logic

It removes duplicated cross-cutting logic from every backend service.

Central Policy Enforcement

It provides a central place for security, throttling, and observability.

Single Point Of Failure

It can become a single point of failure and a performance bottleneck.

Added Latency

It adds an extra network hop and latency to every request.

Risk Of Bloat

It risks becoming a bloated component if too much logic accumulates in it.

Code
# Spring Cloud Gateway: route + auth filter + rate limiting
@Bean
public RouteLocator routes(RouteLocatorBuilder b) {
    return b.routes()
        .route("orders", r -> r.path("/api/orders/**")
            .filters(f -> f
                .addRequestHeader("X-Gateway", "true")
                .requestRateLimiter(c -> c.setRateLimiter(redisRateLimiter())))
            .uri("lb://order-service")) # load-balanced backend
        .build();
}
How it works

path("/api/orders/**") matches inbound requests to a route.

Filters apply cross-cutting policy (headers, rate limiting) before forwarding.

lb://order-service resolves via service discovery and load balances.

Clients call one gateway URL; routing to services stays internal.
