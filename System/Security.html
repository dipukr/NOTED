Security (AuthN, AuthZ, XSS, SSRF, CORS, CSRF, SQL Injection, Secrets)

Application security defends against common web attack classes and data exposure.

AuthN confirms identity; AuthZ enforces least-privilege access.

Injection, XSS, CSRF, SSRF, and misconfigured CORS are recurring OWASP risks.

Secrets must never be hardcoded and must be stored in a dedicated vault.

When to use / Key points
  • Prevent SQL injection with parameterized queries, never string concatenation.
  • Stop XSS by escaping/encoding output and using a Content-Security-Policy.
  • Defend CSRF with anti-forgery tokens and SameSite cookies.
  • Restrict CORS to trusted origins; validate outbound URLs to block SSRF.
Advantages
Protects Data

Safeguards user data, integrity, and organizational reputation.

Defense In Depth

Layered controls limit the blast radius of any single flaw.

Meets Compliance

Satisfies compliance and contractual security obligations.

Disadvantages
Added Overhead

Controls add development effort and can affect performance.

Can Break Features

Overly strict policies such as CORS and CSP can break legitimate features.

Never Done

Security needs continuous review and patching over time.

Code
// Prevent SQL injection with a parameterized query
@Repository
public class UserRepository {

    private final JdbcTemplate jdbc;

    public User findByEmail(String email) {
        // '?' binds safely; user input never becomes SQL code
        String sql = "SELECT id, email FROM users WHERE email = ?";
        return jdbc.queryForObject(sql, this::mapUser, email);
    }

    private User mapUser(ResultSet rs, int row) throws SQLException {
        return new User(rs.getLong("id"), rs.getString("email"));
    }
}
How it works

The ? placeholder is bound as data, so input cannot alter the query.

queryForObject passes email separately from the SQL text.

This defeats classic ' OR 1=1 -- injection attempts.

Apply the same principle for output encoding, CSRF tokens, and secrets in a vault.
