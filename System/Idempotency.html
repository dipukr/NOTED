Idempotency

Idempotency means repeating the same operation has the same intended effect as performing it once.

For an API, this matters because clients often retry requests after timeouts or network failures. An idempotent API prevents those retries from accidentally creating duplicate orders, deducting money twice, or processing the same operation multiple times.

Let us build up the concept and then implement an idempotent order-creation API using Spring Boot.

Understanding idempotency

Consider these two operations:

balance = 1000;

Repeating this assignment leaves the balance at 1000. It is idempotent.

balance = balance + 1000;

Repeating this operation increases the balance each time. It is not idempotent.

OperationOnceThree timesIdempotent?
Set status to CANCELLEDCancelledCancelledYes
Set quantity to 555Yes
Increase quantity by 5Original + 5Original + 15No
Create a new order with a generated IDOne orderThree ordersNo, unless protected
Delete an identified resourceResource absentResource absentYes

The important phrase is same intended effect. It does not mean the server must execute identical instructions or return an identical response every time.

For example:

DELETE /orders/123

The first request might return 204 No Content; a subsequent request might return 404 NOT_FOUND.

The intended effect remains the same: order 123 is absent.

HTTP defines idempotency in terms of the intended server-side effect.

Logging each request or returning a different response does not automatically violate it.

Why APIs need idempotency

Imagine an order API without duplicate protection:

POST /orders
Content-Type: application/json

{
  "productId": 101,
  "quantity": 2
}

The following sequence occurs:

  1. The client sends the request.
  2. The server creates order 5001.
  3. The server commits the database transaction.
  4. The response is lost because the connection drops.
  5. The client sees a timeout.
  6. The client retries.
  7. The server creates order 5002.

The user intended to create one order but the database now contains two.

A timeout does not tell the client whether the server completed the operation.

The server could have failed before doing anything or succeeded and failed only while returning the response.

Idempotency allows the client to retry safely despite this uncertainty.

Idempotency and HTTP methods
HTTP methodIdempotent by HTTP semantics?Example
GETYesRead an order
HEADYesRead response metadata
OPTIONSYesDiscover communication options
PUTYesReplace a resource at a known URI
DELETEYesRemove a resource at a known URI
POSTNot guaranteedCreate a new order
PATCHNot guaranteedApply a partial change

Safe methods, PUT and DELETE are idempotent under HTTP semantics. A server must implement those semantics correctly; using the method name alone does not make faulty application logic idempotent.

A particular PATCH operation can be idempotent:

PATCH /products/101

{
  "stock": 50
}

Setting stock to 50 repeatedly has the same effect.

This operation is not naturally idempotent:

PATCH /products/101

{
  "increaseStockBy": 50
}

Likewise, we can deliberately make a particular POST endpoint idempotent using an idempotency key.

How an idempotency key works

The client generates a unique key for one logical operation:

POST /orders
Idempotency-Key: 63462ee0-8c92-40b1-b598-3fd631b48462
Content-Type: application/json

{
  "productId": 101,
  "quantity": 2
}

The server stores the key together with the request fingerprint and the result.

When the same key arrives again:

  • When the request matches, the server returns the original result.
  • When the request differs, the server rejects the request.
  • When the original request is still running, the server waits or returns a documented in-progress response.

For our implementation:

RequestResult
New key + valid bodyCreate order and store response
Existing key + same bodyReturn stored response
Existing key + different bodyReturn 409 Conflict
Concurrent requests with the same keyOne creates the order; the other waits and replays
Transaction fails before commitRoll back everything; retry may execute again

The client must reuse the same key for retries.

String key = UUID.randomUUID().toString(); Every retry of THIS operation must reuse key.

Generating a new key on every retry defeats the mechanism.

Two intentional purchases of the same product should use different keys, even when the request bodies are identical.

What the server needs to store

A useful idempotency record contains:

FieldPurpose
Caller or tenant IDPrevent different users from sharing the same key scope
OperationDistinguish order creation from other operations
Idempotency keyIdentify this logical request
Request hashDetect reuse of a key with different input
HTTP statusReplay the original result status
Response bodyReplay the original result body
Relevant response headersFor example, Location
Creation timeSupport retention and cleanup

The uniqueness boundary should usually be:

(caller, operation, idempotency_key)

Using only the key globally can cause unintended collisions between users or endpoints.

Why “check first, then insert” is unsafe

This code looks reasonable but contains a race condition:

if (!repository.existsByKey(key)) {
    Order order = createOrder(request);
    repository.saveResult(key, order);
}

Two application instances can execute it simultaneously:

TimeInstance AInstance B
1Checks key: absent |
2Checks key: absent
3Creates order A |
4Creates order B
5Stores resultTries to store duplicate key

Even if the final insert fails, the duplicate business effect may already have happened—especially if it involved another service.

The solution is to atomically claim the key before performing the business operation, and coordinate the claim and database changes in one transaction.

A Java synchronized block is insufficient when the application runs on multiple instances.

Spring Boot implementation

We will implement:

POST /orders
Idempotency-Key: <unique-key>

The example uses:

  • Java 17+.
  • Spring Boot 3.x with Spring MVC.
  • Spring JDBC.
  • PostgreSQL.
  • Bean Validation.
  • application.properties.

Using JDBC makes the transaction and SQL behavior explicit. The same architecture can be implemented using JPA.

Scope: this example creates an order entirely within one database. It does not call a payment provider or another remote service.

Package declarations and routine imports are omitted.

Database schema

Create src/main/resources/schema.sql:

CREATE TABLE IF NOT EXISTS orders (
    id UUID PRIMARY KEY,
    caller_id VARCHAR(100) NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS idempotency_records (
    caller_id VARCHAR(100) NOT NULL,
    operation VARCHAR(100) NOT NULL,
    idempotency_key VARCHAR(100) NOT NULL,

    request_hash CHAR(64) NOT NULL,

    response_status INTEGER,
    response_body TEXT,
    response_location TEXT,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (
        caller_id,
        operation,
        idempotency_key
    )
);

The primary key is the database-level concurrency safeguard.

The response fields are initially empty inside the transaction. They are filled before commit, so another request should never observe a committed incomplete record through this code path.

Request and response models

public record CreateOrderRequest(@NotNull @Positive Long productId, @Min(1) int quantity) {}
public record OrderResponse(UUID orderId, Long productId, int quantity, String status) {}

The service returns the actual serialized response:

public record StoredHttpResponse(int status, String body, String location, boolean replayed) {}

Storing the serialized body avoids rebuilding the response from an order that may have changed since creation.

Request fingerprint

We need to detect this misuse:

Key: abc
First request: product 101, quantity 2

Key: abc
Second request: product 101, quantity 10

Those are different operations, so the second request must not silently reuse the first result.

@Component
public class RequestFingerprint {

    public String hash(CreateOrderRequest request) {
        String canonical = "create-order:v1" + "|productId=" + request.productId()
                         + "|quantity=" + request.quantity(); # Canonical representation for this specific request model.
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] bytes = digest.digest(canonical.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(bytes);
        } catch (NoSuchAlgorithmException ex) {
            throw new IllegalStateException("SHA-256 is unavailable", ex);
        }
    }
}

This uses parsed fields instead of raw JSON, so different whitespace or JSON field ordering does not change the hash.

For complex payloads, define a canonical representation carefully. Include every field that changes the operation, including relevant path parameters and semantic headers. Do not blindly concatenate arbitrary strings with delimiters.

Transactional service

This is the core implementation:

@Service
public class OrderService {

    private static final String OPERATION = "CREATE_ORDER_V1";

    private JdbcTemplate jdbc;
    private ObjectMapper objectMapper;
    private RequestFingerprint fingerprint;

    public OrderService(JdbcTemplate jdbc, ObjectMapper objectMapper, RequestFingerprint fingerprint) {
        this.jdbc = jdbc;
        this.objectMapper = objectMapper;
        this.fingerprint = fingerprint;
    }

    @Transactional(isolation = Isolation.READ_COMMITTED, rollbackFor = Exception.class, timeout = 10)
    public StoredHttpResponse createOrder(String callerId, String key, CreateOrderRequest request) {
        String requestHash = fingerprint.hash(request);
        # 1. Atomically attempt to claim this logical operation.
        int inserted = jdbc.update("""
                INSERT INTO idempotency_records (
                    caller_id,
                    operation,
                    idempotency_key,
                    request_hash
                )
                VALUES (?, ?, ?, ?)
                ON CONFLICT (
                    caller_id,
                    operation,
                    idempotency_key
                ) DO NOTHING
                """, callerId, OPERATION, key, requestHash);
        # 2. A committed result already exists.
        if (inserted == 0) {
            ExistingResult existing = jdbc.queryForObject("""
                    SELECT request_hash,
                           response_status,
                           response_body,
                           response_location
                    FROM idempotency_records
                    WHERE caller_id = ?
                      AND operation = ?
                      AND idempotency_key = ?
                    """,
                    (rs, rowNum) -> new ExistingResult(rs.getString("request_hash"),
                                                       rs.getObject("response_status", Integer.class),
                                                       rs.getString("response_body"),
                                                       rs.getString("response_location")),
                    callerId, OPERATION, key);
            if (existing == null) {
                throw new IllegalStateException("Idempotency record disappeared");
            }
            if (!existing.requestHash().equals(requestHash)) {
                throw new ResponseStatusException(HttpStatus.CONFLICT,
                                                  "Idempotency key was already used with a different request");
            }
            if (existing.status() == null || existing.body() == null || existing.location() == null) {
                throw new IllegalStateException("Committed idempotency result is incomplete");
            }
            return new StoredHttpResponse(existing.status(), existing.body(), existing.location(), true);
        }
        # 3. We own this operation. Perform the database change.
        UUID orderId = UUID.randomUUID();
        jdbc.update("""
                INSERT INTO orders (
                    id,
                    caller_id,
                    product_id,
                    quantity,
                    status
                )
                VALUES (?, ?, ?, ?, ?)
                """, orderId, callerId, request.productId(), request.quantity(), "CREATED");
        # 4. Serialize the result before committing.
        OrderResponse response = new OrderResponse(orderId, request.productId(), request.quantity(), "CREATED");
        String responseBody = toJson(response);
        String location = "/orders/" + orderId;
        # 5. Save the result in the SAME database transaction.
        int updated = jdbc.update("""
                UPDATE idempotency_records
                SET response_status = ?,
                    response_body = ?,
                    response_location = ?
                WHERE caller_id = ?
                  AND operation = ?
                  AND idempotency_key = ?
                """, 201, responseBody, location, callerId, OPERATION, key);
        if (updated != 1) {
            throw new IllegalStateException("Could not store idempotency result");
        }
        return new StoredHttpResponse(201, responseBody, location, false);
    }

    private String toJson(OrderResponse response) {
        try {
            return objectMapper.writeValueAsString(response);
        } catch (JsonProcessingException ex) {
            throw new IllegalStateException("Could not serialize order response", ex);
        }
    }

    private record ExistingResult(String requestHash, Integer status, String body, String location) {}
}

The transaction includes all three steps:

Claim key + create order + store response

They commit together or roll back together.

Spring applies Transactional through a proxy. Calling the service from the controller goes through that proxy; calling an annotated method from another method on the same object generally does not. The explicit rollback rule also covers checked exceptions.

Controller

@RestController
@RequestMapping("/orders")
public class OrderController {

    private OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<String> create(@RequestHeader("Idempotency-Key") String key,
                                         @Valid @RequestBody CreateOrderRequest request) {
        if (!key.matches("[A-Za-z0-9._:-]{1,100}")) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "Invalid Idempotency-Key");
        }
        String callerId = "demo-customer"; # Demo only. In production, derive this from authenticated identity.
        StoredHttpResponse result = orderService.createOrder(callerId, key, request);
        return ResponseEntity
                .status(result.status())
                .contentType(MediaType.APPLICATION_JSON)
                .header(HttpHeaders.LOCATION, result.location())
                .header("Idempotency-Replayed", Boolean.toString(result.replayed()))
                .body(result.body());
    }
}

Idempotency-Replayed is a custom diagnostic header for this example.

In production, derive callerId from a trusted authentication context. Authentication and authorization must run for retries too.

What happens when two requests arrive together?

Suppose requests A and B have the same caller, operation, and key.

The primary key prevents both requests from owning the same key.

PostgreSQL’s ON CONFLICT DO NOTHING can resolve a conflict against a concurrent transaction even when that row was not visible in the insert statement’s original snapshot. At READ COMMITTED, the following SELECT gets a fresh snapshot and can read the committed result. This is why the example uses a separate insert and select.

If A rolls back, B can successfully insert the key and perform the operation itself.

If waiting exceeds the configured timeout, B fails and can retry using the same key.

This design assumes retained records are not deleted concurrently with requests that still fall within the supported retry period.

What happens when failures occur?
Failure pointDatabase outcomeBehavior on retry
Before claiming the keyNo changesExecute normally
After claiming, before inserting the orderTransaction rolls backExecute normally
After inserting order, before storing responseBoth inserts roll backExecute normally
After storing response, before commitEntire transaction rolls backExecute normally
After commit, before client receives responseOrder and response remain savedReplay saved response

The critical case is the last one: the business operation succeeded, but the client does not know it.

Because the response was saved in the same transaction, a retry can recover the result.

A process crash may leave the database transaction open briefly until the connection failure is detected. Competing requests can wait during that interval; they must still respect timeouts.

Why this does not automatically solve remote payments

Consider adding this inside the transaction:

paymentProvider.charge(request);

A dangerous sequence is:

  1. The payment provider charges the customer.
  2. Your application crashes.
  3. Your local transaction rolls back.
  4. A retry finds no idempotency record.
  5. Your application calls the payment provider again.

A local database rollback cannot undo an external HTTP request.

For remote effects, additional coordination is needed:

TechniquePurpose
Provider-side idempotency keyPrevent duplicate remote charges
Transactional outboxAtomically store local changes and an intent to send a message
Idempotent consumerPrevent duplicate message deliveries from repeating database effects
Persistent workflow stateTrack progress and recover uncertain outcomes
ReconciliationAsk the provider what actually happened after a timeout

A payment provider key should identify the same logical payment across every retry and recovery attempt.

An outbox alone does not guarantee that a remote effect happens once.
Dispatch can repeat, so the recipient must also deduplicate or support idempotency.

Short operations versus long-running operations

The implementation above holds one database transaction open until order creation finishes which is appropriate for short, local database work.

Long-running operations often use a persisted state machine:

IN_PROGRESS
COMPLETED
FAILED

The initial claim is committed separately and workers continue processing.

However, this introduces additional questions:

  • What happens when the worker crashes after claiming the key?
  • How do we distinguish a slow worker from a dead worker?
  • Can another worker take over?
  • How do we prevent the original worker from continuing after takeover?
  • What if the external operation succeeded but its result was never recorded?

Such systems may need leases, ownership tokens, fencing, provider idempotency, and reconciliation.

Simply inserting IN_PROGRESS in one transaction and completing the work in another does not provide the same atomic guarantee as our local database example.

Important design decisions

Which errors should be stored?

Our example stores successful results only.

OutcomeExample policy
Invalid request bodyReject before claiming; do not store
Successful order creationStore and replay
Key reused with different inputReject with conflict
Temporary database failureRoll back and allow retry
Final business rejectionDecide whether to store and replay

For example, “insufficient balance” could be treated as a final result for that key, or as a retryable failure. Define the contract explicitly.

If you want to retain a business rejection, store that response and commit it deliberately. Throwing an exception that rolls back the transaction would also remove the result.

How long should keys be retained?

Retention must cover the period during which clients, queues, or recovery jobs might retry.

After deleting the record, the same key can create another order. Therefore, retention limits the duration of the deduplication guarantee.

For business operations that must never repeat, also consider a durable domain constraint, such as:

UNIQUE (merchant_id, merchant_order_reference)

Is idempotency the same as caching?

No.

AspectCachingIdempotency
Main purposeImprove performancePrevent repeated effects
Cache missUsually recomputeMay execute the business operation
Losing stored dataUsually affects performanceCan permit duplicate execution
Key identityData being requestedOne logical operation

An idempotency result store may resemble a cache, but it is part of the correctness mechanism.

Does idempotency prevent all concurrency problems?

No. It coordinates requests with the same operation identity.

Two different keys can still try to purchase the last unit of stock. Inventory correctness needs its own controls, such as an atomic conditional update:

UPDATE inventory
SET available = available - :quantity
WHERE product_id = :productId
  AND available >= :quantity;

Check that exactly one row was updated.

Does idempotency mean exactly-once execution?

No. The server may receive and begin handling a request many times.

The goal here is at most one committed order creation for a retained caller-operation-key combination, with retries returning the saved result.

The essential implementation rule is: claim the key atomically, perform the local business change, and save the result in one transaction. For external effects, extend that protection across the service boundary.
