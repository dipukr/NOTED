Autoscaling

Autoscaling automatically adjusts the number of running instances based on live demand.

It adds capacity when load rises and removes it when load falls, without manual intervention.

Scaling decisions are driven by metrics such as CPU, memory, request rate, or queue depth.

It keeps performance stable during spikes while controlling cost during quiet periods.

When to use / Key points
  • Use for variable or spiky workloads where fixed capacity wastes money or fails under load.
  • Reactive autoscaling responds to metrics; predictive autoscaling forecasts demand.
  • Set min/max bounds and cooldowns to avoid thrashing (rapid scale up/down).
  • Requires stateless, horizontally scalable services to add/remove replicas safely.
  • Pair with health checks so new instances only receive traffic once ready.
Advantages
Cost Efficiency

Matches capacity to demand, cutting idle-resource cost.

Absorbs Spikes

Absorbs traffic spikes without human intervention.

Improved Availability

Improves availability by replacing unhealthy instances.

Disadvantages
Scaling Lag

New instances take time to boot and warm up before serving traffic.

Misconfiguration Risk

Misconfigured thresholds cause flapping or runaway cost.

Stateless Only

Only helps stateless tiers; stateful stores need separate strategies.

Code
# Expose a queue-depth metric so the autoscaler can scale on backlog
@Component
public class QueueMetrics {

    private final TaskQueue queue;

    QueueMetrics(MeterRegistry reg, TaskQueue queue) {
        this.queue = queue;
        reg.gauge("queue.depth", queue, TaskQueue::size); # scaling signal
    }
}
How it works

reg.gauge() continuously publishes the current queue depth.

The autoscaler reads queue.depth and adds workers when backlog grows.

Scaling on backlog reacts faster than CPU for queue-driven workloads.

As workers drain the queue, the metric falls and instances scale back in.
