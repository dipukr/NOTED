Vertical Scaling

Vertical scaling (scaling up) increases the capacity of a single machine by adding CPU, RAM, or faster storage.

The same application runs on a bigger box rather than on more boxes.

It is simple because the architecture and code usually stay unchanged.

It is limited by the maximum size of a single machine and creates a single point of failure.

When to use / Key points
  • Use early, when a bigger machine is cheaper and simpler than going distributed.
  • Good for stateful systems (single-node databases) that are hard to shard.
  • Quick fix for immediate bottlenecks while a scale-out plan is prepared.
  • Watch for the hard ceiling of the largest available instance type.
  • Often combined later with horizontal scaling once the node is maxed out.
Advantages
  • Simple - no code changes or distributed coordination needed.
  • No data partitioning; consistency stays easy on one node.
  • Lower network overhead than a multi-node deployment.
Disadvantages / Trade-offs
  • Hard upper limit set by the biggest machine available.
  • Single point of failure - the one node going down stops everything.
  • High-end hardware gets disproportionately expensive.
  • Upgrades often require downtime or a restart.
Code
# Vertical scaling is mostly config: give the JVM more of the bigger box
# -Xms and -Xmx set heap; more RAM on the host lets you raise them
public class RuntimeInfo {
    public static void print() {
        Runtime rt = Runtime.getRuntime();
        int cores = rt.availableProcessors();      # scales with more CPU
        long maxMb = rt.maxMemory() / (1024 * 1024); # scales with more RAM
        System.out.println("cores=" + cores + " maxHeapMB=" + maxMb);
    }
}
How it works
  • availableProcessors() grows when the host gets more CPU cores.
  • maxMemory() reflects the heap ceiling raised via -Xmx on a bigger box.
  • The application code is unchanged - only the machine and JVM flags grow.
  • This simplicity is the appeal, but the single node remains the limit.
