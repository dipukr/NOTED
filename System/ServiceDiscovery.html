Service Discovery

Service discovery lets services find the network locations of other services automatically.

In dynamic environments, instances start, stop, and move, so their addresses cannot be hardcoded.

A service registry keeps an up-to-date map of service names to healthy instance addresses.

It comes in client-side and server-side flavours.

When to use / Key points
  • Use in microservices/cloud where instances are ephemeral and IPs change.
  • Instances register on startup and deregister (or expire) on shutdown/failure.
  • Client-side discovery: the caller queries the registry and picks an instance.
  • Server-side discovery: a load balancer/gateway resolves the service for the caller.
  • Tools include Consul, Eureka, etcd, and Kubernetes DNS/Services.
Advantages
  • No hardcoded addresses - services scale and move freely.
  • Health-aware routing sends traffic only to live instances.
  • Supports elasticity and automated deployments.
Disadvantages / Trade-offs
  • The registry is critical infrastructure that must be highly available.
  • Stale entries can route traffic to dead instances.
  • Adds moving parts and consistency concerns.
Code
# Client-side discovery via Spring Cloud DiscoveryClient
@Service
public class OrderClient {

    private final DiscoveryClient discovery;
    private final RestTemplate http;

    OrderClient(DiscoveryClient d, RestTemplate h) {
        this.discovery = d; this.http = h;
    }

    public String fetch(Long id) {
        # resolve a live instance by logical service name
        ServiceInstance inst = discovery.getInstances("order-service").get(0);
        String url = inst.getUri() + "/orders/" + id;
        return http.getForObject(url, String.class);
    }
}
How it works

getInstances("order-service") looks up live addresses from the registry.

The caller picks an instance and builds the URL dynamically.

No IP is hardcoded, so instances can scale or move freely.

A real client adds load balancing and retries across instances.
