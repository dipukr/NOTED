CAP Theorem

The CAP theorem states a distributed data store can provide at most two of Consistency, Availability, and Partition tolerance at once.

Consistency means every read sees the most recent write; Availability means every request gets a response; Partition tolerance means the system keeps working despite dropped network messages.

Because network partitions are unavoidable, real systems must tolerate them and then choose between consistency and availability during a partition.

This gives two practical categories: CP systems and AP systems.

When to use / Key points
  • Partition tolerance is mandatory in distributed systems, so the real choice is C vs A during a partition.
  • CP (e.g. many RDBMS clusters, ZooKeeper): reject or block requests to stay consistent.
  • AP (e.g. Cassandra, DynamoDB): keep serving, accepting temporarily stale data.
  • Choose CP for money/inventory correctness; choose AP for feeds/carts where uptime matters more.
  • When no partition exists, systems can offer both C and A - the trade-off only bites during faults.
Pros and Cons
Clear Reasoning Framework

It gives a clear framework for reasoning about distributed trade-offs.

Guides Datastore Choice

It guides datastore selection based on business needs.

Explicit Fault Consequences

It makes the consequences of network faults explicit up front.

Oversimplified Model

It is a simplification, since real systems offer tunable consistency levels.

Ignores Latency

It ignores latency, which PACELC extends to address.

Commonly Misread

"Two of three" is often misread, as partition tolerance is not really optional.

Code
# Tunable consistency: pick CP-ish or AP-ish per query (Cassandra-style)
public Row read(String key, boolean strong) {
    ConsistencyLevel level = strong
        ? ConsistencyLevel.QUORUM   # favours consistency (CP)
        : ConsistencyLevel.ONE;     # favours availability (AP)

    Statement stmt = SimpleStatement.newInstance(
            "SELECT * FROM data WHERE k = ?", key)
        .setConsistencyLevel(level);
    return session.execute(stmt).one();
}
How it works

QUORUM requires a majority of replicas to agree, leaning consistent (CP).

ONE answers from a single replica, leaning available (AP) but possibly stale.

The choice is per-request, showing CAP as a spectrum, not a binary.

During a partition, QUORUM may fail while ONE still responds.
