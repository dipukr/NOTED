Alerting Systems

An alerting system watches metrics and logs and notifies humans when something needs attention.

Rules define thresholds or conditions that, when breached, fire an alert.

Alerts route to channels like email, Slack, or PagerDuty with severity and context.

Good alerting is actionable, low-noise, and tied to user-facing symptoms.

When to use / Key points
  • Alert on symptoms (error rate, latency, saturation), not every internal cause.
  • Use severity levels so pages fire only for urgent, actionable issues.
  • Apply for-durations and grouping to avoid flapping and alert storms.
  • Every alert should link to a runbook describing what to do.
Pros and Cons
Early Detection

Detects incidents early, reducing mean time to detection.

No Constant Watching

Frees engineers from constantly staring at dashboards.

Correct Routing

Routes the right issue to the right on-call responder.

Alert Fatigue

Noisy or flapping alerts cause fatigue and ignored pages.

Bad Thresholds

Poor thresholds miss real issues or fire on non-issues.

Ongoing Tuning

Requires ongoing tuning as the system and traffic evolve.

Code
// Expose a metric that an alerting rule can watch (Micrometer)
@Service
public class PaymentService {

    private final Counter failures;

    public PaymentService(MeterRegistry registry) {
        this.failures = Counter.builder("payment.failures")
                .description("Failed payment attempts")
                .register(registry);
    }

    public void charge(Payment p) {
        try {
            gateway.charge(p);
        } catch (GatewayException ex) {
            failures.increment(); // alert fires when rate crosses threshold
            throw ex;
        }
    }
}
How it works

Counter records a monotonically increasing count of payment failures.

Prometheus scrapes the metric; an alert rule watches its rate over time.

failures.increment() feeds real-time data the alerting engine evaluates.

Alertmanager then groups, deduplicates, and routes the notification.
