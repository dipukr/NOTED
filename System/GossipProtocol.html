Gossip Protocol

A gossip protocol spreads information across a cluster the way rumours spread among people.

Each node periodically exchanges state with a few random peers, and the information propagates exponentially.

It is decentralized, requires no central coordinator, and tolerates node failures well.

It is widely used for membership, failure detection, and eventually-consistent state sharing.

When to use / Key points
  • Use for cluster membership and failure detection in large, dynamic clusters.
  • Each round, a node picks random peers and merges state, converging over time.
  • Scales well - load per node stays roughly constant as the cluster grows.
  • Provides eventual consistency, not immediate agreement.
  • Used by Cassandra, DynamoDB, Consul, and similar systems.
Advantages
  • Highly scalable and robust to node failures.
  • No single point of failure or central coordinator.
  • Fast, exponential propagation of updates.
Disadvantages / Trade-offs
  • Only eventually consistent - updates take several rounds to reach all nodes.
  • Redundant messages consume some bandwidth.
  • Convergence time and reasoning about state are harder than with a coordinator.
Code
# One gossip round: merge state with a few random peers
@Scheduled(fixedRate = 1000) # gossip every second
public void gossip() {
    List<Node> peers = cluster.randomPeers(3);
    for (Node peer : peers) {
        Map<String, Heartbeat> theirs = peer.exchange(localState);
        theirs.forEach((id, hb) ->
            localState.merge(id, hb, Heartbeat::newer)); # keep latest
    }
}
How it works
  • randomPeers(3) picks a small random subset each round.
  • exchange swaps membership/heartbeat state between the two nodes.
  • Heartbeat::newer merges by keeping the most recent info per node.
  • Over successive rounds every node's view converges cluster-wide.
