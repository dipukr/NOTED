Replication (Leader-Follower, Multi-leader)

Replication keeps copies of data on multiple nodes for availability, durability, and read scaling.

In leader-follower, one node accepts writes and streams changes to read-only followers.

Multi-leader allows several nodes to accept writes, needing conflict resolution.

Replication can be synchronous (safe, slower) or asynchronous (fast, risk of loss).

When to use / Key points
  • Use leader-follower to scale reads and provide failover for most databases.
  • Use multi-leader for multi-region writes or offline-capable clients.
  • Synchronous replication guarantees no data loss on failover but adds latency.
  • Watch for replication lag causing stale reads on followers.
Pros and Cons
High Availability

Failover to a replica keeps the system available when the leader goes down.

Read Scaling

Distributing queries across followers spreads read load beyond a single node.

Geographic Locality

Placing replicas near users reduces latency for distant clients.

Risk Of Data Loss

Async replication can lose recent writes if the leader fails before they propagate.

Write Conflicts

Multi-leader setups introduce write conflicts that require resolution logic.

Replication Lag

Lag produces inconsistent, stale reads across replicas.

Code
// Route reads to a follower, writes to the leader datasource
public class RoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        // read-only transactions go to a replica
        return TransactionSynchronizationManager
                .isCurrentTransactionReadOnly() ? "replica" : "primary";
    }
}

@Service
public class ReportService {

    @Transactional(readOnly = true) // served by a follower
    public List<Sale> recentSales() {
        return saleRepository.findTop100ByOrderByCreatedAtDesc();
    }
}
How it works

AbstractRoutingDataSource picks a datasource per transaction at runtime.

isCurrentTransactionReadOnly() distinguishes reads from writes.

@Transactional(readOnly = true) marks queries safe to serve from a replica.

Writes fall through to "primary", the single leader that streams to followers.
