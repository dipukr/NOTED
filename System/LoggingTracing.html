Logging and Distributed Tracing (ELK, Jaeger, Zipkin)

Logging records discrete, timestamped events for debugging and auditing.

The ELK stack (Elasticsearch, Logstash, Kibana) centralizes and searches logs.

Distributed tracing follows a single request across many services as a set of spans.

Jaeger and Zipkin visualize traces to expose latency and bottlenecks.

When to use / Key points
  • Use structured (JSON) logs so they are searchable and machine-parseable.
  • Propagate a trace id and span ids across service boundaries.
  • A trace is a tree of spans; each span times one operation.
  • Sample traces to control volume while keeping representative coverage.
Advantages
  • Centralized logs make cross-service investigation practical.
  • Traces pinpoint which service and call caused latency.
  • Correlating logs with traces speeds root-cause analysis.
Disadvantages / Trade-offs
  • Log and trace volume drives storage and cost.
  • Instrumenting every service consistently takes effort.
  • Aggressive sampling can miss the exact failing request.
Code
// Structured logging plus a manual trace span (Micrometer Tracing)
@Service
public class InvoiceService {

    private static final Logger log =
            LoggerFactory.getLogger(InvoiceService.class);

    private final Tracer tracer;

    public void generate(Long orderId) {
        Span span = tracer.nextSpan().name("invoice.generate").start();
        try (Tracer.SpanInScope scope = tracer.withSpan(span)) {
            log.info("Generating invoice orderId={}", orderId);
            invoiceRepository.create(orderId);
        } finally {
            span.end(); // records duration into the trace
        }
    }
}
How it works

log.info("...{}", orderId) emits a structured, parameterized log line.

tracer.nextSpan() creates a child span for this operation.

withSpan(span) makes the span current so logs carry its trace id.

span.end() records the timing that Jaeger or Zipkin displays.
