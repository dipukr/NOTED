Pagination (Offset vs Cursor)

Pagination splits a large result set into smaller, ordered pages so clients fetch data incrementally.

Offset pagination uses LIMIT and OFFSET to skip rows and return the next slice.

Cursor (keyset) pagination remembers the last seen key and asks for rows after it.

Cursor pagination scales far better on deep pages and stable feeds.

When to use / Key points
  • Use offset pagination for small datasets, admin tables, or jump-to-page UIs.
  • Use cursor pagination for infinite scroll, activity feeds, and large tables.
  • Cursor requires a stable, unique, ordered column (e.g. id or created_at + id).
  • Always apply a deterministic ORDER BY or pages become inconsistent.
Advantages
  • Offset: simple, supports arbitrary page jumps and total counts.
  • Cursor: constant-time page reads regardless of depth.
  • Cursor: no rows skipped or duplicated when data is inserted mid-scroll.
Disadvantages / Trade-offs
  • Offset: deep pages scan and discard many rows, degrading performance.
  • Offset: inserts/deletes shift rows, causing skipped or repeated items.
  • Cursor: cannot jump to an arbitrary page number easily.
  • Cursor: exposing raw keys may leak ordering; encode the cursor token.
Code
// Cursor (keyset) pagination in Spring Data JPA
public interface OrderRepository extends JpaRepository<Order, Long> {

    // Fetch the next page AFTER the last seen id
    List<Order> findByIdGreaterThanOrderByIdAsc(Long lastId, Pageable page);
}

public List<Order> nextPage(Long cursor, int size) {
    Long after = (cursor == null) ? 0L : cursor;
    return orderRepository.findByIdGreaterThanOrderByIdAsc(
            after, PageRequest.of(0, size));
}

// Offset pagination for comparison
public Page<Order> offsetPage(int pageNo, int size) {
    return orderRepository.findAll(
            PageRequest.of(pageNo, size, Sort.by("id")));
}
How it works
  • findByIdGreaterThanOrderByIdAsc reads rows strictly after the cursor, using the primary-key index.
  • PageRequest.of(0, size) limits the fetch; page 0 because the cursor already positions us.
  • cursor == null handles the first request by starting from the lowest id.
  • findAll with a page number shows the classic offset approach that scans skipped rows.
