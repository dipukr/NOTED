Distributed Locks

A distributed lock coordinates access to a shared resource across multiple processes or machines.

It ensures that only one node performs a critical operation at a time, even though they run on different hosts.

Unlike an in-process lock, it relies on an external store such as Redis, ZooKeeper, or etcd.

Correct distributed locks require expiry, ownership checks, and fencing to remain safe.

When to use / Key points
  • Use to prevent duplicate work (one scheduler, one job runner) across a cluster.
  • Always set a TTL so a crashed holder's lock is released automatically.
  • Store a unique owner token so only the owner can release the lock.
  • Use fencing tokens to reject actions from a lock that already expired.
  • Prefer proven implementations (Redisson, ZooKeeper recipes) over hand-rolled ones.
Pros and Cons
Cross-Machine Mutual Exclusion

Guarantees mutual exclusion across separate machines.

Prevents Duplicate Work

Prevents duplicate processing and race conditions on shared resources.

Safe Single-Runner Scheduling

Enables safe single-runner scheduling in a horizontally scaled system.

Hard To Get Correct

Hard to make fully correct under GC pauses, clock skew, and partitions.

Single Point Of Failure

The lock store is a dependency and potential single point of failure.

Latency And Contention

Locks add latency and can become a contention bottleneck.

Code
# Redis distributed lock with owner token and safe release
public boolean acquire(String key, String token, Duration ttl) {
    # SET key token NX EX ttl -> atomic acquire
    return Boolean.TRUE.equals(
        redis.opsForValue().setIfAbsent(key, token, ttl));
}

public void release(String key, String token) {
    # only delete if we still own it (Lua = atomic check+del)
    String lua = "if redis.call('get',KEYS[1])==ARGV[1] " +
                 "then return redis.call('del',KEYS[1]) else return 0 end";
    redis.execute(new DefaultRedisScript<>(lua, Long.class),
        List.of(key), token);
}
How it works

setIfAbsent with a TTL atomically acquires the lock and auto-expires it.

The unique token identifies the owner of the lock.

The Lua script deletes only if the token matches, avoiding releasing someone else's lock.

Fencing tokens are still needed to guard against expired-then-resumed holders.
