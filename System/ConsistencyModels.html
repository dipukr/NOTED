Consistency Models (Strong vs Eventual)

A consistency model defines what guarantees readers get after data is written in a distributed store.

Strong consistency ensures every read returns the most recent committed write.

Eventual consistency allows temporary staleness but converges once updates propagate.

The CAP theorem forces a choice between consistency and availability during partitions.

When to use / Key points
  • Use strong consistency for balances, inventory, and anything requiring correctness now.
  • Use eventual consistency for feeds, counters, and caches that tolerate lag.
  • Read-your-writes and monotonic reads are useful middle-ground guarantees.
  • Consistency level is often tunable per operation (e.g. quorum reads/writes).
Pros and Cons
Simple Reasoning

Strong consistency offers simple reasoning with no stale reads and correctness by default.

Higher Availability

Eventual consistency gives higher availability and lower latency, surviving partitions.

Scales Writes Globally

Eventual consistency scales writes across regions without global coordination.

Latency Under Partitions

Strong consistency brings higher latency and reduced availability under partitions.

Stale Reads And Conflicts

With eventual consistency, apps must handle stale reads and conflict resolution.

Harder To Reason About

Eventual consistency is harder to reason about and test correctly.

Code
// Optimistic locking gives strong consistency on a single row
@Entity
public class Account {

    @Id
    private Long id;

    private BigDecimal balance;

    @Version
    private long version; // incremented on every update
}

@Service
public class AccountService {

    @Transactional
    public void withdraw(Long id, BigDecimal amount) {
        Account acc = repository.findById(id).orElseThrow();
        acc.setBalance(acc.getBalance().subtract(amount));
        // OptimisticLockException if version changed concurrently
        repository.save(acc);
    }
}
How it works

@Version tracks a row version so concurrent updates are detected.

A stale version on save throws an OptimisticLockException, preventing lost updates.

@Transactional makes read-modify-write atomic for strong per-row consistency.

Eventual stores instead accept the write and reconcile versions later.
