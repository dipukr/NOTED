Rate Limiting

Rate limiting is the technique for limiting the number of requests that can be made to a web service in a given period of time.

It protects services from overload, abuse, and runaway clients.

For monetising an API, rate limits are very important when you want to charge clients based on the number of requests made.

Common algorithms include token bucket, leaky bucket, fixed window, and sliding window.

When to use / Key points
  • Protect backends from spikes, scraping, brute-force, and denial-of-service.
  • Enforce fair usage and API tiers/quotas per client or API key.
  • Token bucket allows bursts up to a capacity; leaky bucket smooths output.
  • Return HTTP 429 with a Retry-After header when the limit is exceeded.
  • Use a shared store (e.g. Redis) so limits hold across multiple instances.
Advantages
Overload Protection

Shields services from overload and abusive traffic.

Usage-Based Billing

Enables usage-based billing and fair sharing among clients.

Predictable Capacity

Improves stability and predictable capacity planning.

Disadvantages
Rejected Bursts

Legitimate bursts may be rejected if limits are too tight.

Shared Counter Store

Distributed limiting needs a shared, low-latency counter store.

Algorithm Trade-offs

Fixed windows suffer boundary bursts, while sliding windows cost more to compute.

Code
# Token-bucket rate limiter: allows bursts, refills over time
public class TokenBucket {

    private final long capacity, refillPerSec;
    private double tokens;
    private long last = System.nanoTime();

    public TokenBucket(long capacity, long refillPerSec) {
        this.capacity = capacity; this.refillPerSec = refillPerSec;
        this.tokens = capacity;
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity,
            tokens + (now - last) / 1e9 * refillPerSec); # refill
        last = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false; # caller returns HTTP 429
    }
}
How it works

Tokens refill continuously at refillPerSec up to capacity.

Each request consumes one token; bursts are allowed until the bucket empties.

tryAcquire() returning false signals the caller to respond with 429.

synchronized keeps the counter correct under concurrency (per instance).
