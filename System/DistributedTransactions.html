Distributed Transactions (2PC, Saga)

A distributed transaction spans multiple services or databases that must agree on a single outcome.

In a monolith we can use a single database transaction, but microservices each own their data, so a different approach is needed.

Two-Phase Commit (2PC) coordinates an all-or-nothing commit across participants but blocks and scales poorly.

The Saga pattern manages distributed transactions as a sequence of local transactions with compensating actions to undo them on failure.

When to use / Key points
  • 2PC: a coordinator asks all participants to prepare, then commits only if all vote yes.
  • 2PC gives strong atomicity but blocks resources and stalls if the coordinator fails.
  • Saga: a series of local transactions; each has a compensating transaction to undo it.
  • Sagas run in orchestration (central coordinator) or choreography (services react to events).
  • Sagas use asynchronous communication and give eventual, not immediate, consistency.
Advantages
Strict Atomicity

2PC provides strict atomicity across all participants.

Loose Coupling

Saga keeps services loosely coupled and scales without distributed locks.

High Availability

Saga stays available and resilient to individual service failures.

Disadvantages
Blocking Coordinator

2PC is blocking, slow, and the coordinator is a single point of failure.

Eventual Consistency

Saga only offers eventual consistency and exposes intermediate states.

Complex Compensation

Writing correct compensating transactions is complex and error-prone.

Code
# Orchestrated saga: run steps, compensate in reverse on failure
public void placeOrder(Order o) {
    Deque<Runnable> compensations = new ArrayDeque<>();
    try {
        inventory.reserve(o);
        compensations.push(() -> inventory.release(o)); # undo step

        payment.charge(o);
        compensations.push(() -> payment.refund(o));

        shipping.schedule(o);
    } catch (Exception e) {
        # run compensating transactions in reverse order
        compensations.forEach(Runnable::run);
        throw new SagaFailedException(e);
    }
}
How it works

Each step is a local transaction in its own service.

After each success, its compensating action is pushed onto a stack.

On failure, compensations run in reverse (LIFO) to undo prior steps.

This achieves consistency without a blocking two-phase commit.
