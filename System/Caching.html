Caching (Strategies, Eviction, Stampede, Invalidation)

Caching stores expensive results close to consumers to cut latency and load.

Strategies include cache-aside, read-through, write-through, and write-behind.

Eviction policies (LRU, LFU, TTL) decide what to drop when the cache is full.

Invalidation and stampede protection keep cached data correct and stable.

When to use / Key points
  • Cache read-heavy, expensive, and relatively stable data.
  • Cache-aside: app loads on miss and populates the cache itself.
  • Prevent stampedes with locks, request coalescing, or jittered TTLs.
  • Invalidate on write, or accept staleness bounded by a TTL.
Advantages
Lower Latency

Cache hits are served dramatically faster than recomputing or refetching the result.

Reduced Load

Serving from cache reduces load on databases and downstream services.

Better Throughput

Caching improves throughput and cost efficiency at scale.

Disadvantages
Stale Data

Data can become stale if invalidation is wrong or missing.

Cache Stampede

A stampede on expiry can overwhelm the origin with simultaneous misses.

Added Complexity

Consistency, eviction tuning, and warm-up add operational complexity.

Code
// Cache-aside with Spring Cache abstraction
@Service
public class ProductService {

    // populate on miss, return cached value on hit
    @Cacheable(value = "products", key = "#id")
    public Product getProduct(Long id) {
        return productRepository.findById(id).orElseThrow();
    }

    // invalidate the entry when the product changes
    @CacheEvict(value = "products", key = "#product.id")
    public Product update(Product product) {
        return productRepository.save(product);
    }
}
How it works

@Cacheable checks the cache first and only hits the DB on a miss.

The key = "#id" expression derives the cache key from the argument.

@CacheEvict removes the stale entry on update for correct invalidation.

Configuring TTL and a max size on the backing cache handles eviction and stampede control.
