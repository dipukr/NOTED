Network Partitions

A network partition is a split in a distributed system where nodes cannot communicate with each other.

Messages between one group of nodes and another are dropped or delayed indefinitely.

Partitions are unavoidable in real networks, which is why the CAP theorem treats partition tolerance as mandatory.

During a partition a system must choose between staying consistent and staying available.

When to use / Key points
  • Assume partitions will happen; design for them rather than hoping to avoid them.
  • A "split brain" occurs when both sides keep operating and diverge.
  • Quorum (majority) rules prevent two sides from both accepting writes.
  • CP systems block the minority side; AP systems serve stale data and reconcile later.
  • Use fencing tokens and conflict resolution (e.g. version vectors) after healing.
Advantages
More Robust Systems

Planning for partitions yields more robust, fault-tolerant systems.

Avoids Conflicting Writes

Quorum-based designs avoid conflicting writes automatically.

Predictable Recovery

Explicit partition handling makes recovery behaviour predictable.

Disadvantages
Consistency vs Availability

Forces a hard choice between consistency and availability.

Split Brain Risk

Split brain can corrupt data if not guarded against.

Reconciliation Complexity

Post-partition reconciliation adds significant complexity.

Code
# Quorum check: only the majority side may accept writes during a partition
public boolean canAcceptWrite(int reachableNodes, int totalNodes) {
    int quorum = totalNodes / 2 + 1; # strict majority
    if (reachableNodes < quorum) {
        # minority side: refuse writes to avoid split brain
        return false;
    }
    return true;
}
How it works

quorum is a strict majority, so only one side can ever reach it.

The minority side returns false and stops accepting writes.

This prevents both partitions from diverging (split brain).

When the partition heals, the minority catches up from the majority.
