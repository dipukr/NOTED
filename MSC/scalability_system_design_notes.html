Scalability is a system’s ability to handle increasing workload by adding resources while maintaining acceptable performance and reliability.

For example, an online shopping application might initially serve 1,000 users. Later, it must serve 1 million users, store hundreds of millions of orders, and process thousands of payments per second.

A scalable design lets the system grow to meet that demand without requiring a complete redesign.

However, scalability is not simply “add more servers.” If all those servers depend on one overloaded database, adding servers may achieve very little.

Let’s build the concept step by step.

01 / SCALABILITYWhat exactly needs to scale?

Workload has several dimensions:

DimensionWhat increases?Example
Request volumeRequests per secondAn API grows from 100 to 100,000 requests/second
Concurrent activityWork happening at the same timeA chat application maintains 1 million open connections
Data volumeStored and processed dataAn orders table grows from 1 million to 1 billion rows
Read workloadData retrieval operationsMillions of people browse a product catalog
Write workloadData modification operationsDevices send millions of telemetry events
Computational workloadCPU/GPU workVideo encoding, image processing, ML inference
Network trafficBytes transferredA video platform serves thousands of simultaneous streams
Geographic reachUsers across distant regionsAn application expands from India to worldwide use

A system may scale well along one dimension and poorly along another.

  • A product catalog may support enormous read traffic through caching.
  • The same system may struggle with inventory updates because many transactions modify the same popular product.
  • A chat server may handle many idle connections but struggle when all users send messages simultaneously.
Always ask: “Scalable for which workload?”

02 / SCALABILITYScalability, performance, elasticity, and availability

ConceptMain questionExample
PerformanceHow quickly does the system complete work?An API responds in 100 ms
ScalabilityCan it handle more work as resources increase?Adding application instances increases sustainable throughput
ElasticityCan capacity expand and shrink with demand?Instances automatically increase during a sale and decrease afterward
AvailabilityIs the system accessible when needed?Requests continue succeeding after a server fails
EfficiencyHow much work can it perform per unit of resource or cost?Requests processed per CPU core or per dollar

An application can be fast but not scalable. For example, an in-memory application on one machine might respond in 2 ms, but its data cannot grow beyond that machine’s memory.

An application can also scale to high throughput while individual requests remain slow.

Good system design considers both throughput and latency.

03 / SCALABILITYVertical scalability: make one machine more powerful

Vertical scaling means increasing the resources of an existing machine. This is also called scaling up. Reducing resources is scaling down.

ResourceBeforeAfter
CPU cores432
RAM16 GB128 GB
StorageLower-throughput diskHigher-throughput SSD storage
Network capacityLower bandwidthHigher bandwidth

Your application still runs on one machine, but that machine has more capacity.

For a Java application, this might allow:

  • More CPU-intensive tasks to run concurrently.
  • A larger heap for live application data.
  • More filesystem cache.
  • Higher disk throughput.
  • More concurrent requests, provided the application can use the additional resources.

Ways to scale vertically

  • Increase CPU cores or CPU speed.
  • Add RAM.
  • Use faster storage or increase provisioned storage throughput.
  • Increase network bandwidth.
  • Adjust application limits so it can use the new capacity.

Adding resources does not automatically remove every bottleneck. A single-threaded operation may not benefit much from additional CPU cores. A global lock can prevent multiple threads from doing useful work simultaneously.

Advantages

  • Usually simpler to implement.
  • Often requires fewer architectural changes.
  • Keeps data and transactions within one machine.
  • Useful for databases and applications that are difficult to distribute.

Limitations

  • There is a maximum practical machine size.
  • Larger machines can become disproportionately expensive.
  • Resizing may require interruption, depending on the platform.
  • One machine remains a failure domain unless redundancy is added separately.
Example: If a database is slow because its working set does not fit in memory, adding RAM may be a highly effective first step.

04 / SCALABILITYHorizontal scalability: add more machines or instances

Horizontal scaling means increasing the number of machines or application instances. This is also called scaling out. Removing instances is scaling in.

Instead of one large application server, you run several servers and distribute work across them.

If one instance can sustainably process 500 requests/second, four instances might approach 2,000 requests/second if shared dependencies and workload distribution allow it.

The diagram also reveals a possible limitation: all three instances still depend on the same database.

Ways to scale horizontally

  • Run multiple application instances behind a load balancer.
  • Add worker processes to consume background jobs.
  • Add database read replicas.
  • Shard data across database nodes.
  • Partition event streams and distribute processing.
  • Distribute cache entries across cache nodes.

Advantages

  • Capacity can grow incrementally.
  • Work can be distributed across many machines.
  • Supports redundancy when instances are placed across independent failure domains.
  • Often fits elastic workloads well.

Challenges

  • Requests can reach different instances.
  • Data and sessions must be managed across instances.
  • Network calls introduce latency and partial failures.
  • Coordination and consistency become more complex.
  • Uneven workload distribution can overload individual nodes.

Horizontal scaling is easiest when work can be divided into relatively independent units.

For example, processing 10,000 unrelated images is easier to distribute than coordinating 10,000 purchases of the last available concert ticket.

05 / SCALABILITYDiagonal scaling: combine vertical and horizontal scaling

Diagonal scaling is a commonly used term for combining both approaches.

  1. Start with one instance containing 2 CPU cores and 4 GB RAM.
  2. Increase it to 8 CPU cores and 16 GB RAM.
  3. When further growth makes sense, run several instances of that size.
  4. Continue adjusting both instance size and instance count.

This is common in practice because the smallest possible instances are not always efficient, and the largest possible machines are not always economical.

ApproachMain changeTypical strengthMain limitation
VerticalBigger machinesSimplicityPer-machine capacity ceiling
HorizontalMore machinesDistributed capacityCoordination and shared bottlenecks
DiagonalBigger machines plus more machinesFlexibilityRequires tuning both dimensions

06 / SCALABILITYScale copies, functions, or data

Vertical and horizontal describe how resources grow. Another classification describes how the application’s work is divided.

ApproachWhat is divided?Example
X-axis scalingCopies of the same applicationRun 10 identical application instances
Y-axis scalingBusiness capabilities or functionsScale search separately from checkout
Z-axis scalingData or workload subsetsRoute different customers to different shards

These approaches can be combined.

X-axis: duplicate the application

Each instance runs the same code and can handle the same kinds of requests. For example, run five copies of a Spring Boot application behind a load balancer.

Y-axis: separate functions

Different capabilities receive independent resources.

  • Product search requires substantial read capacity.
  • Order processing requires transactional database capacity.
  • Video processing requires CPU or GPU capacity.
  • Email delivery requires background workers.

You do not need to scale all of them equally.

Microservices can enable this, but microservices do not automatically make a system scalable. Poor boundaries and excessive synchronous calls can create additional bottlenecks.

Z-axis: divide the workload or data

  • Customer IDs in one group go to shard A.
  • Another group goes to shard B.
  • Each shard handles only its assigned customers.

This helps when one database or processing group cannot handle the full dataset or workload.

The difficulty is selecting a partitioning strategy that avoids hotspots and supports your access patterns.

07 / SCALABILITYStateless application design makes horizontal scaling easier

Suppose a user logs in through application instance A, and A stores the user’s session only in its own memory. The next request reaches instance B. B does not have that session.

This creates a problem because requests are distributed across instances.

A more scalable design keeps application instances stateless with respect to durable, user-specific state.

That does not mean the entire system has no state. It means state is stored somewhere appropriate:

StatePossible location
Login sessionShared session store
Orders and paymentsDatabase
Uploaded filesShared object storage
Background job progressDurable job store
Temporary cached resultsLocal or distributed cache, depending on requirements

Now, any healthy instance can handle the next request.

Sticky sessions can route a user back to the same instance, but they can create uneven load and complicate failure handling.

Similarly, storing uploaded files only on an application server’s local disk makes it difficult for other instances to access them.

08 / SCALABILITYDatabase scalability: reads and writes

The database often becomes a bottleneck because many application instances share it.

Before distributing the database, reduce unnecessary work:

  • Add appropriate indexes.
  • Examine expensive query plans.
  • Fetch only required columns and rows.
  • Avoid repeated queries and N+1 query patterns.
  • Keep transactions reasonably short.
  • Use suitable pagination.
  • Batch operations where appropriate.
  • Bound connection pools.

Read scalability

Common approaches include:

  • Caching frequently requested data.
  • Adding read replicas.
  • Precomputing summaries or materialized views.
  • Using a separate search system for search-heavy workloads.
  • Creating read models tailored to query patterns.

With read replicas, writes generally go to a primary, while eligible reads go to replicas.

However, asynchronously replicated data may be temporarily stale. A user who updates an address may not immediately see the update if the next read goes to a lagging replica.

Write scalability

Common approaches include:

  • Reducing unnecessary writes.
  • Batching small writes.
  • Spreading independent writes across shards.
  • Reducing contention on frequently updated rows.
  • Using asynchronous processing where delayed completion is acceptable.
Adding read replicas usually does not increase the primary database’s write capacity.

Also, partitioning a table inside one database can improve management and certain queries, but it does not necessarily distribute work across machines. Sharding specifically distributes subsets of data across database nodes.

Sharding introduces trade-offs:

  • Cross-shard joins become harder.
  • Cross-shard transactions become more complex.
  • Rebalancing requires moving data.
  • Some shards may receive much more traffic than others.

For example, assigning tenants to shards works well until one tenant generates half of all traffic.

09 / SCALABILITYCaching: reduce repeated work

Suppose a product-details endpoint receives 20,000 requests/second. If 95% of those requests can be served from cache, the database receives approximately:

20,000 × (1 − 0.95) = 1,000 reads/second

for that workload.

Cache locationTypical use
BrowserStatic assets and cacheable responses
CDNImages, videos, scripts, and other cacheable content
Reverse proxyCacheable HTTP responses
Application memorySmall, frequently used local data
Distributed cacheData shared across application instances

Caching works best when data is reused enough to justify storing it.

Its challenges include:

  • Stale data.
  • Cache invalidation.
  • Memory limits and eviction.
  • Hot keys.
  • Cache stampedes when many requests regenerate the same expired entry.
A cache reduces backend demand; it does not eliminate the need to plan backend capacity. A cold or unavailable cache can suddenly expose the database to much higher traffic.

10 / SCALABILITYAsynchronous processing: separate requests from background work

Consider an order workflow:

  1. Save the order.
  2. Send a confirmation email.
  3. Generate an invoice.
  4. Update analytics.
  5. Notify the warehouse.

If every action runs synchronously, the user waits for all of them, and downstream delays occupy request-handling capacity.

Instead, the request can complete after the required durable order operation, while suitable follow-up work runs asynchronously.

An outbox can help reliably connect the database transaction to event publication. Each worker group can scale independently.

A queue absorbs bursts; it does not create processing capacity.

If jobs arrive at 10,000/second and workers process 8,000/second:

Backlog growth = 10,000 − 8,000 = 2,000 jobs/second

The backlog keeps growing until processing capacity increases or incoming work decreases.

Queue-based systems also need:

  • Retry handling.
  • Idempotent processing.
  • Backpressure.
  • Handling for repeatedly failing jobs.
  • Ordering rules where required.

11 / SCALABILITYGeographic scalability: bring processing closer to users

When users are distributed worldwide, one region can create long network delays.

Possible approaches include:

  • Serve static and cacheable content through a CDN.
  • Run application instances in multiple regions.
  • Route requests to suitable nearby regions.
  • Replicate data across regions.
  • Assign users or tenants a home region.

The difficult part is usually mutable data.

For example, if two regions simultaneously update the same account balance, the system needs a clear coordination or conflict-resolution strategy.

Synchronous cross-region coordination adds network latency. Asynchronous replication permits temporary differences between regions.

Geographic scaling involves decisions about latency, consistency, availability, and where writes are accepted.

12 / SCALABILITYThe real limit is often the bottleneck

Consider a request path:

Load balancer → application → database → external payment provider

Increasing application capacity does little if the payment provider accepts only 1,000 requests/second.

BottleneckPossible response
Application CPUImprove algorithms, scale up, or add instances
MemoryReduce allocations, bound caches, stream data, or add RAM
Database query costImprove queries, indexes, and access patterns
Database lock contentionShorten transactions and reduce shared updates
Storage throughputReduce I/O or use higher-throughput storage
Network bandwidthCompress, reduce payloads, or use a CDN
External service limitsApply rate limits, queues, or negotiated capacity
Hot data partitionChange partitioning or isolate the hot workload
Excessive coordinationReduce shared state and synchronous dependencies

A subtle example is database connection pools.

If one application instance allows 50 database connections, then 100 instances could collectively attempt:

100 × 50 = 5,000 connections

Scaling the application may therefore overload the database unless pool sizes and concurrency are controlled.

Capacity planning must consider the whole request path.

13 / SCALABILITYScaling is rarely perfectly linear

Ideally, doubling resources doubles throughput:

T(N) ≈ N × T(1)

where T(N) is throughput with N equivalent instances.

Actual throughput is usually lower because of:

  • Shared resources.
  • Network overhead.
  • Coordination.
  • Serial processing.
  • Lock contention.
  • Uneven work distribution.

A useful theoretical model is Amdahl’s law:

Speedup(N) = 1 / [s + (1 − s) / N]

Here:

  • s is the fraction of work that must remain serial.
  • N is the number of parallel workers.

If 10% of a fixed workload is inherently serial, the theoretical maximum speedup is:

1 / 0.10 = 10×

Even an unlimited number of workers cannot remove that serial portion. Real distributed systems may perform worse because this model does not include all communication and coordination costs.

This is why removing a global lock or a centralized sequencing step can matter more than adding servers.

14 / SCALABILITYMeasure scalability against an explicit target

“Handles 10,000 requests/second” is incomplete.

A meaningful target might be:

Sustain 10,000 requests/second with p99 latency below 300 ms, errors below 0.1%, and enough spare capacity to tolerate one instance failure.

Useful measurements include:

MetricWhat it tells you
ThroughputWork completed per second
p95/p99 latencyResponse time experienced by slower requests
Error and timeout rateWhether requests are completing successfully
CPU, memory, disk, and network useResource pressure
Queue length and oldest-message ageWhether background processing is keeping up
Database lock waits and pool waitsContention and concurrency limits
Replication lagHow far replicas trail writes
Cost per request or jobEconomic efficiency

Concurrency also matters.

For a stable system, Little’s law relates average in-flight work, throughput, and average time in the system:

L = λW

At 2,000 requests/second and an average response time of 0.2 seconds:

L = 2,000 × 0.2 = 400 requests in flight

Approximately 400 requests are in flight on average. This does not necessarily mean 400 threads are required; that depends on the execution model.

If response time increases, more requests remain in flight, which can create additional memory and connection pressure.

15 / SCALABILITYAutoscaling needs headroom and overload protection

Autoscaling is a mechanism for adjusting capacity as demand changes. It depends on the system already being able to scale.

Common signals include:

  • CPU utilization.
  • Requests per instance.
  • Queue backlog.
  • Age of the oldest queued job.
  • Active connections.
  • Processing latency.

CPU is not always the right signal. An application waiting on a slow database may have low CPU while requests pile up.

Scaling also takes time: instances must start, initialize, warm caches, and become healthy.

Useful protections include:

  • Spare capacity.
  • Bounded queues.
  • Concurrency limits.
  • Rate limiting.
  • Timeouts.
  • Retries with backoff and jitter.
  • Load shedding when capacity is exhausted.

Without these protections, retries and unbounded queues can turn a temporary overload into a larger failure.

16 / SCALABILITYA practical scaling path for a Spring Boot shopping application

A reasonable progression is driven by measurements:

SituationPotential next step
One instance comfortably handles demandKeep the design simple and monitor
Slow SQL dominates response timeFix queries and indexes
Application CPU is saturatedIncrease CPU or add instances
Multiple instances are neededExternalize sessions and shared files
Product reads overload the databaseAdd caching and eligible read replicas
Email and invoice work delays checkoutMove suitable work to background workers
Search competes with checkout resourcesGive search independent capacity
One database cannot sustain writes or storageEvaluate sharding or workload separation
Distant users experience high latencyAdd CDN coverage and evaluate regional serving

You do not need to implement every technique in advance.

The central design habit is to identify the workload, define acceptable service levels, measure the limiting resource, and choose a scaling approach that addresses that specific limit.
