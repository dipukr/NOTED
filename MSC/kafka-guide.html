Kafka Fundamentals

Apache Kafka is a distributed event-streaming platform built around partitioned append-only logs. A producer writes records to a topic, Kafka stores those records in partitions, and consumers read them by position (offset). Kafka is designed for high throughput, scalable parallelism, durable storage, and independent consumption by multiple consumer groups. citeturn0search0turn0search2

Kafka is more than a traditional message queue

  • A topic can have multiple independent subscribers.
  • Records remain available according to retention policy rather than disappearing immediately after one consumer reads them.
  • Partitions provide both horizontal scalability and the unit of ordering.
  • Consumer groups provide load balancing among consumers while different groups can independently consume the same topic.

Core mental model

Think of Kafka as a distributed collection of durable logs. A consumer does not remove a record from the log; it advances its position in that log. This is why replay, backfilling, and multiple independent consumers are natural Kafka operations.

Architecture

Broker

A broker is a Kafka server responsible for storing partitions and serving client requests. A cluster normally has multiple brokers so partitions and replicas can be distributed.

Controller

In modern Kafka, KRaft controllers manage cluster metadata. Kafka 4.0 operates without ZooKeeper and uses KRaft. citeturn0search3turn0search5

Client communication

Kafka clients communicate with brokers using a binary TCP protocol. Producers and consumers maintain network connections and use Kafka APIs for metadata, produce, fetch, group coordination, and related operations. citeturn0search4

Topics, Partitions and Offsets

Topic

A topic is a logical name for a stream of records. A topic is divided into one or more partitions.

Partition

A partition is an ordered, append-only sequence. Ordering is guaranteed within a partition, not globally across all partitions of a topic. citeturn0search0

Offset

Each record receives an offset that identifies its position within its partition. Consumer progress is represented by committed offsets.

Why partitions matter

  • More partitions permit more consumer parallelism.
  • Partitions distribute storage and request load across brokers.
  • A key can be used to keep related records in the same partition, preserving their relative order.
Producers

A producer creates ProducerRecord objects and sends them to Kafka. The producer obtains metadata about topic partitions and routes records to the appropriate partition leader. Kafka's design allows the client to select partitions directly or use a key-based partitioning strategy. citeturn0search2

Basic Java Producer
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
        StringSerializer.class.getName());
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
        StringSerializer.class.getName());

try (KafkaProducer<String, String> producer =
        new KafkaProducer<>(props)) {

    ProducerRecord<String, String> record =
        new ProducerRecord<>("orders", "order-1001", "CREATED");

    producer.send(record, (metadata, exception) -> {
        if (exception != null) {
            exception.printStackTrace();
            return;
        }

        System.out.printf(
            "topic=%s partition=%d offset=%d%n",
            metadata.topic(),
            metadata.partition(),
            metadata.offset()
        );
    });
}
Explanation

The send operation is asynchronous. The callback is invoked when Kafka acknowledges the request or when the send fails.

Consumers

A consumer fetches records from Kafka and processes them. Consumers normally subscribe to topics and repeatedly call poll(). The consumer controls its position and can resume from committed offsets or seek to other offsets.

Important consumer settings

auto.offset.resetDefines behavior when no valid committed offset exists.
max.poll.recordsMaximum records returned from one poll.
max.poll.interval.msMaximum interval between successful polls before a consumer can be considered unresponsive for group management.
session.timeout.msSession failure-detection configuration used by the consumer group protocol.
Basic Java Consumer
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-service");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
        StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
        StringDeserializer.class.getName());
props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

try (KafkaConsumer<String, String> consumer =
        new KafkaConsumer<>(props)) {

    consumer.subscribe(List.of("orders"));

    while (true) {
        ConsumerRecords<String, String> records =
            consumer.poll(Duration.ofMillis(1000));

        for (ConsumerRecord<String, String> record : records) {
            System.out.printf(
                "partition=%d offset=%d key=%s value=%s%n",
                record.partition(),
                record.offset(),
                record.key(),
                record.value()
            );
        }
    }
}
Explanation

A consumer should call poll regularly. The poll loop is central to fetching data and participating in consumer-group coordination.

Consumer Groups

A consumer group is a set of consumers cooperating to consume a topic. Within a group, a partition is assigned to one consumer at a time. If there are more consumers than partitions, some consumers will have no partition assignment. Different groups can independently consume the same topic. citeturn0search0

Example

Topic partitionsConsumers in groupTypical result
31One consumer processes all 3 partitions.
33Partitions can be distributed one per consumer.
35Only 3 consumers can actively own partitions; 2 can be idle.

Rebalancing

When group membership or partition availability changes, Kafka redistributes partition assignments. Rebalancing is necessary for elasticity and fault tolerance but can temporarily affect processing. Modern Kafka also includes a newer consumer rebalance protocol; Kafka 4.0 introduced the next-generation protocol as generally available. citeturn0search8

Delivery Semantics
SemanticMeaningTypical trade-off
At-most-onceA record is processed zero or one time.Duplicates are avoided at the cost of possible loss.
At-least-onceA record is not intentionally lost but may be processed more than once.Applications must tolerate duplicates.
Exactly-onceKafka can provide transactional processing semantics for Kafka-to-Kafka workflows when correctly configured.More coordination and transactional overhead.

Kafka's design explicitly distinguishes publishing durability from consumption/processing semantics. Exactly-once claims should always be scoped to the system boundary being discussed. citeturn0search2

At-Least-Once Pattern
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");

while (true) {
    ConsumerRecords<String, String> records =
        consumer.poll(Duration.ofSeconds(1));

    for (ConsumerRecord<String, String> record : records) {
        processBusinessLogic(record);
    }

    consumer.commitSync();
}
Explanation

The application processes records before committing offsets. A crash after processing but before commit can cause the record to be processed again, so the business operation should be idempotent where possible.

Replication and Fault Tolerance

Replication is performed at the partition level. A partition has one leader and zero or more follower replicas. Writes are directed to the leader; followers replicate the partition log. The replication factor is the total number of replicas for a partition. citeturn0search2

ISR — In-Sync Replicas

The ISR is the set of replicas considered sufficiently caught up with the leader. Producer durability can be strengthened by combining acks=all with an appropriate min.insync.replicas. Kafka's documentation describes min.insync.replicas as the minimum ISR size required when the producer requests the stronger acknowledgment level. citeturn0search2

Durable Producer Configuration
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

// Example cluster/topic policy:
// replication.factor = 3
// min.insync.replicas = 2
Explanation

This is a common durability-oriented pattern, but exact values should be chosen based on availability, failure tolerance, latency, and workload requirements.

KRaft

KRaft is Kafka's metadata-management architecture based on the Raft consensus protocol. Kafka 4.0 removed ZooKeeper mode and operates entirely in KRaft mode. citeturn0search5

Process roles

  • broker — handles client data traffic and partition storage.
  • controller — participates in the controller quorum and manages cluster metadata.
  • broker,controller — combined role, useful for simpler development deployments.

Kafka's KRaft documentation notes that combined broker/controller servers simplify small deployments but are not recommended for critical environments where controller isolation is important. citeturn0search3

Illustrative KRaft Properties
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@localhost:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
advertised.listeners=PLAINTEXT://localhost:9092
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
log.dirs=/tmp/kafka-logs
Explanation

This is a development-oriented example. Production KRaft configurations should use appropriate listener security, stable storage paths, multiple controllers, and deployment-specific networking.

Serialization

Kafka transports bytes. Java clients use serializers on the producer side and deserializers on the consumer side to convert Java objects to and from bytes.

Common choices

  • String serializer/deserializer for text.
  • ByteArray serializer/deserializer when the application manages raw bytes.
  • JSON serializers for object payloads, with explicit schema/versioning discipline.
  • Avro, Protobuf, or JSON Schema when a schema-registry-based contract is appropriate.
Custom JSON Serialization Concept
public record Order(
    String id,
    String customerId,
    BigDecimal amount
) {}

ObjectMapper mapper = new ObjectMapper();

byte[] payload = mapper.writeValueAsBytes(order);

ProducerRecord<String, byte[]> record =
    new ProducerRecord<>("orders", order.id(), payload);
Explanation

In production, define a clear schema evolution strategy. Serialization is not just a technical conversion; it is part of the event contract between producers and consumers.

Java Producer API
Send with Future
Future<RecordMetadata> future = producer.send(
    new ProducerRecord<>("orders", "order-1001", "CREATED")
);

RecordMetadata metadata = future.get();

System.out.println(metadata.partition());
System.out.println(metadata.offset());
Explanation

Calling get() waits for the send result. It is useful when the application must know whether a specific record was acknowledged, but excessive synchronous waiting can reduce throughput.

Explicit Partition
ProducerRecord<String, String> record =
    new ProducerRecord<>(
        "orders",
        2,
        "order-1001",
        "CREATED"
    );

producer.send(record);
Explanation

An application can explicitly select a partition. This should normally be done only when the partitioning rule is intentional.

Flush and Close
producer.flush();
producer.close();
Explanation

Close the producer during orderly shutdown so buffered records can be flushed and resources released.

Java Consumer API
Assign Specific Partitions
TopicPartition p0 = new TopicPartition("orders", 0);

consumer.assign(List.of(p0));

consumer.seekToBeginning(List.of(p0));

ConsumerRecords<String, String> records =
    consumer.poll(Duration.ofSeconds(1));
Explanation

assign() bypasses normal group subscription/assignment. It is useful for specialized consumers, deterministic replay tools, and administrative workflows.

Seek to Offset
TopicPartition partition =
    new TopicPartition("orders", 0);

consumer.assign(List.of(partition));
consumer.seek(partition, 100);

ConsumerRecords<String, String> records =
    consumer.poll(Duration.ofSeconds(1));
Explanation

seek() changes the consumer's read position. This is one reason Kafka is useful for replay and backfill workflows.

Manual Offset Management
Commit Specific Offsets
Map<TopicPartition, OffsetAndMetadata> offsets =
    new HashMap<>();

for (ConsumerRecord<String, String> record : records) {
    process(record);

    offsets.put(
        new TopicPartition(record.topic(), record.partition()),
        new OffsetAndMetadata(record.offset() + 1)
    );
}

consumer.commitSync(offsets);
Explanation

Kafka commits the next offset to read, so after successfully processing offset N, the committed position is normally N + 1.

Transactions and Exactly Once

Kafka transactions allow a producer to atomically publish records and, when used with a consumer group, commit the consumer offsets as part of the same transaction. This is the foundation for Kafka-to-Kafka exactly-once processing patterns. citeturn0search2

Transactional Producer
props.put(
    ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

props.put(
    ProducerConfig.TRANSACTIONAL_ID_CONFIG,
    "order-transformer-1");

KafkaProducer<String, String> producer =
    new KafkaProducer<>(props);

producer.initTransactions();

producer.beginTransaction();

try {
    producer.send(
        new ProducerRecord<>("orders-out",
            "order-1001", "PROCESSED"));

    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
    throw e;
}
Explanation

A transactional.id identifies the producer instance for transactional semantics. Production deployments need carefully designed stable transactional IDs and fencing/restart behavior.

Consume, Produce, and Commit Offsets Transactionally
producer.beginTransaction();

try {
    for (ConsumerRecord<String, String> record : records) {

        producer.send(
            new ProducerRecord<>(
                "orders-out",
                record.key(),
                transform(record.value())
            )
        );
    }

    Map<TopicPartition, OffsetAndMetadata> offsets =
        currentOffsets(records);

    producer.sendOffsetsToTransaction(
        offsets,
        consumer.groupMetadata()
    );

    producer.commitTransaction();

} catch (Exception e) {
    producer.abortTransaction();
}
Explanation

The important idea is atomicity: the output records and the consumer's progress are committed together. Kafka's transaction design uses the producer transaction to combine these operations. citeturn0search2

Partitioning

Partitioning determines where records are stored and therefore where their ordering and processing locality exist. Kafka allows a key to influence partition selection; for example, using customer ID as a key can place all events for that customer in the same partition. citeturn0search2turn0search4

Partitioning trade-offs

  • More partitions increase parallelism potential.
  • Too many partitions increase metadata and operational overhead.
  • A hot key can create a hot partition.
  • Changing the partitioning scheme can affect ordering and locality.
Key-Based Partitioning
ProducerRecord<String, String> record =
    new ProducerRecord<>(
        "customer-events",
        customerId,
        eventJson
    );

producer.send(record);
Explanation

The key gives the producer a stable partitioning input. The exact partitioning algorithm and behavior can depend on the client version and configuration.

Retry and Dead Letter Topics

Kafka does not require one universal retry design. Common application patterns include delayed retry topics, retry topics with increasing delay, and a dead-letter topic (DLT) for records that repeatedly fail processing.

Example flow

orders → order-service → retry-1 → retry-2 → orders.DLT

A retry record should normally retain enough context to diagnose and safely reprocess the original event, such as original topic, partition, offset, error information, attempt count, and correlation ID.

Simple Retry Metadata
ProducerRecord<String, String> retry =
    new ProducerRecord<>(
        "orders.retry",
        record.key(),
        record.value()
    );

retry.headers()
    .add("retry-attempt", "2".getBytes(StandardCharsets.UTF_8))
    .add("original-topic",
         record.topic().getBytes(StandardCharsets.UTF_8))
    .add("original-offset",
         Long.toString(record.offset())
             .getBytes(StandardCharsets.UTF_8));

producer.send(retry);
Log Retention and Compaction

Time/size retention

Kafka can remove old log segments according to retention configuration. Consumers can therefore replay records while those records remain retained.

Log compaction

Compaction retains the latest value for a key over time, making it useful for state/changelog-style topics. Compaction is different from ordinary time-based deletion.

Create a Compacted Topic
kafka-topics.sh --bootstrap-server localhost:9092   --create   --topic customer-state   --partitions 6   --replication-factor 3   --config cleanup.policy=compact
Kafka Streams

Kafka Streams is a Java library for building stream-processing applications on Kafka. It supports transformations, grouping, aggregation, joins, windowing, state stores, and exactly-once processing modes.

Kafka Streams DSL
Properties props = new Properties();
props.put(
    StreamsConfig.APPLICATION_ID_CONFIG,
    "order-counts");
props.put(
    StreamsConfig.BOOTSTRAP_SERVERS_CONFIG,
    "localhost:9092");
props.put(
    StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG,
    Serdes.StringSerde.class);
props.put(
    StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG,
    Serdes.StringSerde.class);

StreamsBuilder builder = new StreamsBuilder();

KStream<String, String> orders =
    builder.stream("orders");

KTable<String, Long> counts =
    orders
        .groupByKey()
        .count();

counts.toStream().to("order-counts");

KafkaStreams streams =
    new KafkaStreams(builder.build(), props);

streams.start();
Explanation

Streams applications maintain processing topology state and use Kafka topics as durable input/output boundaries. For production use, configure state, exception handling, replication, and processing guarantees deliberately.

Kafka Connect

Kafka Connect is a framework for moving data between Kafka and external systems using connectors. Source connectors bring external data into Kafka; sink connectors send Kafka records to external systems.

Typical architecture

Database → Source Connector → Kafka → Sink Connector → Search/Data Warehouse/Object Storage

Connect is useful when integration can be expressed as connector configuration rather than custom application code.

Schema Evolution

Event schemas should be treated as contracts. A producer and consumer may be deployed independently, so changes should consider backward/forward compatibility.

Common strategies

  • Add optional fields with safe defaults.
  • Avoid changing the meaning of an existing field.
  • Version incompatible event contracts explicitly.
  • Use a schema registry when centralized compatibility enforcement is valuable.
Schema-Oriented Event
public record OrderCreated(
    String eventId,
    String orderId,
    String customerId,
    BigDecimal amount,
    Instant occurredAt
) {}
Explanation

A strongly defined event contract makes compatibility, testing, observability, and consumer development easier.

Security

Encryption

Kafka can use TLS for encrypted network communication.

Authentication

Common Kafka authentication mechanisms include SASL-based mechanisms and TLS client authentication.

Authorization

Kafka supports authorization using ACLs and other configured authorizer mechanisms.

Principle of least privilege

Application identities should receive only the topic/group permissions they require. Separate producer and consumer identities where operationally useful.

Illustrative Java Client Security Properties
props.put(
    CommonClientConfigs.SECURITY_PROTOCOL_CONFIG,
    "SASL_SSL");

props.put(
    SaslConfigs.SASL_MECHANISM,
    "PLAIN");

props.put(

    "username="app" password="secret";");
Explanation

Do not hard-code real credentials. Use a secret-management mechanism appropriate to your environment.

Performance Tuning

Producer

  • Use batching through batch.size and linger.ms.
  • Use compression to reduce network and storage traffic when CPU trade-offs are acceptable.
  • Avoid unnecessary synchronous sends.
  • Use appropriate acks and idempotence settings for the required durability.

Consumer

  • Process records in batches where possible.
  • Keep poll cadence healthy.
  • Tune max.poll.records based on processing time.
  • Scale consumers only when enough partitions exist.

Broker/topic

  • Distribute partitions and leaders across brokers.
  • Use replication for failure tolerance.
  • Choose partition counts based on throughput and consumer parallelism requirements.
Performance-Oriented Producer Baseline
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "zstd");
props.put(ProducerConfig.LINGER_MS_CONFIG, 5);
props.put(ProducerConfig.BATCH_SIZE_CONFIG, 64 * 1024);
Explanation

These are example starting points, not universal optimal values. Benchmark with representative message sizes and traffic patterns.

Monitoring

Producer metrics

Watch request latency, record rate, byte rate, batch behavior, retries, errors, and buffer availability.

Consumer metrics

Watch consumer lag, poll behavior, fetch rate, processing latency, rebalance activity, and commit failures.

Broker metrics

Watch request latency, disk utilization, network throughput, replica health, under-replicated partitions, controller health, and JVM/system resources.

Consumer lag

Lag represents how far a consumer's position is behind the log end. Persistent increasing lag generally means consumption capacity is below production rate, though temporary spikes can be normal.

Operational Design

Capacity planning

Estimate incoming records/sec, average record bytes, peak traffic, retention duration, replication factor, consumer throughput, and required replay window.

Partition planning

Partition count should be driven by expected throughput and parallelism, not simply by the number of brokers.

Failure planning

  • Use multiple brokers.
  • Use replication factor greater than one for important topics.
  • Distribute replicas across failure domains where supported by the deployment.
  • Test broker loss and consumer failure rather than relying only on configuration.

Ordering

If ordering is required for an entity, consistently use an entity key and ensure all related events are routed to the same partition. Kafka does not provide a total order across multiple partitions. citeturn0search0

Common Pitfalls
  • Using one partition for everything: simplifies ordering but limits parallelism.
  • Too many partitions: increases operational and metadata overhead.
  • Assuming Kafka removes messages after consumption: consumers advance offsets; retention controls storage lifetime.
  • Assuming exactly-once is automatic: application boundaries and external side effects matter.
  • Ignoring duplicate processing: at-least-once systems require idempotent business operations or deduplication.
  • Using NOLOCK-like thinking in Kafka: consumer offset management and delivery semantics should be designed explicitly.
  • Ignoring poison messages: use bounded retries and a DLT strategy where appropriate.
  • Hard-coding credentials: use secret management.
