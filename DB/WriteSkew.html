Write Skew

Write skew is a concurrency anomaly where two transactions read the same data, each makes a decision based on it, and both write without conflicting on the same row.

Individually each transaction is valid, but together they violate an invariant.

It can occur even under snapshot isolation because neither transaction updates the row the other read.

A classic example is two doctors each going off-call because the other appears to be on-call.

Serializable isolation prevents it.

When to use / Key points
  • Watch for invariants across rows enforced by application logic.
  • Snapshot isolation does not prevent write skew.
  • Prevent it with Serializable isolation.
  • Or materialize the conflict by locking a shared row (SELECT ... FOR UPDATE).
  • Example: "at least one doctor must remain on-call".
Advantages
  • Awareness prevents subtle invariant violations.
  • Serializable gives a clean guarantee.
  • Explicit locking offers a targeted fix without full serialization.
Disadvantages / Trade-offs
  • Invisible under common snapshot isolation.
  • Hard to detect in testing.
  • Fixes cost concurrency (serialization or locks).
Code
-- Invariant: at least one doctor must remain on-call at all times
CREATE TABLE Shift (
    DoctorId INT PRIMARY KEY,
    Name     VARCHAR(50)  NOT NULL,
    OnCall   BIT          NOT NULL
);
-- Starting state: doctors 1 and 2 are both on-call

-- === Session A (Dr. Alice) ===============================
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
    SELECT COUNT(*) AS OnCallCount
    FROM Shift
    WHERE OnCall = 1;              -- sees 2, decides it is safe to leave

    UPDATE Shift SET OnCall = 0 WHERE DoctorId = 1;
COMMIT TRANSACTION;

-- === Session B (Dr. Bob), running concurrently ============
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
    SELECT COUNT(*) AS OnCallCount
    FROM Shift
    WHERE OnCall = 1;              -- also sees 2 (its own snapshot), also decides it is safe

    UPDATE Shift SET OnCall = 0 WHERE DoctorId = 2;
COMMIT TRANSACTION;
-- Result: both commit, zero doctors on-call -- the invariant is broken

-- Fix: SERIALIZABLE detects the read/write dependency between the sessions
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;
    SELECT COUNT(*) FROM Shift WITH (HOLDLOCK, ROWLOCK)
    WHERE OnCall = 1;
    UPDATE Shift SET OnCall = 0 WHERE DoctorId = 1;
COMMIT TRANSACTION;                     -- the second session now aborts with a serialization failure
How it works
  • Both sessions run under SNAPSHOT isolation and each reads OnCallCount = 2 from its own consistent snapshot.
  • Each transaction updates a different row (a different doctor), so no row-level write conflict is ever detected between them.
  • Both commit successfully, leaving zero doctors on-call and silently violating the "at least one on-call" invariant.
  • Under SERIALIZABLE with HOLDLOCK, the engine tracks the read-write dependency across the whole result set and forces one transaction to fail at commit, preserving the invariant.
