Connection Pool

Database connection pooling reduces the cost of opening and closing connections by maintaining a pool of open connections that can be passed from one database operation to another as needed.

This spares the expense of opening and closing a brand new connection for every operation.

Pooling improves performance by reducing the latency of establishing new connections, leading to faster query execution and response times.

A connection pooler is responsible for opening, closing and maintaining connections on behalf of clients.

Opening a connection involves DNS lookup, TCP handshake, TLS handshake, authentication and authorization, all of which pooling avoids repeating.

When to use / Key points
  • Use a pool in any server application that issues many short database operations.
  • Reuse idle connections instead of creating new ones per request.
  • Tune pool size to match database capacity and expected concurrency.
  • Set connection and idle timeouts to reclaim stale connections.
  • HikariCP is the default pool in Spring Boot.
Advantages
Avoids Setup Cost

Reusing open connections avoids repeating the DNS lookup, TCP handshake, TLS handshake and authentication on every operation.

Lower Latency

Skipping connection establishment lowers latency and raises overall throughput.

Protects Database

Capping the number of connections shields the database from being overwhelmed.

Ready Connections

The pool hands out validated, ready-to-use connections instead of freshly created ones.

Disadvantages
Sizing Is Tricky

A pool that is too small starves requests, while one that is too large overloads the database.

Connection Leaks

Connections that are borrowed but never returned eventually exhaust the pool.

Tuning Burden

Running a pool adds an ongoing tuning and monitoring burden.

Code
-- Inspect current sessions/connections held against the server
SELECT s.session_id, s.login_name, s.host_name, s.program_name,
       s.status, c.connect_time, c.num_reads, c.num_writes
FROM sys.dm_exec_sessions AS s
JOIN sys.dm_exec_connections AS c
    ON s.session_id = c.session_id
WHERE s.program_name = 'AppPool';

-- A short, pool-friendly stored procedure: open, do minimal work, close
CREATE PROCEDURE usp_GetCustomerBalance
    @CustomerId INT
AS
BEGIN
    SET NOCOUNT ON;

    -- keep the transaction/connection hold time as short as possible
    SELECT Balance
    FROM Accounts
    WHERE CustomerId = @CustomerId;
END;

-- Application borrows a pooled connection, runs the proc, releases it fast
EXEC usp_GetCustomerBalance @CustomerId = 42;
How it works

sys.dm_exec_sessions joined with sys.dm_exec_connections shows every live connection a pool is holding open, useful for sizing and diagnosing leaks (the classic sp_who2 use case).

The stored procedure does one small unit of work and returns immediately, so a pooled connection is held only briefly per call.

Short, single-purpose procedures like this let a fixed-size pool serve many more logical requests per second.

Filtering by program_name lets an operator see exactly how many connections the application's pool currently has open.
