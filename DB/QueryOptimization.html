Query Optimization

Query optimization is the practice of rewriting queries and tuning the schema so the database returns results faster and with less resource use.

Core techniques include creating indexes on highly selective columns and caching results of frequent queries.

Use join fetch or eager loading in Hibernate to avoid repeated round trips.

Reading the execution plan reveals full table scans and expensive joins to fix.

The goal is to minimize rows scanned, memory used and network round trips.

When to use / Key points
  • Create indexes on highly selective columns used in filters and joins.
  • Select only the columns you need instead of SELECT *.
  • Use join fetch or eager loading to avoid the N+1 problem where appropriate.
  • Cache results of frequent read queries to reduce database load.
  • Inspect the query plan and remove full table scans.
Advantages
  • Lower query latency and higher throughput.
  • Reduced CPU, memory and I/O on the database.
  • Better scalability under load.
  • Lower infrastructure cost.
Disadvantages / Trade-offs
  • Extra indexes slow down writes and use storage.
  • Over-tuning for one query can hurt others.
  • Requires ongoing profiling as data grows.
Code
CREATE TABLE Orders (
    OrderId     INT PRIMARY KEY,
    Status      VARCHAR(20) NOT NULL,
    OrderDate   DATETIME NOT NULL,
    CustomerId  INT NOT NULL
);

-- SLOW: Status is VARCHAR but compared to an NVARCHAR literal,
-- causing an implicit conversion that blocks index use (full scan)
SELECT * FROM Orders
WHERE Status = N'SHIPPED';

-- OPTIMIZED: matching literal type + only needed columns + covering index
CREATE INDEX idx_orders_status_date
    ON Orders(Status)
    INCLUDE (OrderId, OrderDate, CustomerId);

SELECT OrderId, OrderDate, CustomerId
FROM Orders WITH (INDEX(idx_orders_status_date))
WHERE Status = 'SHIPPED';

-- Compare estimated cost of both forms
SET STATISTICS IO ON;
SELECT OrderId FROM Orders WHERE Status = 'SHIPPED';
SET STATISTICS IO OFF;
How it works
  • Comparing a VARCHAR column to an NVARCHAR literal forces SQL Server to convert every row's value, which disables an index seek and causes a full scan.
  • Matching the literal's type to the column lets the optimizer seek directly on the index instead of scanning.
  • The INCLUDE columns turn the index into a covering index, so the engine never touches the base table for this query.
  • WITH (INDEX(...)) is a hint forcing the optimizer to use a specific index when it might otherwise choose a worse plan.
  • SET STATISTICS IO ON reports logical reads, letting you measure the actual reduction in pages scanned before and after the change.
