Schema Registry

A schema registry is a central service that stores and versions the schemas of messages exchanged between producers and consumers.

It is commonly used with Kafka to manage Avro, Protobuf or JSON schemas.

Producers register a schema and send a small schema ID with each message instead of the full schema.

Consumers fetch the schema by ID to deserialize the message correctly.

The registry enforces compatibility rules so schema changes do not break consumers.

When to use / Key points
  • Use with event streaming to decouple producers and consumers safely.
  • It enforces backward, forward or full compatibility on new schema versions.
  • Messages carry a compact schema ID, reducing payload size.
  • Consumers can evolve independently as long as compatibility holds.
  • Confluent Schema Registry is a common implementation for Kafka.
Advantages
Prevents Breaking Changes

It prevents incompatible schema changes from breaking downstream pipelines.

Smaller Messages

Messages stay smaller because the schema is referenced by a compact ID rather than embedded in full.

Central Source Of Truth

It provides a central, versioned source of truth for message contracts.

Independent Evolution

It lets producers and consumers evolve independently.

Disadvantages
External Dependency

It adds an external dependency to the pipeline.

Availability Risk

If the registry is unavailable, serialization and deserialization can fail.

Compatibility Discipline

It requires discipline around compatibility settings.

Code
-- Table modelling a schema registry: one row per registered schema version
CREATE TABLE SchemaSubject (
    subject_name   VARCHAR(100) NOT NULL,
    version        INT NOT NULL,
    schema_id      INT IDENTITY(1,1),
    schema_text    NVARCHAR(MAX) NOT NULL,
    compatibility  VARCHAR(20) NOT NULL DEFAULT 'BACKWARD',
    registered_at  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK_SchemaSubject PRIMARY KEY (subject_name, version),
    CONSTRAINT CK_SchemaSubject_compat
        CHECK (compatibility IN ('BACKWARD', 'FORWARD', 'FULL', 'NONE'))
);

-- Register a new version for a subject (version must increment by 1)
INSERT INTO SchemaSubject (subject_name, version, schema_text, compatibility)
SELECT 'users-value',
       ISNULL(MAX(version), 0) + 1,
       '{"type":"record","name":"User","fields":[...]}',
       'BACKWARD'
FROM SchemaSubject
WHERE subject_name = 'users-value';

-- Consumer resolves a schema by its compact numeric ID
SELECT schema_text
FROM SchemaSubject
WHERE schema_id = 42;

-- Latest version currently in force for a subject
SELECT TOP (1) *
FROM SchemaSubject
WHERE subject_name = 'users-value'
ORDER BY version DESC;
How it works

Each row is one immutable version of a subject's schema, keyed by (subject_name, version) with a unique schema_id for compact wire references.

The CHECK constraint restricts compatibility to the recognized modes, mirroring how a real registry enforces a compatibility policy per subject.

Registering a new version computes MAX(version) + 1, so versions increase monotonically per subject, just like a schema registry.

Producers embed schema_id in messages; consumers do a cheap lookup by that ID to fetch the exact schema for deserialization.
