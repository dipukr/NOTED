Schema Evolution

Schema evolution is the ability to change a database or message schema over time without breaking existing data or consumers.

It covers adding, removing and modifying fields while keeping backward and forward compatibility.

Backward compatibility lets new code read old data; forward compatibility lets old code read new data.

It is critical for long-lived databases and for event streaming systems like Kafka.

Compatibility rules guide which changes are safe.

When to use / Key points
  • Add new fields as optional or with defaults to stay backward compatible.
  • Avoid renaming or removing fields still used by consumers.
  • Deprecate before deleting; roll changes out in phases.
  • Use expand-and-contract: add new, migrate, then remove old.
  • For events, enforce compatibility via a schema registry.
Pros and Cons
No Downtime

It enables continuous change without requiring downtime.

Safe Coexistence

Old and new versions can coexist safely at the same time.

Fewer Broken Consumers

It reduces the risk of breaking existing consumers.

Independent Deployment

It supports independent deployment of services.

Added Complexity

Maintaining compatibility adds extra complexity.

Lingering Fields

Deprecated fields linger and clutter the schema.

Slower Rollout

Multi-phase changes take longer to complete.

Code
-- Original table
CREATE TABLE AppUser (
    id            INT IDENTITY PRIMARY KEY,
    full_name     VARCHAR(200) NOT NULL
);

-- EXPAND: add new columns as optional / with a default so old writers still work
ALTER TABLE AppUser ADD first_name VARCHAR(100) NULL;
ALTER TABLE AppUser ADD last_name  VARCHAR(100) NULL;
ALTER TABLE AppUser
    ADD status VARCHAR(20) NOT NULL
    CONSTRAINT DF_AppUser_status DEFAULT 'ACTIVE';

-- MIGRATE: backfill new columns from the old one, in batches
UPDATE AppUser
SET first_name = LEFT(full_name, CHARINDEX(' ', full_name + ' ') - 1),
    last_name  = LTRIM(SUBSTRING(full_name, CHARINDEX(' ', full_name + ' '), 100))
WHERE first_name IS NULL;

-- CONTRACT: only after all readers/writers use first_name/last_name
ALTER TABLE AppUser ALTER COLUMN first_name VARCHAR(100) NOT NULL;
ALTER TABLE AppUser DROP COLUMN full_name;
How it works

ADD ... NULL introduces first_name/last_name without breaking existing rows or old writers that don't set them.

The status column uses a DEFAULT constraint so existing rows get a value automatically and old inserts remain valid.

A backfill UPDATE migrates existing data into the new columns while both old and new code paths keep working.

The contract phase (ALTER COLUMN ... NOT NULL, then DROP COLUMN) only runs once every consumer has moved off the old field.
