Denormalization

Denormalization is the deliberate introduction of redundancy into a normalized schema to improve read performance.

It duplicates or pre-joins data so queries need fewer joins.

It is a trade-off: faster reads in exchange for more storage and harder writes.

It is common in read-heavy systems, reporting tables and caches.

Redundant copies must be kept in sync when the source data changes.

When to use / Key points
  • Use when read performance matters more than write simplicity.
  • Good for reporting, dashboards and analytical (OLAP) workloads.
  • Store precomputed aggregates or duplicated columns to avoid joins.
  • Keep redundant data consistent via triggers, events or batch jobs.
  • Apply after profiling shows joins are the bottleneck.
Pros and Cons
Faster Reads

Read performance improves because expensive joins are avoided.

Simpler Queries

Reporting queries become simpler and quicker to run.

Reduced Table Load

It can reduce load on the primary tables.

Inconsistency Risk

Redundant data risks becoming inconsistent across copies.

Complex Writes

Writes become more complex and must update multiple copies.

More Storage

Duplicated data uses more storage space.

Harder Maintenance

It becomes harder to maintain as the schema evolves.

Code
-- Orders table gets a redundant, precomputed OrderTotal column
ALTER TABLE Orders ADD OrderTotal DECIMAL(18,2) NOT NULL DEFAULT 0;

-- Keep OrderTotal in sync whenever OrderItems changes (denormalization write cost)
CREATE TRIGGER TRG_OrderItems_SyncTotal
ON OrderItems
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;

    UPDATE o
    SET o.OrderTotal = agg.Total
    FROM Orders o
    JOIN (
        SELECT OrderId, SUM(Quantity * UnitPrice) AS Total
        FROM OrderItems
        WHERE OrderId IN (SELECT OrderId FROM inserted
                          UNION SELECT OrderId FROM deleted)
        GROUP BY OrderId
    ) agg ON agg.OrderId = o.OrderId;
END;

-- Reporting no longer needs to join and sum OrderItems every time
SELECT OrderId, OrderTotal FROM Orders WHERE CustomerId = 12;
How it works

OrderTotal is redundant data: it can always be recomputed from OrderItems, but storing it avoids that join on every read.

The TRG_OrderItems_SyncTotal trigger fires after any insert, update or delete on OrderItems and recalculates the affected orders' totals.

The inserted and deleted pseudo-tables let the trigger only re-aggregate the orders that actually changed, not the whole table.

Reporting queries now read OrderTotal directly instead of joining and summing OrderItems every time.

The cost of this speed-up is that every write to OrderItems now also pays for the trigger's aggregation.
