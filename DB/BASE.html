BASE

BASE is a consistency model used by many distributed and NoSQL databases as an alternative to ACID.

BASE stands for Basically Available, Soft state and Eventually consistent.

It trades immediate consistency for high availability and horizontal scalability.

The system is basically available, its state may change over time even without input (soft state), and replicas converge to the same value eventually.

BASE arises from the CAP theorem, choosing availability and partition tolerance over strong consistency.

When to use / Key points
  • Basically Available: the system always responds, even if with stale or partial data.
  • Soft state: data may be in flux as replicas sync in the background.
  • Eventually consistent: given no new writes, all replicas converge to the same value.
  • Use BASE for large-scale, write-heavy or globally distributed systems that value uptime.
  • Suitable for feeds, product catalogs and analytics where slight staleness is acceptable.
Advantages
High Availability

The system stays available and fault tolerant, continuing to respond even during failures.

Horizontal Scalability

It scales horizontally with ease by adding more nodes.

Low Latency

Writes achieve low latency because they need not wait for global agreement.

Partition Resilient

The system remains resilient to network partitions.

Disadvantages
Stale Reads

Reads can return stale data because replicas may not yet have converged.

Conflict Handling

The application must handle conflicts and reconciliation itself.

Not Strictly Correct

It is not suitable for operations needing strict correctness like money transfers.

Code
-- Cart row carries a version and last-writer timestamp for reconciliation
CREATE TABLE Cart (
    UserId       INT PRIMARY KEY,
    CartData     NVARCHAR(MAX),
    Version      INT NOT NULL DEFAULT 1,
    UpdatedAt    DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

-- Read from a replica: may return a slightly stale (soft-state) row
SELECT UserId, CartData, Version, UpdatedAt
FROM Cart WITH (NOLOCK)     -- tolerate reading an in-flight replica copy
WHERE UserId = 42;

-- Reconciliation: only overwrite if this write is newer (last-writer-wins)
UPDATE Cart
SET CartData = '{"items":[101,205]}',
    Version = Version + 1,
    UpdatedAt = SYSUTCDATETIME()
WHERE UserId = 42
  AND UpdatedAt < '2026-09-20T10:15:00';   -- reject stale writes, allow convergence
How it works

Every row carries a Version and UpdatedAt so conflicting writes from different replicas can be reconciled.

WITH (NOLOCK) reads whatever the replica currently has, illustrating basic availability even if the value is momentarily stale.

The reconciliation UPDATE only applies when its timestamp is newer, a simple last-writer-wins merge rule.

Given no further writes, all replicas eventually converge on the highest Version/UpdatedAt row.
