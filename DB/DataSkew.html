Data Skew

Data skew is the uneven distribution of data or load across partitions, shards or nodes.

Some partitions hold far more rows or receive far more traffic than others.

The overloaded partition becomes a hotspot and bottlenecks the whole system.

It commonly comes from a poor partition or shard key with low cardinality or skewed values.

It also degrades distributed joins and aggregations.

When to use / Key points
  • Choose a high-cardinality, evenly distributed shard/partition key.
  • Watch for celebrity keys (a few values with huge volume).
  • Add salting or composite keys to spread hot values.
  • Monitor per-partition size and request rate.
  • Rebalance or re-shard when skew develops.
Advantages
  • Detecting and fixing skew restores even load and scalability.
  • Good key choice avoids skew from the start.
  • Salting techniques can neutralize hot keys.
Disadvantages / Trade-offs
  • Hotspots cap throughput regardless of total capacity.
  • Salting complicates queries and reassembly.
  • Rebalancing is disruptive and costly.
Code
-- Reveal skew: one CustomerId dominates the row count (a "celebrity" key)
SELECT CustomerId, COUNT(*) AS OrderCount
FROM Orders
GROUP BY CustomerId
ORDER BY OrderCount DESC;
-- CustomerId 555 might own 40% of all rows, overloading its partition

-- Salting: add a computed bucket column to spread a hot key over N buckets
ALTER TABLE Orders
ADD ShardBucket AS (CustomerId % 16) PERSISTED;

-- Writes: bucket is derived automatically, spreading a hot CustomerId across 16 slots
INSERT INTO Orders (CustomerId, OrderDate, Total)
VALUES (555, SYSUTCDATETIME(), 120.00);

-- Reads for the hot key must fan out across every bucket and merge results
SELECT OrderId, OrderDate, Total
FROM Orders
WHERE CustomerId = 555
  AND ShardBucket BETWEEN 0 AND 15;
How it works

The GROUP BY query exposes skew directly: a few CustomerId values own a disproportionate share of rows.

ShardBucket is a persisted computed column that hashes the hot key into one of 16 buckets.

Writes for the same logical key now spread across 16 physical slots instead of piling onto one partition.

Reads must query across all buckets and merge, trading read simplicity for write-side load balance.
