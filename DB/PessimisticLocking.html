Pessimistic Locking

Pessimistic locking assumes conflicts are likely and locks a row as soon as it is read.

Other transactions that want the same row must wait until the lock is released.

It guarantees exclusive access for the duration of the transaction.

It is implemented with statements like SELECT ... FOR UPDATE.

It favours correctness over concurrency for highly contended data.

When to use / Key points
  • Use when conflicts are frequent or the cost of a retry is high.
  • Good for hot rows like inventory counts or account balances.
  • Acquire the lock with SELECT ... FOR UPDATE inside a transaction.
  • Keep the transaction short to reduce blocking.
  • In JPA, use LockModeType.PESSIMISTIC_WRITE.
Advantages
Exclusive Access

It guarantees exclusive access to a row, avoiding lost updates.

No Wasted Retries

There are no wasted retries on conflict because waiters block until the lock is free.

Simple Mental Model

It provides a simple mental model for contended data.

Predictable Behaviour

It behaves predictably under heavy contention.

Disadvantages
Reduced Concurrency

It reduces concurrency because readers block.

Deadlock Risk

It can cause deadlocks if locks are taken in different orders.

Throughput Cost

Long-held locks hurt throughput.

Code
-- Hot row: stock table backing an inventory reservation
CREATE TABLE Stock (
    StockId      INT PRIMARY KEY,
    Sku          VARCHAR(50) NOT NULL,
    QtyOnHand    INT NOT NULL
);

-- Session A: lock the row so no one else can read/write it until commit
BEGIN TRANSACTION;

SELECT StockId, QtyOnHand
FROM Stock WITH (UPDLOCK, ROWLOCK)
WHERE StockId = 1001;

-- Session B running concurrently blocks here until Session A commits:
-- SELECT * FROM Stock WITH (UPDLOCK, ROWLOCK) WHERE StockId = 1001;

UPDATE Stock
SET QtyOnHand = QtyOnHand - 5
WHERE StockId = 1001;

COMMIT;
-- lock releases here; Session B's SELECT can now proceed

-- ANSI/PostgreSQL equivalent: SELECT ... FOR UPDATE
-- SELECT stock_id, qty_on_hand FROM stock WHERE stock_id = 1001 FOR UPDATE;
How it works

WITH (UPDLOCK, ROWLOCK) takes an update lock on just that row as soon as it is read.

Any other transaction trying to read or write the same row with a compatible lock hint must wait.

The lock is held for the whole transaction and released only on COMMIT or ROLLBACK.

This prevents two concurrent reservations from both reading the same quantity and overselling stock.

SELECT ... FOR UPDATE is the portable ANSI form of the same pattern on PostgreSQL/Oracle/MySQL.
