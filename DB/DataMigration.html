Data Migration

Data migration is the process of moving data from one system, format or schema to another.

It covers database upgrades, moving to a new database, and transforming data into a new structure.

A typical migration extracts data from the source, transforms it, and loads it into the target (ETL).

Migrations should be repeatable, verifiable and reversible where possible.

Schema migrations are usually versioned and applied by tools like Flyway or Liquibase.

When to use / Key points
  • Version every schema change so environments stay in sync.
  • Prefer additive, backward-compatible steps to enable zero-downtime deploys.
  • Validate row counts and checksums after migrating data.
  • Run large data backfills in batches to avoid long locks.
  • Always test migrations on a copy of production first.
Advantages
Repeatable and Auditable

Schema evolution is repeatable and auditable, so every change is tracked and can be reproduced.

Environment Consistency

Keeps all environments consistent by applying the same versioned changes everywhere.

Safe Incremental Change

Enables safe, incremental change instead of large risky one-off updates.

Rollback Support

Supports rollback with down migrations when a change needs to be reverted.

Disadvantages
Locking and Downtime

Large migrations can lock tables and cause downtime while they run.

Risk of Data Loss

Irreversible steps such as dropping columns risk permanent data loss.

Transformation Bugs

Data transformation bugs can corrupt data during the migration.

Deploy Coordination

Requires careful coordination with application deploys to avoid breakage.

Code
-- Track applied migrations so each version runs exactly once per environment
CREATE TABLE SchemaVersion (
    Version     INT PRIMARY KEY,
    Description NVARCHAR(200),
    AppliedAt   DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

-- V2: additive, backward-compatible column with a default
ALTER TABLE Orders ADD Status VARCHAR(20) NOT NULL DEFAULT 'NEW';

-- Move existing data into the new column in small batches to avoid long locks
WHILE 1 = 1
BEGIN
    UPDATE TOP (1000) Orders
    SET Status = 'DONE'
    WHERE Status = 'NEW' AND CompletedAt IS NOT NULL;

    IF @@ROWCOUNT = 0 BREAK;   -- stop once no more rows match
END;

-- Record that this version has been applied to this database
INSERT INTO SchemaVersion (Version, Description)
VALUES (2, 'add status column and backfill');
How it works

SchemaVersion is a versioning table, the SQL equivalent of Flyway/Liquibase's history table, ensuring each migration runs once.

ALTER TABLE ... ADD ... DEFAULT is additive and backward compatible, so old application code keeps working during rollout.

UPDATE TOP (1000) inside a loop backfills in small batches instead of one giant transaction, avoiding a long-held table lock.

@@ROWCOUNT tells the loop when there is no more data left to migrate.

The final INSERT records the version so the migration is not re-applied on the next deploy.
