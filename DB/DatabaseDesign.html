Database Design

Database design is the process of modelling data into tables, columns, keys and relationships so information is stored consistently and retrieved efficiently.

A database is a collection of data modelled and organized in a specific way, managed by a database management system (DBMS).

In a relational database, data is structured into a set of tables and a set of relationships between those tables.

Good design captures entities, their attributes and the cardinality of the relationships between them before any code is written.

The goal is to reduce redundancy, enforce integrity and keep the schema flexible enough to evolve.

When to use / Key points
  • Identify entities and their attributes, then choose a primary key that uniquely identifies each row.
  • Use foreign keys to enforce referential integrity between parent and child tables.
  • Model relationships as one-to-one, one-to-many or many-to-many (with a join table).
  • Apply normalization to remove redundancy, then denormalize selectively for read performance.
  • Pick correct data types and add constraints (NOT NULL, UNIQUE, CHECK) up front.
Advantages
  • Reduces data redundancy and prevents update anomalies.
  • Enforces data integrity through keys and constraints.
  • Makes queries predictable and easier to optimize.
  • A clear schema simplifies onboarding and maintenance.
Disadvantages / Trade-offs
  • Over-normalized schemas can require many joins, hurting read performance.
  • Rigid schemas are harder to change once large amounts of data exist.
  • Poor upfront design is expensive to correct later.
Code
-- A small normalized schema: Country -> Customer -> Order (one-to-many)
CREATE TABLE Country (
    CountryId   INT IDENTITY PRIMARY KEY,
    Name        NVARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE Customer (
    CustomerId  INT IDENTITY PRIMARY KEY,
    Email       NVARCHAR(255) NOT NULL UNIQUE,
    CountryId   INT NOT NULL,
    CONSTRAINT FK_Customer_Country
        FOREIGN KEY (CountryId) REFERENCES Country(CountryId)
);

CREATE TABLE Orders (
    OrderId     INT IDENTITY PRIMARY KEY,
    CustomerId  INT NOT NULL,
    Total       DECIMAL(18,2) NOT NULL CHECK (Total >= 0),
    OrderDate   DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT FK_Order_Customer
        FOREIGN KEY (CustomerId) REFERENCES Customer(CustomerId)
);

-- Joining across the modelled relationships
SELECT c.Email, co.Name AS Country, o.OrderId, o.Total
FROM Customer c
JOIN Country co ON co.CountryId = c.CountryId
JOIN Orders o ON o.CustomerId = c.CustomerId;
How it works
  • Each table has a single-column IDENTITY PRIMARY KEY that uniquely identifies its rows.
  • UNIQUE on Email and Country.Name prevents duplicate values at the schema level.
  • FK_Customer_Country and FK_Order_Customer enforce referential integrity between parent and child tables.
  • The CHECK constraint on Total stops invalid data from ever being stored.
  • The final query walks the one-to-many relationships (Country to Customer to Orders) via ordinary joins.
