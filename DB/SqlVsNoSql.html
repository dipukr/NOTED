SQL vs NoSQL

Depending on how data is modelled and organized, databases are grouped into two broad categories: SQL and NoSQL.

SQL (relational) databases structure data into a set of tables and a set of relationships between those tables, with a fixed schema.

NoSQL databases store data as documents, key-value pairs, wide columns or graphs, usually with a flexible or schema-less model.

SQL databases favour strong consistency and ACID transactions; many NoSQL stores favour availability and horizontal scale.

The right choice depends on data shape, query patterns, consistency needs and scale.

When to use / Key points
  • Use SQL when data is highly relational and you need joins, transactions and strong consistency.
  • Use NoSQL for large volumes of loosely structured data or very high write/read throughput.
  • SQL scales vertically and with read replicas; NoSQL is built to scale horizontally by sharding.
  • SQL enforces schema on write; NoSQL often applies schema on read.
  • Many systems use both (polyglot persistence) for different workloads.
Advantages
SQL Mature Querying

SQL offers mature tooling, ACID guarantees and powerful ad-hoc queries with joins.

SQL Strong Integrity

SQL enforces strong data integrity through keys and constraints.

NoSQL Flexible Scaling

NoSQL provides a flexible schema and easy horizontal scaling.

NoSQL Fast Access

NoSQL delivers high performance for simple key-based access patterns.

Disadvantages
SQL Scaling Limits

With SQL, horizontal scaling is harder and schema changes can be costly.

NoSQL Weak Consistency

NoSQL offers limited or no joins and often only eventual consistency.

NoSQL Rigid Modelling

NoSQL query flexibility is weaker, so you must model data around access patterns.

Code
-- Relational (SQL): normalized tables, joined at query time
CREATE TABLE Customer (
    id            INT PRIMARY KEY,
    email         VARCHAR(200) NOT NULL
);

CREATE TABLE Orders (
    id            INT PRIMARY KEY,
    customer_id   INT NOT NULL REFERENCES Customer(id),
    order_date    DATE NOT NULL,
    total_amount  DECIMAL(10,2) NOT NULL
);

-- One customer's orders, assembled with a JOIN across normalized tables
SELECT c.email, o.order_date, o.total_amount
FROM Customer c
JOIN Orders o ON o.customer_id = c.id
WHERE c.email = 'jane@example.com'
ORDER BY o.order_date DESC;

-- Denormalized (NoSQL-style) single-table equivalent: orders embedded as JSON
CREATE TABLE CustomerDoc (
    id            INT PRIMARY KEY,
    email         VARCHAR(200) NOT NULL,
    orders_json   NVARCHAR(MAX) NOT NULL   -- e.g. '[{"date":"2024-01-05","total":49.99}, ...]'
);

-- Same result, no join needed: shred the embedded JSON with OPENJSON
SELECT d.email, j.order_date, j.total_amount
FROM CustomerDoc d
CROSS APPLY OPENJSON(d.orders_json)
    WITH (order_date DATE '$.date', total_amount DECIMAL(10,2) '$.total') AS j
WHERE d.email = 'jane@example.com'
ORDER BY j.order_date DESC;
How it works

The relational version keeps customers and orders in separate, normalized tables linked by a foreign key, so a JOIN is required to combine them.

The denormalized version embeds each customer's orders directly as JSON in a single row, mirroring how a document store like MongoDB would model the same data.

OPENJSON shreds the embedded array back into rows at query time, avoiding a join at the cost of update complexity and possible duplication.

The normalized model favors consistency and flexible querying; the denormalized model favors fast single-document reads at the expense of join-free, harder updates.
