Lock Escalation

Lock escalation is when the database converts many fine-grained locks (row or page) into a single coarse-grained lock (table).

It happens when a transaction acquires so many locks that tracking them costs too much memory.

Escalating to a table lock reduces lock-management overhead but blocks other transactions.

It is a trade-off between memory usage and concurrency.

Large bulk updates are a common trigger.

When to use / Key points
  • Escalation triggers when the number of row/page locks crosses a threshold.
  • Avoid it by updating in smaller batches instead of one huge statement.
  • Filter updates with indexed predicates to lock fewer rows.
  • Keep transactions short so locks are released quickly.
  • Some engines let you disable or tune escalation per table.
Advantages
Lower Memory Use

It reduces the memory spent tracking many individual row and page locks.

Less CPU Overhead

It lowers the lock-management CPU overhead.

Simpler Bookkeeping

It simplifies the lock manager's bookkeeping.

Disadvantages
Reduced Concurrency

A table lock blocks other transactions, reducing concurrency.

Blocking And Timeouts

It can cause blocking chains and timeouts under load.

More Deadlocks

It increases the chance of deadlocks.

Code
-- A single bulk UPDATE touching millions of rows escalates row -> page -> table
UPDATE Product
SET Price = Price * 1.05
WHERE Updated = 0;
-- once the row/page lock count crosses ~5000, SQL Server escalates to
-- a single table (X) lock, blocking all other writers on Product

-- Disable escalation for this table so it never jumps straight to table-level
ALTER TABLE Product SET (LOCK_ESCALATION = DISABLE);

-- Or escalate to a single partition instead of the whole table
ALTER TABLE Product SET (LOCK_ESCALATION = AUTO);

-- Better fix: batch the update so each transaction stays under the threshold
DECLARE @BatchSize INT = 2000, @RowsAffected INT = 1;

WHILE @RowsAffected > 0
BEGIN
    UPDATE TOP (@BatchSize) Product
    SET Price = Price * 1.05, Updated = 1
    WHERE Updated = 0;

    SET @RowsAffected = @@ROWCOUNT;
END;
How it works

The single unbatched UPDATE can acquire enough row/page locks that SQL Server escalates to one table-level lock, blocking every other writer.

LOCK_ESCALATION = DISABLE stops that table from ever escalating straight to a full table lock (it can still escalate to partition level on a partitioned table).

LOCK_ESCALATION = AUTO lets a partitioned table escalate to a single partition instead of the whole table, keeping other partitions free.

The batched WHILE loop is the more common real-world fix: each 2000-row batch commits and releases its locks before the next one starts, so the row-lock count never gets close to the escalation threshold.
