Materialized Views

A materialized view is a database object that stores the physical result of a query, unlike a regular view which is computed on every access.

It precomputes and persists expensive joins and aggregations so reads are fast.

The stored result must be refreshed to reflect changes in the underlying tables.

Refresh can be full, incremental or on a schedule.

Materialized views are a form of controlled denormalization managed by the database.

When to use / Key points
  • Use for expensive aggregations or joins queried far more often than the data changes.
  • Ideal for dashboards, reports and summary tables.
  • Choose a refresh strategy that matches acceptable staleness.
  • Incremental refresh updates only changed rows for efficiency.
  • Index the materialized view like a normal table.
Advantages
  • Very fast reads because results are precomputed.
  • Offloads heavy computation from query time.
  • Managed and refreshed by the database engine.
  • Can be indexed for further speedups.
Disadvantages / Trade-offs
  • Data is stale between refreshes.
  • Refreshing consumes CPU, I/O and storage.
  • Not all databases support incremental refresh.
Code
-- Base tables
CREATE TABLE Sales (
    SaleId INT IDENTITY PRIMARY KEY,
    SaleDate DATE NOT NULL,
    Amount DECIMAL(10,2) NOT NULL
);

-- Postgres: true materialized view, stored physically until refreshed
CREATE MATERIALIZED VIEW SalesByDay AS
SELECT SaleDate, SUM(Amount) AS TotalAmount
FROM Sales
GROUP BY SaleDate;

-- refresh recomputes and repersists the result (blocks reads unless CONCURRENTLY)
REFRESH MATERIALIZED VIEW CONCURRENTLY SalesByDay;

-- T-SQL equivalent: a schema-bound view backed by a unique clustered index
CREATE VIEW dbo.SalesByDay_V WITH SCHEMABINDING AS
SELECT SaleDate, SUM(Amount) AS TotalAmount, COUNT_BIG(*) AS RowCnt
FROM dbo.Sales
GROUP BY SaleDate;

-- the unique clustered index materializes the view's rows on disk
CREATE UNIQUE CLUSTERED INDEX IX_SalesByDay_V
    ON dbo.SalesByDay_V (SaleDate);
How it works
  • CREATE MATERIALIZED VIEW stores the aggregated SUM per day physically instead of recomputing it on every read.
  • REFRESH MATERIALIZED VIEW CONCURRENTLY recomputes and repersists the result without locking out readers.
  • In SQL Server, WITH SCHEMABINDING plus a unique clustered index turns a normal view into an indexed (materialized) view.
  • Reads against the materialized/indexed view skip the join and aggregation entirely, trading staleness for speed.
