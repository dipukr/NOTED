ACID

ACID properties define the reliability and integrity of database transactions.

They ensure transactions are processed reliably and that the database remains in a consistent state, even in the face of system failures.

ACID stands for Atomicity, Consistency, Isolation and Durability.

These guarantees are the hallmark of traditional relational databases.

They come at a cost in throughput and are relaxed by the BASE model in many distributed systems.

When to use / Key points
  • Atomicity: transactions are a single indivisible unit; either all operations succeed or none do, with rollback on failure.
  • Consistency: a transaction must bring the database from one valid state to another, respecting all constraints and rules.
  • Isolation: concurrent transactions must not interfere, as if they ran sequentially, preventing dirty reads and lost updates.
  • Durability: once committed, changes are permanent and survive crashes and power outages via persistent storage.
  • Use ACID databases when correctness of money, inventory or bookings matters.
Advantages
  • Strong correctness guarantees for critical data.
  • Predictable behaviour under concurrency and failure.
  • Simplifies reasoning about multi-step operations.
  • Well supported by mature relational engines.
Disadvantages / Trade-offs
  • Strong isolation reduces concurrency and throughput.
  • Hard to preserve fully across distributed nodes.
  • Can become a scalability bottleneck at very high load.
Code
-- Accounts table with a CHECK constraint enforcing consistency
CREATE TABLE Accounts (
    AccountId   INT PRIMARY KEY,
    Balance     DECIMAL(18,2) NOT NULL,
    CONSTRAINT CK_Balance_NonNegative CHECK (Balance >= 0)
);

-- Atomicity + Isolation: transfer money between two accounts
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;

BEGIN TRY
    UPDATE Accounts
    SET Balance = Balance - 500
    WHERE AccountId = 1;

    UPDATE Accounts
    SET Balance = Balance + 500
    WHERE AccountId = 2;

    -- Consistency: the CHECK constraint blocks an overdraft here
    COMMIT;                       -- Durability: change is flushed to the log
END TRY
BEGIN CATCH
    ROLLBACK;                     -- Atomicity: undo both updates on any failure
    THROW;
END CATCH;
How it works
  • BEGIN TRANSACTION / COMMIT / ROLLBACK give atomicity: both balance updates apply together or not at all.
  • SET TRANSACTION ISOLATION LEVEL SERIALIZABLE stops a concurrent transaction from seeing a half-completed transfer.
  • The CK_Balance_NonNegative check constraint enforces the consistency rule that no account goes negative.
  • TRY/CATCH rolls back cleanly if the constraint fails or any error occurs mid-transaction.
  • Once COMMIT returns, the transfer is durable and survives a crash or restart.
