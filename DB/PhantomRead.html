Phantom Read

A phantom read occurs when a transaction re-runs a range query and finds new rows that were inserted by another committed transaction.

The same query returns a different set of rows within one transaction.

Unlike a non-repeatable read, which is about a changed row, a phantom is about rows appearing or disappearing.

Phantom reads are prevented at the Serializable isolation level.

Some engines also prevent them at Repeatable Read using range locks or snapshots.

When to use / Key points
  • Happens with range/aggregate queries run twice in one transaction.
  • Prevent it with Serializable isolation.
  • Range locks (next-key locks) block inserts into the queried range.
  • Matters for logic like "count then act on that count".
  • MVCC snapshots can also hide phantoms within a transaction.
Advantages
Guides Isolation Choice

Understanding phantom reads helps you pick the correct isolation level for range-based logic.

Strict Correctness

Serializable isolation eliminates phantoms entirely for strict correctness.

Higher Concurrency

Allowing phantoms keeps concurrency higher when it is safe to do so.

Disadvantages
Broken Invariants

Phantoms can break invariants that depend on a stable set of rows.

Reduced Concurrency

Preventing phantoms with range locks reduces overall concurrency.

Engine Differences

Phantom behaviour differs across database engines.

Code
CREATE TABLE Slot (
    SlotId  INT IDENTITY PRIMARY KEY,
    Day     DATE NOT NULL
);

-- REPEATABLE READ: still allows a phantom row on a re-run range query
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION;

SELECT COUNT(*) FROM Slot WHERE Day = '2024-06-01';  -- returns 0

-- Another session concurrently commits a new row for the same day:
-- INSERT INTO Slot(Day) VALUES ('2024-06-01'); COMMIT;

SELECT COUNT(*) FROM Slot WHERE Day = '2024-06-01';  -- returns 1, a phantom
COMMIT;

-- SERIALIZABLE: takes a range lock so the phantom insert cannot happen
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;

SELECT COUNT(*) FROM Slot WHERE Day = '2024-06-02';  -- returns 0

-- Concurrent INSERT INTO Slot(Day) VALUES ('2024-06-02') now blocks until commit

IF @@ROWCOUNT = 0
    INSERT INTO Slot(Day) VALUES ('2024-06-02');

COMMIT;
How it works

Under REPEATABLE READ, existing rows can't change mid-transaction, but a range query can still gain new rows inserted by others.

The two identical SELECT COUNT(*) calls return different results within the same transaction — a phantom read.

SERIALIZABLE takes a range (key-range) lock covering the queried predicate, blocking concurrent inserts into that range.

This makes the count-then-insert pattern safe: no other transaction can sneak a matching row in between the read and the write.

The trade-off is reduced concurrency, since the range lock is held until COMMIT.
