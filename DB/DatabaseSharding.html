Database Sharding Strategies

Sharding is the process of dividing a database table (dataset) into smaller, more manageable pieces called shards, which are distributed across multiple machines or nodes.

Sharding usually refers to splitting one large table's data horizontally (row-wise) across multiple databases or servers.

Each shard contains a subset of rows of the table, and all shards share the same schema, just different data.

It splits large datasets into smaller chunks to spread load across servers.

A shard key determines which shard a given row belongs to.

When to use / Key points
  • Use sharding when one server can no longer hold the data or handle the write throughput.
  • Range sharding: split by ranges of the shard key (good for range scans, risk of hotspots).
  • Hash sharding: hash the key to distribute rows evenly (good balance, poor range scans).
  • Directory/lookup sharding: a lookup table maps keys to shards (flexible, extra hop).
  • Choose a shard key with high cardinality and even access to avoid hot shards.
Pros and Cons
Horizontal Scaling

Sharding enables near-linear horizontal scaling of both storage capacity and write throughput.

Faster Queries

Smaller per-shard datasets mean queries and indexes run faster.

Fault Isolation

The failure of one shard affects only part of the data rather than the whole dataset.

Complex Cross-Shard Queries

Queries and joins that span multiple shards are complex and slow.

Hotspot Risk

A poorly chosen shard key causes hotspots and uneven load across shards.

Difficult Re-Sharding

Re-sharding to add capacity is difficult and risky to perform.

Hard Distributed Transactions

Distributed transactions spanning multiple shards are hard to guarantee.

Code
-- Every shard database has an identically-shaped Customer table
CREATE TABLE Customer (
    CustomerId  INT PRIMARY KEY,     -- the shard key
    Email       NVARCHAR(255) NOT NULL,
    Region      NVARCHAR(50) NOT NULL
);

-- Insert on Shard1 only routes rows whose CustomerId hashes here
INSERT INTO Customer (CustomerId, Email, Region)
VALUES (10042, 'a@example.com', 'EU');   -- CustomerId % 4 = 2 -> Shard3

-- Cross-shard query fanning out via linked servers and merging results
SELECT CustomerId, Email, Region FROM Shard0.Sales.dbo.Customer
UNION ALL
SELECT CustomerId, Email, Region FROM Shard1.Sales.dbo.Customer
UNION ALL
SELECT CustomerId, Email, Region FROM Shard2.Sales.dbo.Customer
UNION ALL
SELECT CustomerId, Email, Region FROM Shard3.Sales.dbo.Customer
WHERE Region = 'EU';
How it works

Every shard database hosts the identical Customer table definition; only the data differs.

CustomerId is the shard key; a hash of it (CustomerId % 4) decides which shard database owns a given row.

A single-customer lookup goes directly to the one shard that owns that key, an O(1) routing decision.

A query that needs data across all customers, like the Region filter here, must fan out to every shard via four-part names and combine results with UNION ALL.

This fan-out cost is exactly why cross-shard queries and joins are more expensive than single-shard lookups.
