Normalization

Normalization is the process of organizing columns and tables to reduce data redundancy and improve data integrity.

It splits data into related tables so each fact is stored in exactly one place.

Normalization proceeds through normal forms: 1NF, 2NF, 3NF and beyond.

It removes update, insert and delete anomalies caused by duplicated data.

Relationships between the resulting tables are maintained with primary and foreign keys.

When to use / Key points
  • 1NF: atomic column values, no repeating groups.
  • 2NF: 1NF plus no partial dependency of non-key columns on part of a composite key.
  • 3NF: 2NF plus no transitive dependency between non-key columns.
  • Use normalization for write-heavy transactional (OLTP) systems.
  • Each piece of data should be stored once to avoid anomalies.
Advantages
Less Redundancy

Eliminates redundant data and saves storage.

Prevents Anomalies

Prevents update, insert and delete anomalies.

Better Data Integrity

Improves data integrity and consistency.

Easier To Extend

Makes the schema easier to extend.

Disadvantages
More Joins

Reads often need many joins, which can be slower.

Query Complexity

Highly normalized schemas can be complex to query.

Slower Analytics

May hurt performance for read-heavy analytical workloads.

Code
-- UN-NORMALIZED: repeating groups and mixed facts in one row (violates 1NF)
CREATE TABLE OrderFlat (
    OrderId INT,
    CustomerName VARCHAR(100),
    CustomerCity VARCHAR(100),
    Product1 VARCHAR(100), Qty1 INT,
    Product2 VARCHAR(100), Qty2 INT
);

-- 1NF: atomic values, one row per order/product line, no repeating groups
CREATE TABLE OrderLine1NF (
    OrderId INT,
    CustomerName VARCHAR(100),
    CustomerCity VARCHAR(100),
    Product VARCHAR(100),
    Qty INT,
    PRIMARY KEY (OrderId, Product)
);

-- 2NF: split out attributes that depend only on part of the composite key
CREATE TABLE Customer (
    CustomerId INT PRIMARY KEY,
    CustomerName VARCHAR(100),
    CityId INT
);
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    CustomerId INT REFERENCES Customer(CustomerId)
);
CREATE TABLE OrderLine (
    OrderId INT REFERENCES Orders(OrderId),
    Product VARCHAR(100),
    Qty INT,
    PRIMARY KEY (OrderId, Product)
);

-- 3NF: remove the transitive dependency City -> CustomerId -> City name
CREATE TABLE City (
    CityId INT PRIMARY KEY,
    CityName VARCHAR(100),
    Pincode VARCHAR(10)
);
How it works

OrderFlat mixes repeating product columns with customer facts, violating 1NF.

OrderLine1NF makes each product line its own row with atomic values, satisfying 1NF.

Splitting Customer/Orders/OrderLine removes partial dependency on part of the composite key, satisfying 2NF.

Moving city details into their own City table removes the transitive dependency through CustomerId, satisfying 3NF; each fact now lives in exactly one place, joined via foreign keys.
