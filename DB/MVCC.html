MVCC (Multi-Version Concurrency Control)

MVCC is a concurrency control method where the database keeps multiple versions of a row instead of overwriting it in place.

Each transaction sees a consistent snapshot of the data as of its start time.

Readers never block writers and writers never block readers.

A write creates a new row version; old versions remain visible to transactions that started earlier.

Obsolete versions are later reclaimed by a cleanup process (for example vacuum).

When to use / Key points
  • MVCC is the default in PostgreSQL, Oracle and many modern databases.
  • It gives snapshot isolation without read locks.
  • Each version is tagged with transaction visibility information.
  • It prevents dirty reads and non-repeatable reads via snapshots.
  • Dead versions must be garbage collected to reclaim space.
Advantages
High Concurrency

Readers and writers do not block each other, allowing many transactions to proceed in parallel.

Consistent Snapshots

Each transaction sees a consistent point-in-time snapshot of the data as of its start.

No Read Locks

It avoids read locks entirely, so reads never wait on other transactions.

Scales For Reads

It scales well for read-heavy workloads because reads are lock-free.

Disadvantages
Storage Overhead

Old row versions consume storage until they are cleaned up.

Cleanup Overhead

Vacuum and cleanup processes add background overhead to the system.

Version Chain Bloat

Long-running transactions can bloat version chains by keeping old versions alive.

Write Skew Remains

It does not by itself prevent write skew anomalies.

Code
-- Enable row-versioning based MVCC in SQL Server
ALTER DATABASE Shop SET ALLOW_SNAPSHOT_ISOLATION ON;
ALTER DATABASE Shop SET READ_COMMITTED_SNAPSHOT ON;

CREATE TABLE Product (
    ProductId INT PRIMARY KEY,
    Price DECIMAL(10,2) NOT NULL
);

-- Session A: opens a snapshot transaction and reads twice
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

    SELECT Price AS FirstRead FROM Product WHERE ProductId = 1;

    -- Session B commits an update to Price here, concurrently
    -- UPDATE Product SET Price = 250.00 WHERE ProductId = 1;

    -- Session A still sees the price from its own snapshot
    SELECT Price AS SecondRead FROM Product WHERE ProductId = 1;

COMMIT TRANSACTION;
How it works

ALLOW_SNAPSHOT_ISOLATION and READ_COMMITTED_SNAPSHOT turn on row-versioning so readers use a consistent snapshot instead of locks.

Session A's transaction fixes its snapshot at BEGIN TRANSACTION.

Session B's concurrent committed update creates a new row version that is invisible to Session A's snapshot.

FirstRead and SecondRead return the same value, and Session B was never blocked by Session A's reads.
