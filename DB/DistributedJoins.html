Distributed Joins

A distributed join combines rows from tables that live on different nodes, shards or databases.

Because the data is not co-located, the system must move data across the network to perform the join.

Common strategies are broadcast join (send a small table to every node) and shuffle/repartition join (redistribute both tables by the join key).

Distributed joins are expensive and are a key concern in sharded and big-data systems.

Good data modelling tries to avoid them by co-locating related data.

When to use / Key points
  • Broadcast join: replicate a small dimension table to all nodes holding the large table.
  • Shuffle join: repartition both tables by the join key so matching rows land together.
  • Co-locate frequently joined data using the same shard key to avoid network movement.
  • Denormalize to embed related data and skip the join entirely.
  • Push filters down before the join to move less data.
Advantages
Queries Massive Data

They allow querying across data that is too large to fit on a single machine.

Efficient Broadcast Joins

Broadcast joins are efficient when one side of the join is small.

Parallel Execution

Engines parallelize the work across many nodes for faster processing.

Disadvantages
Costly Network Movement

Moving data across the network makes distributed joins slow and costly.

Resource Intensive Shuffles

Shuffle joins can overwhelm memory and network capacity.

Data Skew Hotspots

Data skew on the join key creates hotspots that unbalance the work.

Hard To Keep Low Latency

It is hard to guarantee low latency for interactive queries.

Code
-- Linked server registered once, pointing at the remote SalesDb node
-- EXEC sp_addlinkedserver @server = 'RemoteSalesNode', @srvproduct = '', ...

-- Four-part name join: local Customer joined to a table on another server
SELECT c.CustomerId, c.Name, o.OrderId, o.Total
FROM Customer c
JOIN RemoteSalesNode.SalesDb.dbo.Orders o
    ON o.CustomerId = c.CustomerId
WHERE c.Region = 'EU';

-- OPENQUERY pushes the filter down so it runs on the remote server, not locally
SELECT c.CustomerId, c.Name, o.OrderId, o.Total
FROM Customer c
JOIN OPENQUERY(RemoteSalesNode,
    'SELECT CustomerId, OrderId, Total FROM SalesDb.dbo.Orders WHERE Total > 500') o
    ON o.CustomerId = c.CustomerId;

-- Broadcast-join style: small Region lookup unioned locally rather than joined remotely
SELECT o.OrderId, o.Total, r.RegionName
FROM RemoteSalesNode.SalesDb.dbo.Orders o
JOIN Region r ON r.RegionId = o.RegionId;  -- Region is tiny, kept local on every node
How it works

A linked server lets one SQL Server instance reference tables on another; the four-part name (Server.Database.Schema.Table) addresses the remote table directly.

The plain join pulls rows from the remote table row-by-row over the network, which is the expensive part of a distributed join.

OPENQUERY instead sends the whole filtered query text to execute on the remote server, so only the already-filtered result set crosses the network.

The last query is a broadcast-join pattern: the small Region table is kept locally on every node so it never needs to be shipped across the network to match a large remote table.

Pushing filters down (via OPENQUERY or predicate placement) and co-locating small dimension tables are the two main ways to keep distributed joins affordable.
