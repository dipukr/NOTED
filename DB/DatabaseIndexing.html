Database Indexing

Database indexing is a technique that improves the speed of data retrieval by creating a data structure, like a lookup table, that points to the data's location.

When you create an index on a column, a separate data structure is built with the values from that column and pointers to the corresponding rows in the main table.

Indexing helps us avoid a full table scan.

Indexes are not free: just as an index in a book requires paper, an index in a database requires storage, and every write must update the relevant indexes.

The name comes from a book index: instead of flipping page by page, you look up the topic and jump straight to it.

When to use / Key points
  • Create indexes on highly selective columns used in WHERE, JOIN and ORDER BY.
  • A clustered index physically sorts and stores the table's data by its key; a table can have only one.
  • A non-clustered index is a separate structure of keys plus pointers; a table can have many.
  • Composite indexes help queries that filter on multiple columns in order.
  • Avoid indexing columns that change constantly or have very low cardinality.
Advantages
  • Dramatically speeds up reads by avoiding full table scans.
  • Speeds up sorting and grouping on indexed columns.
  • Enforces uniqueness when created as a unique index.
  • Clustered indexes keep related rows physically close.
Disadvantages / Trade-offs
  • Consume extra storage.
  • Slow down INSERT, UPDATE and DELETE because indexes must be maintained.
  • Too many indexes waste space and confuse the optimizer.
  • Non-clustered indexes are slower to query than clustered ones.
Code
CREATE TABLE Employee (
    EmployeeId    INT IDENTITY PRIMARY KEY,   -- clustered index by default
    Email         NVARCHAR(255) NOT NULL,
    DepartmentId  INT NOT NULL,
    LastName      NVARCHAR(100) NOT NULL,
    HireDate      DATE NOT NULL
);

-- Unique non-clustered index: speeds lookups and enforces uniqueness
CREATE UNIQUE NONCLUSTERED INDEX IX_Employee_Email
    ON Employee(Email);

-- Covering index: includes LastName/HireDate so the query never touches the base table
CREATE NONCLUSTERED INDEX IX_Employee_Dept_Covering
    ON Employee(DepartmentId)
    INCLUDE (LastName, HireDate);

-- This query is fully satisfied by IX_Employee_Dept_Covering (an index-only seek)
SELECT LastName, HireDate
FROM Employee
WHERE DepartmentId = 7;

-- Inspect the execution plan to confirm a seek, not a scan, is used
SET SHOWPLAN_XML ON;
GO
SELECT LastName, HireDate FROM Employee WHERE DepartmentId = 7;
GO
SET SHOWPLAN_XML OFF;
How it works

The PRIMARY KEY creates a clustered index, so Employee rows are physically stored in EmployeeId order.

IX_Employee_Email is a unique non-clustered index: a separate structure of keys and pointers that also enforces uniqueness.

IX_Employee_Dept_Covering uses INCLUDE to add non-key columns, making it a covering index for the department lookup query.

Because every column the query needs is in the index, the engine never has to visit the base table (a "key lookup" is avoided).

SET SHOWPLAN_XML ON reveals the execution plan so you can confirm an index seek is chosen instead of a full scan.
