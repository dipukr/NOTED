Dirty Read

A dirty read happens when one transaction reads data that another transaction has written but not yet committed.

If the other transaction rolls back, the first transaction has read a value that never officially existed.

It is the weakest consistency anomaly and can lead to decisions based on invalid data.

Dirty reads are only possible at the Read Uncommitted isolation level.

Read Committed and higher levels prevent them.

When to use / Key points
  • Occurs only under Read Uncommitted isolation.
  • Prevent it by using Read Committed or higher.
  • Reading uncommitted data risks acting on values that get rolled back.
  • Almost never acceptable for correctness-sensitive logic.
  • May be tolerated only for rough, approximate reporting.
Pros and Cons
Maximum Concurrency

Allowing dirty reads gives maximum concurrency and no read locks.

Approximate Metrics

It can be acceptable for approximate, non-critical metrics.

Clarifies Defaults

Understanding it clarifies why Read Committed is the sane default.

Rolled-Back Values

It can read values that are later rolled back.

Incorrect Decisions

It leads to incorrect business decisions.

Hard To Debug

It is hard to reason about and debug.

Code
-- Session A: modifies a balance but has not committed yet
BEGIN TRANSACTION;
    UPDATE Accounts SET Balance = Balance - 1000 WHERE AccountId = 1;
    -- ... no COMMIT or ROLLBACK yet, transaction is still open ...

-- Session B: READ UNCOMMITTED lets it see Session A's unfinished change
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT Balance FROM Accounts WHERE AccountId = 1;
-- returns the reduced balance, even though Session A may still roll back -- a dirty read

-- Back in Session A: the change is undone
ROLLBACK;
-- Session B's earlier read is now proven wrong: it saw a value that never existed

-- Fix: READ COMMITTED never exposes another transaction's uncommitted rows
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT Balance FROM Accounts WHERE AccountId = 1;   -- blocks until Session A commits/rolls back, then reads the final value
How it works

SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED tells the engine to skip shared locks and read whatever is currently in the buffer, including uncommitted changes.

Session B's SELECT sees Session A's debit before it commits, a dirty read.

When Session A later rolls back, Session B has already acted on a value that never officially existed in the database.

READ COMMITTED (the SQL Server default) prevents this by only ever returning committed row versions, blocking or reading the pre-change value instead.

Dirty reads are only possible at the lowest isolation level; every higher level rules them out.
