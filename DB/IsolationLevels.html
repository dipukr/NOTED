Isolation Levels

Isolation levels define how visible one transaction's uncommitted or in-progress changes are to other concurrent transactions.

They trade consistency for concurrency: stronger isolation prevents more anomalies but reduces throughput.

The SQL standard defines four levels: Read Uncommitted, Read Committed, Repeatable Read and Serializable.

Each level prevents a specific set of read phenomena.

The right level depends on how much concurrency anomaly the application can tolerate.

When to use / Key points
  • Read Uncommitted: allows dirty reads; rarely used.
  • Read Committed: prevents dirty reads; the common default.
  • Repeatable Read: also prevents non-repeatable reads.
  • Serializable: prevents phantom reads too; behaves as if transactions ran one at a time.
  • Pick the lowest level that still avoids the anomalies you care about.
Advantages
  • Lets you tune the consistency/performance trade-off per transaction.
  • Higher levels give stronger correctness guarantees.
  • Lower levels give higher concurrency.
  • Standardized and widely supported.
Disadvantages / Trade-offs
  • Higher isolation reduces concurrency and can increase locking.
  • Serializable may cause serialization failures needing retries.
  • Behaviour varies subtly between database engines.
Code
-- READ COMMITTED: the practical default; blocks dirty reads only
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
    SELECT Balance FROM Accounts WHERE AccountId = 1;
    -- a concurrent committed UPDATE to this row could change the value
    -- if this SELECT ran again in the same transaction (non-repeatable read)
COMMIT;

-- REPEATABLE READ: holds shared locks so re-reading the same rows is stable
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION;
    SELECT Balance FROM Accounts WHERE AccountId = 1;
    -- ... other work ...
    SELECT Balance FROM Accounts WHERE AccountId = 1;
    -- guaranteed to return the same value, but a new matching row could still
    -- appear on a range query (phantom read) at this level
COMMIT;

-- SERIALIZABLE: strongest level, also blocks phantom reads via range locks
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;
    SELECT COUNT(*) FROM Accounts WHERE Balance > 1000;
    -- another transaction cannot insert a new row matching this range until commit
COMMIT;
How it works
  • READ COMMITTED only ever reads committed data, so dirty reads are blocked, but the same row read twice in one transaction can change (non-repeatable read).
  • REPEATABLE READ holds locks on rows it has read for the duration of the transaction, so re-reading the same row is guaranteed stable, but new rows can still appear in a range scan (phantom read).
  • SERIALIZABLE adds range locks, so even a repeated range query like WHERE Balance > 1000 cannot see new phantom rows inserted concurrently.
  • Each step up trades concurrency for a stronger guarantee, which is why the lowest level that avoids the anomalies you actually care about is usually the right choice.
