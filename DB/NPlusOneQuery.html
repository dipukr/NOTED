N+1 Query Problem

The N+1 query problem is a performance issue where the application runs one query to load N parent rows, then one extra query per parent to load its related data.

This results in N+1 total queries instead of one or two.

It commonly appears with ORM lazy loading when iterating over a collection of entities.

It is often invisible in code because the extra queries are triggered implicitly.

The fix is to fetch the related data together using join fetch or a batch strategy.

When to use / Key points
  • Watch for it when looping over entities and accessing lazy associations.
  • Detect it by enabling SQL logging and counting queries.
  • Fix with JOIN FETCH or an entity graph to load associations eagerly.
  • Use batch fetching (@BatchSize) to reduce N queries to a few.
  • Prefer projections/DTOs when you only need a subset of fields.
Advantages
  • Understanding it lets you cut hundreds of queries down to one.
  • Fixing it greatly reduces database round trips and latency.
  • Lazy loading itself is useful when related data is rarely needed.
Disadvantages / Trade-offs
  • Left unfixed, it severely degrades performance at scale.
  • Over-eager fetching can load too much data (the opposite problem).
  • It is easy to reintroduce accidentally during refactoring.
Code
CREATE TABLE Author (AuthorId INT PRIMARY KEY, Name VARCHAR(100));
CREATE TABLE Book (
    BookId INT PRIMARY KEY,
    AuthorId INT REFERENCES Author(AuthorId),
    Title VARCHAR(200)
);

-- PROBLEM: 1 query for authors, then 1 query per author for books (N+1 total)
SELECT AuthorId, Name FROM Author;
-- ...application then loops over each row and issues:
SELECT BookId, Title FROM Book WHERE AuthorId = 1;
SELECT BookId, Title FROM Book WHERE AuthorId = 2;
-- ...one more SELECT per author, N extra round trips

-- FIX: load authors and books together with a single JOIN
SELECT a.AuthorId, a.Name, b.BookId, b.Title
FROM Author a
JOIN Book b ON b.AuthorId = a.AuthorId
ORDER BY a.AuthorId;
How it works

The naive approach issues one SELECT for authors, then loops and fires one more SELECT per author for their books.

That produces N+1 total round trips as the author count grows.

The fixed query uses a single JOIN so authors and books are returned together in one result set.

The application groups the flat rows back into author/books objects in memory, cutting N+1 queries down to 1.
