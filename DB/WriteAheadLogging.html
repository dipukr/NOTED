Write-Ahead Logging (WAL)

Write-ahead logging (WAL) is a technique where changes are first written to a sequential log before being applied to the data files.

The log record must be durably flushed to disk before the corresponding data page is modified.

This guarantees durability and enables crash recovery.

After a crash, the database replays committed log records and rolls back uncommitted ones.

WAL also underpins replication and point-in-time recovery.

When to use / Key points
  • WAL is how relational engines provide the Durability in ACID.
  • Sequential log writes are faster than random data-page writes.
  • On restart, redo committed changes and undo uncommitted ones.
  • Replicas consume the WAL stream to stay in sync.
  • Checkpoints periodically flush data pages so the log can be trimmed.
Advantages
Durability Across Crashes

It guarantees durability even when the system crashes, so committed changes are never lost.

Efficient Sequential Writes

Appending to the log uses fast sequential writes rather than slower random data-page writes.

Recovery and Replication

It enables crash recovery, replication and point-in-time recovery from the log stream.

Deferred Data Writes

It allows random data-file writes to be deferred and batched for better efficiency.

Disadvantages
Commit Flush Overhead

Every commit needs a durable log flush, adding fsync overhead to each transaction.

Extra Disk Space

The log consumes additional disk space on top of the data files.

Recovery Replay Time

Replaying the log during recovery can take time after a crash.

Code
-- Every data change is first hardened to the transaction log (ldf),
-- then applied to the data pages -- that ordering IS write-ahead logging
CREATE TABLE Account (
    AccountId INT PRIMARY KEY,
    Balance   DECIMAL(12,2) NOT NULL
);

BEGIN TRANSACTION;
    -- 1. Log record for this change is written and flushed to the log file first
    UPDATE Account
    SET Balance = Balance - 500.00
    WHERE AccountId = 42;

    -- 2. COMMIT forces a flush of the log records for this transaction (WAL rule)
COMMIT TRANSACTION;
GO

-- A checkpoint writes dirty data pages from memory to disk and
-- records a point after which the log for committed work can be reused
CHECKPOINT;

-- Backing up the log truncates it (in FULL/BULK_LOGGED recovery model),
-- reclaiming space for records already hardened and checkpointed
BACKUP LOG SalesDb
TO DISK = 'D:\Backups\SalesDb_log.trn';

-- Crash recovery on restart: redo committed log records not yet on disk,
-- then undo any records belonging to transactions that never committed
How it works

Each UPDATE generates log records that are appended to the sequential transaction log before the data pages are touched.

COMMIT TRANSACTION cannot return success until its log records are durably flushed to disk, guaranteeing the change survives a crash.

CHECKPOINT flushes dirty data pages to disk and marks how far the log has already been applied, bounding recovery time.

BACKUP LOG archives and truncates the log, reclaiming space for records that are both committed and checkpointed.

On restart after a crash, the engine replays (redoes) committed log records not yet applied, then rolls back (undoes) any uncommitted ones.
