Optimistic Locking

Optimistic locking assumes conflicts are rare and does not lock rows while reading.

Instead, it detects conflicts at write time using a version column or timestamp.

When updating, it checks that the version has not changed since the row was read.

If the version differs, another transaction changed the row and the update fails.

The failed transaction must retry with fresh data.

When to use / Key points
  • Use when conflicts are infrequent and read concurrency matters.
  • Add a version column that increments on every update.
  • The UPDATE includes the expected version in its WHERE clause.
  • Zero rows updated means a conflict occurred.
  • In JPA, @Version enables it automatically.
Pros and Cons
High Concurrency

No locks are held during reads, so many transactions can proceed at once.

No Deadlocks

Because no locks are held, there is no risk of deadlocks from contended locks.

Scales For Reads

It scales well for read-heavy workloads where writes rarely collide.

Simple To Implement

It is simple to implement using just a version field on the row.

Wasted Retries

Work is wasted when conflicts do occur and the transaction must retry.

Poor For Contention

It is a poor fit for highly contended rows that frequently collide.

Caller Must Retry

Callers must handle and retry conflict exceptions themselves.

Code
CREATE TABLE Product (
    Id INT PRIMARY KEY,
    Price DECIMAL(10,2) NOT NULL,
    RowVersion ROWVERSION              -- auto-incrementing binary stamp per write
);

-- application reads the row and its current RowVersion first
SELECT Id, Price, RowVersion
FROM Product
WHERE Id = @Id;

-- update only succeeds if RowVersion still matches what was read
BEGIN TRY
    UPDATE Product
    SET Price = @NewPrice
    WHERE Id = @Id
      AND RowVersion = @OriginalRowVersion;

    IF @@ROWCOUNT = 0
        THROW 51000, 'Optimistic concurrency conflict: row changed since read', 1;
END TRY
BEGIN CATCH
    -- caller re-reads the row and retries with the new RowVersion
    THROW;
END CATCH
How it works

RowVersion is a database-maintained value that changes automatically on every write to the row.

The UPDATE matches both Id and the RowVersion value read earlier, in the same statement.

If another transaction updated the row in between, RowVersion no longer matches and @@ROWCOUNT is zero.

The TRY/CATCH raises a conflict error so the caller can re-read the latest row and retry.
