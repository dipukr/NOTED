Cost-based Optimizer

A cost-based optimizer (CBO) chooses a query execution plan by estimating the cost of each alternative and picking the cheapest.

Cost is estimated from table statistics such as row counts, column cardinality and data distribution.

It contrasts with a rule-based optimizer, which applies fixed heuristics regardless of data.

The CBO weighs I/O, CPU and memory to compare plans.

Accurate, up-to-date statistics are essential for good decisions.

When to use / Key points
  • Most modern relational databases use a cost-based optimizer by default.
  • Keep statistics current with ANALYZE / auto-analyze.
  • The CBO estimates selectivity to choose index vs scan and join order.
  • Bad estimates on skewed data can produce poor plans.
  • Use hints or query rewrites only when the CBO is demonstrably wrong.
Advantages
  • Adapts plans to the actual data distribution.
  • Usually outperforms fixed rule-based heuristics.
  • Automatically reconsiders plans as data grows.
  • Handles complex multi-join queries.
Disadvantages / Trade-offs
  • Depends heavily on accurate statistics.
  • Estimation errors compound in multi-join queries.
  • Plan instability can cause sudden regressions.
  • Planning itself has overhead for very complex queries.
Code
-- Give the optimizer statistics to reason about selectivity
CREATE STATISTICS Stat_Orders_CustomerId
    ON Orders(CustomerId) WITH FULLSCAN;

-- Inspect what the CBO believes about this column's distribution
DBCC SHOW_STATISTICS ('Orders', Stat_Orders_CustomerId);

-- Let the CBO choose freely: it picks a seek if CustomerId is selective
SELECT OrderId, OrderDate, Total
FROM Orders
WHERE CustomerId = 555;

-- Force an index seek instead of trusting the estimate, to compare plans
SELECT OrderId, OrderDate, Total
FROM Orders WITH (INDEX(IX_Orders_CustomerId), FORCESEEK)
WHERE CustomerId = 555;

-- Nightly maintenance keeps row counts and histograms current
UPDATE STATISTICS Orders WITH FULLSCAN;
How it works

CREATE STATISTICS / UPDATE STATISTICS give the CBO a histogram of CustomerId values to estimate selectivity from.

DBCC SHOW_STATISTICS exposes what the optimizer actually believes about the data distribution.

The plain query lets the CBO pick freely between an index seek and a table/clustered scan based on estimated cost.

WITH (INDEX(...), FORCESEEK) overrides that choice, useful for comparing the forced plan's actual cost against the CBO's own pick.

Stale or missing statistics are the most common reason a cost-based optimizer picks a scan when a seek would be far cheaper.
