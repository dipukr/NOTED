Deadlock (Database)

A database deadlock occurs when two or more transactions each hold a lock the other needs, so none can proceed.

Each transaction waits forever for a resource the other will not release.

The database detects the cycle and aborts one transaction (the victim) to break it.

The aborted transaction receives an error and must be retried.

Deadlocks are usually caused by transactions acquiring locks in different orders.

When to use / Key points
  • Prevent deadlocks by always acquiring locks in a consistent order.
  • Keep transactions short to shrink the window for contention.
  • Use lower isolation levels when strict consistency is not required.
  • Handle deadlock errors by catching and retrying the transaction.
  • Index columns used in updates to reduce the range of rows locked.
Advantages
  • Automatic detection prevents transactions from hanging forever.
  • Aborting a victim preserves overall system liveness.
  • Understanding them leads to safer locking patterns.
Disadvantages / Trade-offs
  • The victim transaction's work is lost and must be retried.
  • Frequent deadlocks hurt throughput.
  • Hard to reproduce and diagnose intermittently.
Code
-- Session 1: locks AccountId 1 first, then tries AccountId 2
BEGIN TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1;
-- ... pauses here, holding an exclusive lock on AccountId 1 ...
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountId = 2; -- blocks
COMMIT;

-- Session 2 (running concurrently): opposite lock order -> deadlock cycle
BEGIN TRANSACTION;
UPDATE Accounts SET Balance = Balance - 50 WHERE AccountId = 2;
-- ... pauses here, holding an exclusive lock on AccountId 2 ...
UPDATE Accounts SET Balance = Balance + 50 WHERE AccountId = 1;  -- blocks -> deadlock
COMMIT;

-- Make Session 2 the preferred victim if a deadlock is detected
SET DEADLOCK_PRIORITY LOW;
How it works

Session 1 locks AccountId 1 then waits for 2; Session 2 locks 2 then waits for 1, forming a circular wait.

SQL Server's lock monitor detects the cycle and kills one session with error 1205 to break the deadlock.

SET DEADLOCK_PRIORITY LOW tells the engine to prefer aborting this session over the other one when a deadlock is found.

The fix is to always acquire locks on AccountId in the same order (e.g. lowest id first) in both sessions.

The aborted transaction must catch the deadlock error and retry the whole unit of work.
