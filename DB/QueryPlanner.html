Query Planner

The query planner (or optimizer) is the database component that decides how to execute a SQL statement.

It translates the declarative query into a concrete execution plan: which indexes to use, join order and join algorithms.

It considers many candidate plans and picks the one it estimates to be cheapest.

You can inspect the chosen plan with EXPLAIN.

Understanding the plan is essential for diagnosing slow queries.

When to use / Key points
  • Use EXPLAIN / EXPLAIN ANALYZE to see the plan and actual timings.
  • Look for full table scans where an index seek was expected.
  • Check join order and join type (nested loop, hash, merge).
  • Keep table statistics fresh so estimates are accurate.
  • Rewrite queries or add indexes to guide the planner.
Pros and Cons
No Manual Tuning

It frees developers from hand-optimizing execution by deciding the strategy automatically.

Adapts To Data

It adapts plans as the underlying data and statistics change over time.

Debuggable Plans

It exposes the chosen plans for debugging via EXPLAIN.

Many Strategies

It chooses among many execution strategies automatically to find the cheapest one.

Stale Statistics

Stale statistics lead the planner to poor and inefficient plans.

Bad Plan Choices

It can pick a bad plan for skewed data or complex queries.

Sudden Regressions

Plan changes can cause sudden performance regressions in production.

Code
CREATE TABLE Orders (
    OrderId   INT PRIMARY KEY,
    Status    VARCHAR(20) NOT NULL,
    Total     DECIMAL(10,2) NOT NULL
);

-- Ask the planner to report logical reads and CPU/elapsed time
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT OrderId, Total
FROM Orders
WHERE Status = 'PENDING';

-- Output (conceptual):
-- Table 'Orders'. Scan count 1, logical reads 812   <- high = missing index
-- SQL Server Execution Times: CPU time = 47 ms, elapsed time = 52 ms

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

-- Capture the actual chosen plan in XML for deeper inspection
SET SHOWPLAN_XML ON;
GO
SELECT OrderId, Total FROM Orders WHERE Status = 'PENDING';
GO
SET SHOWPLAN_XML OFF;

-- In the plan, look for: "Clustered Index Scan" (reads every row -> add an
-- index on Status) versus "Index Seek" (planner used an index efficiently)
How it works

SET STATISTICS IO ON reports the logical page reads per table touched, revealing how much data the plan actually scanned.

SET STATISTICS TIME ON reports parse/compile and execution CPU and elapsed time for the statement.

SHOWPLAN_XML captures the planner's chosen plan — join order, operators and estimated costs — without executing the query for real.

A Clustered Index Scan or Table Scan on a filtered column signals a missing or unused index, mirroring a high logical-reads count.

An Index Seek with low logical reads confirms the planner found and used an efficient access path.
