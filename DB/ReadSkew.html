Read Skew

Read skew is a consistency anomaly where a transaction reads related rows at different points in time and sees an inconsistent combination.

It happens when another transaction commits changes between the individual reads.

The result violates an invariant that should hold across the rows read together.

It is a form of non-repeatable read spanning multiple rows.

Snapshot isolation or higher prevents it by giving a consistent view.

When to use / Key points
  • Occurs when reading two related rows separately under weak isolation.
  • Example: read account A, then account B, while a transfer commits in between.
  • Prevent it with snapshot isolation (a consistent read view).
  • Or read all related rows in a single query/snapshot.
  • Repeatable Read (MVCC snapshot) typically avoids it.
Advantages
Guides Correct Design

Recognizing read skew drives correct isolation and query design decisions.

Cheap Prevention

Snapshot isolation removes it cheaply through MVCC.

Lock-Free Batch Reads

Reading related rows in a single batch sidesteps it without heavy locking.

Disadvantages
Inconsistent Snapshots

It produces inconsistent snapshots that violate invariants across related rows.

Hard to Reproduce

It is subtle and hard to reproduce reliably.

Costly Prevention

Preventing it may require higher isolation levels or extra care.

Code
-- Table used by both accounts
CREATE TABLE Account (
    id            INT PRIMARY KEY,
    balance       DECIMAL(12,2) NOT NULL
);

-- Anomaly: read A, then B, with a transfer committing in between
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
    SELECT balance FROM Account WHERE id = 1;   -- e.g. 100
    -- ...meanwhile another session transfers 50 from acct 1 to acct 2 and commits...
    SELECT balance FROM Account WHERE id = 2;   -- already reflects the +50
    -- SUM(100, 150) = 250, but the true total was always 200 -> read skew
COMMIT;

-- Fix: SNAPSHOT isolation gives one consistent view for the whole transaction
ALTER DATABASE CURRENT SET ALLOW_SNAPSHOT_ISOLATION ON;

SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
    SELECT balance FROM Account WHERE id = 1;   -- 100, from tx-start snapshot
    SELECT balance FROM Account WHERE id = 2;   -- 50, same snapshot, transfer invisible
    -- SUM(100, 50) = 150, consistent with the true total before the transfer
COMMIT;

-- Or avoid two round-trips entirely: read both rows in one statement
SELECT SUM(balance) AS total_balance
FROM Account
WHERE id IN (1, 2);
How it works

Under READ COMMITTED, each separate SELECT sees the latest committed data, so a transfer landing between the two reads produces an inconsistent combined total.

SNAPSHOT isolation fixes the visible data as of transaction start, so both reads see the pre-transfer state and the invariant holds.

Enabling ALLOW_SNAPSHOT_ISOLATION is a one-time database setting required before using SNAPSHOT transactions.

A single query summing both rows sidesteps the problem entirely by reading everything at one point in time.
