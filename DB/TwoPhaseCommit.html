Two-Phase Commit (2PC)

Two-phase commit (2PC) is a protocol that coordinates a distributed transaction across multiple participants so they all commit or all abort.

A coordinator drives two phases: prepare (voting) and commit (decision).

In the prepare phase, each participant votes yes only if it can guarantee it will commit.

If all vote yes, the coordinator tells everyone to commit; otherwise everyone aborts.

It provides atomicity across systems but blocks if the coordinator fails.

When to use / Key points
  • Use when a single transaction must span multiple databases or resources atomically.
  • Phase 1 (prepare): participants durably prepare and vote.
  • Phase 2 (commit/abort): coordinator finalizes based on the votes.
  • Implemented in Java via JTA/XA transactions.
  • Prefer sagas for long-running or high-availability microservice flows.
Advantages
  • Guarantees atomicity across multiple resources.
  • All participants reach the same commit/abort decision.
  • Standardized through the XA protocol.
  • Strong consistency for distributed writes.
Disadvantages / Trade-offs
  • Blocking: participants hold locks until the coordinator decides.
  • A coordinator crash can leave participants stuck (in-doubt).
  • Poor availability and latency at scale.
  • Not suited to loosely coupled microservices.
Code
-- Distributed transaction spanning two linked servers (two resource managers)
CREATE TABLE OrderHeader (
    OrderId       INT PRIMARY KEY,
    CustomerId    INT NOT NULL,
    Status        VARCHAR(20) NOT NULL
);

-- Local resource: Payments database (RM #1)
BEGIN DISTRIBUTED TRANSACTION;

BEGIN TRY
    -- RM #1: mark the order as paid
    UPDATE OrderHeader
    SET Status = 'PAID'
    WHERE OrderId = 1001;

    -- RM #2: remote linked server holding the Payments ledger
    INSERT INTO RemoteServer.PaymentsDb.dbo.Ledger
        (OrderId, Amount, PaidAt)
    VALUES (1001, 249.99, SYSUTCDATETIME());

    -- Phase 1 (prepare): MS DTC asks both RMs to vote; Phase 2: commit both
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    -- Any participant voting "no" rolls back both resources
    ROLLBACK TRANSACTION;
    THROW;
END CATCH;
How it works
  • BEGIN DISTRIBUTED TRANSACTION enlists both the local database and the remote linked server as separate resource managers under MS DTC.
  • In the prepare phase, each resource manager durably records its changes and votes yes or no without committing yet.
  • Only if every participant votes yes does COMMIT TRANSACTION tell all of them to make the change permanent.
  • If either statement fails, the CATCH block issues ROLLBACK TRANSACTION, undoing the change on both the local table and the remote ledger.
