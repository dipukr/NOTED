Database Partitioning

Partitioning splits a single large table into smaller physical pieces called partitions, while it still appears as one logical table.

Unlike sharding, partitioning usually happens within a single database instance.

Horizontal partitioning divides rows (for example by date range); vertical partitioning divides columns.

The database engine routes queries only to the partitions that can hold the matching rows (partition pruning).

It is a common way to keep very large tables manageable and fast.

When to use / Key points
  • Use range partitioning for time-series data (partition per month or year).
  • Use list partitioning to group rows by discrete values such as region.
  • Use hash partitioning to spread rows evenly when there is no natural range.
  • Dropping an old partition is far cheaper than deleting millions of rows.
  • Ensure queries filter on the partition key so the engine can prune partitions.
Advantages
Partition Pruning

Queries scan only the relevant partitions, which improves performance.

Faster Maintenance

Maintenance such as archiving and purging is faster when done per partition.

Smaller Indexes

Indexes stay smaller because each partition maintains its own.

Application Transparent

Partitioning is transparent to the application, which still sees a single table.

Disadvantages
Full Partition Scans

Queries that ignore the partition key must scan every partition.

Uneven Partitions

Choosing the wrong partition key causes uneven partitions.

Added Complexity

It adds schema complexity and requires maintaining the partition scheme.

Code
-- Define range boundaries: one partition per year
CREATE PARTITION FUNCTION PF_OrderYear (DATE)
    AS RANGE RIGHT FOR VALUES ('2024-01-01', '2025-01-01', '2026-01-01');

-- Map each partition to a filegroup
CREATE PARTITION SCHEME PS_OrderYear
    AS PARTITION PF_OrderYear
    ALL TO ([PRIMARY]);

-- The table is physically split by CreatedAt, but looks like one table
CREATE TABLE Orders (
    OrderId    INT NOT NULL,
    CustomerId INT NOT NULL,
    CreatedAt  DATE NOT NULL,
    Total      DECIMAL(18,2) NOT NULL,
    CONSTRAINT PK_Orders PRIMARY KEY (OrderId, CreatedAt)
) ON PS_OrderYear(CreatedAt);

-- Filtering on the partition key lets the engine prune to one partition
SELECT COUNT(*)
FROM Orders
WHERE CreatedAt >= '2025-01-01' AND CreatedAt < '2026-01-01';

-- Archiving an old year is a metadata switch, not a row-by-row delete
SELECT $PARTITION.PF_OrderYear(CreatedAt) AS PartitionNumber, COUNT(*)
FROM Orders
GROUP BY $PARTITION.PF_OrderYear(CreatedAt);
How it works

CREATE PARTITION FUNCTION defines the range boundaries that split rows by year.

CREATE PARTITION SCHEME maps each range to physical storage (here, all to the primary filegroup).

The table's ON PS_OrderYear(CreatedAt) clause makes it a partitioned table while the application still sees one logical Orders table.

A WHERE filter on CreatedAt lets the engine perform partition pruning, scanning only the matching year.

$PARTITION.PF_OrderYear(...) reports which partition each row lives in, useful for verifying pruning and planning archive/purge of old partitions.
