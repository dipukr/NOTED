ReentrantLock

ReentrantLock is an explicit lock offering the same mutual exclusion as synchronized with more flexibility.

"Reentrant" means the holding thread can acquire the same lock again without deadlocking.

It supports fairness, interruptible acquisition, timed tries, and multiple condition queues.

The lock must be released in a finally block to avoid leaking it.

When to use / Key points
  • Use when you need tryLock(), timeouts, or interruptible locking.
  • Use multiple Conditions where one monitor's single wait-set is not enough.
  • Optionally construct with fair = true for FIFO ordering.
  • Always pair lock() with unlock() in finally.
Advantages
Non-Blocking Acquisition

Non-blocking tryLock() avoids indefinite waits by returning immediately when the lock is unavailable.

Interruptible Locking

Interruptible locking allows a waiting thread to be cancelled instead of blocking forever.

Conditions and Fairness

It supports multiple conditions and optional fairness for finer control over thread coordination.

Disadvantages
Manual Unlock Required

Manual unlock() is required, and forgetting it in a finally block causes deadlocks.

More Verbose

It is more verbose than synchronized, requiring explicit lock and unlock calls.

Reduced Throughput

Fair mode reduces throughput because it enforces FIFO ordering of waiting threads.

Code
public class Account {

    private final ReentrantLock lock = new ReentrantLock();
    private long balance;

    public void deposit(long amount) {
        lock.lock();
        try {
            balance += amount; // protected critical section
        } finally {
            lock.unlock(); // always release
        }
    }

    public boolean withdrawIfPossible(long amount) {
        if (!lock.tryLock()) return false; // don't block
        try {
            if (balance < amount) return false;
            balance -= amount;
            return true;
        } finally {
            lock.unlock();
        }
    }
}
How it works

lock() blocks until the lock is acquired; the finally guarantees release.

tryLock() returns immediately with false if the lock is held elsewhere.

Being reentrant, the same thread may re-enter another locked method safely.
