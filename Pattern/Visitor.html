Visitor

Visitor pattern allows us to define and add new operations to an existing object structure without modifying the classes of the objects on which those operations operate. This is particularly useful when the object structure and its classes are relatively stable, but we frequently need to introduce new behaviors or operations over those objects.


Instead of placing every possible operation inside the domain classes themselves, this pattern extracts those operations into separate Visitor classes. Each element in the object structure accepts a Visitor and the Visitor contains the operation specific logic for different types of elements. This separates the algorithms or behaviors from the objects they operate on, keeping the object classes focused on representing their core data and responsibilities.


Visitor pattern supports the Open-Closed Principle with respect to operations: the existing element classes can remain closed for modification while new operations can be introduced by creating new Visitor implementations. However,
this comes with a trade-off: adding a new type of element usually requires modifying the Visitor interface and all existing Visitor implementations. Therefore, Visitor is most suitable when the set of element types is stable, while
the set of operations performed on them changes frequently.

Components
  • When an object structure is stable but we frequently need to extend its behaviours with new operations.
  • Visitor – Interface or abstract class for visiting elements.
  • ConcreteVisitor – Implements operations on concrete elements.
  • Element – Interface that defines accept(visitor)
  • ConcreteElement – Implements accept(visitor)
  • Client – Traverses object structure and applies visitor.
Pros and Cons
New Operations Easily

New operations can be added without changing the existing object structures.

Separation Of Concerns

It encourages a clean separation of concerns between data and behavior.

Extensible Operations

It makes operations extensible and easy to manage over time.

Hard To Add Elements

Adding a new element type requires updating all existing visitors.

Double Dispatch

It involves double dispatch – one call from client to element, and one from element to visitor.

Real-world example
  • NIO FileVisitor — Files.walkFileTree traverses a directory tree and calls visitFile and visitDirectory callbacks on each node.
  • ElementVisitor — annotation processors visit program elements (classes, methods, fields) during compilation.
  • Java compiler AST — the TreeVisitor walks syntax tree nodes for analysis and code generation.
  • Bytecode lib — ClassVisitor and MethodVisitor let tools inspect and transform bytecode without changing the class model.
  • Spring BeanDefinitionVisitor — visits bean definitions to resolve and rewrite property placeholder values.
  • ANTLR and XML parsers — generated visitors walk parse trees so each operation (eval, pretty) stays separate from the grammar.
Visitor Design Pattern in Java: Complete Guide

The Visitor Design Pattern is a behavioral design pattern that allows us to define new operations on a group of related objects without modifying their existing classes.

It is especially useful when we have a stable object structure, but frequently need to introduce new behaviors or operations on those objects.

The Visitor pattern separates algorithms (operations) from the objects on which they operate.

For example, suppose an application contains different product types, such as Books, Electronics, and Clothing. We might want to perform several operations on these products:

  • Calculate prices and taxes.
  • Calculate shipping costs.
  • Generate invoices.
  • Generate product reports.
  • Export product information.

Instead of implementing all these operations inside each product class, we can create separate Visitor classes, each responsible for a particular operation.

This follows the Open/Closed Principle in an important way: we can introduce new operations without modifying the existing product classes, although adding new product types generally requires modifying the visitor implementations.

Understanding the problem

Suppose we have an e-commerce application with a common Product interface and multiple product implementations.

public interface Product {
    double calculatePrice();

    double calculateShipping();

    String generateInvoice();
}

public class Book implements Product {
    @Override
    public double calculatePrice() {
        return 500; # Book pricing logic
    }

    @Override
    public double calculateShipping() {
        return 50; # Book shipping logic
    }

    @Override
    public String generateInvoice() {
        return "Book invoice";
    }
}

public class Electronics implements Product {
    @Override
    public double calculatePrice() {
        return 3000; # Electronics pricing logic
    }

    @Override
    public double calculateShipping() {
        return 150; # Electronics shipping logic
    }

    @Override
    public String generateInvoice() {
        return "Electronics invoice";
    }
}

What is the problem with this approach?

Initially, this design works.

However, imagine that the business introduces several new requirements:

  • Calculate discounts.
  • Generate tax reports.
  • Export product data as JSON.
  • Generate analytics reports.

Every time a new operation is introduced, we may need to modify the Product interface and every concrete product class.

This creates several problems:

  • Violation of the Open/Closed Principle: existing classes require changes whenever new operations are added.
  • Poor separation of concerns: product classes contain pricing, shipping, reporting, and other unrelated business logic.
  • Increased maintenance: adding or modifying business operations affects multiple product classes.
  • Growing complexity: product classes become large and difficult to maintain.

The Visitor Pattern solves this problem by moving these operations into separate visitor classes.

How the Visitor Pattern works

Instead of directly calling operations on product objects, we introduce a Visitor interface that declares a separate method for each concrete product type.

Each product supports an accept() method, which receives a visitor and invokes the appropriate visit() method.

Each product delegates the requested operation to a visitor that knows its concrete type.

Main components

ComponentResponsibility
VisitorDeclares operations for each concrete element type.
Concrete VisitorImplements a particular operation, such as pricing or shipping.
ElementDeclares the accept(Visitor) method.
Concrete ElementImplements accept() and passes itself to the visitor.
Client / Object StructureHolds the elements and applies visitors to them.

The most important concept is:

Objects retain responsibility for their core data and structure, while visitors provide additional operations on those objects.

Practical Example 1: E-Commerce Pricing and Shipping

Consider an online shopping application that sells Books and Electronics.

Each product has its own pricing and shipping rules.

Requirements:

  • Books have no additional tax.
  • Electronics have an 18% tax.
  • Books are shipped based on their weight.
  • Electronics have a fixed packaging charge plus weight-based shipping.
  • We should be able to add new operations without changing the existing product classes.

We will implement this example using the Visitor Pattern.

Step 1: Create the Visitor interface

public interface ItemVisitor<R> {
    R visit(Book book);

    R visit(Electronics electronics);
}

The ItemVisitor<R> interface declares a different visit() method for each product type.

The generic parameter R represents the return type of the operation.

For example:

  • ItemVisitor<Double> can calculate prices.
  • ItemVisitor<String> can generate descriptions.
  • ItemVisitor<Boolean> can validate products.
  • ItemVisitor<Void> can perform an operation without returning a value.

This makes the visitor interface reusable for different operations.

Step 2: Create the Element interface

public interface CartItem {
    <R> R accept(ItemVisitor<R> visitor);
}

Every product must implement the accept() method.

The method accepts a visitor and delegates the operation to it.

Notice that CartItem doesn't contain methods such as calculateTax(), calculateShipping(), or generateInvoice().

Instead, we implement these operations using separate visitors.

Step 3: Implement the concrete elements

We'll use Java records to keep the example concise.

public record Book(String title, double unitPrice, int quantity, double weightKg) implements CartItem {
    @Override
    public <R> R accept(ItemVisitor<R> visitor) {
        return visitor.visit(this);
    }
}

public record Electronics(String name, double unitPrice, int quantity, double weightKg) implements CartItem {
    @Override
    public <R> R accept(ItemVisitor<R> visitor) {
        return visitor.visit(this);
    }
}

The key statement is:

return visitor.visit(this);

When a Book receives a visitor, it invokes:

visitor.visit(this); # visit(Book)

When an Electronics object receives a visitor, it invokes:

visitor.visit(this); # visit(Electronics)

This mechanism is called Double Dispatch, which we will examine shortly.

Step 4: Implement a Price Visitor

public class PriceVisitor implements ItemVisitor<Double> {
    @Override
    public Double visit(Book book) {
        return book.unitPrice() * book.quantity(); # Books are tax-exempt
    }

    @Override
    public Double visit(Electronics electronics) {
        double basePrice = electronics.unitPrice() * electronics.quantity();
        double tax = basePrice * 0.18;
        return basePrice + tax;
    }
}

PriceVisitor implements the pricing logic for each product.

Notice that different product types have different pricing rules.

The Book and Electronics classes don't know how pricing is calculated.

If the pricing rules change, we can update the PriceVisitor without modifying the product classes.

Step 5: Implement a Shipping Visitor

public class ShippingVisitor implements ItemVisitor<Double> {
    @Override
    public Double visit(Book book) {
        return book.weightKg() * book.quantity() * 50; # ₹50 per kilogram
    }

    @Override
    public Double visit(Electronics electronics) {
        # ₹100 packaging + ₹80 per kilogram
        double packaging = 100;
        double weightCharge = electronics.weightKg() * electronics.quantity() * 80;
        return packaging + weightCharge;
    }
}

We now have two independent visitors:

  • PriceVisitor handles pricing.
  • ShippingVisitor handles shipping.

Both operate on the same product classes, without requiring any changes to those classes.

Step 6: Create the client

void main(String[] args) {
    List<CartItem> cart = List.of(new Book("Clean Code", 500, 2, 0.5),
                                  new Electronics("Headphones", 3000, 1, 0.4));
    PriceVisitor priceVisitor = new PriceVisitor();
    ShippingVisitor shippingVisitor = new ShippingVisitor();
    double totalPrice = cart.stream().mapToDouble(item -> item.accept(priceVisitor)).sum();
    double totalShipping = cart.stream().mapToDouble(item -> item.accept(shippingVisitor)).sum();
    System.out.println("Total Price: " + totalPrice);
    System.out.println("Shipping: " + totalShipping);
    System.out.println("Grand Total: " + (totalPrice + totalShipping));
}

Output

Total Price: 4540.0
Shipping: 182.0
Grand Total: 4722.0

These pricing and shipping rules are illustrative. For production monetary calculations, prefer BigDecimal or a dedicated Money type rather than double.

Step 7: Understanding the execution flow

Let's trace what happens when the application executes:

item.accept(priceVisitor);

Suppose item refers to a Book object.

Client invokes accept()
item.accept(priceVisitor)
Book.accept() executes
The runtime type of item is Book
Book delegates to the visitor
visitor.visit(this)
PriceVisitor.visit(Book) executes
Book pricing logic is applied
The calculated price is returned
500 × 2 = 1000.0

The same product can be processed using a different visitor:

item.accept(shippingVisitor);

Now, instead of calculating the price, the application calculates shipping.

This demonstrates the central idea:

The data object stays the same, but the operation performed on it changes depending on the visitor.

Understanding Double Dispatch

Double Dispatch is one of the most important concepts behind the Visitor Pattern.

Java normally uses single dispatch for overridden instance methods.

That means Java chooses an overridden method based on the runtime type of the receiver object.

However, Java chooses overloaded methods based on compile-time argument types.

Example: Single dispatch

public class Animal {
    void speak() {
        System.out.println("Animal speaks");
    }
}

public class Dog extends Animal {
    @Override
    void speak() {
        System.out.println("Dog barks");
    }
}

void main(String[] args) {
    Animal animal = new Dog();
    animal.speak(); # Dog barks
}

Here, the method implementation is selected using the runtime type Dog, even though the reference type is Animal.

Why method overloading alone is insufficient

Consider:

public class Animal {}

public class Dog extends Animal {}

public class AnimalVisitor {
    void visit(Animal animal) {
        System.out.println("Visiting Animal");
    }

    void visit(Dog dog) {
        System.out.println("Visiting Dog");
    }
}

void main(String[] args) {
    Animal animal = new Dog();
    AnimalVisitor visitor = new AnimalVisitor();
    visitor.visit(animal);
}

Output:

Visiting Animal

Why?

Because Java resolves overloaded methods based on the compile-time type of the argument.

The variable animal has the declared type Animal, so Java selects:

visit(Animal animal)

It does not select visit(Dog dog), despite the object being a Dog at runtime.

How Visitor achieves Double Dispatch

public interface Animal {
    void accept(AnimalVisitor visitor);
}

public class Dog implements Animal {
    @Override
    public void accept(AnimalVisitor visitor) {
        visitor.visit(this);
    }
}

public class Cat implements Animal {
    @Override
    public void accept(AnimalVisitor visitor) {
        visitor.visit(this);
    }
}

public class AnimalVisitor {
    void visit(Dog dog) {
        System.out.println("Visiting Dog");
    }

    void visit(Cat cat) {
        System.out.println("Visiting Cat");
    }
}

void main(String[] args) {
    Animal animal = new Dog();
    animal.accept(new AnimalVisitor());
}

Output:

Visiting Dog

The method selection now happens in two stages:

First dispatch — element selection

animal.accept(visitor);

Java selects Dog.accept() based on the runtime type of animal.

Second dispatch — visitor operation selection

visitor.visit(this);

Inside Dog.accept(), the compile-time type of this is Dog. Therefore, Java selects the visit(Dog) overload.

If the visitor has overridden that method, Java then dispatches to the concrete visitor implementation.

This combination of method overriding and method overloading achieves Double Dispatch.

Strictly speaking, Java hasn't gained native multiple dispatch. The Visitor Pattern simulates dispatch based on both the element type and visitor type through two ordinary method calls.

Practical Example 2: Visitor Pattern in a Compiler (AST)

One of the most important real-world applications of the Visitor Pattern is in compilers and interpreters.

Compilers commonly represent source code using an Abstract Syntax Tree (AST).

Consider the mathematical expression:

(2 + 3) * 4

Its abstract syntax tree looks like this:

An expression tree containing Number, Addition, and Multiplication nodes.

Now imagine that our compiler needs to perform several operations on this tree:

  • Evaluate the expression.
  • Print the expression.
  • Validate the expression.
  • Perform optimization.
  • Generate machine code.

We could implement all these operations directly inside each AST node.

However, that would tightly couple the AST structure with compiler operations.

With the Visitor Pattern, we can create separate visitors for evaluation, printing, validation, and optimization.

Complete Java implementation

# 1. Element interface
public interface Expr {
    <R> R accept(ExprVisitor<R> visitor);
}

# 2. Visitor interface
public interface ExprVisitor<R> {
    R visit(NumberExpr expr);

    R visit(AddExpr expr);

    R visit(MultiplyExpr expr);
}

# 3. Concrete AST elements
public record NumberExpr(int value) implements Expr {
    @Override
    public <R> R accept(ExprVisitor<R> visitor) {
        return visitor.visit(this);
    }
}

public record AddExpr(Expr left, Expr right) implements Expr {
    @Override
    public <R> R accept(ExprVisitor<R> visitor) {
        return visitor.visit(this);
    }
}

public record MultiplyExpr(Expr left, Expr right) implements Expr {
    @Override
    public <R> R accept(ExprVisitor<R> visitor) {
        return visitor.visit(this);
    }
}

# 4. Concrete Visitor: Evaluation
public class EvaluationVisitor implements ExprVisitor<Integer> {
    @Override
    public Integer visit(NumberExpr expr) {
        return expr.value();
    }

    @Override
    public Integer visit(AddExpr expr) {
        return expr.left().accept(this) + expr.right().accept(this);
    }

    @Override
    public Integer visit(MultiplyExpr expr) {
        return expr.left().accept(this) * expr.right().accept(this);
    }
}

# 5. Concrete Visitor: Pretty Printing
public class PrintingVisitor implements ExprVisitor<String> {
    @Override
    public String visit(NumberExpr expr) {
        return Integer.toString(expr.value());
    }

    @Override
    public String visit(AddExpr expr) {
        return "(" + expr.left().accept(this) + " + " + expr.right().accept(this) + ")";
    }

    @Override
    public String visit(MultiplyExpr expr) {
        return "(" + expr.left().accept(this) + " * " + expr.right().accept(this) + ")";
    }
}

# 6. Client
void main(String[] args) {
    # Represents: (2 + 3) * 4
    Expr expression = new MultiplyExpr(new AddExpr(new NumberExpr(2), new NumberExpr(3)), new NumberExpr(4));
    int result = expression.accept(new EvaluationVisitor());
    String output = expression.accept(new PrintingVisitor());
    System.out.println("Expression: " + output);
    System.out.println("Result: " + result);
}

Output:

Expression: ((2 + 3) * 4)
Result: 20

How does recursive visiting work?

Consider this part of EvaluationVisitor:

@Override
public Integer visit(AddExpr expr) {
    return expr.left().accept(this) + expr.right().accept(this);
}

When the visitor encounters an AddExpr, it recursively visits the left and right child expressions.

The execution works as follows:

NodeValue
MultiplyExpr2 operands
Left: AddExpr2 + 3 = 5
Right: NumberExpr4
Evaluation result5 × 4 = 20

Here, the visitor recursively traverses the expression tree while performing its specific operation.

Importantly, the Visitor Pattern itself does not automatically traverse a tree. In this implementation, traversal happens because the concrete visitor explicitly calls accept(this) on child nodes.

This is also why the Visitor Pattern is frequently used together with the Composite Pattern.

  • Composite Pattern: represents the hierarchical tree structure.
  • Visitor Pattern: defines operations performed on the elements of the tree.

In compiler design, the AST often uses a Composite-like object structure, while visitors implement operations such as semantic analysis, optimization, or code generation.

What happens when we add a new operation?

Suppose we now need to count the number of nodes in our AST.

With the Visitor Pattern, we can simply introduce a new visitor:

public class NodeCountVisitor implements ExprVisitor<Integer> {
    @Override
    public Integer visit(NumberExpr expr) {
        return 1;
    }

    @Override
    public Integer visit(AddExpr expr) {
        return 1 + expr.left().accept(this) + expr.right().accept(this);
    }

    @Override
    public Integer visit(MultiplyExpr expr) {
        return 1 + expr.left().accept(this) + expr.right().accept(this);
    }
}

Usage:

int count = expression.accept(new NodeCountVisitor());
System.out.println(count); # 5

We have added a completely new operation without modifying NumberExpr, AddExpr, or MultiplyExpr.

This is the primary advantage of the Visitor Pattern.

What happens when we add a new element type?

Now suppose the compiler needs to support division.

We introduce:

public record DivideExpr(Expr left, Expr right) implements Expr {
    @Override
    public <R> R accept(ExprVisitor<R> visitor) {
        return visitor.visit(this);
    }
}

However, our existing visitor interface doesn't contain:

R visit(DivideExpr expr);

We must introduce this method in ExprVisitor<R> and update every concrete visitor:

  • EvaluationVisitor
  • PrintingVisitor
  • NodeCountVisitor

Otherwise, the new DivideExpr.accept() won't compile, and concrete visitors will fail to implement the expanded interface.

This reveals the Visitor Pattern's fundamental tradeoff:

ChangeEffortWhat to do
New operationEasy to add.Create a new visitor implementing the existing interface.
New element typeMore expensive to add.Extend the visitor interface and update existing visitors.

Therefore, the Visitor Pattern is most appropriate when the element hierarchy changes infrequently but the operations performed on it change frequently.

Visitor Pattern vs Strategy Pattern

Both Visitor and Strategy separate behavior from the objects using it, but they solve different problems.

AspectVisitorStrategy
Main purposeAdd operations to an object structureMake algorithms interchangeable
FocusDifferent operations across element typesDifferent implementations of one behavior
Key methodaccept(visitor) / visit(element)execute() or a domain-specific method
Double DispatchCentral mechanismGenerally not used
New behaviorAdd a new visitorAdd a new strategy
New element typeUsually requires updating visitorsUsually unrelated
Typical useAST processing, reports, serializationPayment methods, sorting, pricing algorithms

For example, in an e-commerce system:

  • Strategy Pattern: Choose between UPI, credit card, and PayPal as payment algorithms at runtime.
  • Visitor Pattern: Apply tax calculation, shipping calculation, and reporting operations across multiple product types.

A Strategy focuses on which algorithm should be used.

A Visitor focuses on which operation should be performed on each concrete element type.

Advantages and disadvantages

Advantages

  • Open/Closed Principle for new operations: introduce new visitor classes without modifying existing concrete elements.
  • Separation of concerns: business operations are separated from the element classes.
  • Single Responsibility Principle: each visitor can focus on one operation, such as pricing or reporting.
  • Type-specific processing: visitor methods operate directly on concrete element types without repeated instanceof checks or casts.
  • Centralized operations: related logic for multiple element types can be maintained within one visitor.
  • Works well with hierarchical structures: particularly ASTs, document models, and composite object trees.

Disadvantages

  • Difficult to add new element types: the visitor interface and its concrete implementations typically require modification.
  • Increased boilerplate: requires interfaces, visitor classes, and accept() methods.
  • Potential encapsulation concerns: visitors may need access to element data that would otherwise remain private.
  • Tight coupling to concrete types: the visitor interface depends on concrete element classes.
  • Can be excessive for simple applications: straightforward polymorphism or a service class may be clearer.

Also note that a visitor object can store mutable state (such as a running total). Such visitors should not be shared between threads without appropriate synchronization.

When should you use the Visitor Pattern?

The following scenarios are especially suitable:

ScenarioWhy Visitor fits
Compiler ASTPerform interpretation, validation, printing, and code generation on the same syntax tree
Document processingRender, export, validate, or analyze paragraphs, tables, and images
File system representationCalculate size, collect statistics, or build reports for file and directory objects
E-commerceApply specialized pricing, tax, shipping, and reporting logic across stable product types
UI component treesPerform inspections or analysis across different component types
Data transformationConvert structured objects into multiple output formats

However, Visitor isn't automatically better than ordinary polymorphism.

If an operation is fundamental to an object, such as BankAccount.withdraw(), it usually belongs in the object's own abstraction.

If there are only a few elements and one or two operations, introducing visitors may unnecessarily complicate the design.

Key takeaways
  • Visitor is a behavioral design pattern that separates operations from the objects they operate on.
  • It is particularly useful when the object structure is stable but new operations are frequently introduced.
  • The Visitor interface declares an operation for every supported concrete element type.
  • Each element implements an accept() method that delegates to visitor.visit(this).
  • Visitor uses Double Dispatch to select behavior based on both the concrete element and the concrete visitor.
  • New operations are generally easy to introduce by adding new visitors.
  • New element types are generally harder to introduce because existing visitors need to be updated.
  • Visitor is commonly combined with Composite, especially for ASTs and other tree structures.
  • It promotes the Open/Closed Principle along the operation dimension, not necessarily along the element-type dimension.

In one sentence: The Visitor Pattern allows us to add new operations to an existing object structure without changing its element classes, by encapsulating those operations in separate visitor objects and using Double Dispatch to invoke the correct type-specific behavior.

public interface Visitor<R> {
    R visit(Num n);
    R visit(Add a);
    R visit(Mul m);
}

public interface Expr {
    <R> R accept(Visitor<R> v);
}

public class Num implements Expr {
    final int value;
    Num(int value) { this.value = value; }
    public <R> R accept(Visitor<R> v) { return v.visit(this); }
}

public class Add implements Expr {
    final Expr left, right;
    Add(Expr left, Expr right) { this.left = left; this.right = right; }
    public <R> R accept(Visitor<R> v) { return v.visit(this); }
}

public class Mul implements Expr {
    final Expr left, right;
    Mul(Expr left, Expr right) { this.left = left; this.right = right; }
    public <R> R accept(Visitor<R> v) { return v.visit(this); }
}

public class EvalVisitor implements Visitor<Integer> {
    public Integer visit(Num n) { return n.value; }
    public Integer visit(Add a) { return a.left.accept(this) + a.right.accept(this); }
    public Integer visit(Mul m) { return m.left.accept(this) * m.right.accept(this); }
}

public class PrintVisitor implements Visitor<String> {
    public String visit(Num n) { return String.valueOf(n.value); }
    public String visit(Add a) { return "(" + a.left.accept(this) + " + " + a.right.accept(this) + ")"; }
    public String visit(Mul m) { return "(" + m.left.accept(this) + " * " + m.right.accept(this) + ")"; }
}

void main() {
    Expr ast = new Mul(new Add(new Num(2), new Num(3)), new Num(4));
    System.out.println(ast.accept(new PrintVisitor()));
    System.out.println(ast.accept(new EvalVisitor()));
}
How the Visitor works

The expression nodes — Num, Add and Mul — form a stable object structure. Each one implements a single accept() method and nothing else about the operations.

When accept() runs, it calls the visit overload that matches its own node type. This two-step call (client → accept, then accept → visit) is double dispatch: it picks the right method based on both the node type and the visitor type, and it makes the tree walk itself recursively.

Each operation lives in its own visitor — EvalVisitor computes a value, PrintVisitor renders a string — so the algorithms stay out of the node classes.

Adding a new operation (an optimizer, a type checker) means writing one new visitor and touching none of the existing nodes, which is exactly the open-closed benefit of the pattern.
