Visitor

Visitor pattern allows us to define and add new operations to an existing object structure without modifying the classes of the objects on which those operations operate. This is particularly useful when the object structure and its classes are relatively stable, but we frequently need to introduce new behaviors or operations over those objects.


Instead of placing every possible operation inside the domain classes themselves, this pattern extracts those operations into separate Visitor classes. Each element in the object structure accepts a Visitor and the Visitor contains the operation specific logic for different types of elements. This separates the algorithms or behaviors from the objects they operate on, keeping the object classes focused on representing their core data and responsibilities.


Visitor pattern supports the Open-Closed Principle with respect to operations: the existing element classes can remain closed for modification while new operations can be introduced by creating new Visitor implementations. However,
this comes with a trade-off: adding a new type of element usually requires modifying the Visitor interface and all existing Visitor implementations. Therefore, Visitor is most suitable when the set of element types is stable, while
the set of operations performed on them changes frequently.

Components
  • When an object structure is stable but we frequently need to extend its behaviours with new operations.
  • Visitor – Interface or abstract class for visiting elements.
  • ConcreteVisitor – Implements operations on concrete elements.
  • Element – Interface that defines accept(visitor)
  • ConcreteElement – Implements accept(visitor)
  • Client – Traverses object structure and applies visitor.
Pros and Cons
New Operations Easily

New operations can be added without changing the existing object structures.

Separation Of Concerns

It encourages a clean separation of concerns between data and behavior.

Extensible Operations

It makes operations extensible and easy to manage over time.

Hard To Add Elements

Adding a new element type requires updating all existing visitors.

Double Dispatch

It involves double dispatch – one call from client to element, and one from element to visitor.

Real-world example
  • NIO FileVisitor — Files.walkFileTree traverses a directory tree and calls visitFile and visitDirectory callbacks on each node.
  • ElementVisitor — annotation processors visit program elements (classes, methods, fields) during compilation.
  • Java compiler AST — the TreeVisitor walks syntax tree nodes for analysis and code generation.
  • Bytecode lib — ClassVisitor and MethodVisitor let tools inspect and transform bytecode without changing the class model.
  • Spring BeanDefinitionVisitor — visits bean definitions to resolve and rewrite property placeholder values.
  • ANTLR and XML parsers — generated visitors walk parse trees so each operation (eval, pretty) stays separate from the grammar.
public interface Visitor<R> {
    R visit(Num n);
    R visit(Add a);
    R visit(Mul m);
}

public interface Expr {
    <R> R accept(Visitor<R> v);
}

public class Num implements Expr {
    final int value;
    Num(int value) { this.value = value; }
    public <R> R accept(Visitor<R> v) { return v.visit(this); }
}

public class Add implements Expr {
    final Expr left, right;
    Add(Expr left, Expr right) { this.left = left; this.right = right; }
    public <R> R accept(Visitor<R> v) { return v.visit(this); }
}

public class Mul implements Expr {
    final Expr left, right;
    Mul(Expr left, Expr right) { this.left = left; this.right = right; }
    public <R> R accept(Visitor<R> v) { return v.visit(this); }
}

public class EvalVisitor implements Visitor<Integer> {
    public Integer visit(Num n) { return n.value; }
    public Integer visit(Add a) { return a.left.accept(this) + a.right.accept(this); }
    public Integer visit(Mul m) { return m.left.accept(this) * m.right.accept(this); }
}

public class PrintVisitor implements Visitor<String> {
    public String visit(Num n) { return String.valueOf(n.value); }
    public String visit(Add a) { return "(" + a.left.accept(this) + " + " + a.right.accept(this) + ")"; }
    public String visit(Mul m) { return "(" + m.left.accept(this) + " * " + m.right.accept(this) + ")"; }
}

void main() {
    Expr ast = new Mul(new Add(new Num(2), new Num(3)), new Num(4));
    System.out.println(ast.accept(new PrintVisitor()));
    System.out.println(ast.accept(new EvalVisitor()));
}
How the Visitor works

The expression nodes — Num, Add and Mul — form a stable object structure. Each one implements a single accept() method and nothing else about the operations.

When accept() runs, it calls the visit overload that matches its own node type. This two-step call (client → accept, then accept → visit) is double dispatch: it picks the right method based on both the node type and the visitor type, and it makes the tree walk itself recursively.

Each operation lives in its own visitor — EvalVisitor computes a value, PrintVisitor renders a string — so the algorithms stay out of the node classes.

Adding a new operation (an optimizer, a type checker) means writing one new visitor and touching none of the existing nodes, which is exactly the open-closed benefit of the pattern.
