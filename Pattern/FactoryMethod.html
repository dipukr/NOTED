Factory Method

Factory Method is a creational design pattern used when a class needs an object but wants to let subclasses decide which concrete implementation gets created.

The parent class defines when and how an object is used, but delegates which concrete object is created to subclasses. That distinction is what makes Factory Method different from simply putting new inside a helper class.

When to use
  • When a class cannot anticipate the type of objects it must create.
  • When you want subclasses to specify the objects they create.
  • When you want to decouple client code from concrete product classes.
  • When object creation logic should be centralized in one place.
  • When you need to introduce new product types without changing client code.
Pros and Cons
Loose Coupling

Removes tight coupling between the creator and the concrete products it uses.

Single Responsibility

Follows the single responsibility principle by isolating object creation code in one place.

Open/Closed Principle

Follows the open/closed principle so new products can be added easily without changing existing code.

Centralized Creation

Provides a single place to control how objects are created.

Easier To Maintain

Makes the code easier to extend and maintain over time.

More Subclasses

Introduces many new subclasses, increasing overall code complexity.

Overkill For Simple Cases

Can be excessive for simple creation scenarios that do not need the abstraction.

Parallel Hierarchy

Requires a parallel class hierarchy for creators and products.

What problem Factory Method solves

Suppose you are building a notification system. Initially you only support email:

public class NotificationService {
    public void send(String message) {
        EmailNotification notification = new EmailNotification();
        notification.send(message);
    }
}

public class EmailNotification {
    public void send(String message) {
        System.out.println("Sending EMAIL: " + message);
    }
}

This works. But later you add SMS, push notifications, WhatsApp and Slack and you might end up doing.

public class NotificationService {
    public void send(String type, String message) {
        Notification notification;
        if ("email".equals(type)) {
            notification = new EmailNotification();
        } else if ("sms".equals(type)) {
            notification = new SmsNotification();
        } else if ("push".equals(type)) {
            notification = new PushNotification();
        } else {
            throw new IllegalArgumentException("Unsupported type");
        }
        notification.send(message);
    }
}

Now NotificationService knows about every concrete notification implementation.

Every time we add another notification type we modify NotificationService so the class is tightly coupled to concrete implementations. Factory Method moves that object-creation decision somewhere else.

The product and concrete products:

public interface Notification {
    void send(String message);
}

public class EmailNotification implements Notification {
    public void send(String message) {
        System.out.println("Sending EMAIL: " + message);
    }
}

public class SmsNotification implements Notification {
    public void send(String message) {
        System.out.println("Sending SMS: " + message);
    }
}

The creator and concrete creators:

public abstract class NotificationService {
    protected abstract Notification createNotification();

    public void send(String message) {
        Notification notification = createNotification();
        notification.send(message);
    }
}

public class EmailNotificationService extends NotificationService {
    protected Notification createNotification() {
        return new EmailNotification();
    }
}

public class SmsNotificationService extends NotificationService {
    protected Notification createNotification() {
        return new SmsNotification();
    }
}

Usage:

void main(String[] args) {
    NotificationService service = new EmailNotificationService();
    service.send("Your order has been shipped");

    service = new SmsNotificationService();
    service.send("OTP: 123456");
}

Output:

Sending EMAIL: Your order has been shipped
Sending SMS: OTP: 123456

Notice the critical line Notification notification = createNotification();. NotificationService does not know whether it returns an EmailNotification or an SmsNotification: the subclass decides. Adding WhatsApp or Slack means adding a new product and a new service subclass, without touching NotificationService.

Better real-world example

Take a document export system with the same general workflow for every format:

1. Create exporter 2. Add metadata 3. Export document 4. Log completion

The exporter might be PDF, CSV or JSON. The workflow stays mostly the same; only the object being created changes. First define the product and concrete products:

public interface DocumentExporter {
    void export(String data);
}

public class PDFExporter implements DocumentExporter {
    public void export(String data) {
        System.out.println("Exporting PDF: " + data);
    }
}

public class CSVExporter implements DocumentExporter {
    public void export(String data) {
        System.out.println("Exporting CSV: " + data);
    }
}

Now the creator:

public abstract class ExportService {
    protected abstract DocumentExporter createExporter();

    public void exportDocument(String data) {
        System.out.println("Preparing document...");
        DocumentExporter exporter = createExporter();
        exporter.export(data);
        System.out.println("Export completed.");
    }
}

The concrete creators:

public class PDFExportService extends ExportService {
    protected DocumentExporter createExporter() {
        return new PDFExporter();
    }
}

public class CSVExportService extends ExportService {
    protected DocumentExporter createExporter() {
        return new CSVExporter();
    }
}

Usage:

void main(String[] args) {
    ExportService service = new PDFExportService();
    service.exportDocument("Sales Report");
}

Output:

Preparing document...
Exporting PDF: Sales Report
Export completed.

Change the service to new CSVExportService() and the output becomes:

Preparing document...
Exporting CSV: Sales Report
Export completed.

The workflow did not change.

Why not simply create the object directly

You might reasonably ask why not just write DocumentExporter exporter = new PDFExporter(); Sometimes you absolutely should. Factory Method is useful only when object creation needs to vary independently from the code using the object.

public void export(String type, String data) {
    DocumentExporter exporter = null;
    switch (type) {
        case "pdf":
            exporter = new PDFExporter();
            break;
        case "csv":
            exporter = new CSVExporter();
            break;
        case "json":
            exporter = new JSONExporter();
            break;
        default:
            throw new IllegalArgumentException();
    }
    exporter.export(data);
}

Here the client knows PDFExporter, CSVExporter and JSONExporter. Factory Method moves that concrete-object creation out of the reusable algorithm.

The key insight

The most important Factory Method relationship is:

Creator | | calls ↓ createProduct() | | overridden by ↓ ConcreteCreator
public abstract class ExportService {

    protected abstract DocumentExporter createExporter();

    public void exportDocument(String data) {

        DocumentExporter exporter = createExporter();

        exporter.export(data);
    }
}

The factory method is createExporter, not exportDocument. exportDocument is ordinary business or workflow logic.

Why does the Creator often contain business logic?

This point causes a lot of confusion. Consider:

public abstract class NotificationService {
    protected abstract Notification createNotification();

    public void send(String message) {
        Notification notification = createNotification();
        notification.send(message);
    }
}

At first it can look strange that something called NotificationService is responsible for both creating and sending. The answer is that Creator is a GoF role name, not necessarily the class name you should use. Parent is not supposed
to exist only to create objects; usually it owns some useful workflow and contains one overridable creation step.

public abstract class PaymentProcessor {
    protected abstract PaymentGateway createGateway();

    public void process(Payment payment) {
        validate(payment);
        PaymentGateway gateway = createGateway();
        gateway.charge(payment);
        saveTransaction(payment);
        sendReceipt(payment);
    }

    private void validate(Payment payment) {
        System.out.println("Validate payment");
    }

    private void saveTransaction(Payment payment) {
        System.out.println("Save transaction");
    }

    private void sendReceipt(Payment payment) {
        System.out.println("Send receipt");
    }
}

Different subclasses select the gateway:

public class StripePaymentProcessor extends PaymentProcessor {
    protected PaymentGateway createGateway() {
        return new StripeGateway();
    }
}

public class RazorpayPaymentProcessor extends PaymentProcessor {
    protected PaymentGateway createGateway() {
        return new RazorpayGateway();
    }
}

Now Factory Method makes much more sense. The parent owns the workflow, while subclasses choose StripeGateway or RazorpayGateway:

validate ↓ create gateway ↓ charge ↓ save transaction ↓ send receipt

The product and concrete products:

public interface PaymentGateway {

What exactly did Factory Method improve

Without Factory Method:

public class PaymentService {
    public void makePayment(String gatewayType, double amount) {
        PaymentGateway gateway = null;
        if ("stripe".equals(gatewayType)) {
            gateway = new StripeGateway();
        } else if ("razorpay".equals(gatewayType)) {
            gateway = new RazorpayGateway();
        } else {
            throw new IllegalArgumentException();
        }
        gateway.pay(amount);
    }
}

Adding PayPal requires modifying this class:

else if ("paypal".equals(gatewayType)) {
    gateway = new PaypalGateway();
}

With Factory Method, you add a new subclass instead and the original algorithm does not change:

public class PaypalPaymentService extends PaymentService {
    protected PaymentGateway createGateway() {
        return new PaypalGateway();
    }
}
Factory Method and the Open/Closed Principle

Software should be open for extension but closed for modification.

Factory Method often helps here: you add class PaypalPaymentService extends PaymentService instead of modifying PaymentService, so the algorithm remains stable while new creation behaviors can be added.

But this is not magic. Someone still needs to decide which concrete creator to instantiate, for example PaymentService service = new StripePaymentService(); There is still a concrete choice somewhere; Factory Method simply moves that decision away from the reusable algorithm.

Factory Method is based on inheritance

Classic Factory Method relies heavily on polymorphism:

public abstract class Creator {
    protected abstract Product createProduct();
}

public class CreatorA extends Creator {
    protected Product createProduct() {
        return new ProductA();
    }
}

Variation happens through subclassing. This is one of the defining characteristics of Factory Method.

Factory Method looks like Template Method

There is a good reason Factory Method can feel similar to Template Method. Consider:

public abstract class PaymentService {
    public void pay(double amount) {
        validate(amount);
        PaymentGateway gateway = createGateway();
        gateway.pay(amount);
        save();
    }

    protected abstract PaymentGateway createGateway();
}

There are two ideas here. pay() resembles Template Method: it defines the overall algorithm. createGateway() is a Factory Method, because its purpose is creating an object. They frequently appear together:

Sometimes a Factory Method is itself one customizable step inside a Template Method.

  • Template method: steps of an algorithm.
  • Factory method: which object gets created.
When should you use Factory Method

Factory Method is a good candidate when a class creates a concrete object directly but that concrete class might vary:

public class SomeService {
    public void doSomething() {
        ConcreteClass object = new ConcreteClass();
        ...
    }
}

Typical signs:

  • The parent knows the workflow but not the exact implementation it should instantiate.
  • Subclasses naturally correspond to different product types.
  • Creation logic varies while most business logic remains shared.
  • You want framework code to let application code choose implementations.
  • Direct construction would couple reusable code to concrete classes.
When NOT to use Factory Method

Don't introduce Factory Method unless creation genuinely varies.
Use it when that abstraction buys you something.

Frameworks are one of the best use cases

Factory Method works especially well in frameworks. Imagine a framework class:

public abstract class DataImporter {
    protected abstract Parser createParser();

    public void importData(String file) {
        Parser parser = createParser();
        parser.parse(file);
        System.out.println("Save imported data");
    }
}

The framework cannot know which parser the application wants. Each application provides its own:

public class CSVImporter extends DataImporter {
    protected Parser createParser() {
        return new CSVParser();
    }
}

public class JSONImporter extends DataImporter {
    protected Parser createParser() {
        return new JSONParser();
    }
}

This is a natural Factory Method use case: the framework controls the workflow, and the application controls object creation.

Spring changes the picture

Spring creates the concrete object, so manually implementing Factory Method is often unnecessary.
Spring IOC container already handles object creation.

public interface Notification {
    void send(String message);
}

@Component("email")
public class EmailNotification implements Notification {
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

@Component("sms")
public class SmsNotification implements Notification {
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}

You can inject the implementation you need:

@Service
public class NotificationService {

    @Autowired
    @Qualifier("email")
    private Notification notification;

    public void send(String message) {
        notification.send(message);
    }
}

Spring creates the concrete object, so manually implementing Factory Method is often unnecessary.

A practical Spring Boot factory

When selection happens dynamically at runtime, a registry is often cleaner.

public interface Notification {
    String type();
    void send(String message);
}

@Component
public class EmailNotification implements Notification {
    public String type() {
        return "email";
    }
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

@Component
public class SmsNotification implements Notification {
    public String type() {
        return "sms";
    }
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}

The factory:

@Component
public class NotificationFactory {
    private Map<String, Notification> notifications;
    
    public NotificationFactory(List<Notification> notificationList) {
        this.notifications = notificationList.stream()
                .collect(Collectors.toMap(
                        Notification::type,
                        Function.identity()
                ));
    }

    public Notification get(String type) {
        Notification notification = notifications.get(type);
        if (notification == null) {
            throw new IllegalArgumentException("Unknown notification type: " + type);
        }
        return notification;
    }
}

The service and controller:

@Service
public class NotificationService {

    @Autowired
    private NotificationFactory factory;

    public void send(String type, String message) {
        Notification notification = factory.get(type);
        notification.send(message);
    }
}

@RestController
@RequestMapping("/notifications")
public class NotificationController {

    @Autowired
    private NotificationService service;

    @PostMapping
    public void send(@RequestParam String type, @RequestParam String message) {
        service.send(type, message);
    }
}
Why Factory Method is valuable

The biggest benefits are not merely creating objects:

Loose coupling

Instead of new PDFExporter, the parent depends on DocumentExporter. The concrete implementation is selected elsewhere.

Extensibility

You can add an ExcelExporter without rewriting the main workflow.

Reusable workflow

Common logic (validate, prepare, create, execute, log) stays in the parent; only object creation varies.

Testing

The creation step can be overridden with a fake, so the workflow can be tested without calling a real service.

For example, testing the payment workflow without calling Stripe:

public class TestPaymentService extends PaymentService {
    protected PaymentGateway createGateway() {
        return new FakePaymentGateway();
    }
}
Main disadvantage

Factory Method tends to increase the number of classes. A simple feature might turn into:

Notification EmailNotification SmsNotification NotificationService EmailNotificationService SmsNotificationService

When there is no meaningful variation in the parent workflow, that is often overengineering.

An abstract class NotificationCreator whose subclasses do nothing except return new EmailNotification may provide very little benefit. Factory Method is strongest when the Creator itself contains meaningful reusable behavior:

public abstract class FileProcessor {

    public final void process(Path path) {
        validate(path);
        Parser parser = createParser();
        Data data = parser.parse(path);
        validateData(data);
        save(data);
        audit(data);
    }

    protected abstract Parser createParser();
}

Now the abstraction earns its existence.

Modern applications - Strategy plus dependency injection is often preferable to Factory Method because it favors composition over inheritance.

The deepest point: Factory Method is most useful when object creation is one variable part of a larger reusable operation. If you are only wrapping new EmailNotification() with several extra classes and gaining no reusable workflow, a simple factory, dependency injection, or direct construction is usually cleaner.
