Distributed System Architecture

Distributed system architecture structures an application as many nodes cooperating over a network to act as one system.

Nodes communicate and coordinate by passing messages to achieve a common goal.

It defines how components are placed, how they talk, and how the system stays available under failure.

Message passing may use pure HTTP, RPC connectors, or message queues.

When to use / Key points
  • Nodes: the individual computers or processes in the system.
  • Network and communication protocols (REST, RPC, MQ) tie nodes together.
  • Transparency: users are unaware of the underlying distribution.
  • Design for scalability, availability, consistency, and fault tolerance.
Pros and Cons
Horizontal Scalability

The system scales out by simply adding more nodes.

Fault Isolation

Failures are isolated so the whole system stays up.

Data Locality

Compute is placed closer to data or users for better performance.

Consistency Challenge

Keeping data consistent across nodes is a significant challenge (see CAP theorem).

Higher Complexity

Operational cost and complexity are much higher.

Network Failures

Network latency and partial failures must be designed around.

Code
# Resilient remote call with timeout and retry
@Service
public class PricingClient {

    private final RestTemplate rest;

    public PricingClient(RestTemplateBuilder builder) {
        # bound the wait so a slow node cannot hang us
        this.rest = builder
            .setConnectTimeout(Duration.ofSeconds(2))
            .setReadTimeout(Duration.ofSeconds(2))
            .build();
    }

    @Retryable(maxAttempts = 3)
    public Price fetch(String sku) {
        return rest.getForObject(
            "http://pricing-service/price/" + sku, Price.class);
    }
}
How it works

Timeouts stop one slow node from blocking the caller.

@Retryable absorbs transient network failures.

Each node is reached by logical name, decoupled from its location.
