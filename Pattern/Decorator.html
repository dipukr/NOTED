Decorator

The Decorator is a structural design pattern that allows us to dynamically add new responsibilities or behaviors to an individual object without modifying its existing class or affecting other objects of the same class.

It achieves this by wrapping an object inside another object, called a decorator, that implements the same interface as the original object. The decorator delegates operations to the wrapped object while adding its own functionality before or after the delegated operations.

The Decorator pattern provides a flexible alternative to inheritance for extending object behavior. Instead of creating numerous subclasses to support different combinations of features, we can compose objects by stacking multiple decorators around a core object.

Key characteristics:

  • Composition over inheritance: Additional functionality is introduced through object composition rather than subclassing the original concrete class.
  • Dynamic behavior extension: Decorators can be applied when objects are constructed at runtime, allowing different objects to have different combinations of behaviors.
  • Transparent wrapping: Decorators implement the same interface as the objects they wrap, so clients can use decorated and undecorated objects interchangeably.
  • Stackable behavior: Multiple decorators can be combined to build more complex functionality incrementally.
  • Open/Closed Principle: New functionality can be introduced through additional decorator classes without changing existing component implementations.

In simple terms: The Decorator pattern adds features to an object by wrapping it with other objects that provide those features.

Understanding the Problem

Consider a coffee ordering application. Initially the application supports only a simple coffee.

public class Coffee {
    public String getDescription() {
        return "Simple Coffee";
    }

    public double getCost() {
        return 50;
    }
}

Now customers want additional ingredients:

  • Milk (+₹15)
  • Whipped cream (+₹20)
  • Extra espresso shot (+₹25)

Approach 1: Using inheritance

We could create subclasses for every combination.

Illustrative inheritance explosion: combinations require additional concrete classes.

This introduces several problems.

  • Class explosion: Each new ingredient creates more combinations and potentially more subclasses.
  • Lack of flexibility: A predefined subclass determines what functionality an object possesses.
  • Runtime limitations: We can't easily change an existing object's combination of features through inheritance alone.
  • Code duplication: Similar cost and description logic can appear across multiple subclasses.

For three optional ingredients, there are already 23 = 8 possible combinations. For ten optional ingredients, there could be 210 = 1024 combinations.

Approach 2: Using the Decorator Pattern

Instead of using subclasses for every combination, create a separate decorator for each ingredient.

Each decorator wraps the object beneath it, adding a separate responsibility.

We can now combine the ingredients as needed without creating subclasses for every combination.

Structure of the Decorator Pattern

The pattern typically involves four participants.

ParticipantResponsibility
ComponentDefines the common interface for original objects and decorators.
ConcreteComponentThe original object whose behavior can be extended.
DecoratorImplements the Component interface and holds a reference to another Component. Delegates operations to it.
ConcreteDecoratorExtends the decorator and introduces additional functionality.

The key is that the Decorator implements the same interface as the object it wraps.

This allows another decorator to wrap it, creating a chain of objects.

Complete Java Implementation: Coffee Ordering System

Create the Component interface

public interface Coffee {
    String getDescription();
    double getCost();
}

Every concrete coffee and decorator implements this interface.

Create the ConcreteComponent

public class SimpleCoffee implements Coffee {
    @Override
    public String getDescription() {
        return "Simple Coffee";
    }

    @Override
    public double getCost() {
        return 50.0;
    }
}

This represents the original object with no additional features.

Create the base Decorator class

public abstract class CoffeeDecorator implements Coffee {
    protected final Coffee coffee;

    public CoffeeDecorator(Coffee coffee) {
        this.coffee = coffee;
    }

    @Override
    public String getDescription() {
        return coffee.getDescription();
    }

    @Override
    public double getCost() {
        return coffee.getCost();
    }
}

Important points:

  • CoffeeDecorator implements Coffee, making it compatible with any other Coffee object.
  • It contains a reference to another Coffee object — composition.
  • The default methods delegate to the wrapped object.
  • Concrete decorators override the methods they need to extend.

The abstract decorator class is convenient but optional. A concrete decorator could implement Coffee directly.

Create ConcreteDecorators

MilkDecorator

public class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Milk";
    }

    @Override
    public double getCost() {
        return super.getCost() + 15.0;
    }
}

CreamDecorator

public class CreamDecorator extends CoffeeDecorator {
    public CreamDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Cream";
    }

    @Override
    public double getCost() {
        return super.getCost() + 20.0;
    }
}

ExtraShotDecorator

public class ExtraShotDecorator extends CoffeeDecorator {
    public ExtraShotDecorator(Coffee coffee) {

Client code

void main(String[] args) {
    Coffee coffee = new SimpleCoffee();

    System.out.println(coffee.getDescription());
    System.out.println(coffee.getCost());

    # Add milk
    coffee = new MilkDecorator(coffee);

    # Add cream
    coffee = new CreamDecorator(coffee);

    # Add extra espresso shot
    coffee = new ExtraShotDecorator(coffee);

    System.out.println(coffee.getCost());
}

Understanding the execution flow

After wrapping, the object structure looks like this:

Coffee coffee = new ExtraShotDecorator(new CreamDecorator(new MilkDecorator(new SimpleCoffee())));

When coffee.getCost() is called, the outer decorator delegates inward until reaching the actual coffee object.

The evaluation is:

ExtraShotDecorator.getCost()
    = CreamDecorator.getCost() + 25
    = MilkDecorator.getCost() + 20 + 25
    = SimpleCoffee.getCost() + 15 + 20 + 25
    = 50 + 15 + 20 + 25
    = 110

Notice that SimpleCoffee knows nothing about milk, cream, or extra shots. Each decorator has only the responsibility of adding its own functionality.

Real-World Example: Java I/O Streams

One of the most widely used examples of the Decorator pattern is Java's I/O stream API.

Java provides a hierarchy of stream classes that can be wrapped to add additional capabilities.

Consider these classes:

  • FileInputStream: Reads raw bytes from a file.
  • BufferedInputStream: Adds buffering to reduce repeated low-level read operations.
  • DataInputStream: Provides methods to read Java primitive data types.
  • GZIPInputStream: Adds decompression functionality.

Adding buffering to a file stream

void main(String[] args) throws Exception {
    InputStream input = new BufferedInputStream(new FileInputStream("data.txt"));
    try (input) {
        int data;
        while ((data = input.read()) != -1)
            System.out.print((char) data);
    }
}

Here:

new FileInputStream("data.txt")

creates the actual stream.

new BufferedInputStream(fileInputStream)

wraps the stream and adds buffering.

Both can be used as InputStream.

Adding decompression and buffering

void main(String[] args) throws Exception {
    try (InputStream input = new BufferedInputStream(new GZIPInputStream(new FileInputStream("data.txt.gz")))) {
        byte[] buffer = new byte[8192];
        int bytesRead;
        while ((bytesRead = input.read(buffer)) != -1) {
            # Process decompressed bytes
        }
    }
}

The stream is processed through multiple layers:

Client | v BufferedInputStream | v GZIPInputStream | v FileInputStream | v Compressed file

Each wrapper adds a capability without changing FileInputStream.

This is exactly the concept of the Decorator pattern.

Important: The order of decorators may affect behavior and efficiency. For example, buffering compressed bytes versus buffering decompressed bytes are different operations.

Practical Example: Logging and Metrics Around a Service

Consider a Spring Boot-style payment processing application.

Suppose we already have a payment processor, but later want to introduce:

  • Logging of payment requests
  • Execution-time measurement
  • Additional features without modifying the original payment processor

Instead of putting all cross-cutting concerns inside the original implementation, we can wrap it with decorators.

Component interface

public interface PaymentProcessor {
    void processPayment(String paymentId, double amount);
}

Original implementation

public class DefaultPaymentProcessor implements PaymentProcessor {

    @Override
    public void processPayment(String paymentId, double amount) {
        System.out.println("Processing payment: " + paymentId);
    }
}

Logging decorator

public class LoggingPaymentDecorator implements PaymentProcessor {
    private PaymentProcessor delegate;

    public LoggingPaymentDecorator(PaymentProcessor delegate) {
        this.delegate = delegate;
    }

    @Override
    public void processPayment(String paymentId, double amount) {
        System.out.println("Payment started: " + paymentId);
        try {
            delegate.processPayment(paymentId, amount);
            System.out.println("Payment completed: " + paymentId);
        } catch (RuntimeException e) {
            System.out.println("Payment failed: " + paymentId);
            throw e;
        }
    }
}

Metrics decorator

public class MetricsPaymentDecorator implements PaymentProcessor {
    private PaymentProcessor delegate;

    public MetricsPaymentDecorator(PaymentProcessor delegate) {
        this.delegate = delegate;
    }

    @Override
    public void processPayment(String paymentId, double amount) {
        long start = System.nanoTime();
        try {
            delegate.processPayment(paymentId, amount);
        } finally {
            long elapsed = System.nanoTime() - start;
            System.out.println("Execution time: " + elapsed / 1_000_000.0 + " ms");
        }
    }
}

Combining decorators

void main(String[] args) {
    PaymentProcessor processor = new MetricsPaymentDecorator(new LoggingPaymentDecorator(new DefaultPaymentProcessor()));
    processor.processPayment("PAY-101", 5000.0);
}

Example output:

Payment started: PAY-101
Processing payment: PAY-101
Payment completed: PAY-101
Execution time: 2.4 ms

The actual execution time will vary.

How the object chain works

The DefaultPaymentProcessor is completely unaware that logging and metrics are being performed around it.

This makes the design extensible.

For example, a validation decorator can be introduced later without modifying the original processor.

In production, payment amounts should generally use BigDecimal or minor currency units rather than double. Also, any retry decorator for actual payments must account for idempotency and uncertain payment outcomes.

Decorator Design Pattern: ProductService Example (Spring Boot)

Let's apply the Decorator Design Pattern to an ProductService, adding logging, caching, retry, and transactional behavior without modifying its core business logic.

The idea is to keep ProductServiceImpl responsible only for fetching a product from ProductDAO and mapping it to ProductBO. Each decorator adds one additional responsibility.

Architecture

All decorators implement the same ProductService interface and hold a reference to another ProductService.

When a client invokes getProduct(), the call passes through the decorators until it reaches the actual implementation. Each decorator can perform operations before or after delegating, or even return without calling the next service.

Important: The decorator order matters. With this arrangement, a cache hit avoids unnecessary retry and database transaction processing. On a cache miss, each retry attempt gets its own transaction.

Core ProductService implementation

First, let's define the interface and the original implementation.

public interface ProductService {
    ProductBO getProduct(String productId);
}
public class ProductServiceImpl implements ProductService {
    private ProductDAO productDAO;
    private ModelMapper modelMapper;

    public ProductServiceImpl(ProductDAO productDAO, ModelMapper modelMapper) {
        this.productDAO = productDAO;
        this.modelMapper = modelMapper;
    }

    @Override
    public ProductBO getProduct(String productId) {
        Product entity = productDAO.getProduct(productId);
        if (entity == null) return null;
        return modelMapper.map(entity, ProductBO.class);
    }
}

Here:

  • ProductService is the Component interface.
  • ProductServiceImpl is the Concrete Component.
  • ProductDAO accesses the database.
  • ModelMapper converts the database entity into a business object.

Notice that ProductServiceImpl contains no logging, caching, retry, or transaction management code.

We use constructor injection instead of field-level @Autowired. Later, Spring configuration will assemble the service and its decorators.

Abstract base decorator

Every decorator needs to implement ProductService and hold a reference to another ProductService.

Instead of repeating this logic, we can create an abstract base class.

public abstract class ProductServiceDecoratorimplements ProductService {
    protected ProductService delegate;

    protected ProductServiceDecorator(ProductService delegate) {
        this.delegate = Objects.requireNonNull(delegate);
    }

    @Override
    public ProductBO getProduct(String productId) {
        return delegate.getProduct(productId);
    }
}

This class provides the common delegation mechanism. Individual decorators can override getProduct to add their own functionality, typically delegating to the next service in the chain.

Logging decorator

Logging decorator records when a product is fetched, how long the operation takes, and whether it succeeds or fails.

public class LoggingProductServiceDecoratorextends ProductServiceDecorator {
    private static final Logger log = LoggerFactory.getLogger(LoggingProductServiceDecorator.class);

    public LoggingProductServiceDecorator(ProductService delegate) {
        super(delegate);
    }

    @Override
    public ProductBO getProduct(String productId) {
        long startTime = System.nanoTime();
        try {
            ProductBO product = delegate.getProduct(productId);
            long durationMs = (System.nanoTime() - startTime) / 1_000_000;
            log.info("Fetched product={}, duration={}ms", productId, durationMs);
            return product;
        } catch (RuntimeException e) {
            long durationMs = (System.nanoTime() - startTime) / 1_000_000;
            log.error("Failed to fetch product={}, duration={} ms", productId, durationMs, e);
            throw e;
        }
    }
}

How it works

  1. The decorator records the starting time.
  2. It calls delegate.getProduct(productId).
  3. The delegate performs the actual operation, including any inner decorators.
  4. Once the delegate returns, the decorator logs the duration.
  5. If an exception occurs, it logs the error and propagates the exception.

Key advantage: Neither ProductServiceImpl nor ProductDAO needs to know logging is being performed.

Because logging is the outermost decorator, it measures the entire operation, including potential cache lookup, retry delays, and database access.

Caching decorator

The caching decorator first checks whether a product has already been fetched. If found, it returns the cached object without calling the underlying service.

public class CachingProductServiceDecoratorextends ProductServiceDecorator {
    private ConcurrentMap<String, ProductBO> cache = new ConcurrentHashMap<>();

    public CachingProductServiceDecorator(ProductService delegate) {
        super(delegate);
    }

    @Override
    public ProductBO getProduct(String productId) {
        return cache.computeIfAbsent(productId, id -> delegate.getProduct(id));
    }

    public void evict(String productId) {
        cache.remove(productId);
    }

    public void clearCache() {
        cache.clear();
    }
}

How it works

Suppose we execute:

productService.getProduct("P101");
productService.getProduct("P101");
productService.getProduct("P102");
RequestCache resultUnderlying service called?
P101 (first call)MissYes
P101 (second call)HitNo
P102 (first call)MissYes

computeIfAbsent makes the cache implementation concise:

  • If the key exists, return the cached value.
  • Otherwise, execute delegate.getProduct(id).
  • Store the returned value if it is non-null.
  • Return the result.

If the underlying service throws an exception, the cache does not store the failed result.

Production considerations: This is an educational, in-memory cache without expiration. Real services typically use Caffeine, Redis, or Spring Cache for TTL, capacity limits, invalidation, and multi-instance behavior. Cached ProductBO objects should also be immutable or copied defensively to prevent callers from modifying shared cached objects.

Retry decorator

The retry decorator handles temporary failures, such as transient database connection issues or deadlocks.

Instead of immediately failing, it retries the operation a limited number of times.

public class RetryProductServiceDecoratorextends ProductServiceDecorator {
    private static final Logger log = LoggerFactory.getLogger(RetryProductServiceDecorator.class);
    private final int maxAttempts;
    private final long initialDelayMs;

    public RetryProductServiceDecorator(ProductService delegate, int maxAttempts, long initialDelayMs) {
        super(delegate);
        this.maxAttempts = maxAttempts;
        this.initialDelayMs = initialDelayMs;
    }

    @Override
    public ProductBO getProduct(String productId) {
        long delayMs = initialDelayMs;
        for (int attempt = 1; ; attempt++) {
            try {
                return delegate.getProduct(productId);
            } catch (TransientDataAccessException e) {
                if (attempt >= maxAttempts) throw e;
                log.warn("Retrying product={}, attempt={}/{}", productId, attempt + 1, maxAttempts);
                try {
                    Thread.sleep(delayMs);
                } catch (InterruptedException interrupted) {
                    Thread.currentThread().interrupt();
                    throw new IllegalStateException("Retry interrupted", interrupted);
                }
                delayMs = Math.min(delayMs * 2, 2000);
            }
        }
    }
}

How it works

When configured with three maximum attempts and an initial 100 ms delay:

This example uses exponential backoff: the delay doubles after each failed attempt, up to a cap.

Notice that we only retry TransientDataAccessException. We don't retry programming errors, invalid inputs, or arbitrary runtime exceptions.

In a production application, Spring Retry or Resilience4j can provide more sophisticated retry policies, jitter, metrics, and configuration. Also, Thread.sleep blocks the calling thread, so this implementation is intended for synchronous services.

Transactional decorator

Now let's add transaction management without putting @Transactional inside ProductServiceImpl.

For a true decorator impl, TransactionTemplate is useful because it manages transactions programmatically.

public class TransactionalProductServiceDecorator extends ProductServiceDecorator {
    private TransactionTemplate transactionTemplate;

    public TransactionalProductServiceDecorator(ProductService delegate, PlatformTransactionManager transactionManager) {
        super(delegate);
        this.transactionTemplate = new TransactionTemplate(transactionManager);
        transactionTemplate.setReadOnly(true);
        transactionTemplate.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    }

    @Override
    public ProductBO getProduct(String productId) {
        return transactionTemplate.execute(status -> delegate.getProduct(productId));
    }
}

How it works

The transaction decorator:

  1. Starts a new read-only transaction.
  2. Calls the wrapped service.
  3. Lets the DAO fetch the entity and ModelMapper map it.
  4. Commits the transaction if everything succeeds.
  5. Rolls back when an unchecked exception propagates.

The mapping operation happens inside the transaction, which can be useful when JPA entities have lazily loaded associations.

Why use REQUIRES_NEW?

Because our retry decorator sits outside the transaction decorator.

Every retry invokes the transactional decorator again, creating a fresh transaction.

REQUIRES_NEW is useful here to guarantee an independent transaction even when there is an existing transaction on the thread. However, it can suspend outer transactions and consume additional connections. If this service is never invoked inside an existing transaction, REQUIRED would also give each retry its own transaction.

Also, readOnly(true) is a hint to the transaction manager and database infrastructure, not a universal guarantee that writes are prohibited.

Spring Boot configuration: combining all decorators

This is the most important part: assembling the decorators into a single ProductService.

We will use a Spring @Configuration class rather than annotate each decorator with @Component.

@Configuration
public class ProductServiceConfiguration {

    @Bean
    public ProductService productService(ProductDAO productDAO, ModelMapper modelMapper, PlatformTransactionManager txManager) {
        # Core business implementation
        ProductService service = new ProductServiceImpl(productDAO, modelMapper);

        # Transaction management
        service = new TransactionalProductServiceDecorator(service, txManager);

        # Retry transient database failures
        service = new RetryProductServiceDecorator(service, 3, 100);

        # Cache successful results
        service = new CachingProductServiceDecorator(service);

        # Log the entire execution
        service = new LoggingProductServiceDecorator(service);

        return service;
    }
}

The configuration produces this structure:

LoggingProductServiceDecorator └── CachingProductServiceDecorator └── RetryProductServiceDecorator └── TransactionalProductServiceDecorator └── ProductServiceImpl └── ProductDAO

Although we create multiple objects, Spring exposes a single ProductService bean through this configuration.

The service implementation and decorators should not also be registered as independent @Service or @Component beans in this example. Otherwise, you may encounter multiple candidates when injecting ProductService.

Spring injects the outermost LoggingProductServiceDecorator, which wraps the rest of the chain.

The controller simply sees a ProductService.

Why decorator ordering is important

Consider two possible arrangements.

Recommended order: Logging → Caching → Retry → Transaction → DAO
A cache hit avoids the transaction, and every retry creates a new transaction. Logging captures total response time.

Potentially problematic order: Logging → Transaction → Retry → Caching → DAO
A transaction opens even for cache hits. Worse, retries may occur inside one transaction that has already been marked rollback-only.

For the original read operation, the recommended chain is a sensible default. The exact ordering may change for writes, distributed caches, or services with different transaction requirements.

Decorator pattern vs Spring AOP

One interesting point: Spring already provides mechanisms for many of these cross-cutting concerns.

FunctionalityExplicit DecoratorCommon Spring alternative
LoggingLoggingProductServiceDecoratorSpring AOP
CachingCachingProductServiceDecorator@Cacheable
RetryRetryProductServiceDecoratorSpring Retry / Resilience4j
TransactionTransactionalProductServiceDecorator@Transactional
SecurityAuthorizationProductServiceDecoratorSpring Security / method security
MetricsMetricsProductServiceDecoratorMicrometer / AOP

Spring AOP commonly uses proxies to intercept method calls and add behavior around a target object.

The decorator and proxy patterns are related, but not identical in intent: decorators explicitly compose additional behavior, whereas proxies generally control or mediate access to an object.

In typical Spring Boot applications, annotations such as @Transactional and @Cacheable are often more convenient than manually implementing every decorator. Explicit decorators are particularly useful when you want transparent, testable, configurable behavior implemented as ordinary Java objects.

A few production considerations: The in-memory cache requires expiration and invalidation if products can change. Retry should use carefully selected transient exceptions, sensible backoff, and ideally jitter. For operations that modify data, retry safety and transaction boundaries need additional attention because repeating non-idempotent writes can cause duplicate effects.

Final takeaway

The essence of the Decorator Pattern is this:

ProductService service =
    new LoggingProductServiceDecorator(
        new CachingProductServiceDecorator(
            new RetryProductServiceDecorator(
                new TransactionalProductServiceDecorator(
                    new ProductServiceImpl(productDAO, modelMapper),
                    transactionManager
                ),
                3, 100
            )
        )
    );

This is equivalent to our Spring configuration, just written using nested constructors.

The client remains unchanged:

ProductBO product = service.getProduct("P101");

Each decorator decides what to do before or after delegation, and the underlying ProductServiceImpl remains focused on its original responsibility: retrieving and mapping a product.

That is the fundamental advantage of the Decorator Pattern: extending an object's behavior dynamically through composition, without modifying its original implementation.

Decorator Pattern and the Open/Closed Principle

The Open/Closed Principle (OCP) states:

Software entities should be open for extension but closed for modification.

The Decorator pattern supports this principle because we can introduce new behavior without modifying existing component classes. For example, suppose we want to add a discount feature to our coffee ordering system.

We can introduce a new decorator:

public class DiscountDecorator extends CoffeeDecorator {
    public DiscountDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", 10% Discount";
    }

    @Override
    public double getCost() {
        return super.getCost() * 0.90;
    }
}

Use it directly:

Coffee coffee = new DiscountDecorator(new MilkDecorator(new SimpleCoffee()));
System.out.println(coffee.getCost()); # 58.5

Here:

  • SimpleCoffee remains unchanged.
  • MilkDecorator remains unchanged.
  • We simply added a new DiscountDecorator.
  • The client can use the new feature through composition.

The design is open for extension while existing classes remain closed for modification.

Does the Order of Decorators Matter

Yes. Decorator order can matter significantly.

Consider these two configurations.

Configuration A: Apply discount after milk

Coffee coffee = new DiscountDecorator(new MilkDecorator(new SimpleCoffee()));

# (50 + 15) * 0.90 = 58.5

Configuration B: Apply discount before milk

Coffee coffee = new MilkDecorator(new DiscountDecorator(new SimpleCoffee()));

# (50 * 0.90) + 15 = 60.0

The first configuration discounts the entire coffee with milk.

The second configuration discounts only the base coffee price.

This shows that decorators do not necessarily commute. Changing their order can produce different results.

Decorator vs Proxy vs Adapter vs Strategy

These patterns sometimes look similar in code because they use composition, but they have different intentions.

PatternPrimary purposeExample
DecoratorAdd responsibilities or behaviorsAdding buffering to a stream
ProxyControl access to an objectLazy-loading a remote service
AdapterConvert one interface into anotherAdapting InputStream into a Reader
StrategySelect an interchangeable algorithmChoosing a payment calculation strategy
 

PaymentProcessor p = new LoggingPaymentDecorator(original); # Decorator: Adds logging
PaymentProcessor p = new AccessControlPaymentProxy(original);  # Proxy: Controls access
PaymentService service = new PaymentService(new CreditCardStrategy()); # Strategy: Chooses an algorithm

Decorator vs Proxy: Both often expose the same interface and delegate to another object. The difference is mainly their intent. A decorator extends functionality; a proxy controls access, location, lifecycle, or other aspects of using the target.

Decorator vs Strategy: A strategy replaces an algorithm, whereas a decorator adds behavior around or on top of an existing implementation.

Advantages and Disadvantages

Advantages

  • Adds functionality without modifying original classes.
  • Avoids a large number of subclasses.
  • Encourages composition over inheritance.
  • Supports flexible combinations of behaviors.
  • Promotes separation of responsibilities into smaller classes.
  • Allows decorators to be stacked or reused.

Disadvantages

  • Introduces additional objects and classes.
  • Deeply nested decorator chains can become difficult to understand or debug.
  • Decorator order may change application behavior.
  • Removing a decorator from the middle of an existing chain is not always straightforward.
  • Some concrete-component-specific methods are not available through the common component interface.
  • Object identity becomes more complicated because each wrapper is a distinct object.
When Should You Use the Decorator Pattern

The pattern is particularly useful when an application requires flexible combinations of optional features.

Common use cases include:

Use casePossible decorators
Java I/O streamsBuffering, decompression, data reading
HTTP clientLogging, authentication, retry, metrics
Notification systemFormatting, encryption, logging
Payment processingValidation, logging, metrics
Data processing pipelineCompression, encryption, transformation
GUI componentsBorders, scrolling, visual effects
Caching serviceCache, metrics, logging

In Spring Boot applications, decorators are useful when you want to extend a service implementation through ordinary object composition. Some similar cross-cutting requirements are more conveniently implemented using Spring AOP, servlet filters, or interceptors, depending on the responsibility.

When not to use it:

Avoid introducing a decorator architecture when there is only one fixed implementation and no realistic need for combining features. A straightforward class or ordinary method may be easier to maintain.

It is a structural design pattern because it defines how objects are composed and wrapped. Its purpose is to extend behavior through that structure.

It uses both in a typical implementation.

  • Interface implementation or inheritance ensures the decorator has the same contract as the component.
  • Composition allows the decorator to wrap and delegate to another component.

Composition is the primary mechanism for extending functionality.

Can we apply the same decorator multiple times?

Yes. Each decorator adds its own functionality. Whether repeated decoration is meaningful depends on the application.

Can decorators be added at runtime?
Yes. We can choose and construct different decorator chains based on runtime requirements.

However, this does not mean an existing chain automatically becomes mutable. Usually, adding a decorator creates a new outer wrapper.

Can an abstract Decorator class be omitted?
Yes. A concrete decorator can implement the component interface directly and store a reference to another component. The abstract base decorator is mainly a convenience for sharing delegation logic.

Final Summary

The Decorator Design Pattern enables us to extend an object's functionality by wrapping it inside other objects that implement the same interface. Mechanism of decorator pattern is:

Component component = new ConcreteComponent();
component = new DecoratorA(component);
component = new DecoratorB(component);
component = new DecoratorC(component);

Each decorator adds its responsibility while delegating to the object it wraps. Decorator pattern is especially effective when you need optional, independently reusable features that can be combined in different ways without creating a subclass for every possible combination.

Remember: Decorator = Same Interface + Object Composition + Delegation + Additional Behavior.
