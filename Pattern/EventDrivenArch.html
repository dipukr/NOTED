Event-driven Architecture

Event-driven architecture (EDA) is a software design pattern that allows a system to detect, process, and respond to events.

It is a design paradigm where components react to events rather than relying on synchronous request-response patterns.

Events flow through a broker, decoupling the producers of events from their consumers.

It underpins reactive, streaming, and highly scalable systems.

When to use / Key points
  • Producers publish events; consumers subscribe and react.
  • Patterns include pub/sub, event streaming, and event sourcing.
  • Ideal for asynchronous, fan-out, and real-time workloads.
  • Commonly built on Kafka, RabbitMQ, or cloud event buses.
Pros and Cons
Strong Decoupling

Services communicate through events, keeping producers and consumers independent of each other.

Elastic Scaling

Consumers can scale elastically to handle load as event volume rises and falls.

Easy Extensibility

New reactions can be added by subscribing fresh consumers without changing existing producers.

Eventual Consistency

State is only eventually consistent, which complicates reasoning about the system.

Harder Debugging

Distributed tracing and debugging become more difficult across asynchronous event flows.

Idempotent Consumers

Consumers must be idempotent to safely handle duplicate events without side effects.

Code
# In-process EDA with Spring's ApplicationEventPublisher
@Service
public class OrderService {

    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void placeOrder(Order order) {
        # persist, then announce the event
        publisher.publishEvent(new OrderPlacedEvent(order.getId()));
    }
}

@Component
class InvoiceHandler {
    @EventListener
    public void on(OrderPlacedEvent event) {
        System.out.println("Generating invoice for " + event.orderId());
    }
}
How it works

publishEvent broadcasts without knowing who listens.

@EventListener handlers react independently.

Adding a handler needs no change to OrderService.
