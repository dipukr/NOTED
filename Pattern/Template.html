Template

Template is a behavioral design pattern that defines the overall skeleton of an algorithm in a base class while allowing subclasses to customize or override specific steps without changing the algorithm’s overall structure or execution order.

The base class provides a template method that defines the fixed sequence of steps required to perform the algorithm. Some of these steps may have common implementations in the base class, while others may be abstract or overridable so that subclasses can provide their own behavior. This allows the invariant parts of the algorithm to remain fixed and reusable, while the variable parts can be customized by subclasses.

This way template method pattern promotes code reuse, avoids duplication, and ensures that all subclasses follow the same overall algorithm while still allowing controlled variation in individual steps.

When to use
  • When several classes share the same algorithm structure but differ in some steps.
  • When you want to control which parts of an algorithm subclasses may change.
  • When you want to eliminate duplicated code across similar subclasses.
  • Typical uses: frameworks, build or parse pipelines, and data-processing workflows.
Pros and Cons
Removes Duplication

Keeps the common algorithm in one place so shared code is not repeated across subclasses.

Focused Customization

Lets subclasses customize only the parts that vary while the rest stays fixed.

Enforces Structure

Enforces a fixed algorithm structure, reducing the chance of errors.

Hollywood Principle

Follows the "Hollywood Principle": the base class calls the subclass steps.

Inheritance Bound

Relies on inheritance, which is less flexible than composition.

Rigid Skeleton

The fixed skeleton can limit what subclasses are able to change.

Harder Maintenance

Maintaining the base class becomes harder as the number of steps grows.

Real-world example
  • Java IOS — the abstract stream classes define read/write skeletons while concrete streams supply the varying byte operations.
  • Java AbstractList — provides skeletal list behavior and leaves get() and size() for subclasses to implement.
  • Spring JdbcTemplate — fixes the connect, execute, and cleanup sequence while callbacks supply the query and row-mapping steps.
  • Servlet HttpServlet.service() — the fixed service method dispatches to doGet, doPost, and other steps that subclasses override.
  • JUnit test lifecycle — the runner invokes setUp, the test, and tearDown in a fixed order while you fill in each step.
  • Spring AbstractApplicationContext.refresh() — runs a fixed container startup sequence with hooks that subclasses can override.
  • Baking a recipe — the overall steps stay the same while the specific ingredients and flavors change per dish.
What is the Template Method Design Pattern?

The Template Method is a behavioral design pattern that defines the skeleton of an algorithm in a base class and allows subclasses to customize specific steps without changing the algorithm's overall structure.

The base class defines a template method that executes a sequence of operations. Some operations have predefined implementations, while others are abstract or overridable, allowing subclasses to provide their own behavior.

This ensures that the overall algorithm remains consistent while individual steps can vary depending on the implementation.

The central idea is: Define the algorithm's structure once, but allow subclasses to customize certain steps.

Real-world analogy: Preparing beverages

Suppose you have a coffee shop that prepares tea and coffee.

Both beverages follow essentially the same preparation process:

Boil water
Common step
Brew beverage
Different for tea and coffee
Pour into cup
Common step
Add condiments (optional)
Different or skipped depending on beverage

Instead of implementing the entire process separately for tea and coffee, we can define the common algorithm once and customize the brewing and condiment steps.

That is exactly what the Template Method pattern does.

Structure of the Template Method Pattern

The pattern typically involves two participants.

Abstract Class (Template)

  • Defines the template method containing the algorithm's sequence.
  • Implements common operations shared by subclasses.
  • Declares abstract operations that subclasses must implement.
  • May provide optional hooks that subclasses can override.

Concrete Classes

  • Extend the abstract class.
  • Implement the abstract steps.
  • Optionally override hooks.
  • Inherit and reuse the overall algorithm.

The template method orchestrates the sequence:

public final void templateMethod() {
    commonStep();
    requiredStep();
    optionalHook();
}

Here, commonStep() is implemented in the base class, requiredStep() is implemented by subclasses, and optionalHook() has a default implementation that subclasses may override.

The final keyword prevents subclasses from changing the overall algorithm by overriding the template method.

Example 1: Tea and Coffee Preparation

Step 1: Create the abstract class

public abstract class Beverage {
    # Template Method
    public final void prepare() {
        boilWater();
        brew();
        pourInCup();
        if (wantsCondiments()) {
            addCondiments();
        }
    }

    # Common steps
    private void boilWater() {
        System.out.println("Boiling water");
    }

    private void pourInCup() {
        System.out.println("Pouring into cup");
    }

    # Abstract step: subclasses must implement
    protected abstract void brew();

    # Hook: subclasses may override
    protected boolean wantsCondiments() {
        return false;
    }

    # Hook: optional implementation
    protected void addCondiments() {
    }
}

Notice that prepare() determines the order in which all operations execute.

The subclasses cannot change this sequence because prepare() is final.

Step 2: Implement Tea

public class Tea extends Beverage {
    @Override
    protected void brew() {
        System.out.println("Steeping tea leaves");
    }

    @Override
    protected boolean wantsCondiments() {
        return true;
    }

    @Override
    protected void addCondiments() {
        System.out.println("Adding lemon");
    }
}

Step 3: Implement Coffee

public class Coffee extends Beverage {
    @Override
    protected void brew() {
        System.out.println("Brewing coffee");
    }
}

Coffee does not need to override addCondiments() or wantsCondiments(), because the base class already provides default behavior.

Step 4: Client code

void main(String[] args) {
    Beverage tea = new Tea();
    tea.prepare();
    System.out.println("----------");
    Beverage coffee = new Coffee();
    coffee.prepare();
}

Output:

Boiling water
Steeping tea leaves
Pouring into cup
Adding lemon
----------
Boiling water
Brewing coffee
Pouring into cup

How does this work internally?

When the following statement executes:

Beverage tea = new Tea();
tea.prepare();
  1. Java executes prepare() defined in Beverage.
  2. boilWater() executes from the base class.
  3. brew() resolves to Tea.brew() through dynamic method dispatch.
  4. pourInCup() executes from the base class.
  5. wantsCondiments() resolves to Tea.wantsCondiments().
  6. Since it returns true, Tea.addCondiments() executes.

The important distinction is that the parent class controls when methods execute, while subclasses determine how certain methods execute.

Types of Methods in Template Method Pattern

There are four commonly used categories of methods.

Method typePurposeUsually overridden?
Template methodDefines the overall algorithmNo
Abstract methodDefines a required customizable stepYes, mandatory
Concrete methodImplements common behaviorUsually no
Hook methodProvides optional customizationOptional

Template Method

Defines the sequence of operations.

public final void process() {
    step1();
    step2();
    step3();
}

Usually declared final to preserve the algorithm's structure, although the pattern does not strictly require it.

Abstract Method

Forces subclasses to provide their own implementation.

protected abstract void step2();

Concrete Method

Provides behavior common to every subclass.

private void step1() {
    System.out.println("Common processing");
}

Hook Method

Allows optional customization.

protected void beforeProcess() {
    # Default: do nothing
}

A subclass can override it:

@Override
protected void beforeProcess() {
    System.out.println("Starting processing...");
}

Abstract methods are mandatory extension points; hooks are optional extension points.

Example 2: Real-world Data Import System

Consider a backend application that imports customer data from several formats:

  • CSV files
  • Pipe-delimited files
  • Potentially JSON, XML, or other formats in the future

Regardless of the input format, every import must follow a consistent workflow:

  1. Before import (hook)
  2. Read input records
  3. Parse record (subclass)
  4. Validate customer
  5. Save valid customer
  6. After import (hook)

The parsing logic differs by file format, but the overall import algorithm remains the same.

Step 1: Customer model

public record Customer(String id, String name, String email) {}

Step 2: Abstract importer

public abstract class CustomerImporter {
    private List<Customer> database;

    protected CustomerImporter(List<Customer> database) {
        this.database = database;
    }

    # Template Method
    public final int importData(String input) {
        beforeImport();
        int imported = 0;
        for (String line : input.lines().toList()) {
            if (line.isBlank()) {
                continue;
            }
            Customer customer = parse(line); # Format-specific parsing
            if (isValid(customer)) { # Shared validation
                save(customer); # Shared persistence
                imported++;
            }
        }
        afterImport(imported);
        return imported;
    }

    # Must be implemented by subclasses
    protected abstract Customer parse(String line);

    # Default validation
    protected boolean isValid(Customer customer) {
        return !customer.id().isBlank() && !customer.name().isBlank() && customer.email().contains("@");
    }

    # Shared persistence
    private void save(Customer customer) {
        database.add(customer);
    }

    # Common helper for parsers
    protected final Customer fromColumns(String[] columns) {
        if (columns.length != 3) {
            throw new IllegalArgumentException("Expected 3 customer fields");
        }
        return new Customer(columns[0].trim(), columns[1].trim(), columns[2].trim());
    }

    # Optional hooks
    protected void beforeImport() {
    }

    protected void afterImport(int count) {
    }
}

Here, importData() defines the entire workflow.

Subclasses are allowed to change how lines are parsed without changing how records are validated or saved.

Step 3: CSV importer

public class CsvCustomerImporter extends CustomerImporter {
    public CsvCustomerImporter(List<Customer> database) {
        super(database);
    }

    @Override
    protected Customer parse(String line) {
        return fromColumns(line.split(",", -1));
    }

    @Override
    protected void afterImport(int count) {
        System.out.println("CSV import finished: " + count);
    }
}

Step 4: Pipe-delimited importer

public class PipeCustomerImporter extends CustomerImporter {
    public PipeCustomerImporter(List<Customer> database) {
        super(database);
    }

    @Override
    protected Customer parse(String line) {
        return fromColumns(line.split("\\|", -1));
    }

    @Override
    protected void beforeImport() {
        System.out.println("Starting pipe import");
    }
}

Step 5: Client code

void main(String[] args) {
    List<Customer> database = new ArrayList<>();
    CustomerImporter csvImporter = new CsvCustomerImporter(database);
    csvImporter.importData("""
        1,Asha,asha@example.com
        2,,invalid@example.com
        """);
    CustomerImporter pipeImporter = new PipeCustomerImporter(database);
    pipeImporter.importData("""
        3|Ravi|ravi@example.com
        4|Mina|mina@example.com
        """);
    database.forEach(System.out::println);
}

Output:

CSV import finished: 1
Starting pipe import
Customer[id=1, name=Asha, email=asha@example.com]
Customer[id=3, name=Ravi, email=ravi@example.com]
Customer[id=4, name=Mina, email=mina@example.com]

The invalid CSV record is skipped by shared validation.

For simplicity, this example uses strings and an in-memory list. Production importers should use a proper CSV parsing library for quoted/escaped fields, and consider batch persistence, transaction boundaries, error reporting, and recovery from malformed records.

Why is Template Method useful here?

Without Template Method, every importer might independently implement reading, validation, saving, and error handling.

That creates duplicated logic and increases the chance of inconsistent behavior.

With Template Method:

  • The workflow is implemented once.
  • Each format implements only its parsing logic.
  • Shared validation and persistence remain centralized.
  • Hooks allow format-specific actions.
  • New importer subclasses can reuse the same workflow without modifying it.

This supports the Open/Closed Principle: you can extend supported formats through new implementations while leaving the existing import workflow unchanged.

Example 3: Batch Processing with Guaranteed Cleanup

Template Method is also useful when an algorithm requires mandatory setup and cleanup around customizable processing.

For example, a background batch job might always need to:

  1. Open a resource.
  2. Execute job-specific logic.
  3. Close the resource, even if processing fails.
public abstract class BatchJob {
    # Template Method
    public final void execute() {
        openResource();
        try {
            process();
        } finally {
            closeResource();
        }
    }

    private void openResource() {
        System.out.println("Opening resource");
    }

    protected abstract void process();

    private void closeResource() {
        System.out.println("Closing resource");
    }
}

public class ReportJob extends BatchJob {
    @Override
    protected void process() {
        System.out.println("Generating report");
    }
}

public class CleanupJob extends BatchJob {
    @Override
    protected void process() {
        System.out.println("Removing old records");
    }
}

void main(String[] args) {
    BatchJob report = new ReportJob();
    report.execute();
    BatchJob cleanup = new CleanupJob();
    cleanup.execute();
}

Output:

Opening resource
Generating report
Closing resource
Opening resource
Removing old records
Closing resource

The important part is:

try {
    process();
} finally {
    closeResource();
}

Even if process() throws an exception, closeResource() will execute.

Because execute() is final, subclasses cannot override it to accidentally skip the cleanup defined by the base class.

This is especially useful for transaction workflows, resource management, batch jobs, and framework lifecycle operations.

Note that the example assumes openResource() succeeds. Real implementations should also manage partial initialization failures and use try-with-resources when the underlying resource supports it.

Template Method Pattern vs Strategy Pattern

Both are behavioral patterns that allow algorithms to vary, but they achieve flexibility in different ways.

FeatureTemplate MethodStrategy
Primary purposeCustomize steps of a predefined algorithmMake algorithms interchangeable
Main mechanismInheritanceComposition
Algorithm structureDefined by base classDefined by strategy implementation
Behavior changesThrough subclass overridesBy replacing strategy objects
Runtime switchingRequires choosing/replacing an implementation objectCan change a context's strategy at runtime
Best suited forWorkflows with common stepsAlternative algorithms or policies

Template Method

public abstract class PaymentProcessor {
    public final void process() {
        validate();
        authenticate();
        executePayment();
        notifyCustomer();
    }

    private void validate() {
        System.out.println("Validating");
    }

    private void notifyCustomer() {
        System.out.println("Notifying customer");
    }

    protected abstract void authenticate();

    protected abstract void executePayment();
}

Every payment processor follows the same sequence. Subclasses specialize authentication and execution.

Strategy

public interface PaymentStrategy {
    void pay(double amount);
}

public class CardPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Paying by card");
    }
}

public class UpiPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Paying by UPI");
    }
}

public class Checkout {
    private PaymentStrategy strategy;

    public void setStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void pay(double amount) {
        strategy.pay(amount);
    }
}

Here, the Checkout object can change its payment strategy at runtime without needing to be replaced.

Key distinction:

  • Template Method asks: Which steps of this predefined workflow should subclasses customize?
  • Strategy asks: Which interchangeable algorithm should this object use?

These patterns can also work together: a Template Method can orchestrate a workflow while delegating an individual step to a Strategy object.

Where Is Template Method Used in Java and Spring?

The pattern is widely used in frameworks where common processing logic is controlled by a base class.

Java Collections Framework

Java's AbstractList is an example of a skeletal implementation.

You can extend AbstractList and implement methods such as get() and size(). The base class uses those operations to provide other list functionality.

public class MyList<E> extends AbstractList<E> {
    private List<E> data;

    public MyList(List<E> data) {
        this.data = data;
    }

    @Override
    public E get(int index) {
        return data.get(index);
    }

    @Override
    public int size() {
        return data.size();
    }
}

Methods inherited from AbstractList build on the provided primitive operations. This is a related skeletal-implementation technique, although not every inherited method is a classic single template method.

Spring Framework

Spring's AbstractPlatformTransactionManager provides a practical example of template-style behavior.

It coordinates transaction management through common operations such as acquiring, committing, and rolling back transactions, while concrete transaction managers implement resource-specific operations such as doBegin(), doCommit(), and doRollback().

This allows Spring to standardize transaction handling while supporting different transaction management implementations.

A useful distinction: Spring's JdbcTemplate also standardizes common workflows, but it primarily customizes operations using callbacks and composition instead of requiring application code to subclass it. Therefore, it is closer to callback-based templating than the classic inheritance-based GoF Template Method pattern.

Advantages and Disadvantages

Advantages

  • Eliminates duplicate algorithm code.
  • Enforces a consistent sequence of operations.
  • Promotes reuse of common functionality.
  • Allows controlled customization through abstract methods and hooks.
  • Makes it easier to introduce new variants without changing shared workflow logic.

Disadvantages

  • Relies on inheritance, creating tighter coupling between base and derived classes.
  • May produce many subclasses when variations increase.
  • Changes to base-class behavior can unexpectedly affect subclasses.
  • Can be inflexible if implementations require significantly different workflows.
  • Complex inheritance hierarchies can make execution flow harder to understand.
When Should You Use Template Method?

Use Template Method when multiple implementations follow the same overall sequence but differ in one or more well-defined steps.

Typical use cases include data-import pipelines, batch jobs, report generation, document processing, application lifecycle management, transaction handling, and test execution frameworks.

Avoid it when implementations have completely different workflows or when you need to change behavior dynamically on an existing object. Composition or Strategy may be better in those cases.

Best Practices
  • Keep template methods small and meaningful. They should clearly describe the algorithm's sequence.
  • Use final for fixed workflows. This prevents subclasses from accidentally changing required sequencing.
  • Prefer protected for extension points. Abstract steps and hooks generally should not become part of the public API.
  • Minimize the number of abstract steps. Too many mandatory overrides make subclasses difficult to implement.
  • Use hooks sparingly. Hooks are useful for optional behavior, but excessive hooks make execution flow difficult to predict.
  • Enforce critical invariants in the base class. Security checks, validation requirements, or guaranteed cleanup should not depend on subclasses remembering to call super.
  • Prefer composition when flexibility increases. If you need multiple independent behaviors that can change at runtime, consider Strategy rather than building many subclasses.
Key Takeaways
  • Template Method is a behavioral design pattern that defines an algorithm's skeleton in a base class.
  • The base class controls the order and structure of operations.
  • Subclasses customize specific operations by overriding abstract methods or hooks.
  • Abstract methods represent mandatory customization points.
  • Hook methods represent optional customization points and provide default behavior.
  • The template method is commonly declared final to protect the algorithm's structure.
  • The pattern promotes code reuse through inheritance.
  • Unlike Strategy, which primarily relies on composition, Template Method uses subclassing to vary individual steps.
  • It works best when an algorithm is stable but specific steps vary across implementations.

In one sentence: Template Method lets you define what steps must happen and in what order in a base class, while allowing subclasses to determine how selected steps are performed.

public abstract class DataProcessor {
    public final void process() {
        read();
        transform();
        save();
    }

    abstract void read();
    abstract void transform();

    public void save() {
        System.out.println("Saving result");
    }
}

public class CsvProcessor extends DataProcessor {
    public void read() {System.out.println("Read CSV");}
    public void transform() {System.out.println("Transform CSV");}
}

void main() {
    DataProcessor p = new CsvProcessor();
    p.process();
}
How the Template Method works

process() is the template method and is final.

process(): fixed algorithm skeleton.

It fixes the order: read, transform, then save.

Subclasses supply the varying steps like read().

Common steps such as save stay in the base class.
