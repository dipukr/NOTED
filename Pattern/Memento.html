Memento Pattern

Memento is a behavioral design pattern that lets you save and restore the previous state of an object without exposing the details of its implementation.

The object whose state is captured is the originator; the snapshot itself is the memento; and the object that stores mementos is the caretaker.

Because the memento keeps the internal state opaque, encapsulation is preserved while still supporting undo and rollback.

When to use
  • When you need to produce snapshots of an object's state to restore later.
  • When you want undo/redo or rollback functionality.
  • When directly exposing an object's fields would break encapsulation.
  • Typical uses: text editors, transactions, game save points, and checkpoints.
Pros and Cons
Preserves Encapsulation

The saved state stays private to the originator, so internal details are never exposed.

Simplifies Originator

The originator does not have to manage its own history of states.

Easy Undo and Redo

Undo, redo, and state restoration become straightforward to implement.

Simple Caretaker

The caretaker manages snapshots without needing to know their contents.

High Memory Use

Storing many mementos can consume a large amount of memory.

Lifecycle Management

The caretaker must track the lifecycle of mementos to avoid memory leaks.

Expensive Capture

Frequent state capture of large objects can be costly in performance.

Real-world example
  • Java Serializable — serializing an object captures its state so it can be restored later, much like a memento.
  • Text editors and IDEs — undo/redo stacks store snapshots of document state to roll back edits.
  • Database transactions — savepoints and rollback restore a prior state if a transaction fails.
  • Version control (Git) — each commit is a snapshot of the project you can checkout and restore.
  • Video game save points — a save file captures the full game state so play can resume from that moment.
  • Spring Webflow — conversation/flow state is snapshotted so users can navigate back through steps.
  • Browser session restore — open tabs and their state are saved and reopened after a crash or restart.
What is the Memento Design Pattern?

The Memento Pattern is a behavioral design pattern that allows an object to capture and save its internal state at a particular point in time so that it can be restored to that state later, without exposing the object's internal implementation details.

It provides a way to implement functionality such as Undo, Redo, Save, Restore, Checkpoints, and Rollback while preserving encapsulation.

The basic idea is:

  1. An object performs some operations that change its internal state.
  2. Before changing its state, a snapshot of its current state is created.
  3. This snapshot is stored externally without exposing its internal data.
  4. Whenever required, the original object can restore its internal state using the previously saved snapshot.

In simple terms: Memento allows an object to remember its previous state and return to it later.

Real-world analogy: Text editor

Imagine working in a text editor.

StateSnapshotDocument text
1 of 3S0(empty)
2 of 3S1Hello
3 of 3S2Hello World

Each Undo or Redo restores a previously captured document state.

Suppose the following changes occur:

  1. Initial state: Empty document.
  2. First modification: User types Hello.
  3. Second modification: User types World.
  4. Undo: Document returns to Hello.
  5. Redo: Document returns to Hello World.

The editor needs to remember previous states. One way to implement this is by saving immutable snapshots of the document whenever changes are made.

This is where the Memento Pattern becomes useful.

Why do we need the Memento Pattern?

Consider a TextEditor class containing several internal fields:

public class TextEditor {
    private StringBuilder content;
    private int cursorPosition;
    private String fontFamily;
    private int fontSize;
}

Suppose we want to implement undo functionality.

A naive implementation might expose the internal fields using getters and setters, allowing a separate HistoryManager to capture and restore each property.

However, this causes several problems:

  • Encapsulation violation: The history manager needs to know the editor's internal structure.
  • Tight coupling: Whenever the editor's internal representation changes, the history manager might also need modification.
  • Incomplete restoration: Newly added fields may be forgotten during undo.
  • Mutability problems: Storing references to mutable objects may not preserve the original state.

The Memento Pattern solves these problems by making the editor responsible for creating and restoring its own snapshots.

The history manager simply stores these snapshots without understanding their contents.

Main components of the Memento Pattern

The Memento Pattern typically involves three participants:

ComponentResponsibility
OriginatorThe object whose internal state needs to be saved and restored.
MementoAn immutable snapshot representing the Originator's state at a particular moment.
CaretakerStores and manages Mementos, deciding when to save or restore states.

Class interaction diagram

Originator

The Originator is the actual object whose state is changing.

For example, in a text editor, the TextEditor class is the Originator.

Its responsibilities include capturing its current state, creating a Memento containing that state, and restoring its internal fields using an existing Memento.

Memento

A Memento is a snapshot of the Originator's internal state.

Ideally, a Memento should be immutable, and its internal fields should not be accessible to the Caretaker.

For example, a snapshot could contain:

private record Snapshot(String text, int cursorPosition) implements Memento {}

Because this is a private record, external components cannot directly access its implementation. Since both fields are immutable types, this particular snapshot is immutable.

Caretaker

The Caretaker manages the lifecycle of saved snapshots.

For example, an EditorHistory class may maintain two stacks:

Deque<Memento> undoStack;
Deque<Memento> redoStack;

The Caretaker knows when to save or restore a state, but it does not need to know how the state is represented internally.

Important distinction: The Originator understands the Memento's contents. The Caretaker treats the Memento as an opaque object.

Practical Example 1: Text Editor with Undo and Redo

Let's implement a text editor that supports:

  • Typing text at the current cursor position.
  • Moving the cursor.
  • Saving document snapshots.
  • Undoing the last modification.
  • Redoing an undone modification.
  • Clearing redo history when a new modification is made.

We'll use Java 25+, including records and pattern matching for instanceof.

Complete runnable Java implementation

void main(String[] args) {
    TextEditor editor = new TextEditor();
    EditorHistory history = new EditorHistory(editor);
    history.execute(e -> e.type("Hello")); # First modification
    history.execute(e -> e.type(" World")); # Second modification
    System.out.println(editor.getText()); # Hello World
    history.undo(); # Undo the last modification
    System.out.println(editor.getText()); # Hello
    history.redo(); # Redo the last undone modification
    System.out.println(editor.getText()); # Hello World
    history.undo(); # Undo again
    history.execute(e -> e.type(" Java")); # Make a different modification
    System.out.println(editor.getText()); # Hello Java
    System.out.println(history.redo()); # false: redo is no longer available
}

# =====================================
# ORIGINATOR
# =====================================

public class TextEditor {
    # Opaque type exposed to the caretaker
    public interface Memento {}

    # Actual snapshot implementation is private
    private record Snapshot(String text, int cursorPosition) implements Memento {}

    private StringBuilder text = new StringBuilder();
    private int cursorPosition = 0;

    public void type(String value) {
        Objects.requireNonNull(value);
        text.insert(cursorPosition, value);
        cursorPosition += value.length();
    }

    public void moveCursor(int position) {
        if (position < 0 || position > text.length()) {
            throw new IllegalArgumentException("Invalid cursor position");
        }
        cursorPosition = position;
    }

    public String getText() {
        return text.toString();
    }

    public int getCursorPosition() {
        return cursorPosition;
    }

    # Create a snapshot of the current state
    public Memento save() {
        return new Snapshot(text.toString(), cursorPosition);
    }

    # Restore state from a previous snapshot
    public void restore(Memento memento) {
        if (!(memento instanceof Snapshot snapshot)) {
            throw new IllegalArgumentException("Invalid memento");
        }
        this.text = new StringBuilder(snapshot.text());
        this.cursorPosition = snapshot.cursorPosition();
    }
}

# =====================================
# CARETAKER
# =====================================

public class EditorHistory {
    private TextEditor editor;
    private Deque<TextEditor.Memento> undoStack = new ArrayDeque<>();
    private Deque<TextEditor.Memento> redoStack = new ArrayDeque<>();

    public EditorHistory(TextEditor editor) {
        this.editor = Objects.requireNonNull(editor);
    }

    # Execute a modification and record the old state
    public void execute(Consumer<TextEditor> operation) {
        Objects.requireNonNull(operation);
        TextEditor.Memento before = editor.save();
        try {
            operation.accept(editor);
        } catch (RuntimeException | Error ex) {
            editor.restore(before);
            throw ex;
        }
        undoStack.push(before);
        redoStack.clear(); # New modification invalidates redo history
    }

    public boolean undo() {
        if (undoStack.isEmpty()) {
            return false;
        }
        redoStack.push(editor.save()); # Save current state for redo
        editor.restore(undoStack.pop()); # Restore previous state
        return true;
    }

    public boolean redo() {
        if (redoStack.isEmpty()) {
            return false;
        }
        undoStack.push(editor.save()); # Save current state for undo
        editor.restore(redoStack.pop()); # Restore the undone state
        return true;
    }
}

Understanding the implementation

Step 1: The editor captures its state

public Memento save() {
    return new Snapshot(text.toString(), cursorPosition);
}

The editor captures both its content and cursor position.

Notice that it converts StringBuilder into String. This creates an independent, immutable representation of the text rather than retaining a reference to the mutable StringBuilder.

Step 2: The history manager stores the snapshot

TextEditor.Memento before = editor.save();
operation.accept(editor);
undoStack.push(before);

Before applying an operation, the Caretaker obtains a snapshot. It then performs the modification and stores the previous state.

The Caretaker never needs to know whether the saved state contains a string, cursor position, formatting, or any other information.

Step 3: Undo restores an older state

redoStack.push(editor.save());
editor.restore(undoStack.pop());

Undo first saves the current state to the redo stack, then restores the most recent state from the undo stack.

Step 4: Redo restores the undone state

undoStack.push(editor.save());
editor.restore(redoStack.pop());

Redo does the opposite: it stores the current state for future undo and restores the previously undone state.

How the Undo and Redo stacks work internally

History timeline

StepActionEditor textUndo stack (top first)Redo stack (top first)What happens
1Initial(empty)——The document is empty; no snapshots have been stored.
2Type HelloHello(empty)—Save the empty state before inserting Hello.
3Type WorldHello WorldHello, (empty)—Save Hello before adding World.
4UndoHello(empty)Hello WorldRestore Hello and save Hello World for redo.
5RedoHello WorldHello, (empty)—Restore Hello World and put Hello back on undo history.
6Undo againHello(empty)Hello WorldReturn to Hello before branching to a new edit.
7Type JavaHello JavaHello, (empty)—New editing branch: discard all redo states.

The important distinction is that Undo and Redo are not fundamentally different operations. Both restore a previously captured state. Their difference lies in which stack supplies the snapshot and where the current state gets saved.

Why clear the redo stack after a new modification?

Consider:

Hello | v Hello World | Undo | v Hello | New edit | v Hello Java

If the user types Java after undoing World, the previous redo path is no longer valid for a conventional linear undo history.

Therefore:

redoStack.clear();

This is an undo/redo history policy implemented by the Caretaker, not a requirement of the Memento Pattern itself. More sophisticated systems can retain branches of history.

Practical Example 2: Game Checkpoint and Restore

Another common application of the Memento Pattern is a game checkpoint system.

Imagine a player with the following internal state:

  • Health: 100
  • Level: 1
  • Inventory: Sword

Before entering a dangerous area, the game saves a checkpoint. The player then takes damage, collects additional items, and advances to the next level.

If the player wants to restart from the checkpoint, the entire previous state should be restored.

Java implementation

void main(String[] args) {
    Game game = new Game();
    game.collectItem("Sword"); # Player picks up a weapon
    Game.Memento checkpoint = game.save(); # Save checkpoint
    # Player continues playing
    game.takeDamage(60);
    game.collectItem("Shield");
    game.completeLevel();
    System.out.println("After playing:");
    game.printStatus();
    game.restore(checkpoint); # Restore previous checkpoint
    System.out.println("After restoring checkpoint:");
    game.printStatus();
}

public class Game {
    public interface Memento {}

    private record Snapshot(int health, int level, List<String> inventory) implements Memento {}

    private int health = 100;
    private int level = 1;
    private List<String> inventory = new ArrayList<>();

    public void takeDamage(int damage) {
        health = Math.max(0, health - damage);
    }

    public void collectItem(String item) {
        inventory.add(item);
    }

    public void completeLevel() {
        level++;
    }

    # Create checkpoint
    public Memento save() {
        return new Snapshot(health, level, List.copyOf(inventory));
    }

    # Restore checkpoint
    public void restore(Memento memento) {
        if (!(memento instanceof Snapshot state)) {
            throw new IllegalArgumentException("Invalid checkpoint");
        }
        health = state.health();
        level = state.level();
        inventory.clear();
        inventory.addAll(state.inventory());
    }

    public void printStatus() {
        System.out.println("Health: " + health);
        System.out.println("Level: " + level);
        System.out.println("Inventory: " + inventory);
    }
}

Output

After playing:
Health: 40
Level: 2
Inventory: [Sword, Shield]

After restoring checkpoint:
Health: 100
Level: 1
Inventory: [Sword]

Important: Deep copying mutable state

Notice this statement:

List.copyOf(inventory)

We create an independent list for the snapshot.

If we had simply stored a mutable list reference, future changes to the inventory could accidentally alter the saved state.

For example, the following is dangerous:

new Snapshot(health, level, inventory); # Bad when the snapshot must remain independent

List.copyOf() gives us an unmodifiable snapshot of the list structure.

However, this is only a shallow copy of its elements. It is safe here because String is immutable. If the inventory contained mutable Item objects, we would also need to copy those items, or represent them with immutable values.

This is one of the most important considerations in implementing the Memento Pattern correctly.

How Memento preserves encapsulation

The key design principle behind Memento is that the Caretaker should not have direct access to the Originator's private state.

Consider our implementation:

public class TextEditor {
    public interface Memento {}

    private record Snapshot(String text, int cursorPosition) implements Memento {}

    public Memento save() {
        # ...
    }

    public void restore(Memento memento) {
        # ...
    }
}

The Caretaker sees only:

TextEditor.Memento snapshot = editor.save();

It cannot access:

snapshot.text();           # Not accessible
snapshot.cursorPosition(); # Not accessible

Why? Because the public Memento interface exposes no operations, and Snapshot is private to TextEditor.

Only TextEditor knows how to interpret its internal snapshot representation.

This ensures that if the editor later adds new fields, such as text alignment, font properties, or selection information, the Caretaker does not need to change.

The Originator controls what is captured and how restoration works. The Caretaker controls when snapshots are stored and restored.

Memento vs Command Pattern

Both the Memento pattern and Command pattern can implement undo functionality, but their mechanisms differ.

AspectMementoCommand
Main purposeCapture and restore object stateEncapsulate an operation as an object
Undo approachRestore a previous snapshotExecute an inverse operation or use saved undo information
StoresStateOperations and their parameters
DependenciesOriginator understands snapshotsCommands understand how to perform operations
Memory usagePotentially high for full snapshotsOften lower for small operations
Best suited forComplex state restoration, checkpointsReversible operations, command histories

Example: Undo typing

Memento approach

Memento before = editor.save();
editor.type("Hello");
editor.restore(before); # Undo

We don't need to know exactly how typing modified the document. We only need to restore the saved state.

Command approach

public interface Command {
    void execute();

    void undo();
}

public class InsertTextCommand implements Command {
    private TextEditor editor;
    private String text;

    public InsertTextCommand(TextEditor editor, String text) {
        this.editor = editor;
        this.text = text;
    }

    @Override
    public void execute() {
        editor.insert(text);
    }

    @Override
    public void undo() {
        editor.deleteInsertedText(text.length());
    }
}

The Command Pattern tries to reverse the effect of an operation. A real implementation would also record the insertion position and other information necessary to undo correctly.

In contrast, Memento simply restores the previously captured state.

Can Command and Memento be used together?

Yes. They complement each other.

For example, a command can save a Memento before it executes:

public class UpdateDocumentCommand implements Command {
    private Document document;
    private Document.Memento previousState;

    @Override
    public void execute() {
        previousState = document.save();
        document.update();
    }

    @Override
    public void undo() {
        document.restore(previousState);
    }
}

This combines the benefits of both patterns:

  • Command encapsulates the operation.
  • Memento encapsulates the state required to undo it.
  • The command does not need to implement the inverse of every internal modification.

This is especially useful for complex operations where manually reversing each change would be error-prone. Such a simple single-snapshot command assumes it is executed once before being undone; reusable commands need more careful lifecycle handling.

Memento vs Event Sourcing

Since both patterns preserve historical information, it is useful to understand how they differ.

MementoEvent Sourcing
Stores snapshots of stateStores events representing state changes
Restores an object from a snapshotReconstructs state by replaying events
Usually focused on local object restorationOften used for business state history and auditability
Doesn't explain why state changedEvents describe what happened
Can support undo and checkpointsSupports reconstruction, projections, and audit trails

For example:

Memento snapshots:

State 1: Balance = 100
State 2: Balance = 150
State 3: Balance = 120

Event Sourcing:

AccountCreated(balance=100)
MoneyDeposited(amount=50)
MoneyWithdrawn(amount=30)

Memento stores the resulting state, whereas Event Sourcing records the operations or domain events that led to the state.

A system can combine both approaches. In an event-sourced application, snapshots can accelerate recovery by avoiding the need to replay the entire event history.

However, arbitrary restoration of a snapshot is not equivalent to reversing completed business transactions. For example, restoring an old account balance cannot safely undo an actual bank transfer.

Performance considerations

Suppose a document contains 10 MB of text and we save a complete snapshot after every keystroke.

If we retain 100 snapshots, we could consume approximately 1 GB just for the saved text copies, depending on representation and sharing.

For large objects, possible optimizations include incremental snapshots, structural sharing, storing only changed portions, limiting undo history, and periodically consolidating old history.

For example, a sophisticated text editor may use a persistent data structure or piece table instead of copying the complete document after every keystroke.

The Memento Pattern does not require full copying; it requires that each saved state can be used to restore the intended earlier state correctly.

Best practices when implementing Memento
  1. Prefer immutable snapshots. Once captured, the saved state should not change. Java records work well when their components are immutable or defensively copied.
  2. Do not expose snapshot internals to the Caretaker. Use an opaque interface or another visibility mechanism that lets the Originator control state access.
  3. Capture all relevant state. If the editor stores content, cursor position, and formatting, restoring only content may result in inconsistent behavior.
  4. Manage history size. An unbounded undo stack can lead to excessive memory consumption. Use history limits or more efficient representations where necessary.
  5. Treat multi-threaded access carefully. If several threads can modify an Originator, saving and restoring snapshots must be coordinated so that a snapshot represents a consistent state.
  6. Distinguish in-memory undo from durable persistence. A Memento object held in memory disappears when the process terminates. For crash recovery, snapshots need durable storage and potentially schema-versioning support.
  7. Track all relevant modifications. In the text editor implementation, changes should go through EditorHistory.execute(). Changes made directly through editor.type() will not automatically become undoable history entries.
When should you use the Memento Pattern?

Memento is particularly suitable when an object's state must be restored later, the state is complicated, and external components should not manipulate its internal representation directly.

Common applications include:

ApplicationMemento usage
Text editors and IDEsRestore previous document states
Image editing softwareUndo previous editing states
Video gamesSave and restore checkpoints
Drawing applicationsRestore shapes, positions, and styles
Multi-step formsPreserve draft states or restore earlier input
Configuration editorsRevert to previously saved configuration
SimulationsReturn to an earlier simulation state

It may not be ideal for high-frequency changes to very large state objects when complete snapshots are prohibitively expensive. It is also not a substitute for database transactions or distributed consistency mechanisms.

Final summary

The Memento Pattern in one diagram

The Memento Design Pattern separates state ownership, state representation, and state history management into three responsibilities:

  • Originator: Creates snapshots of its internal state and knows how to restore them.
  • Memento: Holds the captured state, ideally immutably and without exposing implementation details.
  • Caretaker: Manages saved snapshots and decides when to restore them.

The most important concept is that the Caretaker does not need to understand the Originator's internal state.

Remember: Memento is about restoring an earlier state, whereas Command is primarily about encapsulating an operation. Both can support undo/redo, and they can work together.

Code
public class Editor {                       # Originator
    private String text = "";

    void type(String words) { text += words; }
    String getText() { return text; }

    Memento save() { return new Memento(text); }
    void restore(Memento m) { text = m.state; }

    public static class Memento {          # Memento
        private final String state;
        Memento(String state) { this.state = state; }
    }
}

void main() {
    Editor editor = new Editor();
    editor.type("Hello");
    Editor.Memento saved = editor.save();  # caretaker holds it
    editor.type(" World");
    editor.restore(saved);
    System.out.println(editor.getText());  # Hello
}
How the Memento works

Editor is the originator that creates and reads snapshots.

Memento stores state with its fields kept private.

save() captures state; restore() rolls it back.

The caller (caretaker) holds mementos without inspecting them.
