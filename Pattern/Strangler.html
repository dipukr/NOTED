Strangler Pattern

The Strangler pattern incrementally replaces a legacy system by building new functionality around it.

It is named after strangler vines that grow around a tree and gradually take over.

A facade routes each request to either the old system or the new replacement.

Over time, more features move to the new system until the old one can be retired.

Key points
  • Use to migrate a monolith to microservices without a big-bang rewrite.
  • A routing facade sits in front of old and new systems.
  • Facade routes traffic to new service or legacy system.
  • Migrate one capability at a time, verifying as you go.
  • Decommission the legacy system only when fully replaced.
Pros and Cons
Low-Risk Migration

Migration happens incrementally with frequent releases, keeping risk low.

Easy Rollback

Old and new systems run side by side, enabling easy rollback.

Continuous Value

The approach delivers value throughout the migration.

Dual Maintenance

Both systems must be maintained during the transition.

Facade Complexity

The routing facade adds complexity and a potential bottleneck.

Prolonged Migrations

Migrations can drag on if not driven to completion.

Code
# Facade routes traffic to new service or legacy system
@RestController
public class OrdersFacade {

    private final NewOrderService modern;
    private final LegacyClient legacy;

    public OrdersFacade(NewOrderService modern, LegacyClient legacy) {
        this.modern = modern;
        this.legacy = legacy;
    }

    @GetMapping("/orders/{id}")
    public OrderDto get(@PathVariable Long id) {
        if (modern.handles(id)) {
            return modern.find(id);   # migrated path
        }
        return legacy.find(id);       # still on old system
    }
}
How it works

The facade decides, per request, which backend serves it.

As features migrate, more calls route to modern.

Once nothing hits legacy, the old system is removed.
