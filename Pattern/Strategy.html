Strategy

Strategy is a behavioral design pattern that defines a family of related algorithms or behaviors, encapsulates each one in a separate class, and makes them interchangeable. It allows the algorithm used by an object to vary independently from the client that uses it. Instead of implementing multiple variations of a behavior directly inside the client or Context class using large if-else or switch statements, each variation is extracted into a separate Strategy implementation that follows a common interface.

Context is the class that needs some behavior or algorithm to perform its job, but does not implement that algorithm itself. The context holds a reference to a strategy object and delegates the work to it, so the behavior can be swapped at runtime.


Context = the object that uses an algorithm.

Strategy = the interface that defines the algorithm or behavior.

Concrete Strategy = the class that implements a particular version of that algorithm.

When to use
  • When you have several variants of an algorithm and want to switch between them.
  • When you want to choose an algorithm's behavior at runtime.
  • When many related classes differ only in their behavior.
  • Typical uses: sorting strategies, payment methods, compression algorithms, and routing.
Pros and Cons
Runtime Swapping

Algorithms can be swapped at runtime without changing the context.

Encapsulated Details

Isolates algorithm implementation details from the code that uses it.

Removes Conditionals

Replaces conditional logic for selecting behavior with polymorphism.

Open/Closed Principle

Follows the Open/Closed Principle, so new strategies add cleanly.

More Classes

Increases the number of objects and classes in the application.

Client Awareness

Clients must be aware of the differences to choose the right strategy.

Possible Overkill

Overkill if the algorithm rarely changes or has only one variant.

Real-world example
  • Comparator — passing different Comparator objects to Collections.sort or List.sort swaps the ordering algorithm.
  • Java layout managers — Swing containers delegate positioning to interchangeable LayoutManager strategies like BorderLayout and GridLayout.
  • Spring Resource loading — ResourceLoader picks different Resource strategies (classpath, file, URL) based on the location prefix.
  • Spring PlatformTransactionManager — the transaction behavior varies by implementation (JPA, JDBC, JTA) behind one interface.
  • Payment checkout — an online store applies card, UPI, or wallet payment strategies chosen at runtime.
  • Compression tools — an archiver selects ZIP, GZIP, or RAR compression strategies for the same file operation.
  • Navigation apps — a maps app switches between driving, walking, and transit route-calculation strategies.
What is the Strategy Design Pattern?

The Strategy Design Pattern is a behavioral design pattern that defines a family of algorithms, encapsulates each algorithm in a separate class, and makes them interchangeable.

It allows the algorithm to vary independently of the client that uses it.

Instead of implementing multiple algorithms directly inside a class using if-else or switch statements, the Strategy pattern moves each algorithm into its own class behind a common interface.

The client, often called the Context, holds a reference to a strategy object and delegates the actual work to it. The strategy can be selected or replaced at runtime without changing the Context's implementation.

Key idea: Separate what needs to be done from how it is done.

For example, consider an e-commerce application supporting multiple payment methods: UPI, credit card, and cash on delivery. Each payment method has different processing logic, but the checkout process should not need to know how each payment method works.

The Strategy pattern allows us to encapsulate each payment algorithm independently.

Problem Without the Strategy Pattern

Consider an e-commerce checkout service.

public class PaymentService {
    public void pay(String paymentMethod, double amount) {
        if (paymentMethod.equals("UPI")) {
            System.out.println("Processing UPI payment: " + amount);
        } else if (paymentMethod.equals("CARD")) {
            System.out.println("Processing Card payment: " + amount);
        } else if (paymentMethod.equals("COD")) {
            System.out.println("Processing Cash on Delivery: " + amount);
        }
    }
}

Usage:

PaymentService service = new PaymentService();
service.pay("UPI", 1000);
service.pay("CARD", 2000);

Problems with this approach

  • Violates Open/Closed Principle: Adding a new payment method requires modifying the existing PaymentService.
  • Violates Single Responsibility Principle: The class manages both checkout coordination and individual payment algorithms.
  • Tight coupling: PaymentService depends on the implementation of every payment method.
  • Difficult testing: Each payment algorithm cannot be tested as independently as a separate class.
  • Growing conditional logic: As payment methods increase, the code becomes harder to maintain.

The Strategy pattern solves these problems by separating individual payment behaviors into independent classes.

Structure of the Strategy Pattern

The Context delegates to a common Strategy interface. Each concrete strategy implements its own algorithm.

The pattern has four main participants:

ComponentResponsibility
StrategyDefines a common interface for all supported algorithms.
Concrete StrategyImplements a particular algorithm.
ContextMaintains a reference to a strategy and delegates work to it.
ClientCreates or selects the appropriate strategy and provides it to the Context.

The Context does not need to know the internal implementation of any concrete strategy. It only knows the Strategy interface.

Practical Example 1: Payment Processing in Java

We will implement the payment system using Strategy.

Step 1: Create the Strategy interface

public interface PaymentStrategy {
    void pay(BigDecimal amount);
}

The PaymentStrategy interface defines the contract that every payment method must follow.

Notice that it does not specify how a payment should be processed.

Step 2: Create Concrete Strategies

UPI Payment Strategy

public class UpiPayment implements PaymentStrategy {
    private String upiId;

    public UpiPayment(String upiId) {
        this.upiId = upiId;
    }

    @Override
    public void pay(BigDecimal amount) {
        System.out.println("Processing UPI payment of Rs. " + amount + " using " + upiId);
    }
}

Credit Card Payment Strategy

public class CardPayment implements PaymentStrategy {
    private String cardToken;

    public CardPayment(String cardToken) {
        this.cardToken = cardToken;
    }

    @Override
    public void pay(BigDecimal amount) {
        System.out.println("Processing credit card payment of Rs. " + amount);
        # In production, use cardToken with a payment gateway.
    }
}

Cash on Delivery Strategy

public class CashOnDeliveryPayment implements PaymentStrategy {
    @Override
    public void pay(BigDecimal amount) {
        System.out.println("Cash on delivery selected. Amount: Rs. " + amount);
    }
}

Each strategy encapsulates a different payment behavior.

The classes implement the same interface, making them interchangeable.

These classes demonstrate the pattern; they simulate payment processing rather than execute real financial transactions.

Step 3: Create the Context class

The Context is the class that uses a Strategy.

public class Checkout {
    private PaymentStrategy paymentStrategy;

    public Checkout(PaymentStrategy paymentStrategy) {
        this.paymentStrategy = Objects.requireNonNull(paymentStrategy);
    }

    public void setPaymentStrategy(PaymentStrategy paymentStrategy) {
        this.paymentStrategy = Objects.requireNonNull(paymentStrategy);
    }

    public void checkout(BigDecimal amount) {
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("Invalid amount");
        }
        paymentStrategy.pay(amount);
    }
}

Important observations:

  • Checkout holds a reference to the PaymentStrategy interface, not to a concrete payment class.
  • When checkout() is invoked, it delegates payment processing to the currently configured strategy:
paymentStrategy.pay(amount);

The Checkout class does not know whether the payment is processed through UPI, credit card, or cash on delivery.

This is an example of composition and polymorphism working together.

Step 4: Client code

void main(String[] args) {
    Checkout checkout = new Checkout(new UpiPayment("customer@upi"));
    checkout.checkout(new BigDecimal("1000"));
    checkout.setPaymentStrategy(new CardPayment("card-token-123")); # Change the strategy at runtime
    checkout.checkout(new BigDecimal("2000"));
    checkout.setPaymentStrategy(new CashOnDeliveryPayment()); # Change it again
    checkout.checkout(new BigDecimal("1500"));
}

Output:

Processing UPI payment of Rs. 1000 using customer@upi
Processing credit card payment of Rs. 2000
Cash on delivery selected. Amount: Rs. 1500

How does it work internally?

Runtime strategy selection

SelectedContextStrategy interfaceConcrete strategyBehavior
UPICheckout.checkout(amount)PaymentStrategy.pay(amount)UpiPaymentProcessing UPI payment
CardCheckout.checkout(amount)PaymentStrategy.pay(amount)CardPaymentProcessing card payment
CODCheckout.checkout(amount)PaymentStrategy.pay(amount)CashOnDeliveryPaymentCash on delivery selected

Only the concrete strategy changes; Checkout and PaymentStrategy remain the same.

When the client configures:

checkout.setPaymentStrategy(new CardPayment("token"));

the Checkout object now references CardPayment.

Subsequently, calling:

checkout.checkout(new BigDecimal("2000"));

results in Java's runtime polymorphism dispatching the pay() call to CardPayment.pay().

The algorithm changes without requiring any modification to Checkout.

Practical Example 2: Shipping Cost Calculation

The previous example demonstrated interchangeable behaviors. Let's consider a case where different strategies implement actual calculation algorithms.

Suppose an e-commerce application offers different shipping options:

Shipping TypeAlgorithm
Standard₹40 base + ₹10 per kg
Express₹90 base + ₹25 per kg
Store PickupFree

Instead of calculating all these shipping costs through conditional statements, we can implement each calculation as a strategy.

Strategy interface

public interface ShippingStrategy {
    BigDecimal calculateCost(BigDecimal weightInKg);
}

Concrete strategies

public class StandardShipping implements ShippingStrategy {
    @Override
    public BigDecimal calculateCost(BigDecimal weightInKg) {
        return new BigDecimal("40").add(weightInKg.multiply(new BigDecimal("10")));
    }
}

public class ExpressShipping implements ShippingStrategy {
    @Override
    public BigDecimal calculateCost(BigDecimal weightInKg) {
        return new BigDecimal("90").add(weightInKg.multiply(new BigDecimal("25")));
    }
}

public class StorePickup implements ShippingStrategy {
    @Override
    public BigDecimal calculateCost(BigDecimal weightInKg) {
        return BigDecimal.ZERO;
    }
}

Context

public class ShippingCalculator {
    private ShippingStrategy strategy;

    public ShippingCalculator(ShippingStrategy strategy) {
        this.strategy = strategy;
    }

    public void setStrategy(ShippingStrategy strategy) {
        this.strategy = strategy;
    }

    public BigDecimal calculate(BigDecimal weightInKg) {
        return strategy.calculateCost(weightInKg);
    }
}

Client

void main(String[] args) {
    ShippingCalculator calculator = new ShippingCalculator(new StandardShipping());
    BigDecimal weight = new BigDecimal("2");
    System.out.println(calculator.calculate(weight));
    calculator.setStrategy(new ExpressShipping());
    System.out.println(calculator.calculate(weight));
    calculator.setStrategy(new StorePickup());
    System.out.println(calculator.calculate(weight));
}

Output:

60
140
0

The shipping calculator performs the same high-level operation, but the selected algorithm determines the result.

Interactive shipping calculator (package weight: 2.0 kg)

Shipping strategyCalculated shipping costFormula
Standard (₹40 + ₹10/kg)₹60.00₹40 + (2 × ₹10) = ₹60
Express (₹90 + ₹25/kg)₹140.00₹90 + (2 × ₹25) = ₹140
Store Pickup (Free)₹0.00Store pickup = Free

This illustrates why the pattern is useful: the calculator stays unchanged even though shipping calculations vary significantly.

Strategy Pattern Using Java Lambdas

In modern Java, we do not always need to create a separate class for every strategy.

If the Strategy interface has only one abstract method, we can make it a functional interface and implement its strategies using lambda expressions.

@FunctionalInterface
public interface ShippingStrategy {
    BigDecimal calculateCost(BigDecimal weightInKg);
}

Now strategies can be defined as lambdas:

ShippingStrategy standard = weight -> new BigDecimal("40").add(weight.multiply(new BigDecimal("10")));
ShippingStrategy express = weight -> new BigDecimal("90").add(weight.multiply(new BigDecimal("25")));
ShippingStrategy pickup = weight -> BigDecimal.ZERO;

Usage:

ShippingCalculator calculator = new ShippingCalculator(standard);
System.out.println(calculator.calculate(new BigDecimal("2")));
calculator.setStrategy(express); # Switch algorithm at runtime
System.out.println(calculator.calculate(new BigDecimal("2")));

This is still the Strategy pattern because algorithms are interchangeable through the same interface.

When to prefer lambdas: When algorithms are small, stateless, and do not require complex dependencies. For strategies requiring extensive processing, configuration, or injected services, separate classes usually provide better organization.

Real-World Example: Strategy Pattern in Spring Boot

In Spring Boot, Strategy is commonly used for business rules such as pricing, discounts, payment processing, tax calculations, and notification delivery.

Consider a pricing application where discounts depend on customer membership.

Regular customers receive no discount, while premium customers receive a 10% discount.

A useful Spring Boot implementation is to register every strategy as a Spring bean, inject all available strategies into a service, and select the appropriate one per request.

Step 1: Define membership types

public enum CustomerTier {
    REGULAR, PREMIUM
}

Step 2: Define the Strategy interface

public interface DiscountStrategy {
    CustomerTier type();

    BigDecimal applyDiscount(BigDecimal amount);
}

The type() method tells us which membership tier the strategy supports.

Step 3: Implement Concrete Strategies

RegularDiscountStrategy.java

@Component
public class RegularDiscountStrategy implements DiscountStrategy {
    @Override
    public CustomerTier type() {
        return CustomerTier.REGULAR;
    }

    @Override
    public BigDecimal applyDiscount(BigDecimal amount) {
        return amount;
    }
}

PremiumDiscountStrategy.java

@Component
public class PremiumDiscountStrategy implements DiscountStrategy {
    @Override
    public CustomerTier type() {
        return CustomerTier.PREMIUM;
    }

    @Override
    public BigDecimal applyDiscount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.90"));
    }
}

Each concrete strategy is annotated with @Component, allowing Spring Boot to discover and manage it.

Step 4: Create the Context service

@Service
public class PricingService {
    private Map<CustomerTier, DiscountStrategy> strategies;

    public PricingService(List<DiscountStrategy> discountStrategies) {
        this.strategies = discountStrategies.stream().collect(Collectors.toUnmodifiableMap(DiscountStrategy::type,
                                                                                           Function.identity()));
    }

    public BigDecimal calculatePrice(CustomerTier tier, BigDecimal amount) {
        if (amount == null || amount.signum() < 0) {
            throw new IllegalArgumentException("Invalid amount");
        }
        DiscountStrategy strategy = strategies.get(tier);
        if (strategy == null) {
            throw new IllegalArgumentException("Unsupported customer tier: " + tier);
        }
        return strategy.applyDiscount(amount).setScale(2, RoundingMode.HALF_UP);
    }
}

Required imports for these snippets include java.math.BigDecimal, java.math.RoundingMode, java.util.List, java.util.Map, java.util.function.Function, java.util.stream.Collectors, and the corresponding Spring annotations.

What's happening here?

Spring Boot automatically discovers the beans implementing DiscountStrategy:

RegularDiscountStrategy
PremiumDiscountStrategy

Through constructor injection:

public PricingService(List<DiscountStrategy> discountStrategies)

Spring supplies those strategies as a list.

We then convert the list into a map:

REGULAR  → RegularDiscountStrategy
PREMIUM  → PremiumDiscountStrategy

During a request, the service selects the appropriate strategy:

DiscountStrategy strategy = strategies.get(tier);

And delegates the actual business logic:

strategy.applyDiscount(amount);

This eliminates the need to maintain an if-else chain containing separate discount algorithms.

Step 5: Expose a REST API

@RestController
@RequestMapping("/prices")
public class PricingController {
    private PricingService pricingService;

    public PricingController(PricingService pricingService) {
        this.pricingService = pricingService;
    }

    @GetMapping
    public BigDecimal getPrice(@RequestParam CustomerTier tier, @RequestParam BigDecimal amount) {
        return pricingService.calculatePrice(tier, amount);
    }
}

Example request:

GET /prices?tier=PREMIUM&amount=1000

Response:

900.00

The controller does not know how the discount is calculated. The service does not implement the discount calculation itself. The selected DiscountStrategy handles it.

Why is this approach useful in Spring Boot?

A Spring @Service bean is generally a singleton by default. If we stored a mutable strategy field and changed it for every incoming request, concurrent requests could interfere with one another.

For example, this approach is problematic:

# Avoid request-specific mutation in a singleton service
private DiscountStrategy currentStrategy;

public void setStrategy(DiscountStrategy strategy) {
    this.currentStrategy = strategy;
}

Two simultaneous requests could overwrite the same field.

Our Spring Boot implementation instead stores an immutable mapping of strategies and chooses a local strategy reference for each request.

That makes strategy selection naturally safer for concurrent web requests, provided the individual strategies are also thread-safe.

Strategy vs State Design Pattern

Strategy and State have very similar class structures. Both use composition and polymorphism to delegate behavior.

However, their intentions are different.

AspectStrategy PatternState Pattern
PurposeSwitch between different algorithmsChange behavior according to an object's internal state
SelectionTypically chosen by client or application logicDetermined by the object's current state and transitions
Behavior changesDifferent ways to perform an operationDifferent behavior at different lifecycle stages
TransitionsNo state-transition requirementState transitions are central to the pattern
ExampleUPI vs credit card paymentOrder: Created → Paid → Shipped
Main questionHow should this operation be performed?What should this object do in its current state?

For example, selecting UPI or a credit card is a Strategy concern because both are different methods of performing payment.

An order moving from CREATED to PAID to SHIPPED is a State concern because its behavior depends on its lifecycle state.

Strategy vs Template Method

Both patterns allow varying algorithms, but they achieve this differently.

AspectStrategyTemplate Method
Primary mechanismCompositionInheritance
Algorithm variationReplace a complete algorithm implementationOverride particular steps of an algorithm
Runtime flexibilityStrategies can be swapped dynamicallyBehavior is generally fixed by the concrete subclass
Shared structureCommon interfaceBase-class template method
ExampleSelecting different payment algorithmsDifferent report generators following the same workflow

Strategy is typically more appropriate when you want complete algorithms to be interchangeable.

Template Method is useful when multiple algorithms share a fixed sequence of steps, but particular steps vary between subclasses.

Advantages and Disadvantages
AdvantagesDisadvantages
Eliminates large conditional branches for alternative algorithmsCan introduce more classes and interfaces
Supports Open/Closed Principle for algorithm implementationsClient still needs a way to select a strategy
Encourages composition over inheritanceAdds abstraction for even simple behaviors
Allows changing behavior at runtimeStrategies may require additional input or dependencies
Improves unit testing and isolationShared context data may complicate interface design
Keeps Context independent of concrete algorithmsCan be unnecessary if there are only trivial alternatives

One important distinction: the Strategy pattern does not mean all conditional statements disappear. A selection mechanism may still be required, such as a factory, registry, configuration map, or user preference. The important improvement is that the algorithm implementations are no longer embedded in the Context.

When Should You Use Strategy?

Strategy is especially useful when a system has multiple ways to accomplish the same task, and those ways need to evolve independently.

Common real-world uses include:

DomainPossible Strategies
Payment processingUPI, credit card, net banking
ShippingStandard, express, pickup
AuthenticationPassword, OAuth, API key
CompressionZIP, GZIP, LZ4
SortingDifferent sorting algorithms
NotificationsEmail, SMS, push notifications
PricingRegular, premium, promotional pricing
Data exportCSV, JSON, XML
RoutingFastest route, shortest route, lowest-cost route
Retry policiesFixed delay, exponential backoff, no retry

Not every group of alternative implementations needs the Strategy pattern. It is most valuable when the variations represent meaningful algorithms or business rules, rather than simple differences in configuration data.

Strategy Pattern and SOLID Principles

The Strategy pattern illustrates several important object-oriented design principles.

  • Single Responsibility Principle (SRP): Each concrete strategy is responsible for one particular algorithm, while the Context coordinates its use.
  • Open/Closed Principle (OCP): New algorithms can be introduced through additional implementations without modifying the Context's algorithm-execution logic. Some selection mechanisms may still require configuration changes.
  • Dependency Inversion Principle (DIP): The Context depends on an abstraction such as PaymentStrategy, rather than depending directly on UpiPayment or CardPayment.
  • Composition over Inheritance: The Context composes a strategy object instead of inheriting and overriding behavior for every possible algorithm variation.
Important Design Consideration: Strategy vs Factory

These patterns are often combined but solve different problems.

A Factory decides which object to create. A Strategy defines how interchangeable algorithms are used.

For example:

PaymentStrategy strategy = paymentFactory.create("UPI");
Checkout checkout = new Checkout(strategy);
checkout.checkout(new BigDecimal("1000"));

Here, paymentFactory handles strategy creation, while Checkout uses that strategy without knowing its concrete implementation.

A factory is optional. Strategies can also be supplied directly, injected through Spring, or selected from a registry.

Summary

The Strategy Design Pattern allows an object to delegate an operation to one of several interchangeable algorithms rather than implementing all possible algorithms itself.

The central structure is:

public interface Strategy {
    void execute();
}

public class ConcreteStrategyA implements Strategy {
    public void execute() {
        # Algorithm A
    }
}

public class ConcreteStrategyB implements Strategy {
    public void execute() {
        # Algorithm B
    }
}

public class Context {
    private Strategy strategy;

    Context(Strategy strategy) {
        this.strategy = strategy;
    }

    void performOperation() {
        strategy.execute();
    }
}

The most important line is:

strategy.execute();

The Context delegates behavior to an abstraction, and Java's runtime polymorphism determines which implementation executes.

Remember the distinction:

  • Strategy: Different algorithms for the same operation.
  • State: Different behavior depending on the object's current state.
  • Template Method: Different implementations of specific steps within a fixed algorithm structure.
  • Factory: Different ways to create or select objects.

The biggest benefit of Strategy is that the algorithm can change without requiring the code that uses the algorithm to change.

Key Takeaways: Strategy Design Pattern
  1. Behavioral Design Pattern: Strategy defines a family of algorithms, encapsulates each algorithm in a separate class, and makes them interchangeable.
  2. Encapsulates Algorithms: Each concrete strategy implements a specific algorithm behind a common interface, allowing algorithms to evolve independently.
  3. Composition over Inheritance: The Context holds a reference to a Strategy interface and delegates operations to it instead of implementing algorithms itself.
  4. Runtime Flexibility: Strategies can be selected or replaced dynamically at runtime without modifying the Context's implementation.
  5. Loose Coupling: The Context depends on the Strategy abstraction rather than concrete implementations, making the system easier to extend, maintain, and test.
  6. Open/Closed Principle: New algorithms can be introduced by adding new Strategy implementations without changing the Context's algorithm-execution logic.
  7. Eliminates Complex Conditionals: Replaces large if-else or switch blocks containing different algorithms with polymorphic method calls. Strategy selection may still require conditional logic.
  8. Context vs Strategy:
    • Context: Defines what operation needs to be performed and delegates its execution.
    • Strategy: Defines how that operation is performed.
    • Concrete Strategies: Provide different implementations of the operation.
  9. Strategy vs State: Strategy focuses on selecting different algorithms, whereas State focuses on changing an object's behavior based on its internal state and lifecycle transitions.
  10. Real-World Applications: Payment processing, discount calculation, shipping methods, authentication, compression, sorting, notification delivery, and retry policies.

Core principle: The Strategy pattern separates what needs to be done from how it is done, allowing behavior to vary independently of the Context that uses it.
