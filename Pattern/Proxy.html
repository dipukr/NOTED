Proxy

The Proxy Design Pattern is a structural design pattern that provides a substitute or placeholder for another object to control access to it. Instead of allowing the client to interact directly with the real object, the Proxy Pattern introduces
an intermediate object (called a proxy) that implements the same interface as the real object.

The proxy intercepts requests from the client and may perform additional operations before or after delegating those requests to the real object.

These additional operations can include:

  • Access Control: Restrict access to certain operations based on permissions.
  • Lazy Initialization: Delay the creation of expensive objects until they are actually needed.
  • Caching: Store previously computed results to avoid repeated expensive operations.
  • Logging and Monitoring: Record method calls, execution times, and other information.
  • Remote Communication: Represent an object residing on another server or process.
  • Resource Management: Manage the lifecycle of an object or its associated resources.

The key idea is that the client interacts with the proxy as though it were the real object, without needing to know the difference.

Understanding the Problem

Consider a video streaming application such as YouTube.

When a user opens a page containing 100 videos, displaying their titles and thumbnails does not require downloading all 100 video files immediately.

If the application eagerly downloads every video, it wastes network bandwidth, memory, and processing time.

Instead, we can introduce a proxy:

  1. The application creates lightweight video proxy objects.
  2. Each proxy stores information identifying its video.
  3. The actual video is not loaded immediately.
  4. When the user clicks Play, the proxy loads the real video and delegates playback to it.
  5. Subsequent playback requests can reuse the loaded video.

This is an example of a Virtual Proxy, which delays expensive object initialization.

Without Proxy

The client directly creates and accesses the expensive object.

With Proxy

The proxy acts as a controlled gateway to the real object. Depending on the implementation, it may execute the request itself, return a cached result, deny the request, or forward it to the real object.

Structure of the Proxy Pattern

The Proxy Pattern generally contains four participants:

ComponentResponsibility
SubjectDefines the common interface used by both proxy and real object.
RealSubjectPerforms the actual business operation.
ProxyImplements the Subject interface, controls access, and delegates to the RealSubject.
ClientUses the Subject interface without depending on the concrete implementation.

A basic implementation looks like this:

public interface Service {
    void execute();
}

public class RealService implements Service {
    @Override
    public void execute() {
        System.out.println("Executing actual operation");
    }
}

public class ServiceProxy implements Service {
    private Service realService;

    public ServiceProxy(Service realService) {
        this.realService = realService;
    }

    @Override
    public void execute() {
        System.out.println("Before execution");
        realService.execute();
        System.out.println("After execution");
    }
}

void main(String[] args) {
    Service service = new ServiceProxy(new RealService());
    service.execute();
}

Output:

Before execution
Executing actual operation
After execution

Notice that the client depends only on Service. Whether it receives a RealService or a ServiceProxy, it uses the same execute method.

This makes it possible to introduce a proxy without changing the client's core business logic.

Practical Example: Virtual Proxy (Lazy Loading)

A Virtual Proxy delays the creation of an expensive object until that object is actually required.

Imagine an image-viewing application. Loading a high-resolution image may involve reading a large file from disk or downloading it from a server. We don't want to load every image at startup.

public interface Image {
    void display();
}

public class RealImage implements Image {
    private String filename;

    public RealImage(String filename) {
        this.filename = filename;
        loadImage();
    }

    private void loadImage() {
        System.out.println("Loading image: " + filename); # Expensive disk or network operation
    }

    @Override
    public void display() {
        System.out.println("Displaying: " + filename);
    }
}

public class ImageProxy implements Image {
    private String filename;
    private RealImage realImage;

    public ImageProxy(String filename) {
        this.filename = filename;
    }

    @Override
    public synchronized void display() {
        if (realImage == null) # Create the real object only when needed
            realImage = new RealImage(filename);
        realImage.display(); # Delegate to the real object
    }
}

void main(String[] args) {
    Image image = new ImageProxy("photo.jpg");
    System.out.println("Proxy created");
    System.out.println("First display:");
    image.display();
    System.out.println("Second display:");
    image.display();
}

Output:

Proxy created
First display:
Loading image: photo.jpg
Displaying: photo.jpg
Second display:
Displaying: photo.jpg

How it works: Object lifecycle

StepWhat happensResult
Proxy is creatednew ImageProxy("photo.jpg")Only the filename is stored. No image is loaded.
First display() callRealImage createdImage is loaded and displayed.
Second display() callExisting instance reusedNo additional loading required.

The proxy holds a reference to RealImage, but it doesn't initialize that reference until the first call to display.

Synchronized keyword prevents concurrent callers from initializing multiple real images in this simple implementation.

Real-world applications: Image galleries, video players, large document viewers, ORM lazy loading, and expensive service clients.

An important distinction: lazy loading is about when the object is initialized. Caching is about whether previously computed results can be reused. A virtual proxy may retain its loaded object, but that is different from caching the result of arbitrary operations.

Practical Example: Protection Proxy (Access Control)

A Protection Proxy controls which clients can access an object or perform certain operations.

Consider a document management system where:

  • Regular users can read documents.
  • Administrators can read and delete documents.
  • Unauthorized deletion attempts must be rejected before the real service is invoked.

Rather than embedding authorization into every business service, a proxy can enforce the access policy.

Java implementation

ProtectionProxyDemo.java

public interface DocumentService {
    String read(String docId);
    void delete(String docId);
}

public class RealDocumentService implements DocumentService {
    private Map<String, String> documents = new ConcurrentHashMap<>(Map.of("doc1", "Confidential Report"));

    @Override
    public String read(String docId) {
        return documents.get(docId);
    }

    @Override
    public void delete(String docId) {
        documents.remove(docId);
        System.out.println("Document deleted");
    }
}

public enum Role {
    USER, ADMIN
}

public class DocumentServiceProxy implements DocumentService {
    private DocumentService realService;
    private Role role;

    public DocumentServiceProxy(DocumentService realService, Role role) {
        this.realService = realService;
        this.role = role;
    }

    @Override
    public String read(String docId) {
        return realService.read(docId);
    }

    @Override
    public void delete(String docId) {
        if (role != Role.ADMIN)
            throw new SecurityException("Only admins can delete documents");
        realService.delete(docId);
    }
}

void main(String[] args) {
    DocumentService realService = new RealDocumentService();
    DocumentService user = new DocumentServiceProxy(realService, Role.USER);
    DocumentService admin = new DocumentServiceProxy(realService, Role.ADMIN);
    System.out.println(user.read("doc1"));
    try {
        user.delete("doc1");
    } catch (SecurityException e) {
        System.out.println(e.getMessage());
    }
    admin.delete("doc1");
}

Output:

Confidential Report
Only admins can delete documents
Document deleted

What is happening?

When user.delete("doc1") is executed:

The real service never receives the unauthorized delete request.

This separates two responsibilities:

  • RealDocumentService handles document operations.
  • DocumentServiceProxy handles access control.

For a production system, the proxy should obtain identity and permissions from a trusted, authenticated security context, not an unverified role supplied by the client. All protected entry points must enforce authorization.

Real-world applications: Role-based APIs, administrative operations, file access permissions, and method-level security in Spring applications.

Practical Example: Caching Proxy with Logging

A Caching Proxy stores previously retrieved results so that repeated requests can be served without calling the expensive real service.

This is particularly useful for database queries, external API calls, or computationally expensive operations.

Suppose we have a product catalog service.

Without caching, every request goes to the database:

getProduct(101) -> Database
getProduct(101) -> Database
getProduct(101) -> Database

With a caching proxy:

getProduct(101) -> Cache Miss -> Database
getProduct(101) -> Cache Hit
getProduct(101) -> Cache Hit

Here we will combine two different proxies: a caching proxy and a logging proxy.

public record Product(long id, String name) {}

public interface ProductService {
    Optional<Product> findById(long id);
}

public class DatabaseProductService implements ProductService {
    private Map<Long, Product> database = Map.of(101L, new Product(101, "Laptop"), 102L, new Product(102, "Keyboard"));

    @Override
    public Optional<Product> findById(long id) {
        System.out.println("Querying database: " + id);
        return Optional.ofNullable(database.get(id));
    }
}

public class CachingProductProxy implements ProductService {
    private ProductService realService;
    private Map<Long, Optional<Product>> cache = new ConcurrentHashMap<>();

    public CachingProductProxy(ProductService realService) {
        this.realService = realService;
    }

    @Override
    public Optional<Product> findById(long id) {
        return cache.computeIfAbsent(id, key -> {
            System.out.println("Cache miss: " + key);
            return realService.findById(key);
        });
    }
}

public class LoggingProductProxy implements ProductService {
    private ProductService delegate;

    public LoggingProductProxy(ProductService delegate) {
        this.delegate = delegate;
    }

    @Override
    public Optional<Product> findById(long id) {
        System.out.println("Request: " + id);
        Optional<Product> result = delegate.findById(id);
        System.out.println("Response: " + result);
        return result;
    }
}

void main(String[] args) {
    ProductService service = new LoggingProductProxy(new CachingProductProxy(new DatabaseProductService()));
    service.findById(101);
    service.findById(101);
    service.findById(102);
}

Output (simplified):

Request: 101
Cache miss: 101
Querying database: 101
Response: Optional[Product[id=101, name=Laptop]]

Request: 101
Response: Optional[Product[id=101, name=Laptop]]

Request: 102
Cache miss: 102
Querying database: 102
Response: Optional[Product[id=102, name=Keyboard]]

How the proxies are composed

This demonstrates an important property of proxies: multiple proxies can be chained because they implement the same interface.

The client only needs the ProductService interface, and each proxy introduces an independent behavior.

In this example, computeIfAbsent gives an atomic per-key computation with ConcurrentHashMap, avoiding duplicate cache initialization for the same key under normal concurrent access. The Optional wrapper allows missing products
to be cached as well.

Production considerations

The example intentionally keeps caching simple. A production caching proxy should usually handle:

  • Cache expiration (TTL).
  • Cache invalidation when products are updated or deleted.
  • Maximum cache size and eviction.
  • Database or API failures.
  • Monitoring cache-hit ratios.
  • Distributed caching when multiple application instances need shared cached data.

For Java, libraries such as Caffeine and integrations such as Spring Cache offer more complete cache management.

Practical Example: Remote Proxy (Microservices Communication)

A Remote Proxy represents an object located in another process, machine, or server.

The client interacts with the proxy through an ordinary Java interface. The proxy translates method calls into network requests and converts responses back into a form usable by the client.

Consider two microservices:

  • Order Service: Needs to retrieve order status.
  • Order Management Service: Owns and manages orders.

Instead of embedding HTTP communication code throughout the app, we can encapsulate it inside a remote proxy.

Architecture

public interface OrderService {
    String getOrderStatus(long orderId) throws IOException, InterruptedException;
}

public class RemoteOrderServiceProxy implements OrderService {
    private HttpClient httpClient;
    private URI baseUri;

    public RemoteOrderServiceProxy(String baseUrl) {
        this.baseUri = URI.create(baseUrl);
        this.httpClient = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(3)).build();
    }

    @Override
    public String getOrderStatus(long orderId) throws IOException, InterruptedException {
        URI uri = baseUri.resolve("orders/" + orderId + "/status");
        HttpRequest request = HttpRequest.newBuilder().uri(uri).timeout(Duration.ofSeconds(5)).GET().build();
        HttpResponse<String> response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
        if (response.statusCode() != 200)
            throw new IOException("Remote service returned HTTP " + response.statusCode());
        return response.body();
    }
}

void main(String[] args) throws Exception {
    OrderService orderService = new RemoteOrderServiceProxy("http://localhost:8081/api/");
    String status = orderService.getOrderStatus(1001);
    System.out.println("Order status: " + status);
}

Assume the remote service exposes:

GET http://localhost:8081/api/orders/1001/status

Response:

SHIPPED

The client simply calls:

orderService.getOrderStatus(1001);

It doesn't need to construct HTTP requests, manage the HTTP client, or interpret the HTTP status code directly.

Why is this a Proxy?

Because RemoteOrderServiceProxy implements the same OrderService interface expected by the client, while performing the actual operation by communicating with a remote service.

Unlike a local object, a remote service can have network latency, timeouts, partial failures, and independent availability. A remote proxy hides communication mechanics, but callers still need to handle those failure conditions.

In real-world systems, remote proxies may additionally provide retries, authentication, load balancing, circuit breaking, tracing, and response serialization. Retries must be designed carefully, especially for operations that change data.

Framework examples: Java RMI, gRPC clients, Spring HTTP Service Clients, Spring Cloud OpenFeign, and other RPC client stubs.

Practical Example: Dynamic Proxy in Java

The previous examples used static proxies.

A static proxy is a class that we manually create to implement the same interface as a real service.

For example:

public class LoggingProductProxy implements ProductService {
    # Manually implemented proxy
}

But what happens if we have hundreds of interfaces and want to apply the same logging behavior to all of them?

Creating a separate logging proxy class for every interface would involve substantial repetitive code.

Java provides Dynamic Proxy, which allows us to create proxy objects at runtime.

The key APIs are:

  • java.lang.reflect.Proxy
  • java.lang.reflect.InvocationHandler
  • java.lang.reflect.Method

Dynamic logging proxy

public interface PaymentService {
    void pay(long amountPaise);
}

public class RealPaymentService implements PaymentService {
    public void pay(long amountPaise) {
        System.out.println("Processing payment of " + amountPaise + " paise");
    }
}

void main(String[] args) {
    PaymentService realService = new RealPaymentService();
    InvocationHandler handler = (proxy, method, methodArgs) -> {
        System.out.println("Before: " + method.getName());
        try {
            Object result = method.invoke(realService, methodArgs);
            System.out.println("After: " + method.getName());
            return result;
        } catch (InvocationTargetException e) {
            throw e.getCause();
        }
    };
    # Create proxy dynamically at runtime
    PaymentService proxy = (PaymentService) Proxy.newProxyInstance(PaymentService.class.getClassLoader(),
                                                                   new Class<?>[] {PaymentService.class}, handler);
    proxy.pay(50000);
}

Output:

Before: pay
Processing payment of 50000 paise
After: pay

How does the Dynamic Proxy work

When the client invokes:

proxy.pay(50000);

The following happens:

  1. Java routes the interface method call to the generated proxy object.
  2. The proxy invokes the InvocationHandler.
  3. The handler receives the method information and arguments.
  4. The handler executes the logging logic.
  5. method.invoke(realService, methodArgs) invokes the real service.
  6. The handler returns the result to the client.

We can reuse the same concept for many different interfaces, rather than writing a proxy implementation for each one.

Static Proxy vs Dynamic Proxy

FeatureStatic ProxyDynamic Proxy
CreationManually implementedGenerated at runtime
BoilerplateMoreLess
Type safetyCompile-time delegationReflection-based invocation
FlexibilityTailored to one interfaceReusable for many interfaces
Common useLazy loading, specialized cachingAOP, tracing, generic interception

Java's built-in JDK dynamic proxies operate through interfaces. Frameworks can also create subclass-based proxies using code-generation techniques, subject to limitations around final classes, final methods, and other language constraints.

Practical Example: Dynamic Proxy Using Annotations

The previous dynamic proxy logged every method. Real frameworks are more selective: they add behavior only to methods marked with an annotation, such as Spring's @Transactional or @Cacheable.

We can build the same idea ourselves. A custom @Timed annotation marks the methods whose execution time should be measured, and an InvocationHandler reads that annotation at runtime to decide whether to add timing or simply pass the call through.

Define the Annotation

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Timed {
}

@Retention(RetentionPolicy.RUNTIME) is essential. Without it, the annotation is discarded by the compiler and
is invisible to reflection, so the proxy could never find it.

@Target(ElementType.METHOD) restricts the annotation to methods.

Define the interface and annotate the implementation

public interface OrderService {
    void placeOrder(String orderId);
    String getStatus(String orderId);
}

public class OrderServiceImpl implements OrderService {
    @Timed
    @Override
    public void placeOrder(String orderId) {
        System.out.println("Placing order: " + orderId);
        simulateWork(200);
    }

    @Override
    public String getStatus(String orderId) {
        return "SHIPPED";
    }

    public void simulateWork(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

Only placeOrder() carries @Timed. The getStatus() method is not annotated, so the proxy should leave it alone.

Create an annotation-aware InvocationHandler

public class TimedInvocationHandler implements InvocationHandler {
    public Object target;

    public TimedInvocationHandler(Object target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        # The proxy receives the interface method; annotations live on the implementation
        Method targetMethod = target.getClass().getMethod(method.getName(), method.getParameterTypes());
        if (!targetMethod.isAnnotationPresent(Timed.class)) {
            return invokeTarget(method, args); # Not annotated: pass straight through
        }
        long start = System.nanoTime();
        try {
            return invokeTarget(method, args);
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println(method.getName() + " took " + elapsedMs + " ms");
        }
    }

    private Object invokeTarget(Method method, Object[] args) throws Throwable {
        try {
            return method.invoke(target, args);
        } catch (InvocationTargetException e) {
            throw e.getCause(); # Rethrow the real exception, not the reflection wrapper
        }
    }
}

Create a small proxy factory

public class ProxyFactory {
    @SuppressWarnings("unchecked")
    public static <T> T create(T target, Class<T> type) {
        return (T) Proxy.newProxyInstance(type.getClassLoader(), new Class<?>[] { type },
                                          new TimedInvocationHandler(target));
    }
}

The factory hides the reflection boilerplate. Callers ask for an OrderService and receive a proxy that looks exactly alike.

Client code

void main(String[] args) {
    OrderService service = ProxyFactory.create(new OrderServiceImpl(), OrderService.class);
    service.placeOrder("ORD-101");
    System.out.println("Status: " + service.getStatus("ORD-101"));
}

Output:

Placing order: ORD-101
placeOrder took 201 ms
Status: SHIPPED

Measured time varies slightly from run to run. Notice that getStatus produced no timing line as it is not annotated.

How it works

The client calls service.placeOrder("ORD-101")
The call goes to the generated proxy, not directly to OrderServiceImpl.
The proxy calls TimedInvocationHandler.invoke()
It receives the interface Method and the arguments.
The handler looks up the implementation method
getMethod() finds OrderServiceImpl.placeOrder(String), where @Timed is declared.
The handler checks for @Timed
If it is present, the call is wrapped with timing; otherwise it is passed straight through.
The real method runs
method.invoke(target,args) calls OrderServiceImpl and the result or exception is returned to the client.

Why look up the implementation method? The Method passed to invoke() belongs to the interface. Annotations on the implementation class are not visible on it. An alternative is to place @Timed on the interface method instead, then check method.isAnnotationPresent(Timed.class) directly.

Things to keep in mind

  • Interfaces only: JDK dynamic proxies can only implement interfaces. Proxying a concrete class needs a bytecode library such as ByteBuddy, which is what frameworks like Spring use internally.
  • Self-invocation bypasses the proxy: if placeOrder called another @Timed method on this, that inner call would not be timed, for the same reason as the Spring self-invocation problem.
  • Reflection cost: every call goes through reflection. Production code usually caches the annotation lookup per Method instead of repeating getMethod on each call.

This is the same mechanism behind Spring annotations such as @Transactional, @Cacheable and @Async: a proxy intercepts the call, inspects the method's annotations, and decides what extra behavior to apply around the real method.

Proxy Pattern in Spring Boot

One of the most important real-world applications of proxies in Java is Spring AOP (Aspect-Oriented Programming).

Spring commonly uses proxies to apply cross-cutting behavior to service methods.

Examples include:

  • @Transactional — transaction management.
  • @Cacheable — caching method results.
  • @Async — asynchronous method execution.
  • Method security annotations such as @PreAuthorize — access control.

Example: Spring transaction management

@Service
public class OrderService {
    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        paymentRepository.save(new Payment(order.getId()));
    }
}

Assuming Spring transaction management is enabled and this bean is invoked through its Spring proxy, Spring can wrap the method call in a transaction.

Conceptually:

You did not manually create the proxy. Spring creates and manages it.

A simplified conceptual implementation would look like:

public class TransactionalOrderServiceProxy implements OrderService {
    private OrderService target;
    private TransactionManager transactionManager;

    public void placeOrder(Order order) {
        transactionManager.begin();
        try {
            target.placeOrder(order);
            transactionManager.commit();
        } catch (RuntimeException | Error e) {
            transactionManager.rollback();
            throw e;
        }
    }
}

This is illustrative pseudocode showing the proxy's responsibility, not a replacement for Spring's transaction implementation.

Important: The Spring self-invocation problem

One subtle limitation of Spring's proxy-based AOP is that calls made from one method to another method on the same object may bypass the proxy. For example:

@Service
public class ProductService {
    public Product loadProduct(Long id) {
        return findById(id);
    }

    @Cacheable("products")
    public Product findById(Long id) {
        return repository.findById(id).orElseThrow();
    }
}

If another Spring bean calls:

productService.loadProduct(101L);

The call to loadProduct goes through the proxy, but the internal call to findById is made on the target object itself.

As a result, the @Cacheable advice on findById is not applied through that internal call.

A common solution is to move the cached method into a separate Spring bean, then inject that bean.

This illustrates why understanding the Proxy Pattern is useful for understanding how Spring works internally.

Proxy vs Decorator vs Adapter vs Facade

These structural patterns can look similar because they all introduce an intermediate object or interface.
Their intentions, however, are different.

PatternPrimary PurposeInterface
ProxyControl access to an objectGenerally the same as the real object
DecoratorAdd or combine responsibilities dynamicallySame as the wrapped object
AdapterMake incompatible interfaces work togetherExposes a different interface
FacadeSimplify access to a complex subsystemExposes a simplified interface

Proxy vs Decorator

This distinction is especially important because both patterns may use nearly identical code.

Consider:

public interface DataService {
    String getData();
}

A caching proxy might look like:

public class CachingProxy implements DataService {
    private DataService target;
    # Intercepts and potentially avoids expensive calls
}

A decorator might look like:

public class EncryptionDecorator implements DataService {
    private DataService target;
    # Adds encryption-related behavior
}

Both implement DataService, both wrap another object, and both can intercept method calls.

The difference is the intention:

  • Proxy: Controls access to the underlying object. It may avoid invoking the real object entirely, as in caching, or restrict access, as in authorization.
  • Decorator: Adds responsibilities to an object while preserving its interface. Decorators are often composed to build combinations of functionality.

There is overlap. A logging wrapper, for instance, can reasonably be viewed as a logging proxy or a decorator, depending on its intended role and architecture.

Proxy vs Adapter

An Adapter changes how an interface is presented.

For example:

Existing external interface

public interface LegacyPaymentGateway {
    void makeTransaction(long amount);
}

Interface expected by the client

public interface PaymentService {
    void pay(long amount);
}

An Adapter translates pay into makeTransaction.

A Proxy, in contrast, would normally implement the same interface as the payment service it controls.

Advantages and Disadvantages

Advantages

  • Separation of concerns: Business code remains focused on business logic.
  • Lazy initialization: Expensive objects are created only when needed.
  • Better performance: Caching can reduce repeated computation and I/O.
  • Improved security: Sensitive operations can be guarded.
  • Transparency: Existing clients can often use the proxy without changes.
  • Centralized cross-cutting functionality: Logging, metrics, authorization and other behaviors can be applied consistently.

Disadvantages

  • Adds extra classes or runtime interception mechanisms.
  • May introduce latency or overhead.
  • Makes debugging and tracing call paths more complex.
  • Caching proxies require invalidation and consistency strategies.
  • Lazy initialization can introduce concurrency issues.
  • Remote proxies can make expensive network operations appear deceptively similar to local method calls.
  • Improper proxy configuration may cause security or transactional advice to be bypassed.
When Should You Use the Proxy Pattern

The Proxy Pattern is useful when you want to introduce an intermediate layer between a client and the actual service without requiring the client to handle that intermediate logic.

Some practical scenarios:

ScenarioSuitable Proxy
Load a large PDF only when the user opens itVirtual Proxy
Only admins can delete recordsProtection Proxy
Avoid repeatedly querying unchanged dataCaching Proxy
Log execution times of repository methodsLogging Proxy
Make RPC calls through a local Java interfaceRemote Proxy
Apply transaction management around service methodsDynamic/AOP Proxy

Do not introduce a proxy simply to add another abstraction. If an ordinary service method or a small helper is sufficient, an extra indirection may increase complexity without providing meaningful benefit.

Key Takeaways
  • The Proxy Pattern is a structural design pattern that introduces a substitute object to control access to a real object.
  • The proxy and the real object generally implement the same interface, allowing the client to interact with either one.
  • A proxy may execute additional operations before or after delegating to the real object, or it may avoid delegation entirely.
  • Common types include Virtual, Protection, Caching, Logging, and Remote proxies.
  • Java supports both manually implemented static proxies and runtime-generated dynamic proxies.
  • Spring AOP is a major practical application of proxy-based interception in Java.
  • Proxy and Decorator may share the same structure, but Proxy emphasizes controlled access while Decorator emphasizes extending responsibilities.

In one sentence: The Proxy Pattern provides a controlled intermediary between the client and the real object, allowing us to introduce behaviors such as lazy loading, caching, security, logging, and remote communication without substantially changing how clients interact with the object.
