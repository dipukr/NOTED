Mediator Pattern

Mediator is a behavioral design pattern that promotes loose coupling between objects by centralizing communication between them.

Instead of objects referring to each other directly, they communicate through a mediator object.

This makes the system easier to maintain, modify, and scale, especially as the number of objects increases.

Mediator pattern focuses on simplifying communication between objects by managing and coordinating their interations through a mediator.

Mediator pattern is used for coordinating communication while the proxy pattern is used for controlling access.

Components
  • Mediator interface: Declares the communication contract used by components.
  • ConcreteMediator: Implements coordination logic and knows all components (colleagues).
  • Colleague: Individual objects that communicate via mediator. Knows about the mediator but not other colleagues.
Pros and Cons
Low Coupling

Promotes low coupling between components by routing their communication through a central mediator.

Easier Maintenance

Simplifies maintenance and enhances reusability since components no longer depend on each other directly.

Centralized Communication

Centralizes complex communications in one place, making the interactions easier to follow and manage.

God Object Risk

The mediator can become a God object if it accumulates too much responsibility and grows too complex.

Poor Scalability

Too much logic packed inside the mediator can lead to poor scalability as the system grows.

Real-world example
  • java.util.Timer — coordinates scheduling and execution of TimerTask objects without them knowing each other.
  • Spring ApplicationEventPublisher — publishers and listeners communicate through the central event multicaster, not directly.
  • JMS message broker — producers and consumers exchange messages via the broker rather than point-to-point links.
  • Air traffic control tower — pilots coordinate takeoffs and landings through the tower instead of talking to each other.
  • Chat room server — users send messages to the server, which relays them to the other participants.
  • GUI dialog controller — a form controller mediates between buttons, text fields, and checkboxes to enable or disable them.
  • Enterprise Service Bus — services integrate through the bus, which routes and transforms messages between them.
What is the Mediator Design Pattern?

The Mediator Pattern is a behavioral design pattern that defines a central object (called the Mediator) to manage and coordinate communication between multiple objects without requiring those objects to communicate directly with one another.

Instead of objects referencing and interacting with each other directly, they communicate through a mediator, which encapsulates the rules and logic governing their interactions.

This promotes loose coupling, reduces dependencies between objects, and makes complex interactions easier to manage, modify, and maintain.

The main idea is:

Objects should not need to know how to communicate with every other object. Instead, they communicate through a mediator that coordinates their interactions.

Real-world analogy: Air Traffic Control

Consider an airport with multiple airplanes.

Without a mediator, each airplane would have to communicate directly with other airplanes to coordinate takeoffs, landings, runway availability, and collision avoidance.

With a mediator, an Air Traffic Control (ATC) Tower coordinates these activities.

  • Each airplane communicates with ATC.
  • ATC maintains information about runway availability and aircraft movements.
  • ATC decides which airplane can take off or land.
  • Airplanes do not have to coordinate their movements directly with every other airplane.

The ATC tower acts as a mediator, centralizing communication and coordination rules.

What problem does the Mediator Pattern solve?

Imagine a GUI application with several components:

  • Username TextField
  • Password TextField
  • Remember Me Checkbox
  • Login Button
  • Status Label

These components depend on one another.

For example, the Login Button should become enabled only when both username and password contain valid values.

Without Mediator

Each component might directly reference other components to coordinate behavior.

Direct communication — tight coupling

Components know about and depend on other components.

This approach creates several problems:

  • Tight coupling: Components directly depend on one another.
  • Difficult maintenance: Changing one component may require changes in multiple others.
  • Poor reusability: A component cannot easily be reused in another form because it assumes the existence of specific components.
  • Complex communication: As more components are added, dependencies become difficult to understand and manage.
  • Difficult testing: Testing one component may require creating several related components.

With Mediator

We introduce a LoginDialogMediator that coordinates all the components.

Centralized coordination — loose coupling

Components communicate through a mediator rather than depending directly on one another.

Now:

  1. The Username TextField informs the mediator when its value changes.
  2. The Password TextField does the same.
  3. The mediator checks whether the form is valid.
  4. The mediator enables or disables the Login Button accordingly.

The individual components no longer need to know about one another.

Important: The Mediator Pattern does not eliminate dependencies entirely. It replaces many direct object-to-object dependencies with dependencies on a common mediator interface.

Structure of the Mediator Pattern

The Mediator Pattern typically contains four participants.

ParticipantResponsibility
MediatorDefines the interface through which colleagues communicate
ConcreteMediatorImplements coordination and interaction rules
ColleagueRepresents a participating object that communicates through the mediator
ConcreteColleagueImplements the behavior of a specific participating object

UML-style class diagram

How the pattern works

  1. A colleague performs an action or changes its internal state.
  2. It notifies the mediator about that event.
  3. The mediator determines how other colleagues should respond.
  4. The mediator invokes the appropriate behavior on those colleagues.
  5. Colleagues remain unaware of each other's internal implementation.

The key architectural principle is that interaction logic belongs to the mediator instead of being distributed across participating objects.

Practical Example 1: Chat Room Application

Let's implement a chat application using the Mediator Pattern.

Requirements

Our application has multiple users: Alice, Bob, and Charlie.

Each user should be able to:

  • Join a chat room.
  • Send a message to everyone.
  • Send a private message to a specific user.
  • Receive messages from other users.

Important: A user should not need references to other users to communicate.

The chat room will act as the mediator.

Class structure

Step 1: Define the Mediator interface

public interface ChatMediator {
    void register(ChatUser user);

    void broadcast(String message, ChatUser sender);

    void sendPrivate(String recipient, String message, ChatUser sender);
}

The mediator interface defines how users communicate.

Notice that the interface does not tell us how messages are delivered. Different implementations can provide different communication policies.

Step 2: Create the Colleague class

Each ChatUser represents a colleague participating in the system.

public class ChatUser {
    private String name;
    private ChatMediator mediator;

    public ChatUser(String name, ChatMediator mediator) {
        this.name = name;
        this.mediator = mediator;
    }

    public String getName() {
        return name;
    }

    public void join() {
        mediator.register(this);
    }

    public void send(String message) {
        System.out.println(name + " broadcasts: " + message);
        mediator.broadcast(message, this);
    }

    public void sendPrivate(String recipient, String message) {
        System.out.println(name + " sends a private message to " + recipient);
        mediator.sendPrivate(recipient, message, this);
    }

    public void receive(String sender, String message) {
        System.out.println(name + " received from " + sender + ": " + message);
    }
}

Observe this declaration:

private ChatMediator mediator;

Each user knows only the mediator.

A ChatUser does not maintain references to other users. It delegates message delivery to the mediator.

Step 3: Implement the Concrete Mediator

public class ChatRoom implements ChatMediator {
    private Map<String, ChatUser> users = new LinkedHashMap<>();

    @Override
    public void register(ChatUser user) {
        if (users.putIfAbsent(user.getName(), user) != null) {
            throw new IllegalArgumentException("Username already exists: " + user.getName());
        }
        System.out.println(user.getName() + " joined the room");
    }

    @Override
    public void broadcast(String message, ChatUser sender) {
        validateSender(sender);
        for (ChatUser user : users.values()) {
            if (user != sender) {
                user.receive(sender.getName(), message);
            }
        }
    }

    @Override
    public void sendPrivate(String recipient, String message, ChatUser sender) {
        validateSender(sender);
        ChatUser receiver = users.get(recipient);
        if (receiver == null) {
            throw new IllegalArgumentException("Recipient not found: " + recipient);
        }
        receiver.receive(sender.getName(), message);
    }

    private void validateSender(ChatUser sender) {
        if (users.get(sender.getName()) != sender) {
            throw new IllegalStateException("Sender has not joined the room");
        }
    }
}

The ChatRoom contains the coordination logic.

It decides:

  • Who is allowed to send messages.
  • Which users receive broadcast messages.
  • Which user receives a private message.
  • Whether a recipient exists.

The users themselves don't implement these communication rules.

Step 4: Client code

void main(String[] args) {
    ChatMediator chatRoom = new ChatRoom();
    ChatUser alice = new ChatUser("Alice", chatRoom);
    ChatUser bob = new ChatUser("Bob", chatRoom);
    ChatUser charlie = new ChatUser("Charlie", chatRoom);
    alice.join();
    bob.join();
    charlie.join();
    System.out.println();
    alice.send("Good morning, everyone!");
    System.out.println();
    bob.sendPrivate("Alice", "Can we review the code?");
}

Output

Alice joined the room
Bob joined the room
Charlie joined the room

Alice broadcasts: Good morning, everyone!
Bob received from Alice: Good morning, everyone!
Charlie received from Alice: Good morning, everyone!

Bob sends a private message to Alice
Alice received from Bob: Can we review the code?

Communication flow

Why is this the Mediator Pattern?

Consider this code inside ChatUser:

public void sendPrivate(String recipient, String message) {
    mediator.sendPrivate(recipient, message, this);
}

The user does not know which object represents the recipient or how to locate it.

That knowledge belongs to ChatRoom.

If we introduce new rules, such as blocking users, muting participants, or restricting private messages, we can implement the coordination logic inside the mediator without changing how ChatUser sends messages.

This is the main benefit of the Mediator Pattern: the communication policy can evolve independently of the participants.

Note that this implementation is an in-memory, synchronous demonstration. A production chat application would also need to handle concurrency, persistence, authentication, and network delivery.

Practical Example 2: Registration Form Using Mediator

This example demonstrates a more important aspect of the Mediator Pattern: coordinating the behavior of multiple components based on their states.

Consider a registration dialog containing:

  • Username field
  • Password field
  • Accept Terms checkbox
  • Register button

Business rules

The Register button should be enabled only when:

  1. Username is not empty.
  2. Password contains at least 8 characters.
  3. User has accepted the terms and conditions.

Instead of letting each control directly interact with the Register button, we will introduce a RegistrationDialog mediator.

Step 1: Define the mediator interface

public interface FormMediator {
    void componentChanged(FormControl source);

    void submit();
}

This interface supports two interactions.

  • componentChanged() is called whenever a form control changes its state.
  • submit() is called when the user clicks the Register button.

Step 2: Create a base Colleague class

public abstract class FormControl {
    private FormMediator mediator;

    public void setMediator(FormMediator mediator) {
        this.mediator = mediator;
    }

    protected void notifyChanged() {
        if (mediator != null) {
            mediator.componentChanged(this);
        }
    }

    protected FormMediator getMediator() {
        return mediator;
    }
}

All components inherit from FormControl.

Notice that components only know the FormMediator interface.

Step 3: Create concrete form components

TextField

public class TextField extends FormControl {
    private String value = "";

    public void setValue(String value) {
        this.value = Objects.requireNonNull(value);
        notifyChanged();
    }

    public String getValue() {
        return value;
    }
}

When the value changes, TextField notifies the mediator.

The text field does not know whether the Register button exists or what validation rules apply.

CheckBox

public class CheckBox extends FormControl {
    private boolean checked;

    public void setChecked(boolean checked) {
        this.checked = checked;
        notifyChanged();
    }

    public boolean isChecked() {
        return checked;
    }
}

Again, the checkbox only reports its state changes to the mediator.

Button

public class Button extends FormControl {
    private boolean enabled;

    public void setEnabled(boolean enabled) {
        if (this.enabled != enabled) {
            this.enabled = enabled;
            System.out.println("Register button " + (enabled ? "enabled" : "disabled"));
        }
    }

    public boolean isEnabled() {
        return enabled;
    }

    public void click() {
        if (!enabled) {
            System.out.println("Button is disabled. Cannot submit.");
            return;
        }
        getMediator().submit();
    }
}

The button doesn't validate the username, password, or checkbox.

It delegates the submission action to the mediator.

Step 4: Implement the Concrete Mediator

public class RegistrationDialog implements FormMediator {
    private TextField username = new TextField();
    private TextField password = new TextField();
    private CheckBox terms = new CheckBox();
    private Button registerButton = new Button();

    public RegistrationDialog() {
        for (FormControl control : List.of(username, password, terms, registerButton)) {
            control.setMediator(this);
        }
        updateRegisterButton();
    }

    @Override
    public void componentChanged(FormControl source) {
        updateRegisterButton();
    }

    private void updateRegisterButton() {
        boolean validUsername = !username.getValue().isBlank();
        boolean validPassword = password.getValue().length() >= 8;
        boolean termsAccepted = terms.isChecked();
        boolean formValid = validUsername && validPassword && termsAccepted;
        registerButton.setEnabled(formValid);
    }

    @Override
    public void submit() {
        if (!isFormValid()) {
            throw new IllegalStateException("Invalid form");
        }
        System.out.println("Registration submitted for: " + username.getValue());
    }

    private boolean isFormValid() {
        return !username.getValue().isBlank() && password.getValue().length() >= 8 && terms.isChecked();
    }

    public TextField username() {
        return username;
    }

    public TextField password() {
        return password;
    }

    public CheckBox terms() {
        return terms;
    }

    public Button registerButton() {
        return registerButton;
    }
}

This is where all the interaction logic lives.

The mediator:

  • Observes state-change notifications from controls.
  • Reads the current form values.
  • Evaluates validation rules.
  • Updates the Register button.
  • Handles submission requests.

No individual component needs to know about another component.

The source parameter also allows the mediator to respond differently to particular controls when necessary.

Step 5: Client code

void main(String[] args) {
    RegistrationDialog dialog = new RegistrationDialog();
    dialog.registerButton().click();
    dialog.username().setValue("Alice");
    dialog.password().setValue("123");
    dialog.terms().setChecked(true);
    dialog.password().setValue("SecurePass123");
    dialog.registerButton().click();
    dialog.terms().setChecked(false);
}

Output

Button is disabled. Cannot submit.
Register button enabled
Registration submitted for: Alice
Register button disabled

Understanding the execution

Without Mediator, a password field might have to know about the username field, checkbox, and Register button.

With Mediator, the password field only says:

notifyChanged();

It doesn't need to understand what happens afterward.

The mediator decides what should happen.

This approach is particularly useful in complex GUI forms involving dynamic visibility, conditional controls, dependent dropdowns, multi-step workflows, and validation rules.

Note: This example simulates UI controls. In an actual registration application, form validation must also happen on the server. The submission method would normally call an application service instead of printing a message.

How Mediator Reduces Coupling

Suppose a system has five interacting components:

A, B, C, D, E

Without a mediator, each component may require references to several others.

With a mediator:

public class ComponentA {
    private Mediator mediator;
}

public class ComponentB {
    private Mediator mediator;
}

public class ComponentC {
    private Mediator mediator;
}

All components depend on a common interface instead of depending directly on each other.

In a fully connected system containing n components, the maximum number of unique direct relationships is:

n(n − 1) / 2

With a single mediator connecting to each component, there are n component-to-mediator relationships, although the mediator must still coordinate those participants.

Number of componentsMaximum direct relationshipsMediator connections
5105
104510
2019020
501,22550

Illustrative maximum for pairwise connections, not a measured complexity or performance comparison. Actual systems may have far fewer direct dependencies.

This reduces the number of relationships that participating objects need to manage themselves.

However, complexity does not disappear. Much of the interaction complexity moves into the mediator.

Mediator vs Observer Design Pattern

Mediator and Observer are both behavioral patterns that manage communication between objects, but they solve different problems.

MediatorObserver
Centralizes coordination among objectsEstablishes a subscription-based notification mechanism
Mediator decides what interactions should occurSubject notifies observers of events
Coordinates behavior and interactionsPrimarily communicates state changes or events
May reference and invoke multiple colleaguesSubject normally maintains a collection of observers
Useful for complex interactionsUseful for event notifications and reactive updates

Observer example

Suppose an order status changes.

order.notifyObservers();

Observers such as EmailNotifier, SmsNotifier, and AuditLogger are notified.

They independently react to the event.

The order does not coordinate the behavior of these observers.

Mediator example

In a checkout application:

checkoutMediator.placeOrder(order);

The mediator may coordinate:

Check inventory ↓ Reserve stock ↓ Process payment ↓ Confirm order

Unlike simple event notifications, the mediator determines the sequence and rules governing interactions among components.

Key distinction: Observer focuses on notifying interested objects about events, whereas Mediator focuses on coordinating how objects interact.

They can also be used together. A mediator may subscribe to events from components using the Observer Pattern and then coordinate other components in response.

Mediator vs Facade Design Pattern

Mediator is sometimes confused with Facade because both introduce an object that sits between other objects.

However, their intentions are different.

MediatorFacade
Coordinates communication among colleaguesProvides a simplified interface to a subsystem
Focuses on interactions between participating objectsFocuses on simplifying client access
Colleagues communicate with the mediatorClients invoke facade operations
Often supports interactions in multiple directionsTypically provides an entry point into lower-level operations
Reduces colleague-to-colleague couplingReduces client-to-subsystem coupling

Facade

public class ComputerFacade {
    private CPU cpu;
    private Memory memory;
    private HardDrive hardDrive;

    public void startComputer() {
        cpu.start();
        memory.initialize();
        hardDrive.loadOS();
    }
}

Here, a client uses one simple method instead of interacting with several subsystem components.

The CPU, Memory, and HardDrive do not necessarily communicate back through the facade or treat it as their coordinator.

Mediator

public class ComputerMediator {
    public void onTemperatureChanged(int temperature) {
        if (temperature > 80) {
            coolingFan.increaseSpeed();
            cpu.reduceFrequency();
        }
    }
}

Here, the mediator coordinates how components react to a change in another component.

The cooling fan doesn't need to know about the CPU or temperature sensor.

The same class can sometimes resemble both patterns, so the important factor is its intended responsibility rather than simply the number of classes it references.

Mediator vs MVC Controller

A question that often arises in application development is whether an MVC Controller is a Mediator.

They can look similar, but they aren't automatically the same.

For example, consider a Spring Boot controller:

@RestController
public class OrderController {
    private OrderService orderService;

    OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping("/orders")
    public void placeOrder(@RequestBody OrderRequest request) {
        orderService.placeOrder(request);
    }
}

This is not necessarily an implementation of the Mediator Pattern.

The controller is primarily responsible for handling HTTP requests and translating them into application operations.

A mediator, on the other hand, coordinates interactions between participating objects and encapsulates the rules governing those interactions.

An application controller can perform mediation-like coordination, but MVC Controller and Mediator are different concepts with different primary purposes.

Example: Switching mediator implementations

Suppose we have:

ChatMediator chatRoom = new ChatRoom();

Later, we might implement:

public class ModeratedChatRoom implements ChatMediator {
    # Enforces moderation and permission rules
}

Then a user can be constructed with either mediator:

ChatUser alice = new ChatUser("Alice", chatRoom);

or:

ChatMediator moderatedRoom = new ModeratedChatRoom();
ChatUser alice = new ChatUser("Alice", moderatedRoom);

The ChatUser class does not need changes, provided the new mediator supports the same interface contract.

This demonstrates how the mediator allows coordination policies to change independently of participating objects.

Disadvantages of the Mediator Pattern

Mediator can become a God Object

This is the most significant drawback.

As more interactions are introduced, the mediator may accumulate excessive responsibilities.

For example:

public class ApplicationMediator {
    void handleUserRegistration() {}

    void processPayment() {}

    void sendEmail() {}

    void updateInventory() {}

    void generateInvoice() {}

    void scheduleDelivery() {}

    void calculateTax() {}
}

This class is handling too many unrelated concerns.

It becomes difficult to understand, maintain, and test.

A better solution is to introduce smaller mediators with clearly defined responsibilities.

For example:

RegistrationMediator
CheckoutMediator
NotificationMediator

Each mediator should coordinate a cohesive set of interactions.

Additional abstraction

Small systems with only two objects may not need a mediator.

For example:

button.setOnClickListener(() -> label.setText("Clicked"));

Introducing a mediator solely for this single relationship may add unnecessary complexity.

Centralization of interaction logic

Changes to collaboration rules often require changing the concrete mediator.

Although this simplifies the individual colleagues, an overly complex mediator may become a maintenance bottleneck.

Potential runtime bottleneck

In a concurrent or distributed implementation, a single mediator instance or service may become a throughput bottleneck if all requests are serialized through it.

The design pattern itself doesn't require a single-threaded implementation or even a network service. Thread safety, concurrency, and availability need separate consideration.

When should you use Mediator?

The Mediator Pattern is especially appropriate when several objects interact in complex ways, and those interactions are difficult to maintain because of direct dependencies.

Examples include:

ScenarioMediator's responsibility
Chat applicationRoute messages and enforce communication rules
GUI formCoordinate dependent fields, buttons, and validation
Air traffic control simulationCoordinate runway access between aircraft
Multiplayer game lobbyCoordinate player readiness and game start
Workflow engineCoordinate transitions between participating workflow steps
Auction systemCoordinate bids between registered bidders
Smart home controllerCoordinate devices based on sensor events

When to avoid it

Avoid introducing a mediator when interactions are simple, objects are already loosely coupled, or the mediator would merely forward every method call without adding meaningful coordination.

Also, do not introduce a single application-wide mediator for every subsystem. Prefer mediators around specific collaborations.

How to recognize Mediator in existing Java code

When reviewing Java code, look for these characteristics:

  • Multiple collaborating objects depend on a shared coordinator interface.
  • Colleagues report actions or state changes to that coordinator.
  • The coordinator contains rules deciding which colleague should do what.
  • Colleagues rarely reference one another directly.
  • Interaction behavior can be changed without rewriting the internal behavior of each participant.

For example:

public interface Mediator {
    void notify(Component sender, String event);
}

And a component might look like:

public class ComponentA {
    private Mediator mediator;

    ComponentA(Mediator mediator) {
        this.mediator = mediator;
    }

    void performAction() {
        System.out.println("Action performed");
        mediator.notify(this, "ACTION_COMPLETED");
    }
}

This structure is a common indication of the Mediator Pattern, although the presence of a class named Mediator alone does not guarantee that the pattern is being used meaningfully.

Summary

The Mediator Pattern replaces complex direct communication between objects with a central coordination mechanism.

Remember these key points:

  • Mediator is a behavioral design pattern.
  • It centralizes interaction and communication rules.
  • Colleagues communicate through the mediator instead of directly depending on one another.
  • It improves loose coupling, reusability, and maintainability when object interactions are complex.
  • It is particularly useful in GUIs, chat systems, and multi-object coordination.
  • Its major drawback is the risk of creating an overly complex mediator.

In one sentence: The Mediator Pattern encapsulates how a group of objects interact, allowing those objects to collaborate without being tightly coupled to one another.

Code
public interface ChatMediator {
    void send(String msg, User from);
}

public class ChatRoom implements ChatMediator {
    private List<User> users = new ArrayList<>();
    void register(User u) { users.add(u); }

    public void send(String msg, User from) {
        for (User u : users)
            if (u != from) u.receive(msg);
    }
}

public class User {
    private String name;
    private ChatMediator mediator;
    User(String name, ChatMediator m) { this.name = name; mediator = m; }

    void send(String msg) { mediator.send(msg, this); }
    void receive(String msg) {
        System.out.println(name + " got: " + msg);
    }
}

void main() {
    ChatRoom room = new ChatRoom();
    User a = new User("Amit", room);
    User b = new User("Bina", room);
    room.register(a); room.register(b);
    a.send("Hello");  # Bina got: Hello
}
How the Mediator works

ChatRoom is the mediator that routes all messages.

User objects never reference each other directly.

A user calls send(); the mediator decides who receives it.

Adding a new user needs no change to existing users.
