Observer

Observer is a behavioral design pattern that defines a one-to-many dependency between objects, where one object, called the Subject (or Publisher), maintains a collection of dependent objects called Observers (or Subscribers). Observers can subscribe to or unsubscribe from the Subject dynamically.

Whenever the Subject's state changes or an important event occurs, the Subject automatically notifies all registered Observers, allowing each Observer to react or update itself accordingly. This promotes loose coupling because the Subject does not need to know the concrete implementations of its Observers - it only communicates with them through a common Observer interface.

When to use
  • Use Observer when you want to automatically notify multiple objects of state changes.
  • Great for event-driven systems, GUIs, distributed messaging, and real-time updates.
  • Think of it as a push-based notification system for objects.
Components
  • Subject (interface) – contract for being observed: keeps the observer list and exposes subscribe|unsubscribe|notify.
  • ConcreteSubject (class) – holds the real state and notifies every observer whenever that state changes.
  • Observer (interface) – contract for listeners: declares the update method the subject calls.
  • ConcreteObserver (class) – reacts to notifications, reading the subject's new state and updating itself.
Pros and Cons
Loose Coupling

The subject and observers interact only through an interface, so neither depends on the other's concrete type.

Dynamic Subscription

Observers can subscribe and unsubscribe at runtime without changing the subject.

Open/Closed Principle

New observer types can be added without modifying the subject's code.

Broadcast Updates

A single state change notifies many observers automatically.

Unpredictable Order

The order in which observers are notified is not guaranteed.

Update Cascades

One change can trigger chains of updates that are hard to trace and can hurt performance.

Memory Leaks

Observers that forget to unsubscribe stay referenced by the subject (the lapsed-listener problem).

Harder Debugging

The indirect, push-based flow makes the control path harder to follow.

Real-world example
  • Java util Observer/Observable — the legacy built-in subject and observer types (deprecated since Java 9).
  • Java PropertyChangeListener — beans fire PropertyChangeEvents to registered listeners on property changes.
  • Swing and AWT listeners — ActionListener and MouseListener are notified when UI events occur.
  • Spring ApplicationEvent — ApplicationListener beans react when the context publishes events.
  • RxJava and Reactor — Observable and Flux push emitted items to their subscribers.
  • JavaScript addEventListener — DOM nodes notify all registered handlers when an event fires.
  • Newsletter subscription — subscribers get every new issue automatically without asking each time.
public interface Observer {
    void update(String news);
}

public interface Subject {
    void subscribe(Observer o);
    void unsubscribe(Observer o);
    void publish(String news);
}

public class NewsAgency implements Subject {
    private List<Observer> observers = new ArrayList<>();

    public void subscribe(Observer o) {observers.add(o);}
    public void unsubscribe(Observer o) {observers.remove(o);}

    public void publish(String news) {
        for (Observer o: observers)
            o.update(news);
    }
}

public class Subscriber implements Observer {
    private String name;
    public Subscriber(String name) {this.name = name;}
    public void update(String news) {
        System.out.println(name + " received: " + news);
    }
}

void main() {
    NewsAgency agency = new NewsAgency();
    agency.subscribe(new Subscriber("Amit"));
    agency.publish("Breaking news!");
}
How the Observer works

NewsAgency implements the Subject interface and holds a list of observers.

Subscriber implements update() to react to changes.

publish() notifies every registered observer.

Observers can subscribe or unsubscribe without touching the subject's logic.
