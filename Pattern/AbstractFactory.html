Abstract Factory

Abstract Factory is a creational design pattern that provides an interface for creating families of related or dependent objects without specifying their concrete classes.

Where a Factory Method creates a single product, an Abstract Factory groups several factory methods to produce a whole family of products that are designed to work together.

Client code interacts only with the abstract factory and abstract products, so an entire family can be swapped by changing the concrete factory.

When to use
  • When your system needs to create families of related products together.
  • When products from one family must be used consistently and not mixed with another.
  • When you want to isolate client code from concrete product classes.
  • When you need to support multiple variants (themes, platforms, vendors).
  • When you want to configure a system with one of several product families.
Pros and Cons
Family Consistency

Guarantees that products from a single family are always used together.

Isolates Concrete Classes

Keeps concrete product classes hidden from the client code.

Easy Family Swapping

Makes swapping entire product families easy and centralized.

Open/Closed Principle

Follows the open/closed principle when adding new families.

Promotes Consistency

Promotes consistency among the objects that are produced.

Added Complexity

Adds many interfaces and classes, increasing overall complexity.

Hard to Extend Products

Adding a new product type requires changing every factory.

Risk of Over-Engineering

Can be over-engineered for systems with only a single product family.

Real-world example
  • javax.xml.parsers.DocumentBuilderFactory — produces a family of related XML parsing objects (DocumentBuilder) hiding the concrete parser implementation.
  • javax.xml.transform.TransformerFactory — creates Transformer and related objects for a chosen XSLT processor without naming its concrete classes.
  • java.awt.Toolkit — returns platform-specific families of AWT peer widgets so one code path renders on Windows, macOS or Linux.
  • Spring BeanFactory and ApplicationContext — produce families of related, wired beans according to the active configuration or profile.
  • JDBC drivers via DriverManager — each driver supplies a matching family of Connection, Statement and ResultSet objects for its database.
  • Cross-platform UI toolkits — a theme factory yields buttons, checkboxes and scrollbars that all share one consistent look and feel.
  • Furniture showroom analogy — a Victorian or Modern factory delivers a matching chair, sofa and table that belong to the same style set.
Abstract Factory Design Pattern

Abstract Factory is a creational design pattern that provides an interface for creating families of related objects without specifying their concrete classes.

The key phrase is: create a family of related objects that are designed to work together.

For example, imagine a cross-platform GUI framework supporting Windows and macOS. Each platform needs related components: Button, Checkbox and Menu.

For Windows, you want WindowsButton, WindowsCheckbox and WindowsMenu.
For macOS: MacButton, MacCheckbox and MacMenu.

You don't want the client code doing this:

if (os.equals("windows")) {
    Button button = new WindowsButton();
    Checkbox checkbox = new WindowsCheckbox();
} else {
    Button button = new MacButton();
    Checkbox checkbox = new MacCheckbox();
}

Instead, you give the application a factory representing the entire product family.

Main idea

Suppose these are your abstract products:

interface Button {
    void render();
}

interface Checkbox {
    void render();
}

Concrete Windows products:

class WindowsButton implements Button {

    @Override
    public void render() {
        System.out.println("Rendering Windows button");
    }
}

class WindowsCheckbox implements Checkbox {

    @Override
    public void render() {
        System.out.println("Rendering Windows checkbox");
    }
}

Concrete macOS products:

class MacButton implements Button {

    @Override
    public void render() {
        System.out.println("Rendering Mac button");
    }
}

class MacCheckbox implements Checkbox {

    @Override
    public void render() {
        System.out.println("Rendering Mac checkbox");
    }
}

Now we create an Abstract Factory.

interface GUIFactory {

    Button createButton();

    Checkbox createCheckbox();
}

Notice something important. The factory doesn't create just one product. It creates an entire family of related products: Button and Checkbox.

Concrete factories

Windows factory:

class WindowsGUIFactory implements GUIFactory {

    @Override
    public Button createButton() {
        return new WindowsButton();
    }

    @Override
    public Checkbox createCheckbox() {
        return new WindowsCheckbox();
    }
}

Mac factory:

class MacGUIFactory implements GUIFactory {

    @Override
    public Button createButton() {
        return new MacButton();
    }

    @Override
    public Checkbox createCheckbox() {
        return new MacCheckbox();
    }
}

Each factory guarantees that compatible objects are created together:

This prevents something undesirable like WindowsButton + MacCheckbox.

Client application

Now create an application that depends only on abstractions.

class Application {

    private final Button button;
    private final Checkbox checkbox;

    public Application(GUIFactory factory) {
        this.button = factory.createButton();
        this.checkbox = factory.createCheckbox();
    }

    public void renderUI() {
        button.render();
        checkbox.render();
    }
}

The application has no idea whether these objects are WindowsButton, MacButton, WindowsCheckbox or MacCheckbox. It only knows Button, Checkbox and GUIFactory. That is the major advantage.

Main method
void main(String[] args) {

    String operatingSystem = "windows";

    GUIFactory factory;

    if (operatingSystem.equalsIgnoreCase("windows")) {
        factory = new WindowsGUIFactory();
    } else {
        factory = new MacGUIFactory();
    }

    Application app = new Application(factory);

    app.renderUI();
}

Output:

Rendering Windows button
Rendering Windows checkbox

Changing operatingSystem = "mac"; gives:

Rendering Mac button
Rendering Mac checkbox

The important thing is that the Application class never changes.

Structure of Abstract Factory

There are normally five major participants.

ParticipantRoleExample
Abstract FactoryDefines methods for creating each kind of product.interface GUIFactory
Concrete FactoryCreates a particular family.WindowsGUIFactory, MacGUIFactory
Abstract ProductDefines the common API.interface Button, interface Checkbox
Concrete ProductPlatform-specific implementations.WindowsButton, MacButton, WindowsCheckbox, MacCheckbox
ClientUses the abstract factory and abstract products.class Application
Why do we need Abstract Factory?

Imagine without the pattern you have:

class Application {

    public void start(String os) {

        Button button;
        Checkbox checkbox;

        if (os.equals("windows")) {
            button = new WindowsButton();
            checkbox = new WindowsCheckbox();
        } else if (os.equals("mac")) {
            button = new MacButton();
            checkbox = new MacCheckbox();
        }

        # ...
    }
}

Initially this looks harmless. But suppose your UI grows to Button, Checkbox, Menu, TextField, Dialog, Toolbar and ScrollBar. Now your code becomes:

if (os.equals("windows")) {

    button = new WindowsButton();
    checkbox = new WindowsCheckbox();
    menu = new WindowsMenu();
    dialog = new WindowsDialog();
    toolbar = new WindowsToolbar();

} else if (os.equals("mac")) {

    button = new MacButton();
    checkbox = new MacCheckbox();
    menu = new MacMenu();
    dialog = new MacDialog();
    toolbar = new MacToolbar();
}

And the same condition might appear in many classes. Abstract Factory centralizes this decision. Instead, you hold a GUIFactory factory; and then everywhere:

factory.createButton();
factory.createCheckbox();
factory.createMenu();
factory.createDialog();
Why not just use constructors?

Because direct construction couples the client to concrete implementations. With Button button = new WindowsButton(); the client now knows WindowsButton. If tomorrow you switch to macOS, Button button = new MacButton(); means the client must change.

With Abstract Factory, Button button = factory.createButton(); the client does not care. The factory decides what concrete object should be created.

When should you use Abstract Factory?

Abstract Factory is particularly useful when you have multiple related objects that vary together. For example:

Family typeFamily AFamily B
DatabaseMySQLConnection, MySQLCommand, MySQLTransactionPostgresConnection, PostgresCommand, PostgresTransaction
CloudAWSStorage, AWSQueue, AWSDatabaseAzureStorage, AzureQueue, AzureDatabase
UIWindowsButton, WindowsMenu, WindowsDialogMacButton, MacMenu, MacDialog

The important condition is: several types of objects change together based on one configuration or environment.

Real-world example: Cloud providers

Consider an application that supports AWS and Azure. We need Storage, MessageQueue and Database. The AWS implementations are S3Storage, SqsQueue and DynamoDatabase; the Azure implementations are BlobStorage, ServiceBusQueue and CosmosDatabase. We could model them using Abstract Factory.

The cloud Abstract Factory

Now define our cloud infrastructure factory.

interface CloudFactory {

    CloudStorage createStorage();

    MessageQueue createQueue();

    Database createDatabase();
}

The factory represents a complete cloud ecosystem.

AWS factory
class AWSCloudFactory implements CloudFactory {

    @Override
    public CloudStorage createStorage() {
        return new S3Storage();
    }

    @Override
    public MessageQueue createQueue() {
        return new SqsQueue();
    }

    @Override
    public Database createDatabase() {
        return new DynamoDatabase();
    }
}
Azure factory
class AzureCloudFactory implements CloudFactory {

    @Override
    public CloudStorage createStorage() {
        return new BlobStorage();
    }

    @Override
    public MessageQueue createQueue() {
        return new ServiceBusQueue();
    }

    @Override
    public Database createDatabase() {
        return new CosmosDatabase();
    }
}

Now we have:

Client service
class OrderService {

    private final CloudStorage storage;
    private final MessageQueue queue;
    private final Database database;

    public OrderService(CloudFactory factory) {

        this.storage = factory.createStorage();
        this.queue = factory.createQueue();
        this.database = factory.createDatabase();
    }

    public void processOrder() {

        database.save("Order-1001");

        queue.send("Order created");

        storage.upload("invoice.pdf");
    }
}

Notice that OrderService knows nothing about AWS, Azure, S3, SQS, DynamoDB, Blob Storage or Cosmos DB. It only depends on abstractions.

Selecting the factory
void main(String[] args) {

    String provider = "AWS";

    CloudFactory factory;

    if (provider.equalsIgnoreCase("AWS")) {
        factory = new AWSCloudFactory();
    } else {
        factory = new AzureCloudFactory();
    }

    OrderService orderService = new OrderService(factory);

    orderService.processOrder();
}

AWS output:

Saving data to DynamoDB: Order-1001
Sending message using AWS SQS: Order created
Uploading invoice.pdf to AWS S3

Changing only CloudFactory factory = new AzureCloudFactory(); produces:

Saving data to Azure Cosmos DB: Order-1001
Sending message using Azure Service Bus: Order created
Uploading invoice.pdf to Azure Blob Storage

The OrderService doesn't change. That is a very good example of why Abstract Factory exists.

The most important concept: product families

This is the part that often makes Abstract Factory confusing. Think of the objects as a table:

Product typeWindows familyMac family
ButtonWindowsButtonMacButton
CheckboxWindowsCheckboxMacCheckbox
MenuWindowsMenuMacMenu

Or:

Product typeAWS familyAzure family
StorageS3Blob Storage
QueueSQSService Bus
DatabaseDynamoDBCosmos DB

Vertical columns are families. Abstract Factory lets you choose a column. For example, CloudFactory factory = new AWSCloudFactory(); effectively means use the AWS column. Then factory.createStorage(), factory.createQueue() and factory.createDatabase() will all return AWS-compatible products.

Why is this better than creating objects individually?

Suppose the application accidentally does this:

CloudStorage storage = new S3Storage();

MessageQueue queue = new ServiceBusQueue();

Database database = new DynamoDatabase();

Now we have a mixture: AWS, Azure, AWS. Sometimes mixing implementations is valid, but sometimes the products are expected to belong to the same family. Abstract Factory can enforce consistency:

CloudFactory factory = new AWSCloudFactory();

CloudStorage storage = factory.createStorage();
MessageQueue queue = factory.createQueue();
Database database = factory.createDatabase();

Now all products come from the AWS family.

Without Abstract Factory:

Very tightly coupled. With Abstract Factory:

class OrderService {

Adding another family

Suppose tomorrow you add Google Cloud. You might create:

class GCSStorage implements CloudStorage {

    @Override
    public void upload(String file) {
        System.out.println("Uploading to Google Cloud Storage");
    }
}

class PubSubQueue implements MessageQueue {

    @Override
    public void send(String message) {
        System.out.println("Sending using Google Pub/Sub");
    }
}

class FirestoreDatabase implements Database {

    @Override
    public void save(String data) {
        System.out.println("Saving to Firestore");
    }
}

And:

class GoogleCloudFactory implements CloudFactory {

    @Override
    public CloudStorage createStorage() {
        return new GCSStorage();
    }

    @Override
    public MessageQueue createQueue() {
        return new PubSubQueue();
    }

    @Override
    public Database createDatabase() {
        return new FirestoreDatabase();
    }
}

Then the application only needs CloudFactory factory = new GoogleCloudFactory();. The business logic stays unchanged. This follows the Open/Closed Principle reasonably well when you're adding a new family.

Important disadvantage

Abstract Factory has an interesting tradeoff. It is very easy to add another family (AWS, Azure, GCP), but harder to add another product type. Suppose we suddenly need a Cache. You must modify:

interface CloudFactory {

    CloudStorage createStorage();

    MessageQueue createQueue();

    Database createDatabase();

    Cache createCache(); # NEW
}

Now every concrete factory must change, AWSCloudFactory, AzureCloudFactory and GoogleCloudFactory, because every family needs to implement createCache(). Therefore:

This is one of the most important tradeoffs of Abstract Factory.

Factory Method vs Abstract Factory

These two are frequently confused. Factory Method usually focuses on creating one product type. For example:

abstract class Dialog {

    abstract Button createButton();
}

class WindowsDialog extends Dialog {

    @Override
    Button createButton() {
        return new WindowsButton();
    }
}

class WebDialog extends Dialog {

    @Override
    Button createButton() {
        return new HTMLButton();
    }
}

Factory Method may exist inside Abstract Factory

An interesting point is that Abstract Factory is often implemented using several factory methods. In interface GUIFactory, each of createButton() and createCheckbox() is essentially a factory method. But together they form an Abstract Factory, because they create a family.

Abstract Factory vs Simple Factory

Suppose you write:

class ButtonFactory {

    public static Button create(String type) {

        return switch (type) {
            case "windows" -> new WindowsButton();
            case "mac" -> new MacButton();
            default -> throw new IllegalArgumentException();
        };
    }
}

This is typically called a Simple Factory. It creates a Button based on a parameter. Abstract Factory instead represents a family:

GUIFactory factory = new WindowsGUIFactory();

Button button = factory.createButton();
Checkbox checkbox = factory.createCheckbox();
Menu menu = factory.createMenu();

Abstract Factory and Dependency Injection

Abstract Factory works very naturally with dependency injection. Instead of doing this:

CloudFactory factory = new AWSCloudFactory();

OrderService service = new OrderService(factory);

Spring could inject it:

@Service
public class OrderService {

    private final CloudFactory cloudFactory;

    public OrderService(CloudFactory cloudFactory) {
        this.cloudFactory = cloudFactory;
    }
}

And configuration decides which implementation exists. For example:

@Configuration
class CloudConfiguration {

    @Bean
    CloudFactory cloudFactory() {
        return new AWSCloudFactory();
    }
}

Now business code doesn't choose the concrete family. Configuration does. Conceptually:

This separation is extremely common in real applications.

When NOT to use Abstract Factory

Don't use it just because you're creating objects. For example, this probably doesn't justify Abstract Factory:

User user = new User();
Order order = new Order();
Product product = new Product();

Those classes don't form interchangeable families. Abstract Factory makes sense when there is something like this, and the families can be switched:

If you only need one abstraction with implementation A and implementation B, then a simple factory, Factory Method, dependency injection, or even normal construction may be enough.

Advantages

Abstract Factory gives you several benefits:

  • Loose coupling — client code depends on interfaces rather than concrete classes.
  • Family consistency — related objects can come from the same implementation family.
  • Easy family switching — changing new AWSCloudFactory() to new AzureCloudFactory() can switch the entire infrastructure family.
  • Centralized object creation — creation logic doesn't spread throughout business code.
  • Supports dependency inversion — high-level code depends on abstractions.
  • Adding new families is relatively easy — you can introduce another concrete factory without modifying most client code.
Disadvantages

There are also costs. The pattern introduces many interfaces and classes:

For a small application this could be unnecessary complexity. Also, as discussed earlier, a new family is easy but a new product type is harder, because adding Slider createSlider(); requires changing every factory implementation.

Final mental model

Remember Abstract Factory like this:

PatternQuestion it asks
Factory MethodWhich concrete implementation of this product should I create?
Abstract FactoryWhich family of related products should my application use?

The strongest signal for Abstract Factory is this requirement: I have multiple related product types, and I want to switch all of their implementations together as one family.

That is the core purpose of the Abstract Factory pattern.
