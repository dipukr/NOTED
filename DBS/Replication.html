Database Replication

Database replication is the process of copying data from one database (the primary) to one or more other databases (the replicas).

Replicas stay in sync by continuously applying the primary's changes, usually from its write-ahead log.

Replication improves read scalability, availability and fault tolerance.

It can be synchronous (the primary waits for replicas to confirm) or asynchronous (the primary does not wait).

Topologies include single-leader, multi-leader and leaderless replication.

When to use / Key points
  • Use read replicas to spread heavy read traffic away from the primary.
  • Use replication for high availability and automatic failover.
  • Synchronous replication protects against data loss but adds write latency.
  • Asynchronous replication is fast but replicas can lag behind (replication lag).
  • Route writes to the primary and reads to replicas at the application layer.
Pros and Cons
Scales Read Throughput

Read traffic can be spread horizontally across multiple replicas.

Higher Availability

It improves availability and enables automatic failover when the primary goes down.

Offloads Backups and Analytics

Replicas can serve backups and analytics workloads without loading the primary.

Lower Latency

Placing replicas closer to users reduces read latency.

Stale Reads

Asynchronous replicas can serve stale data because of replication lag.

Higher Write Latency

Synchronous replication increases write latency since the primary waits for confirmation.

Write Conflicts

Multi-leader setups introduce write conflicts that must be resolved.

Operational Overhead

Replication adds operational complexity and extra storage cost.

Code
-- Writes always target the primary
INSERT INTO Orders (CustomerId, Total, CreatedAt)
VALUES (42, 199.99, SYSUTCDATETIME());

-- Reads are routed to a readable secondary via an availability-group listener
-- (application connection string adds ApplicationIntent=ReadOnly)
SELECT OrderId, Total, CreatedAt
FROM Orders
WHERE CustomerId = 42;

-- On the primary: inspect how far each secondary has caught up
SELECT ag.name AS AvailabilityGroup,
       rs.replica_server_name,
       drs.synchronization_state_desc,
       drs.log_send_queue_size,   -- KB not yet sent to this replica
       drs.redo_queue_size        -- KB received but not yet replayed (lag)
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas rs ON rs.replica_id = drs.replica_id
JOIN sys.availability_groups ag ON ag.group_id = drs.group_id;
How it works

The INSERT is a write and is always sent to the primary replica.

The SELECT is routed to a readable secondary, offloading read traffic from the primary.

sys.dm_hadr_database_replica_states exposes each secondary's synchronization state and queue sizes, the SQL Server equivalent of checking replication lag.

A non-zero redo_queue_size means the secondary has not yet replayed all received log records, so a read against it can return slightly stale data.

Applications routing reads to secondaries must tolerate that lag, the trade-off replication makes for read scalability.
