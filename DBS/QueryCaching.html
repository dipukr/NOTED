Query Caching

Query caching stores the results of queries so subsequent identical requests are served from memory instead of hitting the database.

Caching results of queries gives fast read operations and reduces load on the database.

It is most effective for expensive, frequently run, read-mostly queries.

Caches can live in the database, the ORM (second-level cache) or a dedicated store like Redis.

The main challenge is invalidating the cache when the underlying data changes.

When to use / Key points
  • Cache read-heavy queries whose results rarely change.
  • Set a suitable time-to-live (TTL) or evict on write.
  • Use a cache key that captures all query parameters.
  • Prefer an external cache (Redis) for shared, multi-instance caching.
  • Avoid caching highly volatile or per-user unique data.
Pros and Cons
Faster Repeated Reads

Repeated identical queries are served from memory, making reads dramatically faster.

Reduced Database Load

Serving results from cache reduces load on the database and lowers cost.

Better Response Times

Overall application response times improve as expensive queries are avoided.

Smooths Traffic Spikes

Cached results absorb bursts of traffic and smooth out sudden spikes.

Stale Data Risk

There is a risk of serving stale data if invalidation is done incorrectly.

Hard Invalidation

Cache invalidation is notoriously hard to get right.

Added Cost

Caching adds extra infrastructure and memory cost.

Low Hit Rates

When hit rates are low, the cache provides little benefit.

Code
CREATE TABLE Product (
    ProductId   INT PRIMARY KEY,
    Sku         VARCHAR(50) NOT NULL,
    Price       DECIMAL(10,2) NOT NULL
);

-- Parameterized procedure: the engine caches ONE compiled plan for all ids
CREATE PROCEDURE GetProductById
    @ProductId INT
AS
BEGIN
    SELECT ProductId, Sku, Price
    FROM Product
    WHERE ProductId = @ProductId;
END;

-- First call compiles and caches the plan; later calls reuse it
EXEC GetProductById @ProductId = 101;
EXEC GetProductById @ProductId = 202;

-- Inspect what's currently sitting in the plan cache
SELECT cp.objtype, cp.usecounts, st.text
FROM sys.dm_exec_cached_plans AS cp
CROSS APPLY sys.dm_exec_sql_text(cp.plan_handle) AS st
WHERE st.text LIKE '%GetProductById%';

-- Force recompilation after a schema/statistics change invalidates the cache
EXEC sp_recompile 'GetProductById';
How it works

The stored procedure is compiled once; the resulting execution plan is stored in the plan cache keyed by its signature.

Subsequent EXEC calls with different parameter values reuse the same cached plan instead of recompiling.

sys.dm_exec_cached_plans joined to sys.dm_exec_sql_text shows what plans are cached and how many times each was used (usecounts).

A high usecounts value confirms the plan is being reused rather than recompiled per call.

sp_recompile evicts the cached plan, forcing a fresh compile on the next execution — the SQL analogue of a cache eviction.
