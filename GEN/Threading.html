Why Multithreading

An application uses multiple threads to keep hardware busy and users happy. The most common reasons are:

  • Better use of a single CPU
    While one thread waits for I/O, another thread can use the CPU.
  • Better use of multiple CPUs or cores
    One thread can run on only one core at a time; more threads can keep every core busy.
  • Responsiveness
    Long tasks run in the background, so the UI or the request listener never freezes.
  • Fairness
    Each client gets its own thread, so one slow request cannot hold up everyone else.
  • Simpler program design
    Each thread follows one task from start to end instead of the program juggling the state of many tasks.
Better Utilization of a Single CPU

A thread often spends time waiting, for example for a response to a network request or for a disk read. During that wait the CPU sits idle. With another thread ready to run, the CPU can do useful work in the meantime.

Better Utilization of Multiple CPUs or Cores

A single thread can use at most one CPU core, and as shown above it may not even keep that core fully busy. To use all the cores of a machine, an application needs several threads running in parallel.

Better CPU Utilization: Example

Suppose an application reads files from disk and then processes them. Reading a file takes 5 seconds and processing it takes 2 seconds. Done one after another, two files take:

Sequential
 5 seconds  reading file A
 2 seconds  processing file A
 5 seconds  reading file B
 2 seconds  processing file B
-------------------------------
14 seconds  total

While a file is being read, the CPU mostly waits for the disk. If the program starts reading file B while it processes file A, the waits overlap:

Overlapped
 5 seconds  reading file A
 5 seconds  reading file B + 2 seconds processing file A
 2 seconds  processing file B
-------------------------------
12 seconds  total

The same idea applies to any slow I/O: disk, network or user input. Disk and network I/O are far slower than the CPU and memory, so there is almost always idle CPU time to fill.

Simpler Program Design

Getting the overlapped ordering above in a single thread means tracking by hand how far each file has been read and processed. With two threads, each one simply reads and processes its own file. A thread blocks while its disk read is in progress, and the other thread uses the CPU in the meantime. The disk and the CPU both stay busy, and each thread only has to keep track of one file.

More Responsive Programs

A single-threaded server listens on a port, handles each request completely, and only then goes back to listening:

Single-Threaded Server
while (server is active) {
    listen for request
    process request
}

If a request takes a long time, no other client can connect until it finishes, because requests are only accepted while the server is listening. A better design hands each request to a worker thread and goes straight back to listening:

Server With Worker Threads
while (server is active) {
    listen for request
    hand request to worker thread
}

The worker processes the request and replies to the client, while the listening thread is already accepting the next one. More clients can connect, so the server is more responsive.

Desktop applications work the same way. If the thread that draws windows and buttons also runs a long task, the application appears frozen until the task ends. Handing the task to a worker thread keeps the window thread free to respond to the user. When the worker finishes, it signals the window thread, which then shows the result.

Fairness

Threads also share a machine more fairly among users. Imagine a server that handles every client request on one thread. A single slow request makes all other clients wait until it finishes. When each client’s request runs on its own thread, no single task can monopolize the CPU.
