Livelock

Livelock happens when threads keep changing state in response to each other but make no progress.

Unlike deadlock, the threads are not blocked; they are actively busy yet accomplish nothing.

A classic case is two threads that each politely back off and retry in lock-step forever.

Detection looks for repeated retries with no forward progress over time.

Key points
  • Suspect livelock when CPU is busy but throughput is zero.
  • Common with naive tryLock-and-back-off retry loops.
  • Detect via retry counters, timeouts and progress metrics.
  • Fix with randomised back-off to break the symmetry.
Pros and Cons
Threads Stay Responsive

Threads remain responsive, unlike a hard deadlock where they are fully blocked.

Cheap To Resolve

Randomised back-off usually resolves it cheaply.

Observable And Testable

Retry counters make it observable and testable.

Wastes CPU

It wastes CPU while making no progress.

Hard To Spot

It is harder to spot than deadlock because nothing is blocked.

Tricky To Tune

Detection thresholds are workload-dependent and tricky to tune.

Code
public class LivelockGuard {
    public boolean acquire(ReentrantLock lock) throws InterruptedException {
        int attempts = 0;
        while (attempts < 5) {      # Bounded retries detect livelock
            if (lock.tryLock(50, TimeUnit.MILLISECONDS)) return true;
            attempts++;
            # Randomised back-off breaks the lock-step
            Thread.sleep(ThreadLocalRandom.current().nextInt(10, 100));
        }
        System.out.println("possible livelock, giving up");
        return false;
    }
}
How it works

A bounded attempts counter caps futile retries.

Randomised sleep desynchronises threads that were mirroring each other.

Exceeding the retry limit flags a likely livelock.

The method returns instead of spinning forever.
