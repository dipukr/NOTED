Producer-Consumer Problem

The Producer-Consumer problem coordinates threads that produce data with threads that consume it through a shared bounded buffer. Producers must wait when the buffer is full; consumers must wait when it is empty.

It is a classic inter-thread cooperation problem solved with wait-notify or blocking queues.

Correct signalling prevents lost updates, busy waiting and race conditions on the shared buffer.

Key points
  • Decouple work generation from work processing at different rates.
  • Use a bounded buffer to apply back-pressure and cap memory use.
  • Prefer BlockingQueue which handles the wait/notify internally.
  • Always call wait/notify inside a synchronized block owning the monitor.
Pros and Cons
Smooths Bursty Load

Buffering absorbs uneven production rates so downstream work is smoothed out over time.

Clean Separation

Producer and consumer responsibilities are cleanly decoupled from each other.

No Manual Locking

Blocking queues handle the wait and notify internally, removing the need for manual locking.

Buffer Sizing

Choosing a buffer size is a tuning trade-off between latency and memory use.

Error-Prone Signalling

Manual wait-notify is error-prone, risking missed signals and spurious wakeups.

Slow Consumer Throttles

A slow consumer can throttle the throughput of the whole pipeline.

Code
public class BoundedBuffer {
    private ReentrantLock lock = new ReentrantLock(true);
    private Condition notEmpty = lock.newCondition();
    private Condition notFull = lock.newCondition();
    private Object[] items = new Object[100];
    private int putptr, takeptr, count;

    public void put(Object item) throws Exception {
        lock.lock();
        try {
            while (count == items.length)
                notFull.await();
            items[putptr++] = item;
            if (putptr == items.length)
                putptr = 0;
            count += 1;
            notEmpty.signalAll();
        } finally {
            lock.unlock();
        }
    }

    public Object take() throws Exception {
        lock.lock();
        try {
            while (count == 0)
                notEmpty.await();
            Object item = items[takeptr++];
            if (takeptr == items.length)
                takeptr = 0;
            count -= 1;
            notFull.signalAll();
            return item;
        } finally {
            lock.unlock();
        }
    }
}

void main() throws Exception {
    var buffer = new BoundedBuffer();

    Thread producer = new Thread(() -> {
        try {
            for (int i = 0; i < 10; i++) {
                buffer.put("item-" + i);
                System.out.println("Produced item-" + i);
            }
        } catch (Exception e) {
            Thread.currentThread().interrupt();
        }
    }, "Producer");

    Thread consumer = new Thread(() -> {
        try {
            for (int i = 0; i < 10; i++) {
                Object item = buffer.take();
                System.out.println("Consumed " + item);
            }
        } catch (Exception e) {
            Thread.currentThread().interrupt();
        }
    }, "Consumer");

    producer.start();
    consumer.start();
    producer.join();
    consumer.join();
}
How it works

A single ReentrantLock guards the shared circular array items; only one thread — producer or consumer — can be inside put/take at a time.

lock.newCondition() creates a condition variable bound to that lock. Unlike the lock itself, a condition doesn't protect data; it lets a thread that holds the lock give it up and sleep until some predicate about that data becomes true.

Two separate conditions model two separate predicates on the same buffer: notFull means "there's room to put", notEmpty means "there's an item to take". Splitting them avoids waking every waiter for every change — a producer's signal only wakes consumers, not other producers.

Calling notFull.await() atomically releases lock and suspends the thread. Both steps happen as one operation, so no other thread can sneak in between "check the condition" and "go to sleep" and change the buffer unseen — that gap is exactly what causes the classic lost-wakeup bug.

While a thread waits inside await(), the lock is free, so the other side (say, the consumer taking items) can acquire it, run, and call signalAll().

signalAll() wakes every thread parked on that condition, but they don't resume immediately — each first re-acquires lock (queueing if the signaller still holds it, which it does until unlock() runs in finally), and only then returns from await().

The condition is checked in a while loop, not an if. After being woken, a thread must re-verify the predicate itself: signalAll() can wake more threads than there is capacity for (e.g. three consumers woken by one put), and the JVM is also permitted to wake a waiter with no signal at all (a "spurious wakeup"). The loop re-checks count and calls await() again if the buffer isn't actually in the state this thread needs.

putptr/takeptr wrap around the array (circular/ring buffer) so slots are reused without shifting elements; count is the single source of truth both conditions are evaluated against.

Each successful put increases count and calls notEmpty.signalAll() (data now exists); each successful take decreases count and calls notFull.signalAll() (space now exists) — each side only ever wakes the other.

The try/finally guarantees lock.unlock() runs even if an exception is thrown mid-method, so the lock (and therefore the buffer) can never be left permanently stuck.

void main() sits outside BoundedBuffer as a top-level instance main method (JDK 25's implicitly-declared class feature) — no public static, no enclosing class, no String[] args needed for this simple case.

It starts one producer thread calling put and one consumer thread calling take concurrently on the same buffer; join() waits for both to finish before the program exits.
