Concurrency

Java multithreading and concurrency are fundamental concepts for building efficient and responsive applications, especially in modern multi-core environments.

Multithreading refers to the ability of a program to execute multiple parts of its code (called threads) concurrently within a single process. This allows a program to perform multiple tasks seemingly simultaneously, improving responsiveness and resource utilization. In Java, threads can be created by extending the Thread class or by implementing the Runnable interface.

Concurrency is the ability of multiple threads to access and operate on shared resources (like data or objects) at the same time. While multithreading enables the execution of multiple threads, concurrency addresses the challenges that arise when these threads interact with shared resources. Without proper handling, concurrent access can lead to issues such as:

  • Race Conditions: When the outcome of a program depends on the unpredictable timing of operations by multiple threads accessing shared data.
  • Deadlocks: When two or more threads are blocked indefinitely, waiting for each other to release resources.
  • Data Inconsistency: When shared data is modified by multiple threads in an uncoordinated manner, leading to incorrect or unexpected values.

To manage concurrency and prevent these issues, Java provides various synchronization mechanisms:

  • synchronized keyword: Used to create synchronized blocks or methods, ensuring that only one thread can execute a critical section of code at a time.
  • Lock interface (from java.util.concurrent.locks): Offers more flexible and powerful locking mechanisms than synchronized blocks, including reentrant locks, read-write locks, and condition variables.
  • Semaphore (from java.util.concurrent): Controls access to a limited number of resources.
  • Atomic classes (from java.util.concurrent.atomic): Provide atomic operations on single variables, ensuring thread-safe updates without explicit locking.
  • java.util.concurrent package: Offers a rich set of high-level concurrency utilities, including ExecutorService for managing thread pools, CountDownLatch, CyclicBarrier, and BlockingQueue for inter-thread communication and coordination.
Best Practices for Java Concurrency
  • Minimize shared mutable state: Design classes to be immutable or minimize the amount of mutable data shared between threads.
  • Use appropriate synchronization: Choose the right synchronization mechanism based on the specific needs of the application.
  • Avoid deadlocks: Implement careful resource ordering and timeout mechanisms to prevent deadlocks.
  • Test thoroughly: Concurrent programs can be complex and require extensive testing to ensure correctness and performance.
Concurrency vs Parallelism

The two words are often used interchangeably, but they describe different things. Concurrency is about structure: several tasks are in progress during the same period and their steps may interleave, even on a single CPU core. Parallelism is about execution: several tasks literally run at the same instant on different cores.

A program can be concurrent without being parallel (one core switching between threads) and parallel without much concurrency design (splitting one big computation across cores). Java’s concurrency tools make the first safe and the second practical.

Process vs Thread
  • Process
    An independent running program with its own memory space; processes communicate only through the operating system (files, sockets, pipes).
  • Thread
    A path of execution inside a process; all threads of a process share its heap memory, but each has its own stack and program counter.
  • Why threads are cheaper
    Creating and switching threads costs less than processes because there is no separate memory space to set up, which is also why shared data needs protection.
Pros and Cons

Pros

  • Responsiveness
    Long-running work runs on background threads, so the user interface or request handler is never frozen.
  • Better CPU Utilization
    Work spreads across all cores instead of leaving most of them idle.
  • Higher Throughput
    While one thread waits on I/O, others keep doing useful work.
  • Natural Modelling
    Independent activities, such as serving many clients, map directly to independent threads or tasks.

Cons

  • Hard to Reason About
    The number of possible interleavings explodes, so correctness can no longer be checked by reading the code top to bottom.
  • Non-Deterministic Bugs
    Race conditions and deadlocks may appear only under load or on certain machines, and are hard to reproduce and test.
  • Overhead
    Thread creation, context switching, and lock contention cost time and memory; too many threads can make a program slower.
  • Shared-State Complexity
    Every piece of shared mutable data needs a clear protection strategy, which adds design and review effort.
Creating Threads
public class Worker extends Thread {

    @Override
    public void run() {
        System.out.println("Extending Thread: " + getName());
    }
}

public class Main {

    public static void main(String[] args) throws InterruptedException {
        Thread first = new Worker();
        Runnable task = () -> System.out.println("Implementing Runnable");
        Thread second = new Thread(task);
        first.start(); # start(), not run(), creates a new thread
        second.start();
        first.join(); # wait for both to finish
        second.join();
    }
}
How it works

Extending Thread puts the work in run(); implementing Runnable keeps the task separate from the thread that runs it.

Runnable is usually preferred: the class can still extend something else, and the same task can be handed to a thread pool.

Calling run() directly would execute the code on the current thread; start() is what creates a new one.

Race Condition
public class Counter {

    private int count;

    public void increment() {
        count++; # read, add, write: three steps
    }

    public int get() {
        return count;
    }
}

public class Main {

    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Runnable task = () -> {
            for (int i = 0; i < 10_000; i++) counter.increment();
        };
        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println(counter.get()); # often less than 20000
    }
}
How it works

count++ reads the value, adds one, and writes it back.

If both threads read the same value before either writes, one increment is lost, so the final total changes from run to run.

This is a race condition: the result depends on how the two threads happen to interleave.

Fixing It
public class SynchronizedCounter {

    private int count;

    public synchronized void increment() {
        count++; # one thread at a time
    }

    public synchronized int get() {
        return count;
    }
}

public class AtomicCounter {

    private AtomicInteger count = new AtomicInteger();

    public void increment() {
        count.incrementAndGet(); # lock-free compare-and-set
    }

    public int get() {
        return count.get();
    }
}
How it works

synchronized makes the read-add-write a single critical section, and also guarantees that get() sees the latest value.

AtomicInteger does the same update without locking, using a hardware compare-and-set that retries if another thread changed the value first.

Either version always prints 20000.

Using an Executor
void main(String[] args) {
    AtomicInteger counter = new AtomicInteger();
    try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
        for (int i = 0; i < 1_000; i++) {
            pool.submit(counter::incrementAndGet);
        }
    } # close() waits for every submitted task
    System.out.println(counter.get()); # always 1000
}
How it works

Instead of creating a thread per task, four pooled threads take turns running the 1,000 submitted tasks.

Since Java 19, ExecutorService is AutoCloseable: leaving the try block shuts the pool down and waits for running tasks.

Swapping in Executors.newVirtualThreadPerTaskExecutor() runs each task on its own virtual thread.
