Microservices Resilience Note

Cascading Failure in Microservices

How a local slowdown or failure propagates through dependent services, why retries can amplify it, and how resilience patterns contain the blast radius.

What is a Cascading Failure?

A cascading failure in microservices happens when a failure or slowdown in one service causes dependent services to fail or slow down, and that impact keeps spreading through the system.

Suppose you have:

Client
  |
  v
Order Service
  |
  +----> Payment Service
  |
  +----> Inventory Service
  |
  +----> Shipping Service

Now imagine Payment Service becomes slow.
Order Service calls it and waits. While waiting, its request threads remain occupied.

Payment Service slow
        ↓
Order Service threads start waiting
        ↓
Order Service thread pool fills
        ↓
New Order requests cannot be processed
        ↓
Clients retry
        ↓
More requests hit Order Service
        ↓
Even more calls go to Payment Service
        ↓
Payment Service becomes even more overloaded
That is a cascading failure.

A More Realistic Example

Imagine these services:

API Gateway
     |
     v
Order Service
     |
     +------> User Service
     |
     +------> Inventory Service
     |
     +------> Payment Service
                     |
                     v
                  Bank API

Normally:

Order Service
    |
    | 100 ms
    v
Payment Service
    |
    | 200 ms
    v
Bank API

Total request might finish in about:

~300-500 ms

But suddenly the external Bank API starts taking 20 seconds.

Payment Service threads now look like this:

Thread 1 ───── waiting for Bank API
Thread 2 ───── waiting for Bank API
Thread 3 ───── waiting for Bank API
Thread 4 ───── waiting for Bank API
...
Thread 200 ─── waiting for Bank API

Eventually:

Payment Service thread pool = exhausted

Now Order Service calls Payment Service and waits too.

Bank API slow
     ↓
Payment Service overloaded
     ↓
Order Service requests blocked
     ↓
Order Service thread pool exhausted
     ↓
API Gateway requests wait
     ↓
Gateway connections increase
     ↓
Clients timeout
     ↓
Clients retry
     ↓
Traffic increases further
A single slow external dependency can therefore affect the entire platform.

The Dangerous Part: Retries

Retries often make cascading failures much worse.

Suppose you normally receive:

1000 requests/sec

Payment Service starts timing out. Clients retry 3 times:

Original traffic = 1000 req/sec

Retry #1 = 1000
Retry #2 = 1000
Retry #3 = 1000

Potential effective load:

4000 requests/sec

So the service is already unhealthy, and retries send even more traffic to it.

This is called a retry storm.

Service slow
   ↓
Timeout
   ↓
Retry
   ↓
More traffic
   ↓
Service becomes slower
   ↓
More timeout
   ↓
More retries
   ↓
Collapse

Why Cascading Failures Happen

Several mechanisms commonly cause them.

1. Long or Missing Timeouts

Bad:

paymentService.call();

where the HTTP client effectively waits for a very long time.

One downstream slowdown then holds upstream resources.

Better:

connection timeout = 500 ms
request timeout = 2 sec

Fail quickly rather than hold resources indefinitely.

2. Shared Thread Pools

Suppose Order Service has:

Tomcat worker threads = 200

Every request calls Payment Service synchronously.

If Payment takes 30 seconds:

200 requests
      ↓
200 threads blocked
      ↓
thread pool exhausted

Now even endpoints unrelated to payments may fail.

For example:

GET /health
GET /orders
GET /customers

can become unavailable because the same thread pool is exhausted.

3. Unlimited Queues

Sometimes services try to protect themselves by queueing work.

But an unlimited queue often just delays the crash.

Incoming requests
       ↓
Queue
       ↓
Service

If arrival rate is:

10,000 requests/sec

but processing capacity is:

5,000 requests/sec

the queue grows by:

5,000 requests/sec

Eventually:

huge queue
   ↓
high memory usage
   ↓
GC pressure
   ↓
latency increases
   ↓
OOM

Bounded queues are usually safer.

4. Connection Pool Exhaustion

Suppose:

Order Service
     ↓
Database

Database becomes slow.

Order Service has:

DB connection pool = 50

Soon:

50 slow queries
     ↓
all 50 DB connections occupied
     ↓
new requests wait for connection
     ↓
application threads block
     ↓
thread pool fills

A database slowdown therefore becomes an application outage.

5. Synchronous Dependency Chains

Consider:

Service A
   ↓
Service B
   ↓
Service C
   ↓
Service D
   ↓
Database

If D slows down:

D slow
↓
C waits
↓
B waits
↓
A waits

Long synchronous chains are particularly vulnerable.

How to Prevent Cascading Failures

The most important resilience techniques are:

Timeouts
Circuit Breakers
Bulkheads
Rate Limiting
Backpressure
Retries with Backoff
Load Shedding
Caching
Async Messaging
Fallbacks

These patterns work together.

1. Timeouts

Every remote call should generally have a bounded timeout.

For example:

HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofMillis(500))
        .build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("http://payment-service/pay"))
        .timeout(Duration.ofSeconds(2))
        .build();

Instead of:

Order Service waits 30 seconds

you prefer something like:

Order Service waits max 2 seconds

Then resources are released sooner.

2. Circuit Breaker

A circuit breaker stops repeatedly calling a failing dependency.

Think of an electrical circuit breaker.

Normal state:

Order Service
      |
      v
Payment Service

Circuit = CLOSED

Calls are allowed.

After repeated failures:

Order Service
      |
      X
Payment Service

Circuit = OPEN

Calls fail immediately.

Instead of:

request
   ↓
wait 20 seconds
   ↓
timeout

you get:

request
   ↓
circuit open
   ↓
fail in 1 ms

This protects both services.

With Resilience4j:

@CircuitBreaker(
    name = "paymentService",
    fallbackMethod = "paymentFallback"
)
public PaymentResponse pay(Order order) {

    return paymentClient.pay(order);
}

public PaymentResponse paymentFallback(
        Order order,
        Throwable throwable) {

    return new PaymentResponse(
        "PAYMENT_TEMPORARILY_UNAVAILABLE"
    );
}

3. Bulkhead Isolation

Bulkheads come from ships.

A ship is divided into compartments:

+---------+---------+---------+
| Comp A  | Comp B  | Comp C  |
+---------+---------+---------+

If one compartment floods, the others remain intact.

Apply the same idea to microservices.

Instead of:

Shared thread pool
      |
      + Payment
      + Inventory
      + Shipping

use separate limits:

Payment pool   = 30 threads
Inventory pool = 40 threads
Shipping pool  = 30 threads

If Payment gets stuck:

Payment pool exhausted

but:

Inventory still works
Shipping still works

The failure is contained.

4. Rate Limiting

Prevent excessive traffic from reaching a struggling service.

For example:

Payment Service capacity:

2000 req/sec

Set a limit around that level rather than allowing:

10,000 req/sec

during a traffic spike.

Conceptually:

Requests
   |
   v
Rate Limiter
   |
   +---- allowed ----> Payment
   |
   +---- rejected ---> 429 Too Many Requests

Rejecting some traffic can protect the system from total collapse.

5. Exponential Backoff

Bad retry strategy:

retry after 0 ms
retry after 0 ms
retry after 0 ms

Better:

attempt 1
   ↓
wait 100 ms

attempt 2
   ↓
wait 200 ms

attempt 3
   ↓
wait 400 ms

attempt 4
   ↓
wait 800 ms

Usually add jitter too:

100 ms ± random
200 ms ± random
400 ms ± random

Jitter prevents thousands of clients from retrying at exactly the same time.

6. Backpressure

Suppose:

Producer = 10,000 events/sec
Consumer = 2,000 events/sec

Without backpressure:

Producer
   ↓↓↓↓↓↓↓↓↓↓↓↓↓
Consumer

the consumer becomes overwhelmed.

Backpressure means the consumer or infrastructure communicates:

"Slow down. I cannot process that fast."

This is especially important in reactive and streaming systems.

7. Load Shedding

Sometimes the correct behavior is simply:

Reject some work.

Suppose CPU reaches 95%.

Instead of accepting everything:

100% traffic
    ↓
service dies

accept important traffic and reject less important work:

Critical requests → process

Low-priority requests → reject

This is called load shedding.

A partial service is often better than a completely dead service.

8. Use Asynchronous Communication Where Appropriate

Instead of:

Order
  ↓ synchronous
Email
  ↓ synchronous
Analytics
  ↓ synchronous
Notification

you might use:

Order Service
      |
      v
    Kafka
   /  |   \
  v   v    v
Email Analytics Notification

Order creation no longer depends on all those consumers being immediately healthy.

If Email Service is down:

Kafka retains events

and Email Service catches up later.

This significantly reduces failure propagation.

Failure vs. Cascading Failure

A simple failure:

Payment Service crashes

Only payment requests fail.

Cascading failure:

Payment Service crashes
        ↓
Order Service waits/retries
        ↓
Order Service overloaded
        ↓
API Gateway overloaded
        ↓
clients retry
        ↓
database overloaded
        ↓
entire platform unavailable
The defining characteristic is: The failure spreads beyond the component that originally failed.

A Robust Architecture Might Look Like This

                 Client
                   |
                   v
              API Gateway
                   |
             Rate Limiter
                   |
                   v
             Order Service
              /         \
             /           \
            v             v
      Inventory       Payment
      Bulkhead        Bulkhead
                         |
                   Circuit Breaker
                         |
                       Timeout
                         |
                         v
                      Bank API

And asynchronous side effects:

Order Service
      |
      v
    Kafka
   /  |   \
  v   v    v
Email Analytics Shipping

Now if the Bank API fails:

Bank fails
   ↓
Payment calls timeout
   ↓
Circuit breaker opens
   ↓
Payment failures are isolated
   ↓
Order service remains responsive
   ↓
Other services stay healthy

That is the main goal of resilience engineering:

Don't try to guarantee that nothing fails. Design the system so that failures remain contained.

A Useful Mental Model

Timeout
   prevents long waiting

Circuit Breaker
   prevents repeated calls to broken dependencies

Bulkhead
   prevents resource exhaustion from spreading

Rate Limiter
   prevents overload

Backoff + Jitter
   prevents retry storms

Async Messaging
   reduces synchronous dependency chains

Load Shedding
   protects the system under extreme load

In microservices, a healthy architecture assumes that network calls will fail, services will slow down, databases will stall, and dependencies will sometimes disappear.

Cascading failure occurs when the architecture allows those local failures to consume shared resources and propagate outward.
