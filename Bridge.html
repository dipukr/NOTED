Bridge Pattern

Bridge is a structural design pattern that decouples an abstraction from its implementation so that the two can vary independently.

Instead of binding an abstraction to a single implementation through inheritance, the Bridge places the implementation behind its own interface and holds a reference to it via composition.

This prevents a combinatorial explosion of subclasses when an abstraction can have several dimensions of variation.

When to use
  • When both an abstraction and its implementation should be extensible independently.
  • When you want to avoid a permanent binding between abstraction and implementation.
  • When a class has multiple orthogonal dimensions of variation.
  • When inheritance would otherwise cause a class explosion.
  • When you want to switch implementations at runtime.
Advantages
  • Abstraction and implementation can evolve separately.
  • Avoids a combinatorial explosion of subclasses.
  • Follows the open/closed principle for both hierarchies.
  • Hides implementation details from the client.
  • Allows implementations to be swapped at runtime.
Disadvantages
  • Increases complexity by introducing extra layers and interfaces.
  • Can be hard to apply to a highly cohesive class.
  • The added indirection may be unnecessary for simple designs.
Code
// Implementation side
interface Device {
    void setVolume(int percent);
}

class TV implements Device {
    public void setVolume(int p) {
        System.out.println("TV volume = " + p);
    }
}

// Abstraction side holds a Device (the bridge)
abstract class Remote {
    protected final Device device;
    protected Remote(Device device) {
        this.device = device;
    }
    abstract void volumeUp();
}

class BasicRemote extends Remote {
    public BasicRemote(Device d) { super(d); }
    public void volumeUp() { device.setVolume(30); }
}

void main() {
    Remote r = new BasicRemote(new TV());
    r.volumeUp();
}
How the Bridge works
  • Device is the implementation hierarchy; Remote is the abstraction hierarchy.
  • Remote holds a Device reference by composition instead of extending it.
  • New remotes and new devices can be added independently without cross-multiplying classes.
  • The client combines any remote with any device at runtime.
