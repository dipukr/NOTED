Prototype Pattern

The Prototype Pattern is a creational design pattern that creates new objects by copying an existing object (prototype) instead of creating a new object from scratch. This is useful when object creation is costly or complex, and when a new object should start as a duplicate of a configured instance.

In Java the pattern is often implemented with the Cloneable interface and the clone() method, taking care to choose between shallow and deep copying.

Use Prototype when
Object creation is expensive

Database initialization, complex calculations, large object graphs, external resource loading, or expensive configuration.

Objects have complex configuration

Instead of repeatedly calling many setters, create one configured prototype and copy it.

Many similar objects are required

Clone the prototype and customize each copy.

The concrete class should be hidden

The client works against a prototype abstraction without knowing the construction details.

Pros and Cons
Reduced Creation Cost

Expensive initialization can be avoided for every new object by copying an initialized prototype.

Preserves Object State

A clone starts with the prototype's already-configured state.

Less Repeated Construction

Common configuration lives in the prototype instead of being rebuilt each time.

Hides Complex Construction

The client does not need to know how the object was originally built.

Runtime Configuration

Different prototypes can represent different predefined configurations chosen at runtime.

Cloning Can Be Complicated

Complex object graphs require careful, correct copying.

Shallow-Copy Bugs

Mutable nested objects may accidentally remain shared between original and clone.

Deep-Copy Complexity

Nested references, circular references, and resource ownership make copying difficult.

Maintenance Burden

Whenever the object structure changes, the copy logic may also need to change.

Real-world example
  • Java Object.clone() — the language-level prototype mechanism where a Cloneable object copies itself field by field.
  • Java ArrayList and HashMap copy constructors — new ArrayList<>(list) produces an independent copy of a configured collection.
  • Spring bean scope "prototype" — the container hands out a fresh instance on each request instead of a shared singleton.
  • Object copying libraries — Apache Commons SerializationUtils.clone() and deep-copy utilities duplicate whole object graphs.
  • Game and graphics engines — spawning many enemies, bullets, or shapes by cloning a preconfigured template object.
  • Document and design tools — "Duplicate" on a slide, shape, or layer creates a new item copied from the selected one.
  • Cell division analogy — a cell reproduces by copying itself, producing a new cell that starts from the parent's state.
Code
public class Document implements Cloneable {
    private String title;
    private List<String> pages;

    public Document(String title, List<String> pages) {
        this.title = title;
        this.pages = pages;
    }

    @Override
    public Document clone() {
        # Deep copy of the mutable list
        return new Document(title, new ArrayList<>(pages));
    }

    public void setTitle(String t) {this.title = t;}
}

void main() {
    Document original =
        new Document("Draft", new ArrayList<>());
    Document copy = original.clone();
    copy.setTitle("Final");  # original unaffected
}
How the Prototype works

Document implements Cloneable and overrides clone().

The overridden clone() copies the mutable pages list to give a true deep copy.

New objects are produced by copying an existing prototype, not via new with full setup.

Changing the copy leaves the original untouched because its data was duplicated.

The Problem Prototype Solves

Suppose an application creates a complex Document object:

public class Document {
    private String title;
    private String content;
    private String author;
    private List<String> tags;

    # constructor, getters, setters
}

If every document requires many configuration steps, repeatedly constructing the object can be verbose and expensive.

Document document = new Document();

document.setTitle("Java Design Patterns");
document.setContent("...");
document.setAuthor("John");
document.setTags(List.of("Java", "Design Patterns"));

Now imagine that creating the object also requires

  • Reading configuration
  • Loading data from a database
  • Performing expensive calculations
  • Creating many nested objects
  • Loading external resources

In such cases, cloning an already initialized object can be much cheaper than constructing a fresh one every time.

Simple Java Example

Prototype Interface

public interface Cloneable<T> {
    T clone();
}

Concrete Prototype

public class Document implements Cloneable<Document> {
    private String title;
    private String content;
    private String author;
    private List<String> tags;

    public Document(String title, String content, String author, List<String> tags) {
        this.title = title;
        this.content = content;
        this.author = author;
        this.tags = new ArrayList<>(tags);
    }

    @Override
    public Document clone() {
        return new Document(this.title, this.content, this.author, this.tags);
    }
}

Client Code

Document prototype = new Document(
        "Java Design Patterns",
        "Prototype Pattern...",
        "John",
        List.of("Java", "Design Patterns"));

Document document1 = prototype.clone();
Document document2 = prototype.clone();
Why Not Just Use new?

Without Prototype, the client needs to know the complete construction process:

Document document1 = new Document(
        "Java Design Patterns", "Prototype Pattern...",
        "John", List.of("Java", "Design Patterns"));

Document document2 = new Document(
        "Java Design Patterns", "Prototype Pattern...",
        "John", List.of("Java", "Design Patterns"));

With Prototype:

Document document1 = prototype.clone();
Document document2 = prototype.clone();

The client does not need to know the details of how the original object was constructed.

Prototype with Expensive Object Creation

Consider an object whose constructor performs expensive initialization:

public class Report {

    private String data;

    public Report() {
        loadDataFromDatabase();
        performComplexCalculation();
        initializeFormatting();
    }

    private void loadDataFromDatabase() {
        System.out.println("Loading data...");
    }

    private void performComplexCalculation() {
        System.out.println("Performing calculations...");
    }

    private void initializeFormatting() {
        System.out.println("Initializing formatting...");
    }
}

Repeated construction can repeat the expensive initialization:

Report report1 = new Report();
Report report2 = new Report();
Report report3 = new Report();

With a suitable Prototype implementation, an initialized prototype can be copied and then modified as necessary.

Shallow Copy vs Deep Copy

This is one of the most important considerations when implementing Prototype.

Shallow Copy — copies primitive values and references, but referenced mutable objects may still be shared.

Deep Copy — also copies the nested mutable objects so that the original and clone have independent object graphs.

public class Employee implements Cloneable/span><Employee> {
    private String name;
    private Address address;

    @Override
    public Employee clone() {
        Employee clone = new Employee();
        clone.name = this.name;
        clone.address = this.address.clone();
        return clone;
    }
}
Copy Constructor Approach

An explicit copy constructor is often a clear way to implement Prototype-style copying.

public class Employee {
    private String name;
    private Address address;

    public Employee(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    public Employee(Employee other) {
        this.name = other.name;
        this.address = new Address(other.address);
    }
}

Employee prototype = new Employee("DEEPOO", 
        new Address("Delhi"));

@ copy constructor makes an independent copy
Employee copy = new Employee(prototype);
Prototype Registry

A Prototype Registry stores predefined prototype objects. Clients can request a clone using a key.

public class PrototypeRegistry {
    private final Map<String, Document> prototypes = new HashMap<>();

    public void register(String key, Document prototype) {
        prototypes.put(key, prototype);
    }

    public Document create(String key) {
        Document prototype = prototypes.get(key);
        if (prototype == null)
            throw new IllegalArgumentException("Unknown prototype: " + key);}
        return prototype.clone();
    }
}

Usage:

PrototypeRegistry registry = new PrototypeRegistry();
Document invoicePrototype = new Document("Invoice", "Invoice Content", "Company", List.of("Finance", "Invoice"));
registry.register("invoice", invoicePrototype);

Document invoice1 = registry.create("invoice");
Document invoice2 = registry.create("invoice");
Document invoice3 = registry.create("invoice");
