Outbox Pattern

The Outbox pattern reliably publishes events by writing them to a database table in the same transaction as the business data.

It solves the dual-write problem: updating a database and a message broker cannot be atomic on their own.

A separate relay process reads the outbox table and publishes the events to the broker.

This guarantees an event is published if and only if the business change was committed.

When to use / Key points
  • Use whenever a state change must reliably produce an event.
  • Business row and outbox row are saved in one local transaction.
  • A poller or CDC tool ships outbox rows to the broker.
  • Consumers must be idempotent since delivery is at-least-once.
Advantages
  • No lost events: publishing is atomic with the data change.
  • Works with any broker, no distributed transaction needed.
  • Survives crashes; unsent rows are retried later.
Disadvantages / Trade-offs
  • Adds an outbox table and a relay process to operate.
  • At-least-once delivery requires idempotent consumers.
  • Slight publishing latency from the polling interval.
Code
# Business change and event saved in ONE transaction
@Service
public class OrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;

    public OrderService(OrderRepository orders, OutboxRepository outbox) {
        this.orders = orders;
        this.outbox = outbox;
    }

    @Transactional
    public void placeOrder(Order order) {
        orders.save(order);            # business row
        outbox.save(new OutboxEvent(   # event row, same txn
            "OrderPlaced", order.getId()));
    }
}
# A scheduled relay later reads OutboxEvent rows and publishes them.
How it works

Both saves commit or roll back together under @Transactional.

A relay polls OutboxEvent rows and sends them to the broker.

If the transaction fails, no event is ever emitted.
