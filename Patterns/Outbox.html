Outbox Pattern

Outbox Pattern reliably publishes events by writing them to a DB table in the same transaction as the business data.

Outbox solves the dual-write problem: updating a database and a message broker cannot be atomic on their own.

Outbox is one of the most important patterns for building reliable, event-driven microservices with Spring Boot.

A separate relay process reads the outbox table and publishes the events to the broker.

This guarantees an event is published if and only if the business change was committed.

Consumers must be idempotent since delivery is at-least-once.

Advantages
No Lost Events

The event row commits in the same transaction as the data, so an event exists exactly when the business change did.

No Distributed Transaction

Only a local DB transaction is needed; it avoids two-phase commit (XA) across the database and the broker.

Crash-Safe and Retryable

Unsent rows survive restarts and are retried until delivered, giving at-least-once guarantees.

Decoupled from the Broker

The write succeeds even if Kafka is down; the relay catches up once it recovers.

Broker-Agnostic

Works with Kafka, RabbitMQ, or any transport, since the source of truth is a table.

CDC-Friendly

The same table can be streamed by Debezium for near real-time publishing with no polling overhead.

Disadvantages
More Moving Parts

An outbox table plus a relay (poller or CDC connector) to build, deploy, and monitor.

At-Least-Once, Not Exactly-Once

The same event can be delivered twice, so consumers must be idempotent.

Publishing Latency

A polling relay adds delay up to one poll interval; CDC shrinks this but never fully removes it.

Table Growth

Sent rows must be purged or archived, or the outbox table bloats over time.

Concurrency Care

Scaling to multiple relay instances needs row locking (for example SKIP LOCKED) to avoid double-sends and reordering.

Schema Coupling

The event payload stored in the table has to evolve carefully alongside the data model.

Problem the Outbox pattern solves

When you have a transactional database and you want to publish events (Kafka, RabbitMQ) reliably, a problem arises:

  • You update your database (say, create an order).
  • You need to publish an event (OrderCreated) to Kafka so other services (like Inventory, Payment) know about it.
  • If you update the DB successfully but fail to publish the Kafka message (network down, broker crash, app crash), your system becomes inconsistent.

This is called the Dual-write Problem the DB and Kafka are updated independently, and one might fail.

Outbox pattern: solution

The Outbox pattern avoids the dual-write problem by:

  1. Writing the event into a local outbox table in the same transaction as the business operation.
  2. A background process (Debezium CDC, Scheduled job) reads from the outbox table and publishes events to Kafka.
  3. Once published, the outbox record is marked as sent (or deleted).

This ensures that either both the DB change and the event are recorded, or neither is — giving guaranteed at-least-once delivery of events.

Outbox table

Event is stored as a row alongside the business data. A published flag lets a poller find rows that still need to be sent.

CREATE TABLE outbox_event (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    aggregate_type VARCHAR(255),        # e.g. "Order"
    aggregate_id   VARCHAR(255),        # e.g. "order-101"
    event_type     VARCHAR(255),        # e.g. "OrderCreated"
    payload        JSON,                # event body
    created_at     TIMESTAMP,
    published      BOOLEAN DEFAULT FALSE
);
Entities

The business entity (Order) and the OutboxEvent that records what happened.

@Entity
@Table(name = "orders")
public class Order {
    @Id
    private String id;
    private String status;
    private Double amount;
}

@Entity
@Table(name = "outbox_event")
public class OutboxEvent {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String aggregateType;   # e.g. "Order"
    private String aggregateId;
    private String eventType;

    @Column(columnDefinition = "TEXT")
    private String payload;

    private LocalDateTime createdAt = LocalDateTime.now();
    private Boolean published = false;
}
Repositories
public interface OrderRepository extends JpaRepository<Order, String> {}

public interface OutboxRepository extends JpaRepository<OutboxEvent, Long> {
    List<OutboxEvent> findTop50ByPublishedFalseOrderByCreatedAtAsc();
}
Service layer (transactional save)

The order and its outbox event are saved together under one @Transactional boundary — the heart of the pattern:

@Service
public class OrderService {
    private OrderRepository orderRepository;
    private OutboxRepository outboxRepository;

    public OrderService(OrderRepository orderRepository, OutboxRepository outboxRepository) {
        this.orderRepository = orderRepository;
        this.outboxRepository = outboxRepository;
    }

    @Transactional
    public Order createOrder(Order order) {
        order.setStatus("CREATED");
        orderRepository.save(order);

        # create outbox event in the SAME transaction
        OutboxEvent event = new OutboxEvent();
        event.setAggregateType("Order");
        event.setAggregateId(order.getId());
        event.setEventType("OrderCreated");
        event.setPayload(toJson(order));

        outboxRepository.save(event);
        return order;
    }
}
Scheduled relay publisher

A background job polls unpublished rows, sends them to Kafka, and marks each as sent. A failed send simply stays unpublished and is retried next tick:

@Service
public class OutboxPublisher {
    private OutboxRepository outboxRepository;
    private KafkaTemplate<String, String> kafkaTemplate;

    public OutboxPublisher(OutboxRepository outboxRepository, KafkaTemplate<String, String> kafkaTemplate) {
        this.outboxRepository = outboxRepository;
        this.kafkaTemplate = kafkaTemplate;
    }

    @Scheduled(fixedDelay = 5000)   # every 5 seconds
    public void publishEvents() {
        List<OutboxEvent> events = outboxRepository.findTop50ByPublishedFalseOrderByCreatedAtAsc();
        for (OutboxEvent event: events) {
            try {
                kafkaTemplate.send("order-events", event.getAggregateId(), event.getPayload());
                event.setPublished(true);
                outboxRepository.save(event);
            } catch (Exception e) {
                # log and retry on the next run
            }
        }
    }
}

Production hardening
  • Idempotency — delivery is at-least-once, so consumers must tolerate duplicate events (dedupe on event id).
  • Retries and DLQ — route repeatedly failing publishes to a dead-letter queue instead of blocking the relay.
  • CDC alternative — replace the polling job with a Change Data Capture tool like Debezium that streams outbox rows straight from the transaction log.
  • Ordering — use aggregateId as the Kafka message key so events for one aggregate keep their order (same partition).
  • Monitoring — alert on the count of unsent rows (published = false) and on relay lag.
