Singleton Pattern

Singleton is a creational design pattern that ensures a class has only one instance and provides a global point of access to that instance. The class itself is made responsible for controlling its instantiation, hiding the constructor and exposing a single accessor method. This is commonly used for shared resources such as configuration holders, logging, caches, thread pools, and connection managers.

When to use
  • When exactly one instance of a class must exist across the application.
  • When you need a single, shared point of access to a resource.
  • For managing shared state such as configuration, caches, or logging.
  • When creating the object is expensive and it should be reused.
  • When stricter control over global variables is required.
Pros and Cons
Single Instance

Guarantees that a class has only a single instance across the application.

Global Access Point

Provides a global point of access to that shared instance.

Created Once

The instance is created only once through lazy or eager initialization.

Saves Memory

Saves memory by avoiding repeated object creation.

Coordinates Actions

Useful for coordinating actions across a system.

Global State

Introduces global state, which can make code harder to test and reason about.

Hidden Dependencies

Can hide dependencies instead of exposing them explicitly.

Thread Safety

Requires careful handling to remain thread-safe.

Violates SRP

Violates the single responsibility principle by controlling both logic and its own lifecycle.

Real-world example
  • java.lang.Runtime — Runtime.getRuntime() always returns the one JVM runtime instance per application.
  • Spring beans — the default bean scope is singleton, so the container manages a single shared instance per context.
  • Java Logging — java.util.logging.LogManager and loggers are accessed through a single shared manager.
  • SLF4J and Log4j — the LoggerFactory hands out loggers backed by a single logging context.
  • java.awt.Desktop — Desktop.getDesktop() exposes one instance representing the current desktop environment.
  • Database connection pools — a single pool manager (such as HikariCP's data source) is shared to reuse connections.
  • Government registry — a country has one central authority issuing passports, an everyday single-instance analogy.
Eager, Thread-safe Example
public class ConfigManager {
    private static final ConfigManager INSTANCE = new ConfigManager();
    private String environment;

    private ConfigManager() {
        this.environment = "production";
    }

    public static ConfigManager getInstance() {
        return INSTANCE;
    }

    public String getEnvironment() {
        return environment;
    }
}

void main() {
    ConfigManager cfg = ConfigManager.getInstance();
    System.out.println(cfg.getEnvironment());
}
How the Singleton works

The constructor is private, so no other class can create an instance.

A single static final instance is created when the class loads.

getInstance() returns that same shared instance every time.

Using a static final field makes this eager version inherently thread-safe.
