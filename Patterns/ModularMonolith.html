Modular Monolith

A modular monolith is a single deployable application organized internally into well-defined, loosely coupled modules.

It keeps the operational simplicity of a monolith while enforcing clear boundaries like microservices.

Modules communicate through explicit interfaces, not by reaching into each other's internals.

It is often the sensible middle ground before committing to microservices.

When to use / Key points
  • When you want clear boundaries but not distributed-system complexity.
  • Each module owns its domain, data, and public API.
  • Enforce boundaries with packages, modules, or build rules.
  • A well-modularized monolith can later be split into services.
Advantages
  • Single deploy and one runtime keep operations simple.
  • Clear module boundaries improve maintainability.
  • Local, in-process calls avoid network cost and distributed transactions.
Disadvantages / Trade-offs
  • Boundaries erode without discipline and tooling to enforce them.
  • Still scaled as a single unit, not per module.
  • A crash can still affect the whole application.
Code
# Modules interact only through published interfaces
package com.shop.billing.api;

public interface BillingApi {        # billing module's public port
    Invoice createInvoice(Long orderId);
}

# Ordering module depends on the interface, not internals
package com.shop.ordering;

@Service
public class OrderService {

    private final BillingApi billing;

    public OrderService(BillingApi billing) {
        this.billing = billing;
    }

    public void complete(Long orderId) {
        billing.createInvoice(orderId); # cross-module via API only
    }
}
How it works

BillingApi is the only thing other modules may touch.

Internal classes of billing stay hidden behind that port.

Swapping billing for a remote service later means implementing the same API.
