Bridge Pattern

Bridge is a structural design pattern that decouples an abstraction from its implementation so that the two can vary independently.

Instead of binding an abstraction to a single implementation through inheritance, the Bridge places the implementation behind its own interface and holds a reference to it via composition.

This prevents a combinatorial explosion of subclasses when an abstraction can have several dimensions of variation.

When to use
  • When both an abstraction and its implementation should be extensible independently.
  • When you want to avoid a permanent binding between abstraction and implementation.
  • When a class has multiple orthogonal dimensions of variation.
  • When inheritance would otherwise cause a class explosion.
  • When you want to switch implementations at runtime.
Advantages
Independent Evolution

Abstraction and implementation can evolve separately.

Avoids Class Explosion

It avoids a combinatorial explosion of subclasses.

Open/Closed Principle

It follows the open/closed principle for both hierarchies.

Hides Implementation

It hides implementation details from the client.

Runtime Swapping

It allows implementations to be swapped at runtime.

Disadvantages
Added Complexity

It increases complexity by introducing extra layers and interfaces.

Cohesive Classes

It can be hard to apply to a highly cohesive class.

Needless Indirection

The added indirection may be unnecessary for simple designs.

Real-world example
  • JDBC – the java.sql API is the abstraction while each vendor Driver is the implementation, so the same code runs against any database.
  • SLF4J – the logging facade is the abstraction bridged to concrete backends like Logback or Log4j chosen at deployment.
  • Java AWT – Component classes delegate to peer objects (ComponentPeer) so widgets stay independent of the native windowing toolkit.
  • Spring Resource – the Resource abstraction is bridged to implementations such as ClassPathResource, FileSystemResource and UrlResource.
  • JCA / Java Cryptography – engine classes like MessageDigest and Cipher are bridged to pluggable provider implementations.
  • Device drivers – the operating system exposes one device abstraction while each hardware vendor supplies its own driver implementation.
  • TV and remote – a remote control (abstraction) works with many TV brands (implementations) that can be paired independently.
Code
# Implementation side
public interface Device {
    void setVolume(int percent);
}

public class TV implements Device {
    public void setVolume(int p) {
        System.out.println("TV volume = " + p);
    }
}

# Abstraction side holds a Device (the bridge)
public abstract class Remote {
    protected final Device device;
    protected Remote(Device device) {
        this.device = device;
    }
    abstract void volumeUp();
}

public class BasicRemote extends Remote {
    public BasicRemote(Device d) { super(d); }
    public void volumeUp() { device.setVolume(30); }
}

void main() {
    Remote r = new BasicRemote(new TV());
    r.volumeUp();
}
How the Bridge works

Device is the implementation hierarchy; Remote is the abstraction hierarchy.

Remote holds a Device reference by composition instead of extending it.

New remotes and new devices can be added independently without cross-multiplying classes.

The client combines any remote with any device at runtime.
