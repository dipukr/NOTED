CQRS Pattern

CQRS separates data modification (commands) from data retrieval (queries) into distinct models.

This allows independent scaling and optimization for read-heavy or write-heavy needs.

Commands change state and may carry rich business logic; queries only read and return results.

The write and read sides can use different models and even separate data stores.

When to use / Key points
  • Commands: operations that change state (create, update, delete).
  • Queries: operations that read data without changing state.
  • Models: rich command DTOs vs. lean, view-tailored query DTOs.
  • Use when read and write workloads differ sharply in scale or shape.
Advantages
Independent Scalability

The read and write sides can be scaled and optimized independently for performance.

Simpler Models

No single model has to handle all CRUD operations, keeping each side focused.

Granular Security

Access control can be applied separately for reads and writes.

Clearer Boundaries

The separation keeps boundaries closer to the underlying business logic.

Disadvantages
Added Complexity

Maintaining two separate models adds overhead to the system.

Eventual Consistency

The read side is often only eventually consistent with the write side.

Overkill For Simple CRUD

The pattern is excessive for simple CRUD applications.

Code
# Write side: a command handler
@Service
public class OrderCommandService {

    private final OrderRepository repo;

    public OrderCommandService(OrderRepository repo) {
        this.repo = repo;
    }

    public void handle(PlaceOrderCommand cmd) {
        Order order = Order.from(cmd); # validation + business rules
        repo.save(order);
    }
}

# Read side: a lean query returning a view model
@Service
class OrderQueryService {
    private final OrderViewRepository views;
    OrderQueryService(OrderViewRepository views) { this.views = views; }
    OrderSummary summary(Long id) { return views.findSummary(id); }
}
How it works

OrderCommandService owns writes and business rules.

OrderQueryService returns a denormalized OrderSummary for reads.

Each side can use its own store, tuned for its workload.
