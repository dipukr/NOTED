Visitor Pattern

Visitor is a behavioral design pattern that lets us add new operations to existing object structures without modifying their classes.

Useful in scenario when an object structure is stable but we frequently need to extend its behaviours with new operations.

Visitor pattern helps separate algorithms from the objects on which they operate.

Visitor pattern aligns with open-closed concepts.

Components
  • Visitor – Interface or abstract class for visiting elements.
  • ConcreteVisitor – Implements operations on concrete elements.
  • Element – Interface that defines accept(visitor)
  • ConcreteElement – Implements accept(visitor)
  • Client – Traverses object structure and applies visitor.
Pros and Cons
New Operations Easily

New operations can be added without changing the existing object structures.

Separation Of Concerns

It encourages a clean separation of concerns between data and behavior.

Extensible Operations

It makes operations extensible and easy to manage over time.

Hard To Add Elements

Adding a new element type requires updating all existing visitors.

Double Dispatch

It involves double dispatch – one call from client to element, and one from element to visitor.

Real-world example
  • Java NIO FileVisitor — Files.walkFileTree traverses a directory tree and calls visitFile and visitDirectory callbacks on each node.
  • javax.lang.model.element.ElementVisitor — annotation processors visit program elements (classes, methods, fields) during compilation.
  • Java compiler AST — the com.sun.source.util.TreeVisitor walks syntax tree nodes for analysis and code generation.
  • ASM bytecode library — ClassVisitor and MethodVisitor let tools inspect and transform bytecode without changing the class model.
  • Spring BeanDefinitionVisitor — visits bean definitions to resolve and rewrite property placeholder values.
  • ANTLR and XML parsers — generated visitors walk parse trees so each operation (evaluation, pretty-printing) stays separate from the grammar.
  • Tax auditor analogy — an auditor visits different account types (savings, business, trust) applying rules per type without the accounts changing.
Code
public interface Visitor {
    void visit(Book b);
    void visit(Fruit f);
}

public interface Item {
    void accept(Visitor v);
}

public class Book implements Item {
    int price = 200;
    public void accept(Visitor v) { v.visit(this); }
}

public class Fruit implements Item {
    int weight = 3;
    public void accept(Visitor v) { v.visit(this); }
}

public class PriceVisitor implements Visitor {
    public void visit(Book b) {
        System.out.println("Book: " + b.price);
    }
    public void visit(Fruit f) {
        System.out.println("Fruit: " + f.weight * 50);
    }
}

void main() {
    Item[] cart = { new Book(), new Fruit() };
    Visitor v = new PriceVisitor();
    for (Item i : cart) i.accept(v);
}
How the Visitor works

Item.accept() passes the element to the visitor.

Each element calls the visit overload for its own type (double dispatch).

PriceVisitor holds the operation, kept out of the element classes.

A new operation is just a new visitor, no element changes.
