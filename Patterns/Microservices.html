Microservices

Microservice architecture organizes an application into a collection of small, independent, and loosely coupled services.

Each service focuses on a specific business capability and can be developed, deployed, and scaled independently.

Services do not share code or implementation and communicate via well-defined APIs.

Each component can be operated and scaled without affecting the functioning of other services.

When to use / Key points
  • The key trait is independent development, deployment, and scaling per module.
  • Communication happens through lightweight protocols like REST or messaging.
  • Each service typically owns its own database.
  • Best for large systems and multiple autonomous teams.
Advantages
  • Agility: faster delivery as teams deploy services independently.
  • Scalability: scale individual services instead of the whole app.
  • Resilience: a failure in one service is isolated.
  • Team autonomy: small teams own specific services.
Disadvantages / Trade-offs
  • Complexity: managing a distributed system is harder than a monolith.
  • Communication overhead: network latency and error handling between services.
  • Data consistency across independent services is difficult.
Code
# One service calls another over a well-defined REST API
@FeignClient(name = "inventory-service")
public interface InventoryClient {

    @GetMapping("/stock/{sku}")
    StockDto getStock(@PathVariable String sku);
}

@Service
public class OrderService {

    private final InventoryClient inventory;

    public OrderService(InventoryClient inventory) {
        this.inventory = inventory;
    }

    public boolean canFulfill(String sku) {
        StockDto stock = inventory.getStock(sku); # remote, independent service
        return stock.getQty() > 0;
    }
}
How it works
  • @FeignClient declares a typed client to another service's API.
  • Each service owns its data; they share only the API contract.
  • Services deploy and scale on their own release cycles.
