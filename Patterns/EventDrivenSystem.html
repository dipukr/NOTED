Event-driven System

An event-driven system detects, processes, and responds to events rather than relying on synchronous request-response calls.

An event is a significant change in state, such as an order being placed or a payment succeeding.

Producers emit events and consumers react to them, without knowing about each other directly.

Communication is asynchronous, usually through a message broker or event bus.

When to use / Key points
  • When components must stay loosely coupled and evolve independently.
  • For real-time reactions: notifications, streaming, live updates.
  • When one action must fan out to many independent consumers.
  • Backed by brokers like Kafka, RabbitMQ, or a cloud event bus.
Advantages
  • Loose coupling: producers and consumers evolve separately.
  • Scalability: consumers scale independently of producers.
  • Resilience: a slow consumer does not block the producer.
Disadvantages / Trade-offs
  • Harder to trace and debug flows across asynchronous hops.
  • Eventual consistency, not immediate consistency.
  • Duplicate or out-of-order events must be handled by consumers.
Code
# Producer publishes an event to Kafka
@Service
public class OrderPublisher {

    private final KafkaTemplate<String, OrderEvent> kafka;

    public OrderPublisher(KafkaTemplate<String, OrderEvent> kafka) {
        this.kafka = kafka;
    }

    public void publish(OrderEvent event) {
        kafka.send("orders", event.getOrderId(), event);
    }
}

# Consumer reacts to the same event asynchronously
@Component
class EmailListener {
    @KafkaListener(topics = "orders", groupId = "email")
    public void onOrder(OrderEvent event) {
        System.out.println("Sending email for " + event.getOrderId());
    }
}
How it works

OrderPublisher emits an event and returns without waiting.

@KafkaListener consumers subscribe independently by group.

New reactions are added by adding listeners, not editing the producer.
