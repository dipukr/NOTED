Abstract Factory Pattern

Abstract Factory is a creational design pattern that provides an interface for creating families of related or dependent objects without specifying their concrete classes.

Where a Factory Method creates a single product, an Abstract Factory groups several factory methods to produce a whole family of products that are designed to work together.

Client code interacts only with the abstract factory and abstract products, so an entire family can be swapped by changing the concrete factory.

When to use
  • When your system needs to create families of related products together.
  • When products from one family must be used consistently and not mixed with another.
  • When you want to isolate client code from concrete product classes.
  • When you need to support multiple variants (themes, platforms, vendors).
  • When you want to configure a system with one of several product families.
Pros and Cons
Family Consistency

Guarantees that products from a single family are always used together.

Isolates Concrete Classes

Keeps concrete product classes hidden from the client code.

Easy Family Swapping

Makes swapping entire product families easy and centralized.

Open/Closed Principle

Follows the open/closed principle when adding new families.

Promotes Consistency

Promotes consistency among the objects that are produced.

Added Complexity

Adds many interfaces and classes, increasing overall complexity.

Hard to Extend Products

Adding a new product type requires changing every factory.

Risk of Over-Engineering

Can be over-engineered for systems with only a single product family.

Real-world example
  • javax.xml.parsers.DocumentBuilderFactory — produces a family of related XML parsing objects (DocumentBuilder) hiding the concrete parser implementation.
  • javax.xml.transform.TransformerFactory — creates Transformer and related objects for a chosen XSLT processor without naming its concrete classes.
  • java.awt.Toolkit — returns platform-specific families of AWT peer widgets so one code path renders on Windows, macOS or Linux.
  • Spring BeanFactory and ApplicationContext — produce families of related, wired beans according to the active configuration or profile.
  • JDBC drivers via DriverManager — each driver supplies a matching family of Connection, Statement and ResultSet objects for its database.
  • Cross-platform UI toolkits — a theme factory yields buttons, checkboxes and scrollbars that all share one consistent look and feel.
  • Furniture showroom analogy — a Victorian or Modern factory delivers a matching chair, sofa and table that belong to the same style set.
Code
public interface Button  { void paint(); }
public interface Checkbox { void paint(); }

public class WinButton   implements Button   { public void paint(){ System.out.println("Win button");} }
public class WinCheckbox implements Checkbox { public void paint(){ System.out.println("Win checkbox");} }

# Abstract factory: a family of related products
public interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

public class WinFactory implements GUIFactory {
    public Button createButton()     { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}

void main() {
    GUIFactory factory = new WinFactory();
    factory.createButton().paint();
    factory.createCheckbox().paint();
}
How the Abstract Factory works

Button and Checkbox are abstract products of one family.

GUIFactory declares creation methods for the whole family.

WinFactory produces matching Windows-style widgets that belong together.

The client uses only the factory and product interfaces; swapping to another factory changes the entire look.
