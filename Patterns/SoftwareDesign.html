Software Design

Software design is the tactical, low-level process of detailing how individual components will be built and work together.

Where architecture answers the what and why, design answers the how of a specific implementation.

It translates high-level requirements into concrete classes, interfaces, methods, and their collaborations.

It relies on design patterns and principles such as SOLID to keep code modular, reusable, and maintainable.

When to use / Key points
  • Applies within a single component or service, after the architecture is set.
  • Chooses concrete patterns (Strategy, Factory, Observer) to solve local problems.
  • Defines class responsibilities, boundaries, and interactions.
  • Guided by SOLID, DRY, KISS, and separation of concerns.
Advantages
  • Produces modular, testable, and readable code.
  • Localizes change so edits do not ripple across the system.
  • Encourages reuse through well-defined abstractions.
Disadvantages / Trade-offs
  • Over-engineering with too many abstractions adds needless complexity.
  • Good design takes time and experience to get right.
  • Premature patterns can lock in the wrong structure.
Code
# Strategy pattern: swap payment behaviour without touching callers
public interface PaymentStrategy {
    void pay(int amount);
}

public class UpiPayment implements PaymentStrategy {
    public void pay(int amount) {
        System.out.println("Paid via UPI: " + amount);
    }
}

public class Checkout {
    private final PaymentStrategy strategy;

    public Checkout(PaymentStrategy strategy) {
        this.strategy = strategy; # injected dependency
    }

    public void complete(int amount) {
        strategy.pay(amount);
    }
}
How it works

PaymentStrategy abstracts the varying behaviour behind one interface.

Checkout depends on the abstraction, not a concrete class (Dependency Inversion).

New payment types are added without editing Checkout (Open/Closed).
