Command Pattern

Command is a behavioral design pattern that turns a request into a stand-alone object containing all information about the request.

This encapsulation lets you parameterize methods with different requests, queue or log requests, and support undoable operations.

It decouples the object that invokes an operation (the invoker) from the object that knows how to perform it (the receiver).

When to use
  • When you want to parameterize objects with an action to perform.
  • When you need to queue, schedule, or log requests.
  • When you want to support undo/redo functionality.
  • Typical uses: menu items and buttons, task queues, transactional behavior, and macro recording.
Advantages
Decouples Invoker and Receiver

It separates the object that invokes an operation from the object that knows how to perform the work.

First-Class Commands

Commands are first-class objects that can be stored, passed around, and queued.

Easy To Extend

You can add new commands without changing existing code, following the Open/Closed Principle.

Supports Undo and Logging

It naturally supports undo/redo and logging of operations.

Disadvantages
More Classes

It increases the number of classes, since each command usually needs its own class.

Added Indirection

It adds indirection that can make simple actions look more complex.

Complex Undo State

Maintaining undo state for complex commands can be difficult.

Real-world example
  • java.lang.Runnable – each Runnable wraps an action as an object that an executor invokes later without knowing its details.
  • javax.swing.Action – Swing binds an Action command to buttons, menu items, and key strokes as the invokers.
  • Spring JdbcTemplate – StatementCallback and PreparedStatementCallback encapsulate a database operation passed to the template.
  • java.util.concurrent Callable and Future – a Callable is a queued command whose result is retrieved through its Future.
  • Undo and redo in editors – each edit is stored as a command object so it can be reversed or replayed.
  • Restaurant orders – a waiter writes an order (command) that the kitchen (receiver) later executes, decoupling the two.
  • Task queues and job schedulers – jobs are captured as command objects that workers pull and execute asynchronously.
Code
public interface Command {
    void execute();
}

public class Light {                       # Receiver
    void on()  { System.out.println("Light ON"); }
    void off() { System.out.println("Light OFF"); }
}

public class LightOnCommand implements Command {
    private final Light light;
    LightOnCommand(Light light) { this.light = light; }
    public void execute() { light.on(); }
}

public class Remote {                      # Invoker
    private Command command;
    void setCommand(Command c) { command = c; }
    void press() { command.execute(); }
}

void main() {
    Remote remote = new Remote();
    remote.setCommand(new LightOnCommand(new Light()));
    remote.press();  # Light ON
}
How the Command works

Command declares a single execute() method.

Light is the receiver that knows how to do the work.

LightOnCommand wraps the receiver and the action.

Remote triggers commands without knowing their details.
