Event Sourcing Pattern

Event Sourcing stores the state of an application as an ordered sequence of events rather than as current-state rows.

Every change is captured as an immutable event and appended to an event store.

Current state is derived by replaying the events from the beginning.

It gives a complete, auditable history of everything that ever happened.

When to use / Key points
  • Use when a full audit trail or temporal queries are required.
  • Events are append-only and never updated or deleted.
  • Snapshots speed up rebuilding state from long event streams.
  • Pairs naturally with CQRS for read-side projections.
Advantages
Complete Audit Log

The full event history lets you reconstruct any past state of the application.

Replay and New Projections

Events can be replayed for debugging and to build new projections after the fact.

Fast Append-Only Writes

Writes are simple and fast because events are only ever appended, never modified.

Disadvantages
Added Complexity

It is more complex than simply storing the current state directly.

Current State Queries

Reading the current state requires projections or snapshots rather than a direct lookup.

Schema Evolution

Evolving the schema of old, already-stored events is tricky to manage.

Code
# State is rebuilt by folding over past events
public class Account {

    private long balance;

    # append-only log of what happened
    public static Account replay(List<Event> history) {
        Account acc = new Account();
        for (Event e : history) {
            acc.apply(e);
        }
        return acc;
    }

    private void apply(Event e) {
        if (e instanceof Deposited d) balance += d.amount();
        else if (e instanceof Withdrawn w) balance -= w.amount();
    }

    public long getBalance() { return balance; }
}
How it works

Events like Deposited and Withdrawn are the source of truth.

replay folds the history to compute current balance.

Nothing is overwritten; the full history is always preserved.
