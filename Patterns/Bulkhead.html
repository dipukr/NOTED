Bulkhead Isolation

The Bulkhead pattern isolates resources so a failure in one part of a system cannot sink the whole.

It is named after the watertight compartments in a ship's hull.

Each dependency gets its own pool of threads or connections, capped independently.

If one dependency saturates its pool, others keep running normally.

When to use / Key points
  • Use when several dependencies share one resource pool.
  • Partition thread pools or connection pools per dependency.
  • Prevents one slow call from exhausting all threads.
  • Often paired with a circuit breaker and timeouts.
Advantages
  • Contains failures to a single compartment.
  • Preserves capacity for healthy dependencies.
  • Improves overall system resilience under load.
Disadvantages / Trade-offs
  • Partitioning can under-utilize total resources.
  • Requires sizing each pool correctly.
  • More pools mean more configuration to manage.
Code
# Resilience4j bulkhead caps concurrent calls per dependency
@Service
public class ReportService {

    private final ReportClient client;

    public ReportService(ReportClient client) {
        this.client = client;
    }

    # at most N concurrent calls; extras are rejected fast
    @Bulkhead(name = "reports", fallbackMethod = "busy")
    public Report generate(Long id) {
        return client.build(id);
    }

    public Report busy(Long id, Throwable t) {
        return Report.tryLater(); # compartment is full
    }
}
How it works
  • @Bulkhead limits concurrent calls to the reports pool.
  • Overflow calls hit busy instead of consuming shared threads.
  • A flood of report requests cannot starve other features.
