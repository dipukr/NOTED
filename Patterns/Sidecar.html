Sidecar

The Sidecar pattern deploys a helper component alongside a main service in the same host or pod.

The sidecar handles supporting concerns like logging, configuration, proxying, or security.

It shares the lifecycle and network of the main container but stays a separate process.

It keeps cross-cutting features out of the application code and language-agnostic.

When to use / Key points
  • Use to add capabilities without modifying the main service.
  • Common for proxies, log shippers, and config or secret agents.
  • It is the building block of a service mesh data plane.
  • Main and sidecar communicate over localhost.
Advantages
Language Agnostic Reuse

One sidecar can be reused across services written in any language.

Isolates Concerns

It keeps cross-cutting concerns isolated from the main application code.

Independent Upgrades

The sidecar can be upgraded independently of the service it supports.

Disadvantages
Higher Resource Use

An extra process per instance increases overall resource consumption.

Added Latency

It adds a localhost network hop that introduces some latency.

More Moving Parts

There are more components to deploy and monitor.

Code
# The app talks to its sidecar over localhost
@Service
public class ConfigReader {

    private final RestTemplate rest;

    public ConfigReader(RestTemplate rest) {
        this.rest = rest;
    }

    public String getSecret(String key) {
        # sidecar agent runs on 127.0.0.1 in the same pod
        return rest.getForObject(
            "http://127.0.0.1:8200/secret/" + key, String.class);
    }
}
# The sidecar handles auth to the real secret store,
# so the app never holds those credentials itself.
How it works

The main app calls 127.0.0.1, its co-located sidecar.

The sidecar does the heavy lifting (auth, caching, TLS).

Swapping the sidecar needs no change to the app code.
