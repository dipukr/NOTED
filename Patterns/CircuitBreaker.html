Circuit Breaker

The Circuit Breaker is a resilience pattern that wraps a call to a remote or otherwise unreliable dependency and watches how it behaves. When the dependency starts failing or slowing down, the breaker stops sending it traffic for a while — giving it room to recover and shielding the caller from the cost of waiting on a service that cannot answer.

The name comes from an electrical breaker: instead of letting a fault burn through the whole circuit, it trips and cuts the connection. In software the fault is a failing dependency, and the damage it prevents is a pile-up of blocked threads, exhausted connection pools, and timeouts that cascade upstream to every service that depends on the caller.

The breaker is a small state machine with three states. In closed it lets calls through and counts failures. Once failures cross a threshold it flips to open and rejects calls immediately, usually returning a cached value or a default fallback. After a cooldown it moves to half-open and allows a small number of trial calls: if they succeed it closes again, and
if they fail it re-opens and waits longer.

Because it short-circuits instead of blocking, the caller gets an instant, predictable response even while the dependency is down — which is what keeps a single struggling service from dragging down the rest of the system.

The Three States
ClosedCalls pass through normally while the breaker records each outcome; consecutive or windowed failures increment a counter.
OpenOnce the failure count crosses the threshold, calls short-circuit immediately without touching the dependency, returning a fallback.
Half-OpenAfter the cooldown the breaker admits a few trial calls; success closes it again, any failure sends it back to open with a longer wait.
Using it in Practice
Where to UseWrap it around calls that cross a boundary you don't control: remote HTTP/RPC, database or cache access, message brokers, or any dependency that can fail or slow down.
What to TuneMatch three knobs to your traffic: the failure threshold that trips it, the retry timeout it stays open for, and what the fallback returns.
Watch SlownessTrigger on latency, not just errors; a slow dependency is often more dangerous than a failing one, so count timeouts as failures.
Combine PatternsPair it with timeouts, retries with backoff, and bulkheads; the breaker decides whether to call, those decide how each call behaves.
Per-Dependency and MetricsKeep breaker state per dependency (often per instance), and expose its state and trip events as metrics so you can alert on them.
Advantages
Stops Cascading Failures

Cutting traffic to a sick dependency prevents the failure from spreading up the call chain and taking down healthy services with it.

Fails Fast

Callers get an immediate response instead of blocking on timeouts, so threads and connection-pool slots are freed rather than piling up.

Protects the Dependency

Removing load from a struggling service gives it the breathing room to recover instead of being hammered while it's already down.

Graceful Degradation

The fallback path lets the app keep serving a reduced experience (cached data, defaults) rather than erroring out completely.

Better Latency

Short-circuited calls return in microseconds, so a down dependency doesn't turn every request into a slow one.

Automatic Recovery

Half-open probing means the system heals on its own once the dependency is back, with no manual intervention.

Observability

Trip events and state changes are a clear, actionable signal of dependency health to feed dashboards and alerts.

Disadvantages
Hard to Tune

Thresholds, windows, and timeouts that are too sensitive cause needless trips, while lax ones let failures through; getting them right takes real traffic data.

Can Reject Good Calls

While open, the breaker rejects every request — including ones that would have succeeded — so partial outages can look like total ones.

Fallback Complexity

A meaningful fallback (stale cache, default, degraded response) has to be designed, tested, and kept correct; a bad one can hide real problems.

Added Moving Parts

It introduces extra state and a library/dependency that must be configured, monitored, and reasoned about during incidents.

Distributed State

Per-instance breakers can disagree across a cluster; sharing state adds coordination cost and its own failure modes.

Masks Root Causes

Fast fallbacks can make a degraded system feel healthy, delaying investigation if trips aren't surfaced loudly.

Testing Effort

Exercising open/half-open transitions and recovery reliably requires fault injection, which many test suites lack.

Code
@Service
public class QuoteService {

    private PricingClient pricing;

    public QuoteService(PricingClient pricing) {
        this.pricing = pricing;
    }

    @CircuitBreaker(name = "pricing", fallbackMethod = "cachedPrice")
    public Price getPrice(String sku) {
        return pricing.fetch(sku); # protected remote call
    }

    # invoked when the breaker is open or the call fails
    public Price cachedPrice(String sku, Throwable t) {
        return Price.lastKnown(sku);
    }
}
How it works

@CircuitBreaker tracks failures on the pricing instance.

When it trips open, calls jump straight to cachedPrice.

Half-open probes later restore normal flow if the service recovers.

Manual Implementation
public class CircuitBreaker {
    private AtomicInteger failureCount = new AtomicInteger(0);
    private int failureThreshold;
    private Instant lastFailureTime;
    private Duration retryTimePeriod;
    private State state = State.CLOSED;
    
    public CircuitBreaker(int failureThreshold, Duration retryTimePeriod) {
        this.failureThreshold = failureThreshold;
        this.retryTimePeriod = retryTimePeriod;
    }

    public synchronized boolean allowRequest() {
        if (state == State.OPEN) {
            if (Instant.now().isAfter(lastFailureTime.plus(retryTimePeriod))) {
                state = State.HALF_OPEN;
                return true;
            } else {
                return false; # Fail fast
            }
        }
        return true;
    }

    public synchronized void recordSuccess() {
        failureCount.set(0);
        state = State.CLOSED;
    }

    public synchronized void recordFailure() {
        lastFailureTime = Instant.now();
        int failures = failureCount.incrementAndGet();
        if (failures >= failureThreshold) {
            state = State.OPEN;
            System.out.println("Circuit opened!");
        }
    }

    public State getState() {
        return state;
    }

    enum State {
        CLOSED, OPEN, HALF_OPEN
    }
}
How it works

allowRequest() is the gate: it fails fast while OPEN, but flips to HALF_OPEN once retryTimePeriod has passed to let one probe through.

recordFailure() counts failures and trips the breaker to OPEN once failureThreshold is reached.

recordSuccess() resets the count and returns to CLOSED — a successful half-open probe closes the circuit.

synchronized methods plus an AtomicInteger keep the state consistent under concurrent calls.

Using it in a Spring Boot Application
@Configuration
public class BreakerConfig {

    @Bean
    public CircuitBreaker quoteBreaker() {
        return new CircuitBreaker(5, Duration.ofSeconds(30));
    }
}

@Service
public class QuoteService {

    @Autowired
    private CircuitBreaker breaker;
    
    @Autowired
    private RestTemplate restTemplate;

    public int getPrice(String sku) {
        if (!breaker.allowRequest()) return 0;
        try {
            String url = "http://pricing-service/price/" + sku;
            Integer price = restTemplate.getForObject(url, Integer.class);
            breaker.recordSuccess();
            return price != null ? price : 0;
        } catch (Exception e) {
            breaker.recordFailure();
            return 0;   # fallback: no quote available
        }
    }
}
How it works

Two @Beans expose a shared CircuitBreaker (threshold 5, 30 s retry) and a RestTemplate, so every caller sees the same breaker state.

Spring injects the breaker into QuoteService by the parameter name quoteBreaker, matching the bean method.

Before each remote call, getPrice asks allowRequest — if the breaker is open it returns 0 immediately instead of hitting the down service.

Each attempt reports its outcome with recordSuccess or recordFailure, which drives the state transitions; a failure returns the same safe fallback.

The QuoteController just calls the service — all the resilience logic stays behind getPrice.

Timeouts, Retries and Bulkheads
@Service
public class QuoteService {

    private PricingClient pricing;

    public QuoteService(PricingClient pricing) {
        this.pricing = pricing;
    }

    @Retry(name = "pricing")
    @TimeLimiter(name = "pricing")
    @Bulkhead(name = "pricing", type = Bulkhead.Type.THREADPOOL)
    @CircuitBreaker(name = "pricing", fallbackMethod = "cachedPrice")
    public CompletableFuture<Price> getPrice(String sku) {
        return CompletableFuture.supplyAsync(() -> pricing.fetch(sku));
    }

    # runs when retries are exhausted or the breaker is open
    public CompletableFuture<Price> cachedPrice(String sku, Throwable t) {
        return CompletableFuture.completedFuture(Price.lastKnown(sku));
    }
}

How it works

@Bulkhead caps how many calls run at once, so a slow dependency can't exhaust the whole thread pool — the failure stays isolated to its own pool.

@TimeLimiter aborts any call that exceeds 2s, turning a silent hang into a fast, countable failure.

@Retry re-attempts transient failures with exponential backoff (200ms, 400ms, 800ms) before giving up, so brief blips self-heal.

@CircuitBreaker watches the outcomes; once the failure rate crosses 50% it trips open and short-circuits to cachedPrice.

Order matters: the breaker sees the result of the retries, and cachedPrice runs when retries are exhausted or the breaker is open — the breaker decides whether to call, the others decide how each call behaves.
