Circuit Breaker

The Circuit Breaker pattern prevents an application from repeatedly calling a service that is likely to fail.

Like an electrical breaker, it trips open after too many failures and stops further calls for a while.

It has three states: closed (calls flow), open (calls fail fast), and half-open (a few trial calls).

It protects the system from cascading failures caused by a struggling dependency.

When to use / Key points
  • Use around remote calls that can fail or become slow.
  • Closed: normal; failures are counted.
  • Open: calls short-circuit immediately, often to a fallback.
  • Half-open: limited probes decide whether to close again.
Advantages
  • Stops cascading failures across services.
  • Fails fast instead of piling up blocked threads.
  • Gives the failing dependency time to recover.
Disadvantages / Trade-offs
  • Requires careful tuning of thresholds and timeouts.
  • An open breaker may reject calls that would have succeeded.
  • Adds a dependency and state to monitor.
Code
# Resilience4j circuit breaker with a fallback
@Service
public class QuoteService {

    private final PricingClient pricing;

    public QuoteService(PricingClient pricing) {
        this.pricing = pricing;
    }

    @CircuitBreaker(name = "pricing", fallbackMethod = "cachedPrice")
    public Price getPrice(String sku) {
        return pricing.fetch(sku); # protected remote call
    }

    # invoked when the breaker is open or the call fails
    public Price cachedPrice(String sku, Throwable t) {
        return Price.lastKnown(sku);
    }
}
How it works
  • @CircuitBreaker tracks failures on the pricing instance.
  • When it trips open, calls jump straight to cachedPrice.
  • Half-open probes later restore normal flow if the service recovers.
