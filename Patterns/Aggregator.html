Aggregator (Parallel Fetch) Pattern

The Aggregator pattern collects data from multiple services and combines it into a single response for the client.

A gateway or dedicated service calls each source, often in parallel, then merges the results.

It spares the client from making many round-trips and knowing about every backend.

Parallel fetching keeps total latency close to the slowest single call, not their sum.

When to use / Key points
  • Use when one view needs data from several independent services.
  • Fire calls concurrently to minimize total wait time.
  • Combine responses into one composite DTO.
  • Handle partial failures with defaults or timeouts.
Advantages
Simpler Clients

Clients make fewer round-trips and stay simpler by talking to a single endpoint.

Lower Latency

Firing calls in parallel keeps total latency close to the slowest single call.

Centralized Composition

Composition and cross-cutting logic live in one place instead of being scattered.

Disadvantages
Potential Bottleneck

The aggregator can become a bottleneck or hotspot as all traffic flows through it.

Partial Failures

It must handle partial failures of individual sources with defaults or timeouts.

Backend Coupling

It adds coupling to the shape of many backends whose responses it merges.

Code
# Parallel fetch and merge with CompletableFuture
@Service
public class ProfileAggregator {

    private final UserClient users;
    private final OrderClient orders;

    public ProfileAggregator(UserClient users, OrderClient orders) {
        this.users = users;
        this.orders = orders;
    }

    public Profile load(Long id) {
        # both calls run at the same time
        CompletableFuture<User> u =
            CompletableFuture.supplyAsync(() -> users.get(id));
        CompletableFuture<List<Order>> o =
            CompletableFuture.supplyAsync(() -> orders.forUser(id));

        return new Profile(u.join(), o.join()); # merge results
    }
}
How it works

supplyAsync launches both remote calls concurrently.

join waits for both, so latency tracks the slower call.

The merged Profile is returned as one response.
