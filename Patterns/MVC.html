MVC Pattern

MVC (Model-View-Controller) is an architectural pattern that separates an application into three interconnected parts.

The Model holds data and business logic, the View renders the UI, and the Controller handles input.

The Controller mediates between the View and the Model.

This separation of concerns makes applications easier to develop, test, and maintain.

The three roles
Model

The application's data, state, and business rules. It knows nothing about the UI — in classic MVC it notifies its observers (views) whenever its state changes.

View

The presentation layer. It renders the model's data to the user and forwards user actions to the controller. It holds no business logic.

Controller

Receives user input (clicks, requests), translates it into operations on the model, and selects which view to render.

Interaction flow
  • The user acts on the View (e.g. clicks a button).
  • The Controller handles the event and updates the Model.
  • The Model changes state and notifies its observers.
  • The View reads the updated model and re-renders — the user sees the new output.
  • In classic desktop MVC the Model uses the Observer pattern to push change notifications; in web MVC (Spring MVC) each request is a fresh cycle and the controller hands a model to the view to render.
When to use
  • Interactive applications where the same data is shown in multiple ways or must stay in sync across views.
  • The backbone of web frameworks (Spring MVC, ASP.NET MVC, Rails) and desktop UI toolkits (Java Swing).
  • Whenever you want UI, logic, and input handling to evolve and be tested independently.
Advantages
  • Clear separation of concerns.
  • Views and models can be developed and tested independently.
  • Supports multiple views over the same model.
Disadvantages / Trade-offs
  • Extra layers add boilerplate for simple screens.
  • Controllers can grow bloated if logic leaks into them.
  • Navigating the layers has a learning curve.
Web MVC Example — Spring
// Controller: turns a request into a model + a view name
@Controller
@RequestMapping("/products")
public class ProductController {

    private final ProductService service;

    public ProductController(ProductService service) {
        this.service = service;   // constructor injection
    }

    @GetMapping("/{id}")
    public String details(@PathVariable Long id, Model model) {
        Product product = service.findById(id)          // the Model data
            .orElseThrow(() -> new ProductNotFoundException(id));

        model.addAttribute("product", product);
        return "product-details";                        // the View name
    }
}
How it works
  • The Controller receives the HTTP request and asks the service for data — it holds no business logic itself.
  • A missing product becomes a domain exception instead of a silent null, keeping error handling out of the view.
  • The fetched Product is placed on the Model, and the returned name ("product-details") selects the View template that renders it.
Java Swing Example — a Calculator

A desktop MVC calculator: the Model holds the running result and the arithmetic rules and notifies listeners when the result changes; the View is a Swing window with a display, two number fields, and operation buttons; the Controller reads the inputs, calls the right model operation, and the view re-renders. The view and model never reference each other directly.

Model
// Holds the result + arithmetic rules; notifies observers on change
public class CalculatorModel {

    private double result = 0;
    private final List<Runnable> listeners = new ArrayList<>();

    public double getResult() {
        return result;
    }

    public void add(double a, double b)      { result = a + b; notifyListeners(); }
    public void subtract(double a, double b) { result = a - b; notifyListeners(); }
    public void multiply(double a, double b) { result = a * b; notifyListeners(); }

    public void divide(double a, double b) {
        if (b == 0) throw new ArithmeticException("divide by zero");
        result = a / b;
        notifyListeners();
    }

    public void addListener(Runnable listener) {
        listeners.add(listener);
    }

    private void notifyListeners() {
        for (Runnable listener : listeners) listener.run();
    }
}
How it works
  • Owns the result and the four arithmetic rules — the business logic.
  • Validates input (division by zero) independently of any UI.
  • Fires its listeners on every change (Observer), with no reference to Swing.
View
// Renders the UI; exposes widgets, holds no business logic
public class CalculatorView extends JFrame {

    private final JTextField a = new JTextField(6);
    private final JTextField b = new JTextField(6);
    private final JLabel display = new JLabel("0", SwingConstants.CENTER);
    private final JButton plus = new JButton("+");
    private final JButton minus = new JButton("-");
    private final JButton times = new JButton("*");
    private final JButton divide = new JButton("/");

    public CalculatorView() {
        setTitle("MVC Calculator");
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        setLayout(new BorderLayout(8, 8));

        JPanel inputs = new JPanel();
        inputs.add(a); inputs.add(b);
        JPanel ops = new JPanel();
        ops.add(plus); ops.add(minus); ops.add(times); ops.add(divide);

        add(inputs, BorderLayout.NORTH);
        add(display, BorderLayout.CENTER);
        add(ops, BorderLayout.SOUTH);
        setSize(320, 160);
    }

    public double getA() { return Double.parseDouble(a.getText()); }
    public double getB() { return Double.parseDouble(b.getText()); }

    public void setDisplay(String text) { display.setText(text); }

    // let the controller attach handlers to each operation
    public void addAddListener(ActionListener l)      { plus.addActionListener(l); }
    public void addSubtractListener(ActionListener l) { minus.addActionListener(l); }
    public void addMultiplyListener(ActionListener l) { times.addActionListener(l); }
    public void addDivideListener(ActionListener l)   { divide.addActionListener(l); }
}
How it works
  • Lays out the fields, display, and operation buttons.
  • Exposes getA()/getB() to read input and setDisplay() to show results.
  • Offers one add…Listener per button so the controller can react; it holds no arithmetic.
Controller
// Wires input to the model, and model changes back to the view
public class CalculatorController {

    private final CalculatorModel model;
    private final CalculatorView view;

    public CalculatorController(CalculatorModel model, CalculatorView view) {
        this.model = model;
        this.view = view;

        // user input -> call the matching model operation
        view.addAddListener(e -> run(model::add));
        view.addSubtractListener(e -> run(model::subtract));
        view.addMultiplyListener(e -> run(model::multiply));
        view.addDivideListener(e -> run(model::divide));

        // model change -> refresh the display
        model.addListener(() -> view.setDisplay(String.valueOf(model.getResult())));
    }

    private void run(BiConsumer<Double, Double> op) {
        try {
            op.accept(view.getA(), view.getB());
        } catch (NumberFormatException ex) {
            view.setDisplay("enter two numbers");
        } catch (ArithmeticException ex) {
            view.setDisplay(ex.getMessage());
        }
    }
}
How it works
  • Each button maps to a model method reference (model::add, etc.).
  • It reads the two operands from the view, invokes the model, and translates errors into a friendly display message.
  • When the model updates, its listener refreshes the display — model and view stay decoupled.
Wiring it together
void main(String[] args) {
    SwingUtilities.invokeLater(() -> {
        CalculatorModel model = new CalculatorModel();
        CalculatorView view = new CalculatorView();
        new CalculatorController(model, view);   // controller wires them
        view.setVisible(true);
    });
}
How it works
  • Creates the three parts and lets the controller connect them.
  • invokeLater builds the UI on the Swing event-dispatch thread.
  • Clicking an operator flows: View → Controller → Model → (notify) → View.
