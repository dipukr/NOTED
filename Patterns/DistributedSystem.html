Distributed System

Distributed computing involves multiple computers working together over a network to solve a problem, acting as a single, powerful system.

It is a divide-and-conquer approach where tasks are broken down and processed concurrently on different nodes, then combined.

Components communicate and coordinate by passing messages to achieve a common goal.

When one component fails, the entire system does not fail.

When to use / Key points
  • Three core challenges: concurrency, lack of a global clock, and independent failures.
  • Message passing may use pure HTTP, RPC connectors, or message queues.
  • Examples range from SOA and microservices to MMO games and peer-to-peer apps.
  • Use when a single machine cannot meet scale, performance, or resilience needs.
Pros and Cons
Greater Scalability

The system scales out simply by adding more nodes to handle increased load.

Higher Performance

Tasks are processed concurrently across nodes, boosting overall throughput.

Improved Resilience

Failures are isolated to individual nodes, so the whole system stays operational.

Higher Cost

They cost significantly more than monolithic architectures due to extra hardware, gateways, and proxies.

Hard To Reason About

Network partitions and partial failures make the system difficult to reason about.

Consistency Challenges

Maintaining consistency across many nodes is a significant challenge.

Code
# Inter-node communication over HTTP using RestTemplate
@Service
public class InventoryClient {

    private final RestTemplate rest;

    public InventoryClient(RestTemplate rest) {
        this.rest = rest;
    }

    public boolean isAvailable(String sku) {
        try {
            StockDto stock = rest.getForObject(
                "http://inventory-service/stock/" + sku, StockDto.class);
            return stock != null && stock.getQty() > 0;
        } catch (RestClientException e) {
            # remote node may be down: fail gracefully
            return false;
        }
    }
}
How it works

One node calls another by its logical service name, resolved by the network.

The catch block treats a remote failure as a normal, expected case.

No shared memory: coordination happens purely through messages.
