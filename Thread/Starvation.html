Starvation

Starvation occurs when a thread is perpetually denied access to resources it needs to make progress.

It often results from greedy threads or unfair scheduling that always favours others.

The starved thread stays runnable but never actually gets CPU time or a lock.

Unlike deadlock, other threads keep working; only the victim is stuck.

When to use / Key points
  • Recognise it when low-priority threads never run under load.
  • The synchronized keyword does not support fairness, so any waiter may win.
  • Long-held locks and unbounded priorities aggravate starvation.
  • Fair locks and balanced priorities are the usual remedies.
Advantages
  • Understanding it drives fairer lock and scheduler design.
  • Highlights why priority alone is not a correctness tool.
  • Motivates timed acquisition and back-off strategies.
Disadvantages / Trade-offs
  • Hard to reproduce; appears only under specific load.
  • Fairness fixes lower overall throughput.
  • Symptoms mimic performance bugs, delaying diagnosis.
Code
public class StarvationDemo {
    // Unfair lock (default) may repeatedly favour the same threads
    private final ReentrantLock unfair = new ReentrantLock(false);

    // Fair lock grants the lock to the longest-waiting thread
    private final ReentrantLock fair = new ReentrantLock(true);

    public void doWork(ReentrantLock lock) {
        lock.lock();
        try {
            System.out.println(Thread.currentThread().getName() + " ran");
        } finally {
            lock.unlock();
        }
    }
}
How it works
  • ReentrantLock(false) is unfair and can starve waiting threads.
  • ReentrantLock(true) hands the lock to the longest waiter.
  • Fairness trades throughput for progress guarantees.
  • Switching to the fair lock removes chronic starvation.
