ThreadLocal Usage

ThreadLocal gives each thread its own independent copy of a variable.

Threads share heap memory, so shared mutable objects need synchronization; ThreadLocal sidesteps this by not sharing at all.

It is ideal for per-thread context such as user identity, transactions, or non-thread-safe helpers.

Values must be removed explicitly to avoid leaks in pooled threads.

When to use / Key points
  • Wrap non-thread-safe objects like SimpleDateFormat for reuse.
  • Carry request-scoped context (user, tenant, correlation id).
  • Always call remove() in a finally block in thread pools.
  • InheritableThreadLocal passes values to child threads.
Advantages
  • No synchronization needed; each thread is isolated.
  • Avoids passing context through every method parameter.
  • Makes non-thread-safe objects safe to reuse per thread.
Disadvantages / Trade-offs
  • Memory leaks in pooled threads if remove() is forgotten.
  • Hidden global state makes code harder to reason about and test.
  • Does not propagate across asynchronous task boundaries by default.
Code
public class RequestContext {

    private static final ThreadLocal<String> USER =
            ThreadLocal.withInitial(() -> "anonymous");

    public static void set(String user) {
        USER.set(user);
    }

    public static String current() {
        return USER.get();
    }

    public static void handle(String user, Runnable job) {
        set(user);
        try {
            job.run();
        } finally {
            // critical in pooled threads to avoid leaks
            USER.remove();
        }
    }
}
How it works

withInitial supplies a default value the first time a thread reads it.

get()/set() operate only on the calling thread's slot.

remove() in finally clears the entry before the thread returns to the pool.
