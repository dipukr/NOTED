Memory Leaks

A Java memory leak happens when objects are no longer needed but remain reachable, so GC cannot reclaim them.

In concurrent code, common culprits are unremoved ThreadLocals, unbounded caches, and listener registrations.

Leaks manifest as steadily rising heap usage and eventual OutOfMemoryError.

They are found with heap dumps and diagnosed by tracing GC roots.

When to use / Key points
  • Always remove() ThreadLocals in pooled threads.
  • Bound caches or use WeakHashMap/eviction policies.
  • Deregister listeners and callbacks when done.
  • Analyze heap dumps to find the retaining GC root.
Advantages
  • Fixing leaks restores stable memory and uptime.
  • Prevents costly production crashes.
  • Improves GC efficiency and latency.
Disadvantages / Trade-offs
  • Leaks can stay hidden until sustained load.
  • Heap-dump analysis is time-consuming.
  • Weak references add complexity and subtle behavior.
Code
public class RequestScope {

    private static final ThreadLocal<byte[]> BUFFER =
            new ThreadLocal<>();

    public void handle(Runnable job) {
        BUFFER.set(new byte[1 << 20]); // 1 MB per thread
        try {
            job.run();
        } finally {
            // WITHOUT this, pooled threads leak 1 MB each
            BUFFER.remove();
        }
    }
}
How it works
  • Pool threads live long, so a ThreadLocal value survives every request.
  • Without remove(), each thread permanently retains its 1 MB buffer.
  • Clearing it in finally lets the GC reclaim the buffer between requests.
