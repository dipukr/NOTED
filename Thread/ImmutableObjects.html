Immutable Objects

An immutable object cannot change state after construction, so it is inherently thread-safe.

Since read-read sharing is safe and there are no writes, no synchronization is ever needed.

They are built with final fields, no setters, and defensive copies of mutable inputs.

Java records and String are common examples of immutable types.

When to use / Key points
  • Value objects, DTOs, configuration, and map/set keys.
  • Make the class final and all fields final and private.
  • Defensively copy mutable fields on the way in and out.
  • Return new instances instead of mutating.
Advantages
  • Thread-safe with zero locking.
  • Safe to share, cache, and reuse freely.
  • Simpler reasoning; no hidden state changes.
Disadvantages / Trade-offs
  • Every change allocates a new object, adding GC pressure.
  • Awkward for large objects with many fields.
  • Defensive copies add overhead for mutable members.
Code
public final class Money {

    private final long amount;
    private final String currency;
    private final List<String> tags;

    public Money(long amount, String currency, List<String> tags) {
        this.amount = amount;
        this.currency = currency;
        // defensive copy of mutable input
        this.tags = List.copyOf(tags);
    }

    public Money plus(long delta) {
        // return a new instance, never mutate
        return new Money(amount + delta, currency, tags);
    }

    public long amount() { return amount; }
    public List<String> tags() { return tags; } // already unmodifiable
}
How it works
  • final class and fields guarantee state is fixed after construction.
  • List.copyOf makes a defensive, unmodifiable copy of the input list.
  • plus() returns a fresh Money rather than changing this one.
