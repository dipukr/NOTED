Shared Resources

Shared resources are data or objects accessed by multiple threads, such as memory, files or network connections.

When multiple threads modify a shared resource at once, the outcome is non-deterministic.

Concurrent access must be explicitly synchronized in a multi-threaded environment.

Read-read sharing is safe, but read-write and write-write access needs protection.

When to use / Key points
  • Any mutable state reachable from more than one thread.
  • Cached shared data can hide updates made by other threads without volatile.
  • Protect with locks, atomics or thread-safe collections.
  • Prefer immutability or confinement to avoid sharing entirely.
Pros and Cons
Thread Collaboration

Allows multiple threads to collaborate on common state.

Encapsulated Locking

Thread-safe collections encapsulate the locking internally.

Lock-Free Updates

Atomics offer lock-free updates for simple cases.

Race Conditions

Race conditions and visibility bugs occur if access is unguarded.

Reduced Parallelism

Locking reduces parallelism and can lead to deadlock.

Contention Limits Scaling

Contention on hot resources limits scalability.

Code
public class SharedState {
    // Lock-free thread-safe counter
    private final AtomicInteger hits = new AtomicInteger();

    // Thread-safe map handles its own synchronization
    private final ConcurrentHashMap<String, Integer> cache = new ConcurrentHashMap<>();

    public void record(String key) {
        hits.incrementAndGet();                 // atomic update
        cache.merge(key, 1, Integer::sum);      // atomic per-key
    }

    public int total() { return hits.get(); }
}
How it works

AtomicInteger updates the counter without explicit locks.

ConcurrentHashMap synchronizes access internally per bucket.

merge performs an atomic read-modify-write per key.

No shared field is mutated without a thread-safe primitive.
