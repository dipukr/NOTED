Reader-Writer Problem

The Reader-Writer problem coordinates access to shared data where many threads read but few write.

Read-read sharing is safe, but read-write and write-write access must be mutually exclusive.

The goal is to allow concurrent reads while giving writers exclusive access.

Java's ReentrantReadWriteLock provides a ready-made solution.

When to use / Key points
  • Read-heavy shared data such as caches or configuration.
  • Multiple readers may hold the read lock at once.
  • A writer needs the exclusive write lock; readers block while it is held.
  • Choose a fairness/bias policy to avoid starving writers or readers.
Advantages
Higher Read Throughput

It allows many readers to proceed concurrently, giving higher read throughput than a plain mutex.

Preserves Correctness

It preserves correctness by serialising writes so they never overlap with reads or other writes.

Built-in Lock

The built-in lock avoids hand-rolled synchronization and its associated bugs.

Disadvantages
Starvation Risk

Reader preference can starve writers, and writer preference can starve readers.

Extra Overhead

It carries more overhead than a simple lock for write-heavy workloads.

No Lock Upgrade

Upgrading a lock from read to write is not supported directly.

Code
public class SharedStore {
    private final ReadWriteLock lock = new ReentrantReadWriteLock();
    private int value = 0;

    public int read() {
        lock.readLock().lock();
        try { return value; }        // concurrent readers allowed
        finally { lock.readLock().unlock(); }
    }

    public void write(int v) {
        lock.writeLock().lock();
        try { value = v; }             // exclusive access
        finally { lock.writeLock().unlock(); }
    }
}
How it works

readLock() can be held by many threads simultaneously.

writeLock() is exclusive and blocks all readers and writers.

Unlocking in finally guarantees release even on exception.

The pair enforces the read-read-safe, write-exclusive rule.
