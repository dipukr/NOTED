Semaphores

A semaphore is a counter that controls how many threads may access a resource at once.

Threads acquire a permit before entering and release it when done.

Unlike a mutex which allows exclusive access, a semaphore allows limited concurrency.

A binary semaphore (one permit) behaves like a lock.

When to use / Key points
  • Limit concurrent access to a pool of N resources (connections, slots).
  • acquire() blocks when no permits remain; release() returns one.
  • Use a fair semaphore to grant permits in FIFO order.
  • Always release in a finally block to avoid permit leaks.
Advantages
Bounded Concurrency

It expresses a limit on how many threads may access a resource at once, directly.

Cross-Thread Release

A permit can be released by a different thread than the one that acquired it.

Fairness And Timed Acquisition

It supports fair ordering and timed or try-based acquisition of permits.

Disadvantages
Permit Leaks

Forgetting to release a permit leaks it and can eventually deadlock the system.

No Ownership Tracking

Unlike a reentrant lock, a semaphore does not track which thread owns a permit.

Fairness Costs Throughput

Enabling fair mode reduces overall throughput.

Code
public class ConnectionLimiter {
    // Allow at most 3 threads at a time
    private final Semaphore permits = new Semaphore(3, true);

    public void useResource() throws InterruptedException {
        permits.acquire();               // wait for a free slot
        try {
            System.out.println(Thread.currentThread().getName() + " working");
            Thread.sleep(500);
        } finally {
            permits.release();           // always return the permit
        }
    }
}
How it works

new Semaphore(3, true) creates 3 fair permits.

acquire() blocks the 4th thread until a permit frees up.

release() in finally guarantees the slot is returned.

Concurrency is capped at three without full exclusion.

Semaphore Control

A Semaphore maintains a set of permits controlling how many threads may access a resource at once.

acquire() takes a permit (blocking if none are free) and release() returns one.

A binary semaphore (one permit) acts like a mutex; a counting semaphore limits concurrency to N.

It is the standard tool for rate limiting and bounded resource pools.

When to use / Key points
  • Limit concurrent access to a pool of connections or files.
  • Throttle the number of in-flight requests.
  • Use tryAcquire(timeout) to avoid indefinite blocking.
  • Always release() in a finally block.
Advantages
Simple Concurrency Cap

It is a simple way to cap concurrency to a fixed number of threads.

Cross-Thread Release

Permits can be released by a different thread than the one that acquired them.

Fairness And Timed Acquisition

It supports fair ordering and timed acquisition of permits.

Disadvantages
No Ownership Tracking

There is no ownership tracking, so a forgotten release() leaks permits.

Not Reentrant

A semaphore is not reentrant, so re-acquiring within the same thread can deadlock.

Misconfigured Permit Counts

Setting the permit count wrong silently under-throttles or over-throttles access.

Code
public class ConnectionPool {

    // allow at most 3 concurrent users
    private final Semaphore permits = new Semaphore(3, true);

    public String query(String sql) throws InterruptedException {
        permits.acquire(); // blocks if all 3 in use
        try {
            return execute(sql);
        } finally {
            permits.release(); // hand permit back
        }
    }

    private String execute(String sql) {
        return "result";
    }
}
How it works

The semaphore starts with 3 permits, capping concurrency at three threads.

acquire() blocks a fourth thread until a permit is released.

release() in finally guarantees the permit returns even on error.
