Race Condition

Race condition occurs when multiple threads try to update mutable shared data at the same time.

Two or more threads simultaneously reading data from the same object is not a problem.

When many threads are simultaneously try to update the same object then memory inconsistencies may arise.

When one thread is updating the object while the other is reading it then memory inconsistencies may arise.

  • Read-read sharing is safe.
  • Both read-write and write-write races are a problem.

When multiple threads try to modify a shared resource at the same time then the final outcome is non deterministic.

We must explicitly synchronize concurrent access to a shared resource in a multi-threaded environment.

When a thread enters synchronized code (calling the synchronized method of that object) it takes the lock on that object. Thus other threads cannot enters synchronized code because there is only one lock per object.

Cached shared data causes a thread not to notice that data has been changed by the another thread.

Resources Memory Files Network connections

Solutions to race condition
  • Locks-Mutexes: Ensure only one thread can access the shared data at a time, like a key to a room.
  • Atomic Operations: Operations that complete indivisibly, preventing interruption.
  • Semaphores-Monitors: Other synchronization tools to control access to resources.
Examples
Movie Ticket

Suppose you are buying theatre tickets online and after you pick your seats and are entering your credit card information, someone else buys that seat and they are no longer available. If multiple threads have access to a collection object and they are adding and removing at the same time, there will be an error unless the collection is thread-safe.

Bank Account

Two people withdraw money from the same account at once. Without locks, both might read the balance, one withdraws, then the second withdraws, potentially leaving the account overdrawn or losing one withdrawal's record.

Document Editing

Two users edit the same document. One saves changes, but before they're fully synced, the other saves, overwriting the first user's work.

Shared Counter

Two threads try to increment a counter variable at the same time, and one increment can be silently lost.

Code
public class Counter {
    private AtomicInteger count = new AtomicInteger();

    public void inc() {
        count.incrementAndGet();   # single atomic op
    }

    public int get() {
        return count.get();
    }
}
How the fix works

Plain count++ lets two threads read the same value and overwrite each other.

AtomicInteger performs the update as one indivisible CAS operation.

No lock is needed, so it scales well under contention.

The final count is always correct regardless of interleaving.
