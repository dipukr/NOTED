Volatile Variables

The volatile keyword marks a field so that every read and write goes directly to main memory rather than a thread-local cache.

It guarantees visibility of changes across threads and establishes a happens-before relationship on that field.

Cached shared data can cause a thread not to notice that data was changed by another thread; volatile prevents this.

It does not provide atomicity for compound actions such as increment.

When to use / Key points
  • Use for a simple flag or state signal written by one thread and read by others.
  • Guarantees visibility but not mutual exclusion.
  • Reads/writes of volatile long and double are atomic (unlike plain ones).
  • Not a substitute for locks when multiple variables must change together.
Pros and Cons
Very Cheap

It is far cheaper than locking, with no blocking or context switches involved.

Guaranteed Visibility

It guarantees the latest value is always visible to every thread.

Prevents Reordering

It prevents instruction reordering around the field access.

No Atomicity

It provides no atomicity for read-modify-write operations like count++.

No Multi-Field Coordination

It cannot coordinate invariants that span multiple fields.

Can Mask Real Needs

Overuse can hide the need for proper synchronization.

Code
public class Worker implements Runnable {

    // visible to all threads immediately
    private volatile boolean running = true;

    public void stop() {
        // write flushed to main memory
        running = false;
    }

    @Override
    public void run() {
        while (running) {
            // loop keeps re-reading the fresh value
            doUnitOfWork();
        }
        System.out.println("Stopped cleanly");
    }

    private void doUnitOfWork() { /* ... */ }
}
How it works

volatile boolean running forces the reading thread to see writes from other threads.

Without volatile the JIT could cache running in a register, looping forever.

stop() only flips a flag; there is no compound update, so volatile is sufficient.
