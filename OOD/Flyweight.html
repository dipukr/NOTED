Flyweight

The Flyweight Design Pattern is a structural design pattern that minimizes memory consumption by sharing common data among multiple objects instead of storing duplicate copies of the same data in every object.

It is particularly useful when an application needs to create a very large number of similar objects, where most of their data is identical and only a small portion varies.

The fundamental idea is:

Separate an object's state into shared (intrinsic) and unique (extrinsic) state, then reuse the shared state across multiple objects.

Understanding the problem

Consider a game that contains a forest with 1 million trees.

Every tree has several properties:

public class Tree {
    int x;
    int y;
    String name;
    String color;
    String texture;
}

Imagine that the forest contains only three types of trees:

  • Oak — Green — oak.png
  • Pine — Dark Green — pine.png
  • Mango — Light Green — mango.png

Although there are 1 million individual trees, there are only three unique combinations of tree characteristics.

With a conventional implementation, each Tree object stores its own tree characteristics.

Without Flyweight

The important observation is that name, color and texture are common to all trees of the same type, while x and y are different for each tree.

The Flyweight pattern solves this by extracting the common properties into a separate shared object.

Intrinsic vs Extrinsic State

This is the most important concept in the Flyweight pattern.

Intrinsic stateExtrinsic state
Shared among multiple objectsUnique to an individual object or operation
Independent of individual object contextDepends on the individual object's context
Stored inside the FlyweightStored externally or passed as arguments
Typically immutableCan change independently
Example: tree type, color, textureExample: tree position (x, y)

For our tree example:

# Intrinsic state
String name;
String color;
String texture;
# Extrinsic state
int x;
int y;

After applying Flyweight, the structure looks like this:

With Flyweight

Now each tree stores only its individual position and a reference to the common TreeType object.

If 500,000 trees are Oak trees, all 500,000 can point to the same TreeType instance.

This is the essence of Flyweight.

Flyweight Pattern Structure

The pattern usually involves four participants.

  • Flyweight (TreeType) — Holds the shared intrinsic state.
  • Flyweight Factory (TreeTypeFactory) — Creates and caches Flyweight objects, returning existing instances whenever possible.
  • Context (Tree) — Stores unique extrinsic state and references the shared Flyweight.
  • Client (Forest) — Creates trees through the factory and manages them.

The factory is not strictly mandatory in every implementation, but it is commonly used to ensure consistent sharing.

Practical Example: Forest Rendering System

Create the Flyweight (TreeType)

public record TreeType(String name, String color, String texture) {
    public void draw(int x, int y) {
        System.out.printf("Drawing %s tree at (%d, %d), color=%s, texture=%s%n", name, x, y, color, texture);
    }
}

Notice two important things.

First, TreeType contains only intrinsic state: name, color, texture.

Second, draw() receives x and y as parameters because these values belong to individual trees.

We are not storing individual tree positions inside the Flyweight.

Also, Java records are suitable here because their instance fields are final. We are using String components, so this Flyweight is immutable.

Create the Flyweight Factory

The factory ensures that only one TreeType is created for each unique combination of properties.

public record TreeTypeKey(String name, String color, String texture) {}

public class TreeTypeFactory {
    private Map<TreeTypeKey, TreeType> cache = new ConcurrentHashMap<>();

    public TreeType getTreeType(String name, String color, String texture) {
        TreeTypeKey key = new TreeTypeKey(name, color, texture);
        return cache.computeIfAbsent(key, k -> new TreeType(k.name(), k.color(), k.texture()));
    }

    public int getUniqueTypeCount() {
        return cache.size();
    }
}

The factory uses computeIfAbsent:

  • If the key exists in the map, return the existing Flyweight.
  • Otherwise, create a new Flyweight, store it and return it.

Using ConcurrentHashMap also supports concurrent access to the factory.

For example:

TreeTypeFactory factory = new TreeTypeFactory();
TreeType oak1 = factory.getTreeType("Oak", "Green", "oak.png");
TreeType oak2 = factory.getTreeType("Oak", "Green", "oak.png");
TreeType pine = factory.getTreeType("Pine", "DarkGreen", "pine.png");
System.out.println(oak1 == oak2); # true
System.out.println(oak1 == pine); # false

oak1 and oak2 refer to the same object. The factory creates a separate object for Pine because it has a different key.

Create the Context (Tree)

Each tree has its own coordinates but holds a reference to a shared TreeType.

public record Tree(int x, int y, TreeType treeType) {
    public void draw() {
        treeType.draw(x, y);
    }
}

Notice that:

TreeType treeType;

is just a reference.

If 100,000 trees have the same type, they share the same TreeType object.

Also notice how the extrinsic state flows:

treeType.draw(x, y);

Tree supplies its unique coordinates to the shared Flyweight, rather than having the Flyweight store the coordinates.

Create the Client (Forest)

public class Forest {
    private List<Tree> trees = new ArrayList<>();
    private TreeTypeFactory factory = new TreeTypeFactory();

    public void plantTree(int x, int y, String name, String color, String texture) {
        TreeType treeType = factory.getTreeType(name, color, texture);
        trees.add(new Tree(x, y, treeType));
    }

    public void drawFirst(int count) {
        trees.stream().limit(count).forEach(Tree::draw);
    }

    public int getTreeCount() {
        return trees.size();
    }

    public int getUniqueTypeCount() {
        return factory.getUniqueTypeCount();
    }

    public Tree getTree(int index) {
        return trees.get(index);
    }
}

The Forest manages all the trees, and each Tree refers to a cached TreeType.

Main Application

void main(String[] args) {
    Forest forest = new Forest();
    forest.plantTree(10, 20, "Oak", "Green", "oak.png");
    forest.plantTree(50, 70, "Oak", "Green", "oak.png");
    forest.plantTree(80, 90, "Pine", "DarkGreen", "pine.png");
    for (int i = 3; i < 100_000; i++) { # Plant additional trees
        if (i % 2 == 0) forest.plantTree(i, i, "Oak", "Green", "oak.png");
        else forest.plantTree(i, i, "Pine", "DarkGreen", "pine.png");
    }
    forest.drawFirst(3);
    System.out.println("Total trees: " + forest.getTreeCount());
    System.out.println("Unique tree types: " + forest.getUniqueTypeCount());
    System.out.println("First two trees share the same type: " + (forest.getTree(0).treeType() == forest.getTree(1).treeType()));
}

Output (the first three drawing lines are abbreviated):

Drawing Oak tree at (10, 20), color=Green, texture=oak.png
Drawing Oak tree at (50, 70), color=Green, texture=oak.png
Drawing Pine tree at (80, 90), color=DarkGreen, texture=pine.png

Total trees: 100000
Unique tree types: 2
First two trees share the same type: true

We have created 100,000 individual Tree objects, but only two TreeType objects.

When the shared state consists of just a few small fields or references to already-shared strings, the memory savings may be modest.

Practical Example: Text Editor with Character Formatting

Consider a text editor like Microsoft Word or Google Docs.

Every character in a document can have formatting properties:

public class Character {
    char value;
    int position;
    String font;
    int fontSize;
    boolean bold;
    String color;
}

Suppose a document contains 1 million characters.

Most of those characters may use the same formatting:

Font: Arial
Size: 12
Bold: false
Color: Black

Duplicating these formatting attributes for every character introduces unnecessary state.

Instead, the editor can share formatting objects.

Shared CharacterStyle Flyweight

public record CharacterStyle(String font, int size, boolean bold, String color) {}

CharacterStyle Factory

public class CharacterStyleFactory {
    private Map<CharacterStyle, CharacterStyle> cache = new HashMap<>();

    public CharacterStyle getStyle(String font, int size, boolean bold, String color) {
        CharacterStyle style = new CharacterStyle(font, size, bold, color);
        return cache.computeIfAbsent(style, key -> key);
    }

    public int getUniqueStyleCount() {
        return cache.size();
    }
}

This factory uses the immutable CharacterStyle value itself as a map key. Its record-generated equals and hashCode methods make equivalent formatting configurations share the same canonical instance.

Character Context

public record StyledCharacter(char value, int position, CharacterStyle style) {
    public void display() {
        System.out.printf("Character '%c' at position %d uses %s%n", value, position, style);
    }
}

Usage

CharacterStyleFactory factory = new CharacterStyleFactory();
CharacterStyle normal1 = factory.getStyle("Arial", 12, false, "Black");
CharacterStyle normal2 = factory.getStyle("Arial", 12, false, "Black");
CharacterStyle bold = factory.getStyle("Arial", 12, true, "Black");
StyledCharacter c1 = new StyledCharacter('H', 0, normal1);
StyledCharacter c2 = new StyledCharacter('e', 1, normal2);
StyledCharacter c3 = new StyledCharacter('!', 2, bold);
System.out.println(c1.style() == c2.style()); # true
System.out.println(c1.style() == c3.style()); # false
System.out.println(factory.getUniqueStyleCount()); # 2

Here:

StateTypeStored in
FontIntrinsicCharacterStyle
Font sizeIntrinsicCharacterStyle
BoldIntrinsicCharacterStyle
ColorIntrinsicCharacterStyle
Character valueExtrinsic in this designStyledCharacter
Character positionExtrinsicStyledCharacter

The key advantage is that 1 million characters can reference just a handful of shared formatting objects.

A production editor might store text in a rope or piece table and apply styles to ranges, but Flyweight remains useful for sharing the style definitions themselves.

Flyweight in the Java Standard Library

Java uses similar object-sharing techniques internally.

Example: Integer.valueOf

Integer a = Integer.valueOf(100);
Integer b = Integer.valueOf(100);
System.out.println(a == b); # true

Why? Java guarantees caching through Integer.valueOf for values from -128 to 127.

Both variables refer to the same cached Integer instance.

Integer x = Integer.valueOf(1000);
Integer y = Integer.valueOf(1000);

For 1000, identity is not guaranteed because the implementation may or may not cache values outside the required range. This is Flyweight-like behavior: reuse immutable objects representing identical values.

Example: String Interning

String a = new String("Hello");
String b = new String("Hello");
System.out.println(a == b); # false
String c = a.intern();
String d = b.intern();
System.out.println(c == d); # true

The intern method returns a canonical reference for an equal string.

This is another example of sharing equivalent objects, reducing duplication in suitable scenarios.

However, interning is not automatically beneficial for every application. Retaining large numbers of distinct interned values can increase memory pressure.

Is Flyweight Just Caching

Flyweight and caching are related, but they have different primary objectives.

FlyweightGeneral-purpose cache
Primarily reduces memory duplicationPrimarily avoids repeated computation, retrieval or creation
Shares common state across logical objectsStores reusable results or objects
Explicitly separates intrinsic and extrinsic stateDoes not require state separation
Often uses a factory with a mapCan use maps, LRU, TTL, Redis, etc.
Example: shared font stylesExample: cached database query results

A Flyweight factory usually uses caching as its implementation mechanism.

But simply using a HashMap to cache objects does not automatically make an implementation a Flyweight pattern.

The defining characteristic is sharing reusable state among many logical objects while keeping individual context separate.

Flyweight vs Singleton

These patterns are sometimes confused because both reuse objects.

FlyweightSingleton
Can have multiple shared instancesNormally one instance per controlled scope
One shared object per unique intrinsic stateOne controlled instance of a class
Optimizes repeated state across many logical objectsControls the number of instances
Example: one TreeType for Oak, another for PineExample: one application-wide configuration manager

In our forest example:

TreeType oak = factory.getTreeType("Oak", "Green", "oak.png");
TreeType pine = factory.getTreeType("Pine", "DarkGreen", "pine.png");

Both are Flyweights. They are different instances, but each can be reused by thousands of trees.

A Singleton would generally restrict the relevant class to one instance.

Important Design Considerations

Flyweights should usually be immutable

Consider this dangerous design:

public class TreeType {
    public String color;
    public void setColor(String color) {
        this.color = color;
    }
}

If thousands of trees share the same TreeType, changing its color would affect every tree using it.

That could be unintended.

Prefer immutable objects:

public record TreeType(String name, String color) {}

If one tree needs a different color, it should use another suitable Flyweight, or the color must be treated as extrinsic state if it is truly individual to that tree.

Avoid unbounded Flyweight caches

A Flyweight factory typically maintains a map:

Map<Key, Flyweight> cache;

If every lookup has a different key, the cache could keep growing.

For example, suppose you put unique user IDs into the intrinsic state:

factory.getStyle(userId, font, color);

If every userId is unique, sharing becomes ineffective.

For applications with potentially unlimited intrinsic-state combinations, consider bounded caches, eviction policies or weak-reference-based strategies where appropriate.

Do not make the Flyweight depend on mutable extrinsic state

Avoid implementations where the shared Flyweight stores temporary state for the current caller:

# Bad design
sharedTreeType.setCurrentPosition(x, y);
sharedTreeType.draw();

This can introduce race conditions when multiple threads use the same Flyweight.

Prefer:

sharedTreeType.draw(x, y); # Better design

Each operation supplies its own context without modifying the shared Flyweight.

Sharing introduces indirection

Flyweight makes object creation and memory management more complex because you must maintain factories, keys, and references. It is not necessarily useful for a small number of inexpensive objects.

Where Is Flyweight Used in Real Applications
  • Game engines — Thousands of game objects share textures, sprite assets, meshes or material definitions.
    Each entity retains its own position, rotation and movement state.
  • Text editors and font rendering — Characters and text runs can share fonts, styles and glyph resources, while
    their locations and document content remain individual.
  • Maps and visualization systems — Thousands of markers can reuse the same icon or symbol definition while maintaining different coordinates and metadata.
  • Compilers and IDEs — Large structures such as syntax trees can reuse immutable descriptors, canonical identifiers or type information instead of repeatedly allocating equivalent objects.

These are common uses scenarios for the pattern, although the exact sharing strategy depends on the implementation.

When Should You Use Flyweight

Flyweight is appropriate when:

  • Your application creates a very large number of objects.
  • Many of those objects contain substantial duplicated data.
  • You can clearly separate intrinsic and extrinsic state.
  • The shared state can be immutable.
  • The memory saved is worth the additional factory and lookup complexity.

Avoid it when objects are few, their data is mostly unique, or separating the state makes the design significantly harder to maintain without meaningful memory savings.

Summary

The Flyweight pattern reduces memory usage by separating shared state from individual state and allowing many logical objects to reference the same reusable, typically immutable object.

In the forest example:

# Shared intrinsic state
TreeType oakType = factory.getTreeType("Oak", "Green", "oak.png");
# Unique extrinsic state
Tree tree1 = new Tree(10, 20, oakType);
Tree tree2 = new Tree(30, 40, oakType);
Tree tree3 = new Tree(50, 60, oakType);

All three trees have their own coordinates, but they share the same TreeType instance.

The key takeaway: Flyweight is not about eliminating individual objects altogether. It is about eliminating unnecessary duplication of their common state.
