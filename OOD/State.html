State Pattern

State is a behavioral design pattern that lets an object alter its behavior when its internal state changes, so the object appears to change its class.

Each possible state is represented by a separate class, and the context delegates state-specific behavior to the current state object.

It is essentially an object-oriented way to implement a finite state machine, replacing large conditional statements with polymorphism.

When to use
  • When an object's behavior depends on its state and must change at runtime.
  • When you have large conditionals that branch on the object's state.
  • When state-specific code is duplicated across many methods.
  • Typical uses: workflow engines, TCP connections, vending machines, and media players.
Pros and Cons
Removes Conditionals

It replaces bulky conditional statements with polymorphism.

Cohesive Classes

It organizes state-specific behavior into separate, cohesive classes.

SRP and OCP

It follows the Single Responsibility and Open/Closed Principles.

Explicit Transitions

It makes state transitions explicit and easier to reason about.

More Classes

It increases the number of classes, one per state.

Can Be Overkill

It can be overkill when there are only a few states with simple logic.

Scattered Transition Logic

Transition logic may be scattered across the state classes.

Real-world example
  • Java Thread — a thread moves through states like NEW, RUNNABLE, BLOCKED, WAITING and TERMINATED, each allowing different operations.
  • TCP connection — a socket behaves differently in states such as LISTEN, ESTABLISHED, CLOSE_WAIT and CLOSED.
  • Spring Statemachine — models application workflows as explicit states and transitions.
  • Media player — play, pause and stop buttons behave differently depending on whether the player is playing, paused or stopped.
  • Vending machine — the same coin or button acts differently in idle, coin-inserted and dispensing states.
  • Order processing — an order in NEW, PAID, SHIPPED or DELIVERED state allows different actions like cancel or refund.
  • Traffic light — each colour decides the next colour and how long it stays, without any central conditional.
What is the State Design Pattern?

The State Design Pattern is a behavioral design pattern that allows an object to change its behavior dynamically when its internal state changes, making it appear as though the object has changed its class.

Instead of implementing state-dependent behavior using large if-else or switch statements, the State Pattern encapsulates the behavior associated with each state into separate classes.

The object, called the Context, maintains a reference to its current state object and delegates state-dependent operations to it. As the internal state changes, the Context switches to a different state object, automatically changing how it responds to operations.

Key idea: An object's behavior depends on its current state, and this behavior can change at runtime without modifying the object's class.

Real-world example: Order management system

Consider an e-commerce application where an order moves through several states:

Conceptual order lifecycle. Cancellation is allowed from CREATED; the normal path proceeds through payment, shipping, and delivery.

An order supports operations like pay(), ship(), deliver(), and cancel().

However, the same operation may behave differently depending on the current state.

Current stateOperationResult

CREATEDship()Not allowed
CREATEDcancel()Transition to CANCELLED
PAIDship()Transition to SHIPPED
SHIPPEDdeliver()Transition to DELIVERED
DELIVEREDcancel()Not allowed

Without the State Pattern, we would typically use conditional statements to handle these rules.

The Problem Without State Pattern

Consider this simple Java implementation:

public class Order {
    private String state = "CREATED";

    public void pay() {
        if (state.equals("CREATED")) {
            state = "PAID";
            System.out.println("Payment successful");
        } else {
            throw new IllegalStateException("Cannot pay in state: " + state);
        }
    }

    public void ship() {
        if (state.equals("PAID")) {
            state = "SHIPPED";
            System.out.println("Order shipped");
        } else {
            throw new IllegalStateException("Cannot ship in state: " + state);
        }
    }

    public void cancel() {
        if (state.equals("CREATED")) {
            state = "CANCELLED";
        } else {
            throw new IllegalStateException("Cannot cancel in state: " + state);
        }
    }
}

This works, but imagine an order system with 15 states and 20 operations.

Problems:

  • Every operation requires multiple state checks.
  • All state-specific behavior is concentrated in one class.
  • Adding a new state may require modifying many existing methods.
  • Complex transitions become difficult to understand and maintain.
  • State-specific rules are difficult to test independently.

The State Pattern addresses these problems by moving the behavior associated with each state into a separate class.

Structure of the State Pattern

The State Pattern usually consists of three main components.

Component 1: State interface

The State interface declares operations that depend on the current state.

public interface State {
    void handle(Context context);
}

Each concrete state provides its own implementation.

Component 2: Concrete states

Concrete states implement the state interface and define the behavior specific to each state.

public class ConcreteStateA implements State {
    @Override
    public void handle(Context context) {
        System.out.println("Behavior of State A");
        context.setState(new ConcreteStateB());
    }
}

public class ConcreteStateB implements State {
    @Override
    public void handle(Context context) {
        System.out.println("Behavior of State B");
        context.setState(new ConcreteStateA());
    }
}

Notice that concrete state objects can also initiate state transitions.

Component 3: Context

The Context holds a reference to the current State object and delegates requests to it.

public class Context {
    private State state = new ConcreteStateA();

    public void setState(State state) {
        this.state = state;
    }

    public void request() {
        state.handle(this);
    }
}

The Context doesn't need to know the detailed behavior of every state. It delegates the operation to the current state.

Practical Java Example #1: E-commerce Order Management

Let's implement the order management system using the State Pattern.

Step 1: Define the State interface

public interface OrderState {
    String name();

    default void pay(Order order) {
        throw new IllegalStateException("Cannot pay when order is " + name());
    }

    default void ship(Order order) {
        throw new IllegalStateException("Cannot ship when order is " + name());
    }

    default void deliver(Order order) {
        throw new IllegalStateException("Cannot deliver when order is " + name());
    }

    default void cancel(Order order) {
        throw new IllegalStateException("Cannot cancel when order is " + name());
    }
}

Here, Java's default methods provide a common implementation for invalid operations.

Each concrete state only overrides the operations allowed in that state.

Step 2: Implement concrete states

CreatedState

public class CreatedState implements OrderState {
    @Override
    public String name() {
        return "CREATED";
    }

    @Override
    public void pay(Order order) {
        System.out.println("Payment completed");
        order.transitionTo(new PaidState());
    }

    @Override
    public void cancel(Order order) {
        System.out.println("Order cancelled");
        order.transitionTo(new CancelledState());
    }
}

An order in the CREATED state can either be paid for or cancelled.

PaidState

public class PaidState implements OrderState {
    @Override
    public String name() {
        return "PAID";
    }

    @Override
    public void ship(Order order) {
        System.out.println("Preparing shipment");
        order.transitionTo(new ShippedState());
    }
}

Only the ship() operation is allowed in this simplified PAID state.

ShippedState

public class ShippedState implements OrderState {
    @Override
    public String name() {
        return "SHIPPED";
    }

    @Override
    public void deliver(Order order) {
        System.out.println("Order delivered");
        order.transitionTo(new DeliveredState());
    }
}

DeliveredState

public class DeliveredState implements OrderState {
    @Override
    public String name() {
        return "DELIVERED";
    }
}

CancelledState

public class CancelledState implements OrderState {
    @Override
    public String name() {
        return "CANCELLED";
    }
}

The last two states are terminal states in this example.

Since they don't override any operations, every attempted operation is rejected automatically.

Step 3: Implement the Context

public class Order {
    private String orderId;
    private OrderState state = new CreatedState();

    public Order(String orderId) {
        this.orderId = orderId;
    }

    public void pay() {
        state.pay(this);
    }

    public void ship() {
        state.ship(this);
    }

    public void deliver() {
        state.deliver(this);
    }

    public void cancel() {
        state.cancel(this);
    }

    public String getStatus() {
        return state.name();
    }

    # Intended for use by state implementations.
    # Keep state transitions inside the order's domain logic.
    void transitionTo(OrderState newState) {
        System.out.printf("Order %s: %s -> %s%n", orderId, state.name(), newState.name());
        this.state = newState;
    }
}

This is the most important part of the implementation.

Notice that:

  • Order maintains its current state through the OrderState reference.
  • Order delegates operations to the current state.
  • Each state determines how to handle an operation.
  • Concrete states initiate transitions using order.transitionTo(...).
  • No large switch or if-else statements are necessary.

Step 4: Client code

void main(String[] args) {
    Order order = new Order("ORD-101");
    order.pay();
    order.ship();
    order.deliver();
    System.out.println("Final status: " + order.getStatus());
    try {
        order.cancel();
    } catch (IllegalStateException e) {
        System.out.println(e.getMessage());
    }
    Order secondOrder = new Order("ORD-102"); # Another order follows a different path.
    secondOrder.cancel();
}

Output

Payment completed
Order ORD-101: CREATED -> PAID

Preparing shipment
Order ORD-101: PAID -> SHIPPED

Order delivered
Order ORD-101: SHIPPED -> DELIVERED

Final status: DELIVERED
Cannot cancel when order is DELIVERED

Order cancelled
Order ORD-102: CREATED -> CANCELLED

Step 5: Understanding how it works internally

Let's trace order.pay():

  1. The client calls order.pay().
  2. Order delegates the call to the current CreatedState.
  3. CreatedState.pay() executes its state-specific behavior.
  4. The state object changes the Context's current state to PaidState.
  5. Subsequent calls are handled by PaidState, not CreatedState.

Important observation: The Order instance remains the same object throughout the process. Only the object referenced by its state field changes.

This is exactly what makes the State Pattern useful.

Practical Java Example #2: Media Player

A media player is another excellent example because the same user action can produce different behavior depending on the player's current state.

Consider three states:

  • StoppedState
  • PlayingState
  • PausedState

The media player provides three operations: play(), pause(), and stop().

State transitions

Complete Java implementation

public interface PlaybackState {
    void play(AudioPlayer player);

    void pause(AudioPlayer player);

    void stop(AudioPlayer player);

    String name();
}

# Context
public class AudioPlayer {
    private PlaybackState state = new StoppedState();

    public void play() {
        state.play(this);
    }

    public void pause() {
        state.pause(this);
    }

    public void stop() {
        state.stop(this);
    }

    public String getState() {
        return state.name();
    }

    void changeState(PlaybackState newState) {
        System.out.println(state.name() + " -> " + newState.name());
        this.state = newState;
    }
}

# Concrete State 1
public class StoppedState implements PlaybackState {
    public String name() {
        return "STOPPED";
    }

    public void play(AudioPlayer player) {
        System.out.println("Starting audio");
        player.changeState(new PlayingState());
    }

    public void pause(AudioPlayer player) {
        System.out.println("Cannot pause stopped audio");
    }

    public void stop(AudioPlayer player) {
        System.out.println("Already stopped");
    }
}

# Concrete State 2
public class PlayingState implements PlaybackState {
    public String name() {
        return "PLAYING";
    }

    public void play(AudioPlayer player) {
        System.out.println("Already playing");
    }

    public void pause(AudioPlayer player) {
        System.out.println("Pausing audio");
        player.changeState(new PausedState());
    }

    public void stop(AudioPlayer player) {
        System.out.println("Stopping audio");
        player.changeState(new StoppedState());
    }
}

# Concrete State 3
public class PausedState implements PlaybackState {
    public String name() {
        return "PAUSED";
    }

    public void play(AudioPlayer player) {
        System.out.println("Resuming audio");
        player.changeState(new PlayingState());
    }

    public void pause(AudioPlayer player) {
        System.out.println("Already paused");
    }

    public void stop(AudioPlayer player) {
        System.out.println("Stopping audio");
        player.changeState(new StoppedState());
    }
}

# Client
void main(String[] args) {
    AudioPlayer player = new AudioPlayer();
    player.play();   # STOPPED -> PLAYING
    player.pause();  # PLAYING -> PAUSED
    player.play();   # PAUSED -> PLAYING
    player.play();   # Already playing
    player.stop();   # PLAYING -> STOPPED
    player.pause();  # Cannot pause stopped audio
}

What's interesting here?

Look at the play() method.

When the player is stopped:

public void play(AudioPlayer player) {
    System.out.println("Starting audio");
    player.changeState(new PlayingState());
}

When the player is paused:

public void play(AudioPlayer player) {
    System.out.println("Resuming audio");
    player.changeState(new PlayingState());
}

When the player is already playing:

public void play(AudioPlayer player) {
    System.out.println("Already playing");
}

The client always invokes the same method:

player.play();

But the behavior depends entirely on the current state object.

The media player example simulates playback with messages. A real implementation would also delegate to an audio playback engine.

Who Should Control State Transitions?

There are two common approaches to controlling state transitions.

Approach A: Concrete states control transitions

This is the approach used in our examples.

public class StoppedState implements PlaybackState {
    @Override
    public void play(AudioPlayer player) {
        player.changeState(new PlayingState());
    }
    # Other methods omitted
}

The concrete state knows what state should come next.

Advantages: State-specific transition logic stays together, making it easier to understand the lifecycle of individual states.

Disadvantages: Concrete states become coupled to other concrete state classes.

Approach B: Context controls transitions

Another approach is to let the Context decide when to switch states.

For example:

public class AudioPlayer {
    private PlaybackState state;

    public void play() {
        state.play(this);
        if (state instanceof StoppedState) { # Context decides the next state.
            state = new PlayingState();
        }
    }
}

This simplified example demonstrates the ownership difference, but it reintroduces conditional logic and doesn't handle every playback state.

A more structured Context can coordinate transitions from events, while individual states remain responsible for behavior.

Which approach is better? When transition rules are naturally associated with the states themselves, Approach A is often simpler. When transitions must be centrally coordinated or audited, Context-controlled transitions or a dedicated state machine may be preferable.

State Pattern vs Strategy Pattern

These two patterns have very similar structures. Both use composition, interfaces, and runtime polymorphism.

However, their intentions are different.

FeatureState PatternStrategy Pattern
PurposeChange behavior based on internal stateSwitch between algorithms or policies
Behavior changesAs the object's lifecycle progressesBased on a selected strategy
SwitchingOften initiated internally by statesOften selected by client or configuration
Concrete implementationsMay know about transitions to other statesUsually independent of one another
ExampleCREATED → PAID → SHIPPEDCreditCardPayment vs UPIPayment
Main focusState-dependent behaviorAlgorithm interchangeability

Strategy example

public interface PaymentStrategy {
    void pay(double amount);
}

public class CreditCardPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Paying with credit card");
    }
}

public class UpiPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Paying with UPI");
    }
}

Here, we select how to perform a payment. One algorithm is substituted for another.

State example

public interface OrderState {
    void pay(Order order);
}

Here, how the operation behaves depends on the order's current lifecycle state.

A payment might be allowed in one state and forbidden in another.

The difference can be summarized as:

  • Strategy: How should this operation be performed?
  • State: What should this operation do in the object's current condition?

These are conceptual distinctions, not absolute rules. Strategies can be changed internally, and States can sometimes be selected externally.

State Pattern vs Finite State Machine

The State Pattern is closely related to the concept of a Finite State Machine (FSM), but the two aren't exactly the same.

A finite state machine is a behavioral model consisting of:

  • A finite collection of states.
  • Events or inputs.
  • Rules describing valid transitions.
  • Optionally, actions associated with transitions.

The State Pattern is an object-oriented design technique that can be used to implement the behavior of such a machine.

For example, our order lifecycle is a finite state machine, while the OrderState implementations are its object-oriented implementation.

For complicated workflows, such as loan approvals or payment processing, a declarative state machine framework may be easier to manage than dozens of interconnected concrete state classes.

Advantages and Disadvantages

Advantages

  • Single Responsibility Principle: Each class handles behavior associated with one state.
  • Open/Closed Principle: Many new states or behaviors can be introduced with less modification to the Context, although existing transitions may still need changes.
  • Eliminates complex conditionals: Reduces large state-dependent if-else and switch statements.
  • Better maintainability: State-specific logic is easier to locate.
  • Runtime flexibility: Behavior changes dynamically as the state object changes.
  • Improved testing: Individual state classes can be tested independently.

Disadvantages

  • More classes: Each state generally requires a separate class.
  • Additional complexity: Can be excessive for very simple workflows.
  • Transition coupling: Concrete states may depend on each other.
  • Harder navigation: Understanding the whole lifecycle may require inspecting several classes.
Practical Considerations for Production Applications

There are a few important differences between our educational implementations and a production system.

A. Persisting the current state

In a Spring Boot order service, the state would typically be persisted to a database.

For example:

@Entity
public class OrderEntity {
    @Id
    private Long id;
    @Enumerated(EnumType.STRING)
    private OrderStatus status;
    @Version
    private Long version;
}

The OrderStatus enum represents the stored state name, while State Pattern classes implement the corresponding behavior.

When loading the entity, the application can map the stored status to its respective state implementation.

B. Handling concurrency

Imagine two requests arriving simultaneously:

  • Request A tries to ship the order.
  • Request B tries to cancel the order.

An in-memory State Pattern implementation doesn't automatically protect against race conditions.

In a distributed Spring Boot application, you still need transactional consistency, such as optimistic locking using @Version, to ensure conflicting state transitions cannot both commit.

C. External side effects

In our example:

public void pay(Order order) {
    System.out.println("Payment completed");
    order.transitionTo(new PaidState());
}

A real application must confirm that payment succeeded before treating the order as paid.

For workflows involving external services, consider idempotency, retry handling, and the transactional outbox pattern where appropriate.

The State Pattern organizes business behavior; it does not replace transaction management or distributed consistency mechanisms.

D. Reusing state objects

When states are stateless, they can be shared rather than repeatedly allocated.

public class States {
    static final OrderState CREATED = new CreatedState();
    static final OrderState PAID = new PaidState();
}

This works because these state objects contain no order-specific mutable fields. Each Order still keeps its own reference to its current state.

When Should You Use the State Pattern?

Use it when an object has several well-defined states and its behavior changes significantly depending on the active state.

Some practical examples:

ApplicationStates
E-commerce orderCreated, Paid, Shipped, Delivered
Media playerStopped, Playing, Paused
TCP connectionClosed, Listening, Established
Document approvalDraft, Submitted, Approved, Rejected
ATMIdle, CardInserted, Authenticated, Dispensing
Vending machineIdle, MoneyInserted, ProductSelected, Dispensing

SubscriptionTrial, Active, Suspended, Expired

However, if you only have two or three simple states, a handful of operations, and straightforward transition rules, using an enum with a switch may be more readable.

Key Takeaways

The State Pattern is based on a simple principle: encapsulate state-dependent behavior in separate objects and delegate operations to the object representing the current state.

Remember these four ideas:

  1. Context maintains the current State object.
  2. State interface defines the common operations.
  3. Concrete states implement behavior specific to each state.
  4. State transitions replace the active State object, changing future behavior at runtime.

Most importantly, the State Pattern doesn't merely store the object's state in another class. It moves the behavior associated with that state into a separate class. That is what distinguishes it from simply keeping a status variable or enum in an object.

Code
public interface State {
    void next(TrafficLight light);
    String color();
}

public class RedState implements State {
    public void next(TrafficLight l) { l.setState(new GreenState()); }
    public String color() { return "RED"; }
}

public class GreenState implements State {
    public void next(TrafficLight l) { l.setState(new RedState()); }
    public String color() { return "GREEN"; }
}

public class TrafficLight {              # Context
    private State state = new RedState();
    void setState(State s) { state = s; }
    void change() { state.next(this); }
    String show() { return state.color(); }
}

void main() {
    TrafficLight light = new TrafficLight();
    System.out.println(light.show());  # RED
    light.change();
    System.out.println(light.show());  # GREEN
}
How the State works

State defines behavior common to all states.

TrafficLight is the context that delegates to its current state.

Each state decides the next state in its next() method.

Behavior changes without any if/switch in the context.
