Composite

The Composite Design Pattern is a structural design pattern that allows you to represent individual objects and groups of objects using a common interface, so that clients can treat both uniformly.

It is especially useful when your application deals with hierarchical (tree-like) structures, such as file systems, GUI components, organizational hierarchies, menus, and document structures.

What is the Composite Design Pattern

The Composite Design Pattern allows you to compose objects into tree structures to represent part-whole hierarchies.

It enables clients to treat individual objects (Leaves) and collections of objects (Composites) through the same abstraction (Component), without needing to know whether they are working with a single object or a group.

The pattern has three main elements:

  • Component: Common interface or abstract class implemented by all objects in the structure.
  • Leaf: An individual object that doesn't contain child components.
  • Composite: A container object that holds other Components (Leaves or Composites) and delegates operations to its children.

Basic structure. A Composite stores children through the Component abstraction, allowing nesting at any depth.

Key idea: Instead of writing separate logic for an individual object and a group of objects, we create a common abstraction that supports both.

For example, imagine a file system:

  • A File is an individual object.
  • A Folder is a collection of files and other folders.
  • Both are file system entries.
  • Both can support operations like getSize() and display().
  • A folder calculates its size by recursively adding the sizes of its contents.
Why do we need the Composite Pattern

Imagine building a file management application. You have two classes:

public class File {
    private String name;
    private long size;

    public long getSize() {
        return size;
    }
}
public class Folder {
    private String name;
    private List<Object> items;

    # Calculate total size of contents
}

Without a common interface, the application might calculate size using type checks:

public long calculateSize(Object item) {
    if (item instanceof File file) return file.getSize();
    if (item instanceof Folder folder) {
        long total = 0;
        for (Object child : folder.getItems())
            total += calculateSize(child);
        return total;
    }
    throw new IllegalArgumentException("Unknown type");
}

Problems with this approach

  • Type checking: Client code must know the concrete type.
  • Tight coupling: The calculation explicitly depends on File and Folder.
  • Poor extensibility: Adding another type may require changing the existing logic.
  • Duplicated logic: Different clients might independently implement the same recursive traversal.
  • Complex client code: Clients must distinguish individual objects from collections.

The Composite Pattern solves this by introducing a common abstraction:

public interface FileSystemNode {
    long getSize();
}

Now both File and Folder implement it, and client code becomes:

public void printSize(FileSystemNode node) {
    System.out.println(node.getSize());
}

Regardless of whether node represents a file or a folder, the client uses exactly the same method. The recursion happens inside the Composite implementation, not in the client.

How does the Composite Pattern work

Think about the following structure:

When you call rootFolder.getSize(); the following happens:

  1. RootFolder calls getSize() on each child.
  2. file1.txt returns its own size.
  3. ImagesFolder calls getSize() on its children.
  4. a.png and b.png return their sizes.
  5. ImagesFolder returns the sum.
  6. RootFolder returns the overall sum.

This is recursive composition: composites can contain other composites, so the same operation can process a hierarchy of arbitrary depth.

Complete Java example: File System

This is one of the clearest real-world examples of the Composite Pattern.

Define the Component

public interface FileSystemNode {
    String getName();
    long getSize();
    void display(String indentation);
}

The interface defines operations supported by both files and folders. Notice that it does not include add or remove.
Only folders can contain children, so we'll place those methods directly in Folder.

Create the Leaf

public class File implements FileSystemNode {
    private String name;
    private long size;

    public File(String name, long size) {
        this.name = name;
        this.size = size;
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public long getSize() {
        return size;
    }

    @Override
    public void display(String indentation) {
        System.out.println(indentation + "File: " + name + " (" + size + " KB)");
    }
}

A File is a Leaf because it has no child components. Its getSize() method returns its own size.

Create the Composite

public class Folder implements FileSystemNode {
    private String name;
    private List<FileSystemNode> childs = new ArrayList<>();

    public Folder(String name) {
        this.name = name;
    }

    public void add(FileSystemNode node) {
        children.add(node);
    }

    public void remove(FileSystemNode node) {
        children.remove(node);
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public long getSize() {
        long total = 0;
        for (FileSystemNode child: childs)
            total += child.getSize();
        return total;
    }

    @Override
    public void display(String indentation) {
        System.out.println(indentation + "Folder: " + name);
        for (FileSystemNode child: childs)
            child.display(indentation + "    ");
    }
}

The folder stores FileSystemNode objects, not just File objects.
This means the folder can contain both individual files and other folders.

Client code

void main(String[] args) {
    File file1 = new File("notes.txt", 10);
    File file2 = new File("photo.jpg", 200);
    File file3 = new File("video.mp4", 500);

    Folder images = new Folder("Images");
    images.add(file2);

    Folder documents = new Folder("Documents");
    documents.add(file1);

    Folder root = new Folder("Root");
    root.add(documents);
    root.add(images);
    root.add(file3);

    root.display("");

    System.out.println("Total size: " + root.getSize() + " KB");
}

Output:

Folder: Root
    Folder: Documents
        File: notes.txt (10 KB)
    Folder: Images
        File: photo.jpg (200 KB)
    File: video.mp4 (500 KB)

Total size: 710 KB

Client doesn't care whether it's a File or Folder

public static void printDetails(FileSystemNode node) {
    System.out.println("Name: " + node.getName());
    System.out.println("Size: " + node.getSize());
}

Now:

printDetails(file1);     # Works
printDetails(images);    # Works
printDetails(documents); # Works
printDetails(root);      # Works

The client handles every object through the same interface. This is the primary benefit of the Composite Pattern.

Real-world scenario: GUI component hierarchy

Modern GUI frameworks often organize UI elements as hierarchical trees. Consider an application screen:

A screen consists of nested panels, labels, inputs, and buttons. Here:

  • Button, Label, and TextField are Leaves.
  • Panel is a Composite.
  • UIComponent is the common abstraction.

Parent panel can call render on every child without knowing whether it is rendering a button, text field or other panel.

public interface UIComponent {
    public void render();
}
public class Button implements UIComponent {
    private final String text;
    public Button(String text) {
        this.text = text;
    }
    public void render() {
        System.out.println("Rendering Button: " + text);
    }
}
public class Label implements UIComponent {
    private final String text;
    public Label(String text) {
        this.text = text;
    }
    public void render() {
        System.out.println("Rendering Label: " + text);
    }
}
public class Panel implements UIComponent {
    private List<UIComponent> childs = new ArrayList<>();
    public void add(UIComponent component) {
        children.add(component);
    }
    public void remove(UIComponent component) {
        children.remove(component);
    }
    public void render() {
        System.out.println("Rendering Panel");
        for (UIComponent child: childs)
            child.render();
    }
}
void main(String[] args) {
    UIComponent label = new Label("Username");
    UIComponent button = new Button("Login");
    Panel loginPanel = new Panel();
    loginPanel.add(label);
    loginPanel.add(button);
    Panel mainPanel = new Panel();
    mainPanel.add(new Label("Welcome"));
    mainPanel.add(loginPanel);
    mainPanel.render();
}

Output:

Rendering Panel
Rendering Label: Welcome
Rendering Panel
Rendering Label: Username
Rendering Button: Login

Why is Composite suitable here?
Imagine a window containing 100 individual controls and 20 nested panels. Without Composite, the window may need to understand every control type and every nesting level. With Composite, it simply calls mainPanel.render.

Every component is responsible for rendering itself or delegating rendering to its children. Same pattern can support operations such as show, hide, enable, disable, validate, and layout.

Real frameworks: Java Swing uses a related hierarchical model in which Container can hold components and containers can be nested. The analogy is strong, although Swing's actual API is more complex than this simplified implementation.

Real-world scenario: E-commerce product bundles

Suppose you're building an e-commerce application. A customer can purchase either individual products or bundles containing products and other bundles. For example:

Implementation

public interface CartItem {
    public int getPrice();
}

public class Product implements CartItem {
    private final String name;
    private final int price;

    public Product(String name, int price) {
        this.name = name;
        this.price = price;
    }

    @Override
    public int getPrice() {
        return price;
    }
}

public class ProductBundle implements CartItem {
    private List<CartItem> items = new ArrayList<>();

    public void add(CartItem item) {
        items.add(item);
    }

    @Override
    public int getPrice() {
        int total = 0;
        for (CartItem item: items) 
            total += item.getPrice();
        return total;
    }
}
void main(String[] args) {
    Product laptop = new Product("Laptop", 40000);
    Product mouse = new Product("Mouse", 1000);
    Product keyboard = new Product("Keyboard", 4000);

    ProductBundle accessories = new ProductBundle();
    accessories.add(mouse);
    accessories.add(keyboard);

    ProductBundle officeBundle = new ProductBundle();
    officeBundle.add(laptop);
    officeBundle.add(accessories);

    System.out.println(officeBundle.getPrice());
}

Output:

45000

In real e-commerce systems, you could extend this with discounts, taxes, and quantities.

The important design property is that both a Product and a ProductBundle implement CartItem, so checkout code can price either one uniformly.

Two ways to implement Composite: Safe vs Transparent

There are two common approaches for designing the Component interface.

Safe Composite (recommended in most applications). Only Composite classes define child-management methods.

public interface Component {
    void operation();
}

public class Leaf implements Component {

    @Override
    public void operation() {
        System.out.println("Leaf operation");
    }
}
public class Composite implements Component {
    private List<Component> children = new ArrayList<>();

    public void add(Component child) {
        children.add(child);
    }

    @Override
    public void operation() {
        for (Component child: children)
            child.operation();
    }
}

Advantages: Type-safe, clean abstractions, and Leaves don't expose meaningless operations.

Disadvantage: Clients cannot call add() through a Component reference.

Approach B: Transparent Composite. The common Component interface declares child-management operations.

public interface Component {
    void operation();
    void add(Component child);
}

Leaf:

public class Leaf implements Component {

    @Override
    public void operation() {
        System.out.println("Leaf operation");
    }

    @Override
    public void add(Component child) {
        throw new UnsupportedOperationException(
            "Leaf cannot contain children"
        );
    }
}

Composite:

public class Composite implements Component {
    private List<Component> childs = new ArrayList<>();

    @Override
    public void add(Component child) {
        childs.add(child);
    }

    @Override
    public void operation() {
        for (Component child: childs)
            child.operation();
    }
}

Recommendation: Use the Safe Composite approach when you design new Java applications. Place add(), remove(), and other child-management operations in the Composite unless your requirements genuinely justify the alternative.

When should you use Composite

Use the Composite Pattern when:

  • Your domain naturally has a tree-like structure. Examples include directories, organizational units, document elements, UI containers, nested menus, and product bundles.
  • Individual objects and collections share meaningful operations. For instance, both a file and a folder can report size, and both a product and a bundle can report price.
  • Clients should treat Leaves and Composites uniformly. A client should be able to call operation() without checking concrete types.
  • You need recursive behavior. Operations such as aggregate calculation, rendering, validation, or export can naturally propagate through nested components.
  • The hierarchy must be extensible. New Leaf or Composite implementations can generally be introduced without modifying existing client logic, provided they honor the Component contract.

When NOT to use Composite. Avoid introducing it merely because one class contains a list of other objects.

public class Order {
    List<OrderItem> items;
}

An Order containing OrderItem objects does not automatically justify Composite. If Order and OrderItem do not share meaningful operations or should not be interchangeable through a common interface, ordinary composition
is simpler.

Composite is not just about containment. It is about recursive containment combined with a common abstraction and uniform operations.

Composite vs Decorator vs ordinary composition

Composite

public interface Component {
    void operation();
}

public class Composite implements Component {
    private List<Component> childs;

    public void operation() {
        for (Component child: childs)
            child.operation();
    }
}

The Composite organizes a collection and delegates an operation to its children.

Decorator

public class LoggingDecorator implements Component {
    private Component wrapped;

    public LoggingDecorator(Component wrapped) {
        this.wrapped = wrapped;
    }

    public void operation() {
        System.out.println("Before");
        wrapped.operation();
        System.out.println("After");
    }
}

A Decorator wraps another component to augment its behavior. Although both depend on a common interface and delegation, Composite emphasizes hierarchy, while Decorator emphasizes behavior extension.

Important implementation considerations

The basic examples above are intentionally simple. Production-quality Composite implementations need a few additional safeguards.

Prevent circular references. Suppose you create:

Folder folderA = new Folder("A");
Folder folderB = new Folder("B");

folderA.add(folderB);
folderB.add(folderA);

Now folderA.getSize(); will recurse indefinitely until a StackOverflowError occurs. A Composite tree must not contain cycles. You should prevent:

  • Adding a Composite as its own child.
  • Adding an ancestor as a descendant.
  • Accidentally creating shared ownership when your business model requires a strict tree.

A common solution is to track parent references and reject modifications that create cycles.

Avoid unintended double counting. Consider:

Product laptop = new Product("Laptop", 40000);

ProductBundle bundle = new ProductBundle();
bundle.add(laptop);
bundle.add(laptop);

The calculated amount becomes 80000. That may be correct if the bundle contains two laptops. But it may be a bug if the second addition was accidental. Decide whether your domain represents a strict tree, a directed acyclic graph, or a collection where repetitions are valid.

Consider performance. Suppose a folder hierarchy contains 100,000 files. Each time you call root.getSize() the recursive implementation visits every descendant. For a tree with n nodes:

  • Time complexity: O(n) in the size of the traversed subtree.
  • Extra memory: O(h) for the recursive call stack, where h is tree height.

For frequently requested aggregated values, caching can help. However, cached results must be invalidated whenever descendants change. For very deep hierarchies, iterative traversal may be preferable to avoid excessive recursion depth.

Concurrency and mutability. If multiple threads can update a Composite while another thread traverses it, you must define thread-safety behavior. Options include synchronization, immutable snapshots, copy-on-write structures, or explicit locking. Simply using an ArrayList does not make concurrent mutation safe.

How Composite relates to the Open/Closed Principle

One of Composite's major strengths is that clients depend on an abstraction rather than concrete implementations. Suppose a file management system originally supports File and Folder. Later, the requirements introduce a new file system node:

public class CloudFile implements FileSystemNode {
    private final String name;
    private final long size;

    public CloudFile(String name, long size) {
        this.name = name;
        this.size = size;
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public long getSize() {
        return size;
    }

    @Override
    public void display(String indentation) {
        System.out.println(indentation + "Cloud: " + name);
    }
}

You can now add root.add(new CloudFile("backup.zip", 1000)); without modifying Folder.getSize().
This works because the folder depends on FileSystemNode, not on File or CloudFile.

However, there is a qualification: Composite makes it easier to add new component types, but adding new operations may still require changing the Component interface and its implementations. If your object hierarchy is stable but you frequently need to introduce completely new operations, the Visitor Pattern may be worth considering.

Composite is not simply a class containing other objects. It is a design in which both an individual object and a collection of objects conform to the same abstraction, allowing the same operations to work recursively across the entire hierarchy.

For example:

FileSystemNode node = ...;

node.getSize();

Whether node represents a single file, a folder containing 10 files, or a folder containing thousands of nested folders, the client uses the same interface. That is the essence of the Composite Design Pattern.

Real-world example
  • Java Swing — a JPanel (composite) holds buttons and other panels, and paint or layout calls recurse through the whole component tree uniformly.
  • HTML DOM and the browser — every Node has children, so an element and a whole subtree are treated the same when rendering or removing.
  • File systems — directories contain files and other directories, and operations like size or delete apply uniformly to either.
  • Java AWT Container — Component is the leaf base and Container is the composite that nests further components.
  • JSF and Android View hierarchies — a ViewGroup or UIComponent tree lets a container and a single widget be drawn and traversed the same way.
  • XML and JSON documents — nested elements and objects form part-whole trees that parsers walk recursively.
  • Organization charts — a manager and an individual employee are both handled as the same unit when totalling headcount or cost.
