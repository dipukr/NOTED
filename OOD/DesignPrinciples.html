Object-Oriented Software Design Principles — Comprehensive Guide with Java Examples

Object-Oriented Software Design (OOD) is the process of designing software systems using objects, classes, interfaces, responsibilities, and relationships so that the resulting software is maintainable, extensible, testable, reusable, and easy to understand.

Writing object-oriented code does not automatically mean that the software is well-designed.

For example, a Java application can use classes, inheritance, interfaces, and polymorphism and still suffer from tight coupling, duplicated logic, poor encapsulation, and fragile dependencies.

Object-oriented design principles guide us in deciding what responsibilities each class should have, how classes should collaborate, and how a system should evolve when requirements change.

Object-oriented design encompasses several related groups of principles.

2. OOP Foundations

Before exploring software design principles, we should understand the four fundamental concepts of object-oriented programming.

2.1 Encapsulation

Encapsulation is the practice of bundling data and the operations that manipulate that data inside an object, while restricting direct access to its internal state.

A well-encapsulated object controls how its state changes and protects its business invariants.

Consider a bank account.

Poor design — exposed mutable state

public class BankAccount {
    public BigDecimal balance;
}

Any external code can manipulate the balance:

BankAccount account = new BankAccount();
account.balance = new BigDecimal("-50000");

This bypasses all business rules.

Better design — encapsulated state

public final class BankAccount {
    private BigDecimal balance;

    public BankAccount(BigDecimal openingBalance) {
        if (openingBalance == null || openingBalance.signum() < 0) {
            throw new IllegalArgumentException("Opening balance cannot be negative");
        }
        this.balance = openingBalance;
    }

    public void deposit(BigDecimal amount) {
        validateAmount(amount);
        balance = balance.add(amount);
    }

    public void withdraw(BigDecimal amount) {
        validateAmount(amount);
        if (balance.compareTo(amount) < 0) {
            throw new IllegalStateException("Insufficient funds");
        }
        balance = balance.subtract(amount);
    }

    public BigDecimal getBalance() {
        return balance;
    }

    private void validateAmount(BigDecimal amount) {
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
    }
}

Usage:

BankAccount account = new BankAccount(new BigDecimal("1000.00"));
account.deposit(new BigDecimal("500.00"));
account.withdraw(new BigDecimal("200.00"));
System.out.println(account.getBalance()); # 1300.00

The object’s balance cannot be modified directly. Every balance change must go through an operation that enforces the relevant rules.

This example demonstrates encapsulation, not concurrency control. A real banking implementation would also require atomic updates, transaction boundaries, and appropriate persistence guarantees.

Important distinction: Encapsulation is not simply declaring fields private and generating getters and setters. Providing unrestricted setters may expose essentially the same design problem.

The goal is to protect behavior and invariants, not merely hide variables.

2.2 Abstraction

Abstraction exposes the essential capabilities of an object while hiding its implementation details.

For example, a checkout service should know how to initiate a payment, but it should not necessarily know how a payment provider handles HTTP requests, authentication, or response parsing.

public interface PaymentGateway {
    PaymentResult charge(String orderId, BigDecimal amount);
}

Possible implementations:

public class CardPaymentGateway implements PaymentGateway {
    @Override
    public PaymentResult charge(String orderId, BigDecimal amount) {
        return PaymentResult.SUCCESS; # Integrate with a card payment provider
    }
}
public class WalletPaymentGateway implements PaymentGateway {
    @Override
    public PaymentResult charge(String orderId, BigDecimal amount) {
        return PaymentResult.SUCCESS; # Integrate with a wallet provider
    }
}

With the common result type:

public enum PaymentResult {
    SUCCESS, DECLINED
}

The business code can depend on PaymentGateway without knowing which provider implements it.

The interface describes what is available, while implementations determine how it works.

In Java, abstraction can be implemented using interfaces, abstract classes, and carefully designed public APIs.

2.3 Inheritance

Inheritance allows one class to extend another class, inheriting accessible state and behavior and optionally redefining certain operations.

public abstract class Employee {
    protected String name;

    protected Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract BigDecimal calculateSalary();
}
public class SalariedEmployee extends Employee {
    private BigDecimal monthlySalary;

    public SalariedEmployee(String name, BigDecimal monthlySalary) {
        super(name);
        this.monthlySalary = monthlySalary;
    }

    @Override
    public BigDecimal calculateSalary() {
        return monthlySalary;
    }
}

A SalariedEmployee is an Employee, and it supplies a specific implementation for salary calculation.

However, inheritance introduces strong relationships between classes. A change in a superclass can affect its subclasses.

Therefore:

Use inheritance primarily for genuine subtype relationships that preserve the superclass contract, rather than merely to reuse code.

Later, we will examine why composition is often a better alternative.

2.4 Polymorphism

Polymorphism means that different objects can be treated through a common type while providing different behavior.

Consider the following interface:

public interface Shape {
    double area();
}

Implementations:

public record Circle(double radius) implements Shape {
    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
public record Rectangle(double width, double height) implements Shape {
    @Override
    public double area() {
        return width * height;
    }
}

Usage:

List<Shape> shapes = List.of(new Circle(5), new Rectangle(4, 6));
for (Shape shape : shapes) {
    System.out.println(shape.area());
}

Each object responds to the same area() operation using its own implementation.

The client does not require separate logic for every concrete shape.

This makes polymorphism particularly useful for eliminating complex conditional statements and implementing extensible behavior.

3. SOLID Principles

SOLID is an acronym for five influential object-oriented design principles popularized by Robert C. Martin.

Its primary goal is to help developers create software that is easier to change, extend, understand, and test.

3.1 S — Single Responsibility Principle (SRP)

Definition

A module or class should have one reason to change.

This does not mean a class must contain only one method or perform only one tiny operation.

It means that the class should have one coherent responsibility associated with a particular area of business or technical concern.

Example: Invoice processing

Suppose we design an invoice-processing class.

Poor design

public class InvoiceService {
    public BigDecimal calculateTotal(Invoice invoice) {
        return BigDecimal.ZERO; # Calculate invoice totals
    }

    public byte[] generatePdf(Invoice invoice) {
        return new byte[0]; # Generate PDF document
    }

    public void sendEmail(Invoice invoice, String recipient) {
        # Send invoice by email
    }

    public void saveToDatabase(Invoice invoice) {
        # Persist invoice
    }
}

This class has several independent reasons to change.

Requirement changeAffected responsibility
New tax calculation rulesInvoice calculation
New invoice PDF layoutDocument generation
New email providerEmail communication
Database migrationPersistence

Even if the invoice calculation logic remains unchanged, modifying the email provider requires changing the same class.

The class is tightly coupled to several unrelated concerns.

Better design: Separate responsibilities

public class InvoiceCalculator {
    public BigDecimal calculateTotal(Invoice invoice) {
        return BigDecimal.ZERO; # Invoice calculations
    }
}
public class InvoicePdfGenerator {
    public byte[] generate(Invoice invoice) {
        return new byte[0]; # PDF generation
    }
}
public class InvoiceEmailSender {
    public void send(byte[] pdf, String recipient) {
        # Email delivery
    }
}
public class InvoiceRepository {
    public void save(Invoice invoice) {
        # Database persistence
    }
}

A coordinating service can compose them:

public class InvoiceWorkflow {
    private InvoiceCalculator calculator;
    private InvoicePdfGenerator pdfGenerator;
    private InvoiceEmailSender emailSender;
    private InvoiceRepository repository;

    public InvoiceWorkflow(InvoiceCalculator calculator, InvoicePdfGenerator pdfGenerator,
                           InvoiceEmailSender emailSender, InvoiceRepository repository) {
        this.calculator = calculator;
        this.pdfGenerator = pdfGenerator;
        this.emailSender = emailSender;
        this.repository = repository;
    }

    public void process(Invoice invoice, String recipient) {
        BigDecimal total = calculator.calculateTotal(invoice);
        # Use the calculated total in the invoice workflow as required.
        repository.save(invoice);
        byte[] pdf = pdfGenerator.generate(invoice);
        emailSender.send(pdf, recipient);
    }
}

The coordinating service is responsible for orchestrating the invoice workflow, not for implementing each technical operation itself.

Responsibility separation

InvoiceWorkflow

Orchestration responsibility

InvoiceCalculator

InvoicePdfGenerator

InvoiceEmailSender

InvoiceRepository

Benefits

SRP improves cohesion, makes tests more focused, reduces the number of unrelated changes within a class, and can make code easier to maintain.

Important clarification

SRP does not suggest creating a separate class for every individual statement or method.

For example, an Order class may legitimately contain:

public void addItem(OrderItem item);
public void removeItem(String productId);
public BigDecimal calculateTotal();
public void cancel();

All these operations can belong to the cohesive responsibility of managing an order.

The relevant question is: Do these methods belong to the same responsibility, and are they likely to change for related reasons?

3.2 O — Open/Closed Principle (OCP)

Definition

Software entities should be open for extension but closed for modification.

This means we should be able to introduce new behavior without repeatedly modifying stable, existing business logic.

It does not mean existing classes must never be modified.

Example: Discount calculation

Suppose an e-commerce system supports several discount types.

Poor design — conditional logic

public class DiscountCalculator {
    public BigDecimal calculate(String discountType, BigDecimal amount) {
        if ("REGULAR".equals(discountType)) {
            return amount.multiply(new BigDecimal("0.05"));
        } else if ("PREMIUM".equals(discountType)) {
            return amount.multiply(new BigDecimal("0.10"));
        } else if ("FESTIVAL".equals(discountType)) {
            return amount.multiply(new BigDecimal("0.20"));
        }
        return BigDecimal.ZERO;
    }
}

Every new discount type requires modifying DiscountCalculator.

Adding "LOYALTY" means editing the existing conditional logic.

As the application grows, this can become difficult to maintain and test.

Better design — polymorphism

Define a common abstraction.

public interface DiscountPolicy {
    BigDecimal calculateDiscount(BigDecimal amount);
}

Regular discount:

public class RegularDiscount implements DiscountPolicy {
    @Override
    public BigDecimal calculateDiscount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.05"));
    }
}

Premium discount:

public class PremiumDiscount implements DiscountPolicy {
    @Override
    public BigDecimal calculateDiscount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.10"));
    }
}

Festival discount:

public class FestivalDiscount implements DiscountPolicy {
    @Override
    public BigDecimal calculateDiscount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.20"));
    }
}

Now the calculator depends on the abstraction:

public class DiscountCalculator {
    private DiscountPolicy discountPolicy;

    public DiscountCalculator(DiscountPolicy discountPolicy) {
        this.discountPolicy = discountPolicy;
    }

    public BigDecimal calculate(BigDecimal amount) {
        return discountPolicy.calculateDiscount(amount);
    }
}

Usage:

DiscountPolicy policy = new PremiumDiscount();
DiscountCalculator calculator = new DiscountCalculator(policy);
BigDecimal discount = calculator.calculate(new BigDecimal("1000"));
System.out.println(discount); # 100.00

To introduce a new discount, create another implementation.

public class LoyaltyDiscount implements DiscountPolicy {
    @Override
    public BigDecimal calculateDiscount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.15"));
    }
}

DiscountCalculator does not need to change.

However, the application still needs to select or configure the appropriate policy. OCP does not eliminate all changes; it attempts to localize them to the relevant extension points.

Relationship with design patterns

This design uses the Strategy Design Pattern.

OCP is also commonly supported by the Factory Method, Template Method, Decorator, and other patterns.

When to apply OCP

OCP is especially valuable when a behavior has several known variations, when plugins or providers need to be added, or when a stable component must support new implementations.

Avoid creating elaborate extension mechanisms for behavior that is unlikely to vary.

The objective is to encapsulate likely changes, not to predict every possible future requirement.

3.3 L — Liskov Substitution Principle (LSP)

Definition

Objects of a subtype should be usable wherever objects of their base type are expected, without violating the correctness or expected behavior of the program.

LSP was introduced by Barbara Liskov and concerns behavioral compatibility between types.

Just because Java allows a class to extend another class does not mean the resulting relationship is a valid design.

Example: Bank accounts

Suppose we have an account that supports withdrawals.

public class SavingsAccount {
    protected BigDecimal balance;

    public SavingsAccount(BigDecimal balance) {
        this.balance = balance;
    }

    public void withdraw(BigDecimal amount) {
        if (amount.signum() <= 0 || balance.compareTo(amount) < 0) {
            throw new IllegalArgumentException();
        }
        balance = balance.subtract(amount);
    }
}

Now consider a fixed-deposit account that does not allow withdrawals before maturity.

Poor design

public class FixedDepositAccount extends SavingsAccount {
    public FixedDepositAccount(BigDecimal balance) {
        super(balance);
    }

    @Override
    public void withdraw(BigDecimal amount) {
        throw new UnsupportedOperationException("Withdrawals not supported");
    }
}

Client code:

public void payBill(SavingsAccount account) {
    account.withdraw(new BigDecimal("500"));
}

This works for an eligible savings account but unexpectedly fails for a fixed-deposit account, even when its balance is sufficient.

The subtype has strengthened the preconditions for a successful withdrawal.

It violates the behavioral expectations of the base type.

Better design — model capabilities correctly

public interface DepositableAccount {
    void deposit(BigDecimal amount);
}
public interface WithdrawableAccount extends DepositableAccount {
    void withdraw(BigDecimal amount);
}
public class SavingsAccount implements WithdrawableAccount {
    # Valid deposit and withdrawal implementations

    @Override
    public void deposit(BigDecimal amount) {
        # Deposit rules
    }

    @Override
    public void withdraw(BigDecimal amount) {
        # Withdrawal rules
    }
}
public class FixedDepositAccount implements DepositableAccount {
    @Override
    public void deposit(BigDecimal amount) {
        # Deposit rules
    }

    # Does not promise ordinary withdrawals.
}

The billing operation now explicitly requires the capability it needs.

public void payBill(WithdrawableAccount account, BigDecimal amount) {
    account.withdraw(amount);
}

A fixed-deposit account cannot accidentally be passed to this method.

In a real application, maturity withdrawals could be modeled with a separate contract describing the applicable preconditions.

The deeper meaning of LSP

Behavioral subtyping involves more than compatible Java method signatures.

Contract elementLSP guideline
PreconditionsA subtype must not demand stronger conditions
PostconditionsA subtype must preserve the guarantees promised by the base type
InvariantsA subtype must maintain the relevant invariants
ExceptionsA subtype should not introduce unexpected failure behavior that violates the contract
Observable behaviorClients relying on the base contract should continue to work

For example, suppose an interface promises:

# Returns a non-null list.
# Returns an empty list when no records exist.
List<Order> findOrders();

An implementation that returns null when there are no orders violates the contract even though Java permits it.

@Override # Incorrect
public List<Order> findOrders() {
    return null;
}

A compatible implementation returns an empty list.

@Override
public List<Order> findOrders() {
    return List.of();
}

LSP and the Rectangle–Square problem

The classic example involves a mutable Rectangle with independently configurable width and height.

If Square extends Rectangle, overriding width and height setters so both dimensions remain equal, code expecting independent dimension changes can break.

Mathematically, every square is a rectangle. But that does not imply that every mutable square object is a behavioral subtype of a mutable rectangle API.

A valid inheritance relationship depends on the software contract, not merely on a conceptual “is-a” relationship.

3.4 I — Interface Segregation Principle (ISP)

Definition

Clients should not be forced to depend on interfaces containing methods they do not use.

Large, general-purpose interfaces can create unnecessary dependencies and force implementations to support inappropriate operations.

Example: Office machines

Poor design

public interface OfficeMachine {
    void print(Document document);

    void scan(Document document);

    void fax(Document document);
}

A basic printer only supports printing.

public class BasicPrinter implements OfficeMachine {
    @Override
    public void print(Document document) {
        System.out.println("Printing...");
    }

    @Override
    public void scan(Document document) {
        throw new UnsupportedOperationException();
    }

    @Override
    public void fax(Document document) {
        throw new UnsupportedOperationException();
    }
}

The class must implement methods that have nothing to do with its capabilities.

Better design — segregated interfaces

public interface Printer {
    void print(Document document);
}
public interface Scanner {
    void scan(Document document);
}
public interface FaxMachine {
    void fax(Document document);
}

A basic printer implements only the required contract:

public class BasicPrinter implements Printer {
    @Override
    public void print(Document document) {
        System.out.println("Printing...");
    }
}

A multifunction printer can support multiple interfaces.

public class MultiFunctionPrinter implements Printer, Scanner, FaxMachine {
    @Override
    public void print(Document document) {
        # Print
    }

    @Override
    public void scan(Document document) {
        # Scan
    }

    @Override
    public void fax(Document document) {
        # Fax
    }
}

ISP in backend development

Suppose a service exposes all repository operations through one interface:

public interface UserRepository {
    User findById(long id);

    void save(User user);

    void delete(long id);

    void exportAllUsers();

    void rebuildIndexes();
}

A read-only reporting service should not need to depend on user deletion or index maintenance capabilities.

A narrower interface can better communicate its responsibilities:

public interface UserReader {
    Optional<User> findById(long id);
}
public interface UserWriter {
    void save(User user);

    void delete(long id);
}

Different consumers can depend on the contracts they actually need.

Important clarification

ISP does not mean every method needs its own interface.

An interface with ten closely related methods may be better than ten tiny interfaces if those methods genuinely form one coherent capability.

The goal is client-specific, cohesive abstractions, not arbitrary fragmentation.

3.5 D — Dependency Inversion Principle (DIP)

Definition

The Dependency Inversion Principle states:

  1. High-level modules should not depend directly on low-level modules. Both should depend on abstractions.
  2. Abstractions should not depend on implementation details. Implementation details should depend on abstractions.

DIP is particularly important for enterprise Java, Spring Boot, microservices, testing, and Clean Architecture.

Example: Order payment processing

A high-level checkout service contains business workflow logic.

A payment provider integration is a lower-level infrastructure detail.

Poor design — direct dependency

public class CheckoutService {
    private StripePaymentGateway gateway = new StripePaymentGateway();

    public void checkout(Order order) {
        gateway.charge(order.getTotal());
    }
}

CheckoutService is directly coupled to one concrete payment provider.

This creates several problems: switching payment providers requires changing business code; isolated testing is difficult; and business logic becomes dependent on infrastructure choices.

Better design — depend on an abstraction

First define the contract:

public interface PaymentGateway {
    void charge(BigDecimal amount);
}

Create the implementation:

public class StripePaymentGateway implements PaymentGateway {
    @Override
    public void charge(BigDecimal amount) {
        # Stripe integration logic
    }
}

Now the high-level service depends on the abstraction.

public class CheckoutService {
    private PaymentGateway paymentGateway;

    public CheckoutService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void checkout(Order order) {
        paymentGateway.charge(order.getTotal());
    }
}

Usage:

PaymentGateway gateway = new StripePaymentGateway();
CheckoutService checkoutService = new CheckoutService(gateway);
checkoutService.checkout(order);

The CheckoutService no longer creates or imports a specific payment provider implementation.

The important inversion is that the lower-level implementation now conforms to a contract that the business layer can own.

DIP vs Dependency Injection vs IoC

These concepts are related but different.

ConceptMeaning
Dependency Inversion PrincipleA design principle governing dependency direction
Dependency Injection (DI)A technique for supplying dependencies to an object

Constructor injection is one way to implement DIP, but dependency injection does not automatically guarantee dependency inversion.

For example:

public CheckoutService(StripePaymentGateway gateway) {
    # ...
}

This uses constructor injection but still depends directly on the concrete class.

DIP with Spring Boot

Spring Boot supports this design naturally.

public interface PaymentGateway {
    void charge(BigDecimal amount);
}
@Component
public class StripePaymentGateway implements PaymentGateway {
    @Override
    public void charge(BigDecimal amount) {
        # Payment provider integration
    }
}
@Service
public class CheckoutService {
    private PaymentGateway paymentGateway;

    public CheckoutService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void checkout(BigDecimal amount) {
        paymentGateway.charge(amount);
    }
}

Spring supplies the registered implementation to CheckoutService.

If multiple PaymentGateway implementations exist, they must be selected explicitly, for example through qualifiers, a primary bean, configuration, or an appropriate strategy registry.

Testing benefit

DIP makes it easy to substitute infrastructure dependencies.

public class FakePaymentGateway implements PaymentGateway {
    private BigDecimal chargedAmount;

    @Override
    public void charge(BigDecimal amount) {
        chargedAmount = amount;
    }

    public BigDecimal chargedAmount() {
        return chargedAmount;
    }
}

Test:

@Test
void checkoutShouldChargeCorrectAmount() {
    FakePaymentGateway gateway = new FakePaymentGateway();
    CheckoutService checkout = new CheckoutService(gateway);
    checkout.checkout(new BigDecimal("500.00"));
    assertEquals(0, new BigDecimal("500.00").compareTo(gateway.chargedAmount()));
}

No Spring container, database, or real payment system is necessary for this unit test.

4. Other Essential Object-Oriented Design Principles

SOLID is only one part of object-oriented design. The following principles are equally important when building maintainable software.

4.1 DRY — Don’t Repeat Yourself

Every piece of knowledge or business logic should have one authoritative representation within a system.

DRY is not simply about eliminating duplicated lines of code. Its deeper purpose is to avoid duplicating knowledge that must remain synchronized.

Example: Tax calculation

Suppose tax calculation is duplicated across multiple services.

public class OrderService {
    public BigDecimal calculateTax(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.18"));
    }
}
public class InvoiceService {
    public BigDecimal calculateTax(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.18"));
    }
}

If the applicable tax rate or calculation rules change, both classes must be updated.

A developer may update one class and forget the other.

A better design centralizes the shared policy.

public class TaxCalculator {
    private BigDecimal taxRate;

    public TaxCalculator(BigDecimal taxRate) {
        this.taxRate = taxRate;
    }

    public BigDecimal calculateTax(BigDecimal taxableAmount) {
        return taxableAmount.multiply(taxRate);
    }
}

Now both services use TaxCalculator.

public class OrderService {
    private TaxCalculator taxCalculator;

    public OrderService(TaxCalculator taxCalculator) {
        this.taxCalculator = taxCalculator;
    }
}

The same instance or configuration can serve multiple consumers.

For a real tax system, applicable rates may depend on jurisdiction, product, date, and other rules. The centralization should cover the actual shared policy rather than assuming one universal percentage.

Important consideration

Two pieces of code that look similar may represent different business rules.

If domestic shipping and international shipping happen to use the same fee calculation today, combining them into one implementation could create unnecessary coupling when the rules diverge.

DRY means avoid duplicated knowledge, not blindly eliminate all similar-looking code.

4.2 KISS — Keep It Simple, Stupid

KISS encourages developers to choose the simplest design that correctly satisfies the requirements.

Complexity makes software harder to understand, test, debug, and modify.

Example

Suppose we need to determine whether a list contains any active users.

Overcomplicated approach:

List<User> activeUsers = users.stream().filter(User::isActive).collect(Collectors.toList());
boolean hasActiveUsers = activeUsers.size() > 0;

Simpler approach:

boolean hasActiveUsers = users.stream().anyMatch(User::isActive);

The second implementation expresses the intention directly, avoids creating an unnecessary list, and can stop as soon as an active user is found.

KISS applies to architecture as well.

For example, a small application may not need microservices, Kafka, a distributed cache, an event-sourcing framework, and multiple database technologies.

A modular monolith may be easier to operate and sufficiently scalable.

Simplicity is not the same as minimal code length. A longer implementation that clearly handles errors and business rules may be much simpler to maintain than a short but obscure one.

4.3 YAGNI — You Aren’t Gonna Need It

YAGNI means:

Do not implement functionality merely because you think it might be required in the future.

Suppose your current application sends email through one provider.

You could build a sophisticated plugin framework supporting hundreds of providers, runtime module loading, plugin versioning, dynamic discovery, and fallback chains.

But if the requirement only calls for one email provider, most of that infrastructure may be unnecessary.

A simple implementation might be sufficient:

public class EmailService {
    private EmailClient client;

    public EmailService(EmailClient client) {
        this.client = client;
    }

    public void send(String to, String message) {
        client.send(to, message);
    }
}

If supporting multiple providers becomes a real requirement, the abstraction and implementation can be extended.

YAGNI does not prohibit good design. It discourages expensive speculation.

These principles help prevent overengineering, including excessive application of SOLID.

4.4 High Cohesion

Cohesion measures how closely related the responsibilities within a module or class are.

High cohesion means the elements of a class work together to accomplish a clearly defined responsibility.

Consider:

public class UserManager {
    void registerUser() {}

    void generateSalaryReport() {}

    void clearSystemCache() {}

    void sendMarketingEmail() {}

    void backupDatabase() {}
}

The methods are largely unrelated.

This is low cohesion.

A more cohesive design might have:

public class UserRegistrationService {
    void registerUser() {}
}

public class PayrollReportService {
    void generateSalaryReport() {}
}

public class CacheMaintenanceService {
    void clearSystemCache() {}
}

Each class has a more focused purpose.

High cohesion and SRP are closely related, but cohesion describes how strongly a module’s elements belong together, while SRP focuses on reasons for change.

4.5 Low Coupling

Coupling describes how dependent one software component is on another.

A tightly coupled component knows too much about other components’ implementation details.

Consider:

public class OrderService {
    private MySqlOrderRepository repository = new MySqlOrderRepository();
    private SmtpEmailSender emailSender = new SmtpEmailSender();
    private StripePaymentClient paymentClient = new StripePaymentClient();
}

This class directly constructs and depends on several infrastructure implementations.

A less coupled design:

public class OrderService {
    private OrderRepository repository;
    private NotificationSender notificationSender;
    private PaymentGateway paymentGateway;

    public OrderService(OrderRepository repository, NotificationSender notificationSender,
                        PaymentGateway paymentGateway) {
        this.repository = repository;
        this.notificationSender = notificationSender;
        this.paymentGateway = paymentGateway;
    }
}

The service still has dependencies, but they are dependencies on defined contracts instead of concrete infrastructure implementations.

Low coupling does not mean zero coupling. Collaborating objects necessarily depend on each other’s contracts.

The objective is to make those dependencies explicit, limited, and stable.

4.6 Composition over Inheritance

Favor combining objects with complementary behaviors over creating inheritance hierarchies solely for code reuse.

Inheritance creates a relationship between types. Composition creates a relationship between collaborating objects.

Problem: Inheritance explosion

Imagine a file-backup system that supports different compression algorithms and storage locations.

An inheritance-heavy design might produce classes such as:

ZipLocalBackup
ZipS3Backup
ZipAzureBackup
GzipLocalBackup
GzipS3Backup
GzipAzureBackup

As compression strategies and storage backends grow, the number of combinations can become large.

Better design: Composition

Define the interchangeable behaviors.

public interface Compressor {
    byte[] compress(byte[] input);
}
public interface Storage {
    void save(String key, byte[] data);
}

Implement the compression behavior:

public class GzipCompressor implements Compressor {
    @Override
    public byte[] compress(byte[] input) {
        return input; # Apply GZIP compression
    }
}

Implement storage behavior:

public class LocalStorage implements Storage {
    @Override
    public void save(String key, byte[] data) {
        # Write data to the filesystem
    }
}

Compose them:

public class BackupService {
    private Compressor compressor;
    private Storage storage;

    public BackupService(Compressor compressor, Storage storage) {
        this.compressor = compressor;
        this.storage = storage;
    }

    public void backup(String key, byte[] data) {
        byte[] compressed = compressor.compress(data);
        storage.save(key, compressed);
    }
}

Usage:

BackupService backupService = new BackupService(new GzipCompressor(), new LocalStorage());
backupService.backup("orders.dat", fileData);

Changing compression or storage requires changing the composed object, not the BackupService implementation.

The actual compressor and storage implementations would need to perform real compression and I/O; the methods above are illustrative placeholders.

Composition also supports the Strategy, Decorator, Bridge, and other patterns.

4.7 Program to an Interface, Not an Implementation

This principle encourages clients to depend on contracts rather than unnecessary concrete implementation details.

For example:

List<String> names = new ArrayList<>();

is usually preferable to declaring the variable as:

ArrayList<String> names = new ArrayList<>();

when the code only needs operations from List.

Likewise:

PaymentGateway gateway;

can be preferable to:

StripePaymentGateway gateway;

when business code should be independent of the payment provider.

However, an interface is not automatically useful for every class.

A stable immutable value object such as Money, Address, or DateRange often does not need a separate interface.

Use abstractions where they create meaningful boundaries or interchangeable behavior.

4.8 Encapsulate What Varies

Identify aspects of a system likely to change and isolate them behind stable boundaries.

Suppose an application calculates shipping charges.

Potential sources of change include the delivery provider, weight-based pricing, international shipping rules, insurance, and delivery speed.

Rather than embedding every rule inside OrderService, isolate the variable behavior.

public interface ShippingCostPolicy {
    BigDecimal calculate(Shipment shipment);
}

Implementations can include:

public class StandardShippingPolicy implements ShippingCostPolicy {
    @Override
    public BigDecimal calculate(Shipment shipment) {
        return BigDecimal.ZERO; # Standard pricing
    }
}
public class ExpressShippingPolicy implements ShippingCostPolicy {
    @Override
    public BigDecimal calculate(Shipment shipment) {
        return BigDecimal.ZERO; # Express pricing
    }
}

The order-processing workflow interacts with the common shipping contract.

This principle is one of the central ideas behind the Strategy pattern and OCP.

4.9 Law of Demeter — Principle of Least Knowledge

The Law of Demeter encourages objects to interact with a limited set of collaborators rather than navigating deeply into other objects’ internal structures.

Example: Deep object navigation

String postalCode = order.getCustomer().getAddress().getPostalCode();

The calling component now knows the internal navigation path through Order, Customer, and Address.

If the customer or address model changes, the calling component may also require modification.

An alternative is to expose an operation at the appropriate boundary.

public class Order {
    private Customer customer;

    public String shippingPostalCode() {
        return customer.getShippingAddress().getPostalCode();
    }
}

Client code:

String postalCode = order.shippingPostalCode();

The client depends on the meaning of the operation rather than on the internal navigation path.

This is often summarized as avoiding excessive object chains.

Important nuance

Not every chained method call violates the Law of Demeter.

For example:

orders.stream().filter(Order::isPaid).toList();

is not inherently problematic. The issue is unnecessary knowledge of collaborators’ internal structures, not the number of dots in an expression.

Similarly, simple navigation through data transfer objects can be entirely appropriate. Avoid creating forwarding methods with no meaningful design benefit.

4.10 Tell, Don’t Ask

Prefer telling an object to perform a business operation instead of extracting its internal state, making decisions externally, and then modifying it.

This principle emphasizes behavior-rich domain objects.

Poor design

if (order.getStatus() == OrderStatus.PENDING) {
    order.setStatus(OrderStatus.PAID);
}

The caller is responsible for checking and enforcing the business transition.

Multiple callers may repeat this logic inconsistently.

Better design

public class Order {
    private OrderStatus status;

    public void markPaid() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Only pending orders can be paid");
        }
        status = OrderStatus.PAID;
    }
}

Client:

order.markPaid();

The Order object now owns the rules governing its status.

This helps maintain invariants and reduce duplicated business decisions.

Tell, Don’t Ask is particularly valuable for domain entities and aggregates in Domain-Driven Design.

It does not mean getters or queries are forbidden. Reporting, serialization, and other operations often legitimately require reading data.

4.11 Separation of Concerns (SoC)

Separation of Concerns states that different areas of responsibility should be separated to make software easier to understand and change.

Unlike SRP, which is frequently applied to classes and modules, SoC applies across multiple architectural levels.

For example, a typical Spring Boot application might separate:

ComponentConcern
ControllerHTTP request/response handling
Application serviceWorkflow coordination
Domain modelBusiness rules and invariants
Repository abstractionPersistence contract
Repository implementationDatabase interaction
Infrastructure adapterExternal system integration

A controller should not usually contain all the business rules, payment API calls, SQL queries, and email delivery logic.

Likewise, a domain entity generally should not depend on Spring MVC request objects.

Separating concerns helps establish meaningful architectural boundaries.

4.12 Information Hiding

Information Hiding means concealing design decisions that should not be exposed to other modules.

Encapsulation is one technique for achieving information hiding, but the idea is broader than private fields.

Suppose a service returns account data. Consumers should not need to know whether the data is stored in PostgreSQL, MongoDB, an API, or an in-memory cache.

public interface AccountRepository {
    Optional<Account> findById(UUID id);
}

The interface hides the persistence mechanism.

Information hiding protects consumers from changes in implementation decisions.

4.13 Design by Contract

Design by Contract expresses the behavioral obligations between a component and its clients.

A contract can specify:

  • Preconditions: What must be true before an operation is executed.
  • Postconditions: What the operation guarantees after successful execution.
  • Invariants: What must remain true for the object or system.

Consider a transfer between bank accounts.

public void transfer(BankAccount from, BankAccount to, BigDecimal amount) {
    if (amount == null || amount.signum() <= 0) {
        throw new IllegalArgumentException("Amount must be positive");
    }
    # Perform the transfer through a suitable transactionally consistent mechanism.
}

The precondition requires a positive amount.

A postcondition could require that the intended amount is transferred exactly once, provided the operation succeeds.

An invariant might require that the total funds across the two accounts remain unchanged by the transfer, assuming there are no fees.

In distributed systems, these guarantees require more than object-level method checks. Database transactions, idempotency, recovery, and consistency mechanisms may be necessary.

Design by Contract is closely related to LSP because subtype implementations must respect the contracts on which clients rely.

4.14 Favor Immutability

An immutable object cannot change its observable state after construction.

Immutable objects are useful because they reduce accidental state changes, make reasoning easier, and can simplify concurrent programming.

Java records are convenient for representing immutable value objects.

public record Money(BigDecimal amount, String currency) {
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        if (currency.isBlank()) {
            throw new IllegalArgumentException("Currency is required");
        }
    }

    public Money add(Money other) {
        if (!currency.equals(other.currency())) {
            throw new IllegalArgumentException("Currency mismatch");
        }
        return new Money(amount.add(other.amount()), currency);
    }
}

Usage:

Money a = new Money(new BigDecimal("100.00"), "INR");
Money b = new Money(new BigDecimal("50.00"), "INR");
Money total = a.add(b);
System.out.println(total.amount()); # 150.00

The original Money objects remain unchanged.

Records provide shallow immutability: their component references are final, but referenced mutable objects can still change. The example is safe in that respect because BigDecimal and String are immutable.

A production money type would typically also standardize currency identifiers, precision, and rounding rules.

Where immutability is useful

Value objects such as money, coordinates, date ranges, configuration values, and identifiers are often excellent candidates.

Mutable entities may still be appropriate when their identity persists through legitimate state transitions.

4.15 Command–Query Separation (CQS)

The Command–Query Separation principle distinguishes between operations that modify state and operations that retrieve information.

A command changes state. A query returns information without changing observable state.

Example:

public class ShoppingCart {
    private List<CartItem> items = new ArrayList<>();

    public void addItem(CartItem item) { # Command
        items.add(item);
    }

    public int itemCount() { # Query
        return items.size();
    }
}

addItem() modifies the cart, while itemCount() reads its state without modifying it.

This separation makes APIs easier to reason about.

CQS is related to but distinct from CQRS (Command Query Responsibility Segregation). CQRS is an architectural approach that separates read and write models or responsibilities, potentially using different storage or processing arrangements.

CQS does not require separate databases, microservices, or event sourcing.

Pragmatic APIs may combine commands with useful results, such as returning the identifier of a newly created order. The principle is a guideline for clarity, not an absolute prohibition.

4.16 Principle of Least Astonishment

The Principle of Least Astonishment suggests that software components should behave in ways consistent with users’ and developers’ reasonable expectations.

For example, a method named:

List<Order> getOrders();

should not unexpectedly delete expired orders, send notifications, or initiate payments as part of its ordinary behavior.

Likewise, a method named calculateTotal() should usually calculate and return the total rather than also persisting the result and modifying unrelated state.

Clear method names, predictable error behavior, consistent return values, and stable contracts help achieve this principle.

5. GRASP — General Responsibility Assignment Software Patterns

GRASP is a set of nine principles and patterns introduced by Craig Larman to guide the assignment of responsibilities in object-oriented systems.

SOLID focuses heavily on maintainability and extensibility; GRASP is especially useful when deciding which object should perform which operation.

5.1 Information Expert

A responsibility should generally be assigned to the object that has the information needed to fulfill it.

For example, an order contains its line items.

public class Order {
    private List<OrderItem> items;

    public Order(List<OrderItem> items) {
        this.items = List.copyOf(items);
    }

    public BigDecimal calculateTotal() {
        return items.stream().map(OrderItem::getSubtotal).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

The order knows its contents, so calculating the total from those contents is often a natural responsibility.

This is typically preferable to making an unrelated UserService navigate an order’s internal data to calculate its total.

However, taxes, discounts, and other context-dependent pricing rules may belong in dedicated policy or domain services.

5.2 Creator

GRASP’s Creator principle helps determine which object should create another.

A good creation candidate may aggregate, contain, closely use, or possess the initialization data needed for the new object.

For example, a shopping cart may have the information necessary to create an order draft.

public OrderDraft createOrderDraft() {
    return new OrderDraft(List.copyOf(items));
}

If construction is complex, requires several external dependencies, or spans multiple domain objects, a factory may be more appropriate.

The goal is not to create a factory for every class.

5.3 Controller

The GRASP Controller coordinates requests corresponding to system operations.

For example, placing an order involves selecting products, calculating prices, charging payment, and persisting the resulting order.

An application-level CheckoutService can coordinate these operations.

public class CheckoutService {
    public Order placeOrder(CheckoutCommand command) {
        # Coordinate the use case
        # Delegate domain logic to appropriate objects
        # Delegate infrastructure through ports
        # Return the resulting order
        return null;
    }
}

This is distinct from a Spring MVC @RestController.

The MVC controller handles the HTTP interaction, while the application service coordinates the business use case.

5.4 Pure Fabrication

Not every responsibility fits naturally within a business entity.

For example, database persistence is a technical responsibility.

Adding SQL directly to an Order entity may increase coupling and reduce cohesion.

Creating an OrderRepository abstraction provides a suitable home for that responsibility without forcing it into the domain object.

This is called Pure Fabrication: introducing a non-domain class to improve the design.

5.5 Indirection and Protected Variations

Suppose checkout logic communicates with a third-party payment API.

Directly coupling checkout logic to provider-specific requests and responses exposes the workflow to external API changes.

A PaymentGateway abstraction introduces indirection and protects the checkout code from those variations.

The remaining GRASP principles—Low Coupling, High Cohesion, and Polymorphism—were discussed earlier and complement these responsibility-assignment decisions.

6. Additional Package and Architectural Design Principles

Object-oriented design also applies beyond individual classes.

Robert C. Martin described principles for organizing packages and their dependencies, which remain useful when considering Java packages, modules, and application boundaries.

PrincipleDescription
REP — Reuse/Release EquivalenceGroup reusable elements into meaningful, releasable units
CCP — Common ClosureGroup components that tend to change for the same reasons
CRP — Common ReuseAvoid forcing consumers to depend on components they do not actually use
ADP — Acyclic DependenciesAvoid cycles in package/module dependencies
SDP — Stable DependenciesPrefer dependencies pointing toward more stable modules
SAP — Stable AbstractionsHighly stable modules should expose appropriate abstraction and extensibility

Example: Circular dependencies

Consider three modules:

order-module → payment-module
payment-module → notification-module
notification-module → order-module

These form a cycle.

Changes, testing, build configuration, and independent evolution become more difficult.

Possible remedies include separating shared contracts, moving a responsibility to the correct module, introducing an application-level coordinator, or replacing an unnecessary dependency with an event or appropriate abstraction.

The goal is not to mechanically introduce interfaces everywhere. It is to establish a coherent dependency structure.

Dependency direction in layered architecture

A common design is:

Presentation Layer

REST Controllers, request DTOs

Application Layer

Use cases, workflow orchestration

Domain Layer

Entities, value objects, policies, core contracts

Infrastructure implements inward-facing ports

Infrastructure Adapters

Database, email, external APIs

Here the arrows represent conceptual source-code dependencies, not the chronological flow of runtime calls.

In a layered or hexagonal design, business rules should generally avoid depending on provider-specific infrastructure. Infrastructure can instead implement the contracts required by the business layer.

This makes it easier to replace databases, external APIs, message brokers, and other implementation details without rewriting the domain logic.

Step 1: Create the order domain model

Order.java

package com.example.checkout;

public record Order(UUID id, String sku, int quantity, BigDecimal total, Status status) {
    public enum Status {
        PENDING, PAID, DECLINED
    }

    public Order {
        Objects.requireNonNull(id);
        Objects.requireNonNull(total);
        Objects.requireNonNull(status);
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU is required");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
        if (total.signum() < 0) {
            throw new IllegalArgumentException("Total cannot be negative");
        }
    }

    public Order complete(Status newStatus) {
        if (status != Status.PENDING) {
            throw new IllegalStateException("Order is not pending");
        }
        if (newStatus != Status.PAID && newStatus != Status.DECLINED) {
            throw new IllegalArgumentException("Invalid final status");
        }
        return new Order(id, sku, quantity, total, newStatus);
    }
}

Principles applied: Encapsulation, immutability, Tell Don’t Ask, Design by Contract, and Information Expert.

The order controls which state transitions are valid. External code cannot mutate its fields directly.

Step 2: Define abstraction contracts

Contracts.java

Step 3: Implement the checkout service

CheckoutService.java

package com.example.checkout;

@Service
public class CheckoutService {
    private ProductCatalog productCatalog;
    private DiscountPolicy discountPolicy;
    private PaymentGateway paymentGateway;
    private OrderRepository orderRepository;

    public CheckoutService(ProductCatalog productCatalog, DiscountPolicy discountPolicy,
                           PaymentGateway paymentGateway, OrderRepository orderRepository) {
        this.productCatalog = productCatalog;
        this.discountPolicy = discountPolicy;
        this.paymentGateway = paymentGateway;
        this.orderRepository = orderRepository;
    }

    public Order checkout(String sku, int quantity) {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU is required");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
        BigDecimal unitPrice = productCatalog.priceFor(sku); # Trusted price comes from the product catalog.
        BigDecimal subtotal = unitPrice.multiply(BigDecimal.valueOf(quantity));
        BigDecimal discount = discountPolicy.discountFor(subtotal);
        if (discount == null || discount.signum() < 0 || discount.compareTo(subtotal) > 0) {
            throw new IllegalStateException("Invalid discount");
        }
        BigDecimal total = subtotal.subtract(discount);
        # Create pending order.
        Order order = new Order(UUID.randomUUID(), sku, quantity, total, Order.Status.PENDING);
        orderRepository.save(order);
        # Payment adapter receives order ID for use as a provider idempotency reference.
        ChargeOutcome outcome = paymentGateway.charge(order.id(), order.total());
        Order.Status finalStatus = outcome == ChargeOutcome.APPROVED ? Order.Status.PAID : Order.Status.DECLINED;
        Order completedOrder = order.complete(finalStatus);
        orderRepository.save(completedOrder);
        return completedOrder;
    }

    public Optional<Order> findById(UUID id) {
        return orderRepository.findById(id);
    }
}

This service does not know how prices are stored, how discounts are implemented, which payment provider is used, or which persistence technology saves orders.

It coordinates the workflow through interfaces.

This is an application of SRP, DIP, OCP, ISP, Separation of Concerns, and composition.

Step 4: Create implementations

DemoAdapters.java

package com.example.checkout;

@Component
public class InMemoryCatalog implements ProductCatalog {
    private Map<String, BigDecimal> prices = Map.of("BOOK-1", new BigDecimal("499.00"), "COURSE-1",
                                                    new BigDecimal("1999.00"));

    @Override
    public BigDecimal priceFor(String sku) {
        BigDecimal price = prices.get(sku);
        if (price == null) {
            throw new IllegalArgumentException("Unknown product: " + sku);
        }
        return price;
    }
}

@Component
public class TenPercentDiscount implements DiscountPolicy {
    @Override
    public BigDecimal discountFor(BigDecimal subtotal) {
        return subtotal.multiply(new BigDecimal("0.10"));
    }
}

@Component
public class DemoPaymentGateway implements PaymentGateway {
    @Override
    public ChargeOutcome charge(UUID orderId, BigDecimal amount) {
        # Simulated payment provider.
        # No actual charge is performed.
        return ChargeOutcome.APPROVED;
    }
}

@Repository
public class InMemoryOrderRepository implements OrderRepository {
    private Map<UUID, Order> orders = new ConcurrentHashMap<>();

    @Override
    public void save(Order order) {
        orders.put(order.id(), order);
    }

    @Override
    public Optional<Order> findById(UUID id) {
        return Optional.ofNullable(orders.get(id));
    }
}

Because each implementation fulfills one contract, we can replace it without changing the checkout workflow.

For example, a new discount policy can implement DiscountPolicy. Spring configuration would then select which implementation to inject.

A PostgreSQL repository could replace InMemoryOrderRepository, and a production payment adapter could replace DemoPaymentGateway.

Step 5: Create the REST controller

CheckoutController.java

package com.example.checkout;

@RestController
@RequestMapping("/orders")
public class CheckoutController {
    private CheckoutService checkoutService;

    public CheckoutController(CheckoutService checkoutService) {
        this.checkoutService = checkoutService;
    }

    public record CheckoutRequest(String sku, int quantity) {}

    @PostMapping
    public ResponseEntity<Order> checkout(@RequestBody CheckoutRequest request) {
        Order order = checkoutService.checkout(request.sku(), request.quantity());
        return ResponseEntity.status(HttpStatus.CREATED).body(order);
    }

    @GetMapping("/{id}")
    public ResponseEntity<Order> findById(@PathVariable UUID id) {
        Optional<Order> result = checkoutService.findById(id);
        return result.map(ResponseEntity::ok).orElseGet(() -> ResponseEntity.notFound().build());
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, String>> handleBadRequest(IllegalArgumentException ex) {
        return ResponseEntity.badRequest().body(Map.of("error", ex.getMessage()));
    }
}

package com.example.checkout;

public class CheckoutServiceTest {
    @Test

        ProductCatalog catalog = sku -> new BigDecimal("100.00");

                return Optional.ofNullable(data.get(id));

7.4 Important production considerations

The example demonstrates object-oriented design, but it is intentionally not a production-complete payment implementation.

A real checkout system must address several additional concerns.

Payment state uncertainty: If a payment provider completes a charge but the network response is lost, the application must not automatically assume the payment was declined. An unknown state may require reconciliation.

Idempotency: Retrying checkout must not create duplicate payments. The system needs a stable client request idempotency key, and the payment adapter must actually enforce or forward a suitable provider idempotency key. The demonstration does not implement these mechanisms.

Persistence consistency: Saving a pending order, performing an external payment, and saving the final status are not one atomic transaction. A crash between these steps may require recovery.

Concurrency: A real repository may need optimistic locking or other controls to prevent competing requests from overwriting order state.

External side effects: Sending order-confirmation emails or publishing events should use an appropriately reliable mechanism, such as a transactional outbox with asynchronous processing, where warranted.

Good object-oriented design improves separation of responsibilities, but it does not replace distributed-systems reliability patterns.

8. Common Object-Oriented Design Mistakes

Understanding design principles is also about recognizing situations where they have been violated.

Code smellMeaningLikely improvement
God ObjectA class manages too many unrelated responsibilitiesSRP, high cohesion
Shotgun SurgeryOne change requires modifications across many classesDRY, encapsulation, better ownership
Divergent ChangeOne class changes for several unrelated reasonsSRP, separation of concerns
Feature EnvyA method operates heavily on another object’s dataInformation Expert, Tell Don’t Ask
Long Parameter ListMethods require many loosely associated argumentsValue objects, cohesive abstractions
Primitive ObsessionDomain concepts are represented by unrestricted primitive valuesValue objects
Deep InheritanceExcessive inheritance makes behavior difficult to understandComposition
Refused BequestA subclass cannot meaningfully support inherited operationsLSP, ISP
Switch ExplosionSimilar type-based conditionals are scattered across the systemPolymorphism, OCP
Circular DependenciesComponents depend on each other in cyclesClear dependency direction
Anemic Domain ModelDomain objects contain only data while rules are scattered elsewhereEncapsulation, Information Expert
Premature AbstractionInterfaces and frameworks are introduced without meaningful needKISS, YAGNI

These are diagnostic clues, not absolute rules. For example, data-transfer objects are intentionally data-oriented, and a simple conditional may be clearer than a hierarchy of strategies.

9. How the Principles Work Together

Consider a requirement:

Add a new payment provider to an existing checkout application.

A well-designed system can apply several principles simultaneously.

PrincipleHow it helps
SRPCheckout workflow and payment integration have different responsibilities
OCPAdd a provider implementation without rewriting checkout logic
LSPThe provider must respect the shared payment contract
ISPThe payment contract exposes only the required capabilities
DIPCheckout depends on PaymentGateway, not a provider SDK
CompositionThe desired provider is supplied to the checkout service
Low CouplingProvider changes have limited effects on the business layer
Protected VariationsProvider-specific API behavior remains inside the adapter
KISSAvoid building a complex provider framework if one simple adapter is sufficient

This demonstrates an important point: design principles are not independent rules. They reinforce one another to solve the underlying problems of responsibility assignment, dependency management, and change.

10. How to Decide Which Principle to Apply

You do not need to introduce an interface, factory, strategy, or additional class every time you write a method.

Instead, use the following questions while designing a component.

Design questionRelevant principle
Does this class have unrelated responsibilities?SRP
Will adding another implementation require editing multiple conditionals?OCP, Polymorphism
Does a subclass violate expected behavior?LSP
Must a class implement methods it cannot support?ISP
Is business logic tied to a database, SDK, or framework?DIP
Is the same business rule implemented in several places?DRY
Is the design becoming unnecessarily complicated?KISS
Am I implementing hypothetical future requirements?YAGNI
Is this inheritance relationship only being used for code reuse?Composition over Inheritance
Does a method repeatedly inspect another object’s internal state?Information Expert, Tell Don’t Ask
Does one component know too much about another’s internal structure?Law of Demeter, Information Hiding
Can this value object be immutable?Favor Immutability
Is a supposedly read-only operation unexpectedly changing state?CQS
Are packages or modules depending on each other in cycles?Acyclic Dependencies
11. Principle vs Design Pattern vs Architecture Pattern

These terms are related but should not be confused.

ConceptDescriptionExamples
Design PrincipleGeneral guidance for making design decisionsSRP, OCP, DIP, DRY
Design PatternReusable arrangement of classes or objects solving a recurring design problemStrategy, Factory, Observer, Decorator
Architecture PatternSystem-level organizational approachLayered Architecture, Hexagonal Architecture, CQRS
Programming ParadigmGeneral approach to structuring programsObject-Oriented, Functional, Procedural

For example, OCP is a principle; Strategy is one design pattern that can help implement OCP.

DIP is a principle; Dependency Injection is a technique that can help achieve it.

Separation of Concerns is a general principle; Hexagonal Architecture is one architectural approach that applies it along with dependency inversion.

12. Final Summary

The most important OOD objectives

High Cohesion

Keep related responsibilities together.

Low Coupling

Reduce unnecessary dependencies.

Strong Encapsulation

Protect state and business rules.

Controlled Extensibility

Isolate behavior likely to change.

Testability

Make dependencies substitutable.

Simplicity

Avoid speculative abstractions.

A useful mental model is:

OOP provides the programming mechanisms. SOLID and GRASP guide how those mechanisms are used. General design principles keep the resulting system simple, cohesive, and maintainable. Design patterns provide reusable solutions for recurring problems.

The ultimate goal of object-oriented design is not to maximize the number of interfaces, classes, or patterns in a codebase. It is to build software whose responsibilities are clear, whose behavior is correct, and whose inevitable changes can be made with minimal disruption.
