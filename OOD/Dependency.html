Dependency Injection

Dependency injection generally means passing a dependent object as a parameter to a method rather than having the method create the dependent object.

Dependency injection is a software design pattern that allow us to develop loosely-coupled software.

Dependecy injection allows us to depends more on abstraction rather than the concrete implementation, which promotes loosely-coupled architecture, flexibility and pluggability within our code.

What it means in practice is that the method does not have a direct dependency on a particular implementation, any implementation that meets the requirements can be passed as a parameter.

Dependency injection is a programming technique where an object or function receives its dependencies (other objects or functions it needs) from an external source, rather than creating them itself. This approach, which is a form of Inversion of Control, makes code more flexible, maintainable, and testable by decoupling components and allowing them to be replaced or mocked easily.

Types of Dependency Injection
  1. Constructor Injection – dependencies are passed through a class constructor.
  2. Setter Injection – dependencies are set using setter methods.
  3. Field Injection – dependencies are directly injected into fields (commonly via annotations like @Autowired).
In Spring Boot:
  • @Autowired on constructor → Constructor Injection
  • @Autowired on setter → Setter Injection
  • @Autowired on field → Field Injection
Inversion of Control (IoC)DI is the main way IoC is achieved in Spring. The control of creating and managing dependencies is inverted from the developer to the Spring container.Instead of you building your house, a builder constructs it and hands you the keys.
Benefits
  • Promotes loose coupling.
  • Improves testability (e.g., easy to mock dependencies).
  • Enhances code reusability.
  • Simplifies maintenance and configuration.
You can test OrderService by injecting a mock PaymentService.
Dependency Inversion Principle

High level modules should not depend on low level modules.

Both should depend on abstractions.

Abstraction should not depend on implementation.

Implementation should depend on abstraction.

Benefits of Dependency Inversion
  • Easier testing
    Because high-level modules depend on abstractions, they can be tested with mock implementations of the low-level modules instead of the real ones. Tests become faster and more reliable, since there is no need to set up a real database or other external resources.
  • Easier reuse
    High-level modules can be used in different contexts without changing the low-level modules they depend on. This makes code easier to reuse and avoids duplication, and adding new implementations requires minimal changes.

Together, these make the dependency inversion principle a way to build more flexible, maintainable and testable software.

Code
public interface MessageService {
    void send(String msg);
}

@Service
public class EmailService implements MessageService {
    public void send(String msg) {
        System.out.println("Email: " + msg);
    }
}

@Component
public class Notifier {

    private final MessageService service;

    # Constructor injection
    @Autowired
    Notifier(MessageService service) {
        this.service = service;
    }

    void notifyUser() {
        service.send("Welcome!");
    }
}

# The Spring container injects EmailService into Notifier;
# Notifier never calls new EmailService() itself.
How Dependency Injection works

Notifier depends on the MessageService abstraction.

The dependency is passed in through the constructor.

The container picks the @Service bean and wires it in.

Swapping to an SMS service needs no change inside Notifier.
