Observer

The Observer Pattern is a behavioral design pattern that defines a one-to-many dependency between objects, so that when one object (called the Subject) changes its state, all its dependent objects (called Observers) are automatically notified and can react to that change.

The Observer pattern establishes a loosely coupled relationship between the object that generates events and the objects that respond to those events.

It allows multiple objects to observe changes in another object without requiring the subject to know the concrete implementations of its observers.

Observer is a behavioral design pattern that defines a one-to-many dependency between objects, where one object, called the Subject (or Publisher), maintains a collection of dependent objects called Observers (or Subscribers). Observers can subscribe to or unsubscribe from the Subject dynamically.

Whenever the Subject's state changes or an important event occurs, the Subject automatically notifies all registered Observers, allowing each Observer to react or update itself accordingly. This promotes loose coupling because the Subject does not need to know the concrete implementations of its Observers - it only communicates with them through a common Observer interface.

Key characteristics:

  • One-to-many relationship: A single subject can have multiple observers.
  • Automatic notification: When the subject's state changes, its registered observers receive notifications.
  • Loose coupling: The subject depends only on an observer interface, not on concrete observer classes.
  • Dynamic subscription: Observers can be registered or unregistered at runtime.
  • Independent reactions: Each observer can respond differently to the same event.

The pattern is commonly used in event-driven programming, GUI frameworks, notification systems, stock market applications, and application event handling.

Real-World Example: E-Commerce Order Tracking

Imagine an e-commerce application where customers place orders.

Whenever an order's status changes, several independent components need to react:

  • Email Notification: Sends an email to the customer.
  • Dashboard: Updates the order status displayed to the user.
  • Audit Logger: Records the order status change.
  • Analytics: Updates business metrics.

Without the Observer pattern, the Order class might directly call each component.

public class Order {
    public void updateStatus(String status) {
        this.status = status;
        emailService.sendEmail(status);
        dashboardService.updateDashboard(status);
        auditService.log(status);
        analyticsService.track(status);
    }
}

Problems with this approach

  • The Order class is tightly coupled to several services.
  • Adding a new notification mechanism requires modifying the Order class.
  • Removing or replacing a service also requires changing the Order implementation.
  • The Order class has multiple responsibilities instead of focusing on order management.

Solution using Observer

Instead of invoking specific components, the Order class maintains a collection of objects implementing a common OrderObserver interface. Whenever its status changes, it notifies all registered observers.

Each observer implements the same interface but performs its own action.

Now Order class does not need to know whether an observer sends emails, updates a dashboard, or writes audit logs.

It simply announces that a change has occurred.

Main Components of the Observer Pattern
ComponentResponsibility
Subject (Observable)Maintains registered observers and notifies them about changes.
ObserverDefines a common interface for receiving notifications.
Concrete SubjectStores application state and triggers notifications when it changes.
Concrete ObserverImplements the observer interface and defines its response to notifications.

How the pattern works

Registration
Interested observers subscribe to the subject using a method such as subscribe(observer).
State change
An operation changes the internal state of the subject.
Notification
The subject iterates through its registered observers and calls their notification method.
Reaction
Each observer performs its own action based on the event.
Unsubscription
An observer can stop receiving events by unregistering itself.
Java Implementation: Order Notification System

We will implement the Observer pattern using an order tracking application.

Define an order status

public enum OrderStatus {
    CREATED, CONFIRMED, SHIPPED, DELIVERED
}

Define an event

Rather than sending just the new status, we can create an event containing information about the change.

public record OrderStatusChanged(String orderId, OrderStatus oldStatus, OrderStatus newStatus) {}

For example, an event might contain:

orderId   = ORD-101
oldStatus = CONFIRMED
newStatus = SHIPPED

Passing an event object makes the Observer implementation more flexible because observers have access to the information needed to process the change.

Create the Observer interface

@FunctionalInterface
public interface OrderObserver {
    void onStatusChanged(OrderStatusChanged event);
}

This interface defines the contract that every observer must implement.

The subject doesn't need to know what individual observers do.

It only needs to know that they implement OrderObserver.

Create the Subject

public class Order {
    private String id;
    private OrderStatus status = OrderStatus.CREATED;
    private CopyOnWriteArrayList<OrderObserver> observers = new CopyOnWriteArrayList<>();

    public Order(String id) {
        this.id = id;
    }

    # Register an observer
    public void subscribe(OrderObserver observer) {
        observers.addIfAbsent(observer);
    }

    # Unregister an observer
    public void unsubscribe(OrderObserver observer) {
        observers.remove(observer);
    }

    # Change the order status
    public void updateStatus(OrderStatus newStatus) {
        if (newStatus == null) {
            throw new IllegalArgumentException("Status cannot be null");
        }
        if (this.status == newStatus) {
            return;
        }
        OrderStatus oldStatus = this.status;
        this.status = newStatus;
        OrderStatusChanged event = new OrderStatusChanged(id, oldStatus, newStatus);
        notifyObservers(event);
    }

    # Notify all registered observers
    public void notifyObservers(OrderStatusChanged event) {
        for (OrderObserver observer : observers) {
            observer.onStatusChanged(event);
        }
    }

    public OrderStatus getStatus() {
        return status;
    }
}

Important observations:

  • The Order class stores references to objects implementing the OrderObserver interface.
  • Observers register using subscribe().
  • Whenever updateStatus() changes the state, notifyObservers() is invoked.
  • Every registered observer receives the same event.
  • An observer can unregister at runtime.

Here, CopyOnWriteArrayList allows the observer collection to be safely iterated while subscriptions are added or removed, including from another thread. It does not, by itself, make concurrent order-status updates thread-safe.

Step 5: Create Concrete Observers

Email Notification Observer

public class EmailNotification implements OrderObserver {
    public void onStatusChanged(OrderStatusChanged event) {
        if (event.newStatus() == OrderStatus.SHIPPED) {
            System.out.println("Email: Order " + event.orderId() + " has been shipped.");
        }
    }
}

This observer responds only when an order is shipped.

Dashboard Observer

public class DashboardUpdater implements OrderObserver {
    public void onStatusChanged(OrderStatusChanged event) {
        System.out.println("Dashboard: Order " + event.orderId() + " status updated to " + event.newStatus());
    }
}

This observer responds to every status change.

Audit Logger Observer

public class AuditLogger implements OrderObserver {
    public void onStatusChanged(OrderStatusChanged event) {
        System.out.println("Audit: Order " + event.orderId() + " changed from " + event.oldStatus() + " to " + event.newStatus());
    }
}

Notice how every observer implements the same interface, but each performs a completely different action.

Client Code

void main(String[] args) {
    Order order = new Order("ORD-101");
    OrderObserver email = new EmailNotification();
    OrderObserver dashboard = new DashboardUpdater();
    OrderObserver audit = new AuditLogger();
    # Subscribe observers
    order.subscribe(email);
    order.subscribe(dashboard);
    order.subscribe(audit);
    order.updateStatus(OrderStatus.CONFIRMED); # First status change
    order.updateStatus(OrderStatus.SHIPPED); # Second status change
    order.unsubscribe(email); # Dynamically remove an observer
    order.updateStatus(OrderStatus.DELIVERED); # Third status change
}

Output

Dashboard: Order ORD-101 status updated to CONFIRMED
Audit: Order ORD-101 changed from CREATED to CONFIRMED

Email: Order ORD-101 has been shipped.
Dashboard: Order ORD-101 status updated to SHIPPED
Audit: Order ORD-101 changed from CONFIRMED to SHIPPED

Dashboard: Order ORD-101 status updated to DELIVERED
Audit: Order ORD-101 changed from SHIPPED to DELIVERED

When the email observer is removed, it stops receiving subsequent notifications.

The Order class itself does not need to change.

Adding a New Observer

Suppose we want to add an analytics component.

public class AnalyticsObserver implements OrderObserver {
    public void onStatusChanged(OrderStatusChanged event) {
        System.out.println("Analytics: Tracking order status " + event.newStatus());
    }
}

We simply register it:

order.subscribe(new AnalyticsObserver());

No modification is required in the existing Order class.

This demonstrates the Open/Closed Principle: new observer behaviors can be added without modifying the subject's notification logic.

Push vs Pull Models in Observer Pattern

There are two common ways an observer obtains information from a subject.

Push Model
The subject sends relevant data directly to its observers when notifying them.

Pull Model
The subject notifies observers, which then retrieve the required information.

Push Model

In the previous example, we used the Push Model.

public interface OrderObserver {
    void onStatusChanged(OrderStatusChanged event);
}

The subject pushes the event to its observers:

observer.onStatusChanged(event);

The observer doesn't need to query the subject for information.

Advantages: Fewer queries back to the subject, easy event processing, and the event can preserve the state at the moment the change occurred.

Disadvantages: Events can contain more data than some observers need.

Pull Model

In the Pull Model, the observer receives a reference to the subject and retrieves the information it needs.

For example, we could define a different observer interface:

public interface OrderObserver {
    void update(Order order);
}

Inside the subject, notification looks like this:

public void notifyObservers() {
    for (OrderObserver observer: observers) {
        observer.update(this);
    }
}

The observer pulls the current status:

public class DashboardObserver implements OrderObserver {
    @Override
    public void update(Order order) {
        OrderStatus status = order.getStatus();
        System.out.println("Current status: " + status);
    }
}

Advantages: Observers retrieve only the information they need; notification messages can remain small.

Disadvantages: Observers depend on the subject's read interface and may need additional method calls. If the subject changes again before an observer reads it, the observer could see a newer state rather than the state that triggered the notification.

In practice, immutable event objects (Push Model) are often a good choice for event-driven applications.

Real-World Example: Observer Pattern in Java GUI Frameworks

One of the most common uses of the Observer pattern is in GUI event handling.

Consider a button in a Java Swing application.

The button acts as an event source, while registered listeners react when the button is clicked.

void main(String[] args) {
    SwingUtilities.invokeLater(() -> {
        JFrame frame = new JFrame("Observer Example");
        JButton button = new JButton("Click Me");
        button.addActionListener(event -> { # First observer
            System.out.println("Button clicked!");
        });
        button.addActionListener(event -> { # Second observer
            System.out.println("Analytics event recorded");
        });
        frame.add(button);
        frame.setSize(300, 150);
        frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        frame.setVisible(true);
    });
}

Interactive illustration of the button event

Both listeners react to the same click. Each click of Click Me adds to the event log:

Button clicked!
Analytics event recorded

The button doesn't need to know what the listeners do.

One listener might update a label, another might play a sound, and another might record analytics.

All can respond to the same user action.

This is a practical application of Observer-style event handling.

Observer Pattern Using Java's Built-in PropertyChangeSupport

Java provides PropertyChangeSupport in the java.beans package, which implements property-change listener registration and notification.

It is useful when observers need to monitor changes to an object's properties.

Consider a temperature monitoring system.

public class TemperatureSensor {
    private double temperature;
    private PropertyChangeSupport support = new PropertyChangeSupport(this);

    public void addListener(PropertyChangeListener listener) {
        support.addPropertyChangeListener("temperature", listener);
    }

    public void removeListener(PropertyChangeListener listener) {
        support.removePropertyChangeListener("temperature", listener);
    }

    public void setTemperature(double newTemperature) {
        double oldTemperature = this.temperature;
        this.temperature = newTemperature;
        support.firePropertyChange("temperature", oldTemperature, newTemperature);
    }
}

Now register two observers:

void main(String[] args) {
    TemperatureSensor sensor = new TemperatureSensor();
    sensor.addListener(event -> { # Observer 1: Display
        System.out.println("Display: " + event.getNewValue() + "°C");
    });
    sensor.addListener(event -> { # Observer 2: Temperature alert
        double temperature = (double) event.getNewValue();
        if (temperature > 40) {
            System.out.println("ALERT: High temperature!");
        }
    });
    sensor.setTemperature(25);
    sensor.setTemperature(45);
}

Output:

Display: 25.0°C
Display: 45.0°C
ALERT: High temperature!

Here, PropertyChangeSupport manages the observer list and notification mechanism.

Note: Java also has the older java.util.Observer and java.util.Observable APIs, but they were deprecated in Java 9. Prefer listener interfaces, PropertyChangeSupport, or modern event APIs for new code.

Observer Pattern in Spring Boot

Spring provides an application event mechanism that follows the Observer principle.

Instead of manually maintaining a collection of observers, we can use:

  • ApplicationEventPublisher to publish events.
  • @EventListener to register event-handling methods.

Step 1: Define an event

public record OrderShippedEvent(String orderId) {}

Step 2: Publish an event

@Service
public class OrderService {
    private ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void shipOrder(String orderId) {
        # Business logic for shipping an order
        System.out.println("Order shipped: " + orderId);
        publisher.publishEvent(new OrderShippedEvent(orderId));
    }
}

Step 3: Create observers using @EventListener

Email Listener

@Component
public class EmailListener {
    @EventListener
    public void onOrderShipped(OrderShippedEvent event) {
        System.out.println("Sending email for order: " + event.orderId());
    }
}

Analytics Listener

@Component
public class AnalyticsListener {
    @EventListener
    public void trackShipping(OrderShippedEvent event) {
        System.out.println("Recording shipping analytics: " + event.orderId());
    }
}

When OrderService publishes an OrderShippedEvent, Spring dispatches it to both listeners.

The service does not know either concrete listener.

Important considerations in Spring

  • By default, Spring's standard application event listeners execute synchronously in the publisher's thread.
  • That means a slow listener can delay the original service operation.
  • For asynchronous handling, Spring supports @Async when asynchronous execution is configured appropriately.
  • When events are associated with database transactions, @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) can defer listener execution until a successful transaction commit.

For reliable delivery across microservices, particularly when database changes and event publishing must remain consistent, the Transactional Outbox Pattern together with a message broker such as Kafka is often more appropriate than an in-process observer alone.

Observer Pattern vs. Publish-Subscribe Pattern

Observer and Publish-Subscribe are closely related, but they aren't exactly the same architectural mechanism.

AspectObserverPublish-Subscribe
CommunicationSubject notifies registered observersPublisher emits messages through an intermediary
CouplingSubject knows observer interfaces/referencesPublishers and subscribers can remain unaware of each other
IntermediaryNot requiredTypically an event bus or message broker
ExecutionOften synchronousCan be synchronous or asynchronous
ScopeCommonly within one application/processCan work across processes and services
ExampleJava listeners, GUI eventsKafka, RabbitMQ, event buses

A typical Observer implementation has the subject manage its subscribers directly.

A Publish-Subscribe implementation introduces an event channel or broker that manages routing between publishers and subscribers.

Spring's application event mechanism combines Observer-like listener notification with an in-process event-dispatching abstraction.

The key distinction is not simply synchronous versus asynchronous communication. Both models can support either behavior.

Advantages and Disadvantages

Advantages

  • Loose coupling
    The subject depends on an interface instead of concrete observer implementations.
  • Open/Closed Principle
    New observers can be introduced without modifying the subject's notification implementation.
  • Dynamic relationships
    Observers can subscribe and unsubscribe at runtime.
  • Separation of concerns
    The subject manages its own state, while observers handle independent reactions to changes.
  • Event-driven behavior
    Changes can automatically trigger other application components.

Disadvantages

  • Unpredictable execution cost
    In a synchronous implementation, notifying many observers can make a state-change operation slow.
  • Error propagation
    An exception thrown by one observer can prevent subsequent observers from receiving the event unless failures are handled.
  • Memory leaks
    If long-lived subjects retain references to observers that are no longer needed, those observers can remain in memory. Proper unsubscription or lifecycle management is important.
  • Notification ordering
    Observer notification order should not be relied on unless your implementation explicitly guarantees it.
  • Complex event chains
    An observer might change another subject, which triggers more observers. This can make event flows difficult to understand and can even introduce circular notification loops.
  • Concurrency concerns
    When several threads update the same subject, state updates and notification ordering must be coordinated. Thread-safe observer collections alone do not solve these problems.

For important business events, decide explicitly whether observer failures should stop an operation, be isolated, or be retried.

Observer Pattern and SOLID Principles

The Observer pattern aligns particularly well with three SOLID principles.

PrincipleHow Observer helps
Single Responsibility Principle (SRP)The subject manages its state, while each observer handles its own reaction.
Open/Closed Principle (OCP)New observer behavior can be added without changing existing subject notification logic.
Dependency Inversion Principle (DIP)The subject depends on the Observer abstraction rather than concrete implementations.

For example:

private List<OrderObserver> observers;

This is preferable to a design where the subject directly depends on:

EmailNotification email;
DashboardUpdater dashboard;
AuditLogger audit;

The Observer abstraction makes the system easier to extend and maintain.

When Should You Use the Observer Pattern

Use Observer when a change in one object should automatically trigger behavior in multiple independent components.

Good use cases include:

  • GUI event handling: button clicks, keyboard input, mouse events.
  • Notification systems: email, SMS, push notifications.
  • Monitoring applications: sensor readings, stock prices, system metrics.
  • Domain events: an order being placed, an invoice being paid, a user being registered.
  • Model-view synchronization: updating multiple views when model state changes.

Avoid introducing Observer when a simple direct method call is sufficient, especially when there is exactly one fixed dependency or when the caller must explicitly coordinate the result of the invoked operation.

Also avoid relying solely on in-memory observers for critical cross-service delivery, because an application crash can result in lost notifications.

Observer vs Strategy vs Mediator

These patterns sometimes appear similar because they reduce direct coupling, but they solve different problems.

PatternMain purpose
ObserverNotify multiple dependent objects when an event or state change occurs.
StrategySelect or replace an algorithm or behavior.
MediatorCentralize communication and coordination among interacting objects.

For example, in an e-commerce application:

  • Observer: When an order ships, notify the email, analytics, and audit components.
  • Strategy: Choose a shipping-cost calculation algorithm based on delivery method.
  • Mediator: Coordinate interactions among checkout, payment, inventory, and shipping components through a central coordinator.
Key Takeaways

The Observer pattern creates a one-to-many relationship between a subject and its observers. The subject maintains subscriptions and notifies observers when relevant changes occur, while each observer independently decides how to react.

In Java, you can implement it using your own observer interfaces, GUI listener APIs or PropertyChangeSupport.
In Spring Boot, ApplicationEventPublisher and @EventListener provide a convenient application-level event mechanism.

The central idea is that the object producing a change should not need to know every concrete component interested in that change.
This separation makes event-driven systems more modular, extensible, and loosely coupled.
