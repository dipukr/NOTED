Command

The Command Pattern is a behavioral design pattern that encapsulates a request or operation as an object, allowing the request to be parameterized, queued, logged, executed, undone, or redone independently of the object that initiates it. Instead of directly calling a method on an object to perform an operation, the Command pattern
wraps the operation inside a separate command object.

This creates a separation between:

  • The object that requests an operation — Invoker.
  • The object that performs the actual operation — Receiver.
  • The object that encapsulates the operation — Command.

By treating operations as first-class objects, the Command pattern provides greater flexibility in how operations are executed, scheduled, stored, and reversed.

Key idea: Encapsulate a request as an object, thereby decoupling the sender of the request from the object responsible for executing it.

Understanding the Problem

Imagine we are building a smart home application where a remote control can operate different devices:

  • Turn lights on-off.
  • Start-stop a fan.
  • Open-close curtains.
  • Turn a television on-off.

Without the Command Pattern

We might implement the remote control like this:

public class RemoteControl {
    private Light light;
    private Fan fan;

    public RemoteControl(Light light, Fan fan) {
        this.light = light;
        this.fan = fan;
    }

    public void pressButton(String action) {
        switch (action) {
            case "LIGHT_ON" -> light.turnOn();
            case "LIGHT_OFF" -> light.turnOff();
            case "FAN_ON" -> fan.start();
            case "FAN_OFF" -> fan.stop();
            default -> throw new IllegalArgumentException();
        }
    }
}

This implementation has several problems.

  • Tight coupling: RemoteControl directly depends on Light, Fan, and their methods.
  • Violation of the Open/Closed Principle: Adding a new device requires modifying the remote control.
  • Difficult undo/redo: The remote control must know how to reverse every operation.
  • Poor extensibility: Scheduling, queuing, and logging actions require additional conditional logic.

With the Command Pattern

Instead of knowing how to operate every device, the remote control only knows how to execute commands.

public interface Command {
    void execute();
}

public class LightOnCommand implements Command {
    private Light light;

    public LightOnCommand(Light light) {
        this.light = light;
    }

    @Override
    public void execute() {
        light.turnOn();
    }
}

The remote control becomes extremely simple:

public class RemoteControl {
    public void pressButton(Command command) {
        command.execute();
    }
}

Now the remote control doesn't need to know whether the command operates a light, fan, TV, or something else.

Any new functionality can be introduced by creating another Command implementation.

Structure of the Command Pattern

Conceptual command flow. The client configures the command and passes it to the invoker, which executes it without knowing the receiver's implementation.

Main components

ComponentResponsibilityExample
CommandDeclares an operationCommand interface
Concrete CommandImplements the operation, usually by delegating to a receiverLightOnCommand
ReceiverContains the actual business logicLight
InvokerTriggers command executionRemoteControl
ClientCreates and connects the objectsMain

The execution flow is:

  1. The client creates a receiver.
  2. The client creates a concrete command containing a reference to the receiver.
  3. The client passes the command to the invoker.
  4. The invoker calls command.execute().
  5. The concrete command delegates the actual work to its receiver.

The invoker knows only the Command interface, not the internal implementation of the operation.

Practical Example: Smart Home Remote Control with Undo/Redo

Let's implement a smart home remote control where users can turn lights on/off and undo or redo their actions.

This example demonstrates the Command pattern's main advantage: we can treat an operation as an object and maintain a history of executed operations.

Define the Command interface

public interface Command {
    void execute();
    void undo();
}

Every command must support two operations:

  • execute() performs the requested action.
  • undo() reverses the effects of that action.

Note that undo is optional in the Command pattern. We are including it because our application requires undo/redo functionality.

Create the Receiver

The receiver contains the actual functionality.

public class Light {
    private String name;
    private boolean on;

    public Light(String name) {
        this.name = name;
    }

    public void setOn(boolean on) {
        this.on = on;
        System.out.println(name + " -> " + (on ? "ON" : "OFF"));
    }

    public boolean isOn() {
        return on;
    }
}

Notice that Light knows nothing about commands, command history, or the remote control.

It simply manages the actual light's state.

Create the Concrete Command

public class SetLightCommand implements Command {
    private Light light;
    private boolean targetState;
    private boolean previousState;

    public SetLightCommand(Light light, boolean targetState) {
        this.light = light;
        this.targetState = targetState;
    }

    @Override
    public void execute() {
        previousState = light.isOn(); # Capture state before changing it
        light.setOn(targetState); # Delegate to the receiver
    }

    @Override
    public void undo() {
        light.setOn(previousState); # Restore the previous state
    }
}

Here:

  • light is the receiver.
  • targetState represents the requested operation.
  • previousState stores information needed to undo that operation.
  • execute() delegates the operation to Light.
  • undo() restores the previous state.

Why store previousState?

Suppose the light was already on and someone executes a command to turn it on again. Undoing that command should leave the light on, because that was its original state.

Simply turning the light off in undo() would be incorrect.

This illustrates an important principle: Undo should reverse the effects of a command, not blindly execute its opposite.

Create a reusable Command History manager

The command history manager will execute commands and maintain two stacks:

  • Undo stack — successfully executed commands.
  • Redo stack — commands that have been undone and can be executed again.
public class CommandHistory {
    private Deque<Command> undoStack = new ArrayDeque<>();
    private Deque<Command> redoStack = new ArrayDeque<>();

    public void execute(Command command) {
        command.execute();
        undoStack.push(command);
        redoStack.clear(); # A new action invalidates the redo history
    }

    public void undo() {
        if (undoStack.isEmpty()) return;
        Command command = undoStack.peek();
        command.undo();
        undoStack.pop();
        redoStack.push(command);
    }

    public void redo() {
        if (redoStack.isEmpty()) return;
        Command command = redoStack.peek();
        command.execute();
        redoStack.pop();
        undoStack.push(command);
    }
}

Notice that CommandHistory doesn't know anything about lights or other devices.

It can execute any object implementing the Command interface.

The example assumes synchronous, successful operations. A production implementation would additionally define failure handling and command-history limits.

Create the Remote Control (Invoker)

public class RemoteControl {
    private CommandHistory history = new CommandHistory();

    public void pressButton(Command command) {
        history.execute(command);
    }

    public void pressUndo() {
        history.undo();
    }

    public void pressRedo() {
        history.redo();
    }
}

The remote control has no knowledge of the devices it controls.

Its only responsibility is to dispatch the commands and provide undo/redo controls.

Client code

void main(String[] args) {
    Light livingRoom = new Light("Living Room");
    RemoteControl remote = new RemoteControl();
    remote.pressButton(new SetLightCommand(livingRoom, true)); # Turn on
    remote.pressButton(new SetLightCommand(livingRoom, false)); # Turn off
    remote.pressUndo(); # Undo turn off
    remote.pressUndo(); # Undo turn on
    remote.pressRedo(); # Redo turn on
}

Output:

Living Room -> ON
Living Room -> OFF
Living Room -> ON
Living Room -> OFF
Living Room -> ON

How Undo/Redo works internally

Let's visualize the command history after each action.

StepActionLightUndo stack
(top first)		Redo stack
(top first)		What happens
1Turn ONONONEmptyThe first command executes and enters the undo stack.
2Turn OFFOFFOFF, ONEmptyThe second command executes and goes on top of the undo stack.
3UndoONONOFFThe OFF command restores the previous state and moves to the redo stack.
4Undo againOFFEmptyON, OFFThe ON command is reversed and moved to the redo stack.
5RedoONONOFFThe ON command executes again and returns to the undo stack.

One important detail: if the user undoes an operation and then executes a completely new command, the redo stack must be cleared. This is because the previous redo history no longer belongs to the current sequence of actions.

Also, create a new stateful command object for each user action. Reusing the same mutable command instance for multiple history entries can corrupt undo information.

Practical Example: Text Editor with Undo/Redo

A text editor is one of the most practical examples of the Command pattern.

Consider operations such as:

  • Insert text.
  • Delete text.
  • Replace text.
  • Undo a change.
  • Redo a change.

Text editors benefit from representing each editing operation as a command object, because those commands can be stored in a history.

Create the Receiver (Document)

public class TextDocument {
    private StringBuilder content = new StringBuilder();

    public void insert(int position, String text) {
        content.insert(position, text);
    }

    public String delete(int position, int length) {
        String removed = content.substring(position, position + length);
        content.delete(position, position + length);
        return removed;
    }

    public String getContent() {
        return content.toString();
    }
}

The document provides the actual editing operations.

InsertTextCommand

public class InsertTextCommand implements Command {
    private TextDocument document;
    private int position;
    private String text;

    public InsertTextCommand(TextDocument document, int position, String text) {
        this.document = document;
        this.position = position;
        this.text = text;
    }

    @Override
    public void execute() {
        document.insert(position, text);
    }

    @Override
    public void undo() {
        document.delete(position, text.length());
    }
}

When execute() is called, the command inserts text.

When undo() is called, it removes the same text from the same position.

DeleteTextCommand

public class DeleteTextCommand implements Command {
    private TextDocument document;
    private int position;
    private int length;
    private String deletedText;

    public DeleteTextCommand(TextDocument document, int position, int length) {
        this.document = document;
        this.position = position;
        this.length = length;
    }

    @Override
    public void execute() {
        deletedText = document.delete(position, length); # Save removed content for undo
    }

    @Override
    public void undo() {
        document.insert(position, deletedText); # Restore the deleted content
    }
}

This example shows why a command object is useful.

A method call such as:

document.delete(5, 6);

doesn't inherently contain the information needed to undo the deletion.

However, a DeleteTextCommand can remember the deleted text and restore it later.

Client code

Reuse the Command interface and CommandHistory implementation from the previous example.

void main(String[] args) {
    TextDocument document = new TextDocument();
    CommandHistory history = new CommandHistory();
    history.execute(new InsertTextCommand(document, 0, "Hello"));
    history.execute(new InsertTextCommand(document, 5, " World"));
    System.out.println(document.getContent());
    history.execute(new DeleteTextCommand(document, 5, 6));
    System.out.println(document.getContent());
    history.undo();
    System.out.println(document.getContent());
    history.undo();
    System.out.println(document.getContent());
    history.redo();
    System.out.println(document.getContent());
}

Output:

Hello World
Hello
Hello World
Hello
Hello World

Important observation

The same CommandHistory class works with both:

  • Smart home devices.
  • Text editor operations.

We didn't modify CommandHistory when introducing the text editor.

This is one of the most important benefits of the Command pattern: the infrastructure for invoking and managing operations can be reused independently of the operations themselves.

The editor implementation assumes commands are applied sequentially and that document changes go through the command history. Collaborative editing, external modifications, and concurrent updates require additional conflict-handling logic.

Practical Example: Macro Commands (Executing Multiple Operations)

Another powerful use case of the Command pattern is combining multiple commands into a single command.

Consider a smart home application with a Movie Mode button.

When pressed, it should:

  1. Turn off the living room lights.
  2. Turn off the bedroom lights.
  3. Perform all operations as one action.

When the user presses Undo, all these operations should be reversed.

MacroCommand implementation

public class MacroCommand implements Command {
    private List<Command> commands;

    public MacroCommand(List<Command> commands) {
        this.commands = List.copyOf(commands);
    }

    @Override
    public void execute() {
        for (Command command: commands)
            command.execute();
    }

    @Override
    public void undo() {
        for (int i = commands.size() - 1; i >= 0; i--) # Undo in reverse execution order
            commands.get(i).undo();
    }
}

Usage

Light livingRoom = new Light("Living Room");
Light bedroom = new Light("Bedroom");
RemoteControl remote = new RemoteControl();
# Initially, turn both lights on
livingRoom.setOn(true);
bedroom.setOn(true);
# Define movie mode
Command movieMode = new MacroCommand(List.of(new SetLightCommand(livingRoom, false), new SetLightCommand(bedroom, false)));
remote.pressButton(movieMode); # Execute multiple actions with one command
remote.pressUndo(); # Restore previous state

Output:

Living Room -> ON
Bedroom -> ON

Living Room -> OFF
Bedroom -> OFF

Bedroom -> ON
Living Room -> ON

The important part is that MacroCommand also implements Command.

Therefore, the remote control doesn't need to distinguish between:

  • A command that performs one operation.
  • A macro command that performs multiple operations.

This combines the Command Pattern with the Composite Pattern, because a macro command contains other commands and exposes the same interface.

Why undo in reverse order?

Suppose a macro executes A, then B, where B depends on A. Undoing B before A is generally necessary to reverse the sequence correctly.

One limitation: this simple implementation assumes every subcommand succeeds. Production macro commands need a defined policy for partial failures, such as compensating for already-executed steps. A macro is not automatically an atomic transaction.

Practical Example: Command Queuing and Asynchronous Execution

Command objects can also be placed into queues and executed later.

Consider a backend service that receives a request to generate a large PDF report.

Generating the report might take considerable time. Rather than blocking the API request, the application can enqueue the operation and execute it asynchronously.

For this scenario, undo is unnecessary, so let's use a simpler command interface.

Define an executable command

@FunctionalInterface
public interface ActionCommand {
    void execute();
}

Create the receiver

public class ReportService {
    public void generateReport(long reportId) {
        System.out.println("Generating report: " + reportId);
        # Actual PDF generation logic
    }
}

Create a concrete command

public class GenerateReportCommand implements ActionCommand {
    private ReportService reportService;
    private long reportId;

    public GenerateReportCommand(ReportService reportService, long reportId) {
        this.reportService = reportService;
        this.reportId = reportId;
    }

    @Override
    public void execute() {
        reportService.generateReport(reportId);
    }
}

Create the asynchronous Invoker

public class CommandExecutor implements AutoCloseable {
    private ExecutorService executor = Executors.newSingleThreadExecutor();

    public void submit(ActionCommand command) {
        executor.submit(command::execute);
    }

    @Override
    public void close() {
        executor.shutdown();
    }
}

Usage

void main(String[] args) {
    ReportService reportService = new ReportService();
    try (CommandExecutor executor = new CommandExecutor()) {
        executor.submit(new GenerateReportCommand(reportService, 101));
        executor.submit(new GenerateReportCommand(reportService, 102));
    }
    System.out.println("Main thread continues...");
}

Possible output:

Main thread continues...
Generating report: 101
Generating report: 102

The main thread does not execute the report-generation logic. Instead, the executor runs the commands on a worker thread. The exact interleaving of output between threads may vary.

Where this becomes useful

The same idea appears in backend systems for:

  • Background report generation.
  • Image processing.
  • Email sending.
  • Batch processing.
  • Scheduled operations.

For production distributed applications, an in-memory Java executor is not a durable queue. If the process crashes, queued commands may be lost.

You can instead store serializable command data in a database or send it to a message broker such as Kafka or Rabbit. A worker then reconstructs or dispatches the appropriate operation. Such systems also need retry handling, idempotency, and a clear acknowledgment strategy.

Also, a simple Runnable or lambda can act as a command when only deferred execution is needed:

ActionCommand command = () -> reportService.generateReport(101);
executor.submit(command);

Dedicated command classes become more valuable when operations require distinct parameters, validation, metadata, undo behavior, or lifecycle management.

How the Command Pattern Supports Different Capabilities

The Command pattern doesn't automatically provide every feature. Rather, it provides a structure that makes these features easier to build.

CapabilityHow Command helps
DecouplingThe invoker depends on a command interface rather than the receiver
Undo/RedoCommand objects can preserve information needed to reverse operations
QueuingCommands can be stored and executed later
SchedulingA scheduler can invoke commands at a specified time
LoggingCommand identity and parameters can be recorded
MacrosMultiple commands can be combined into one
RetryA failed command can potentially be re-executed
ExtensibilityNew operations can be introduced without changing a generic invoker

For example, consider a command that transfers money.

Retrying that command blindly would be dangerous because a transfer might be processed twice. A production implementation would need an idempotency key or other mechanism to ensure the operation is not duplicated.

Likewise, undoing a money transfer would normally require a new compensating business transaction, not simply reversing some in-memory variables.

Command Pattern vs Strategy Pattern

These patterns look similar because both encapsulate behavior behind interfaces. However, their intentions differ.

AspectCommand PatternStrategy Pattern
Primary purposeEncapsulate a request or actionEncapsulate an interchangeable algorithm
Main questionWhat operation should be performed?How should the operation be performed?
Typical methodexecute()calculate(), sort(), compress()
Common usageUndo/redo, queues, scheduling, actionsSelecting algorithms or business policies

Typical examplesDeleteTextCommand, SaveFileCommandQuickSortStrategy, DiscountStrategy

Example: Strategy

public interface PaymentStrategy {
    void pay(double amount);
}

public class CardPayment implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        System.out.println("Paying by card: " + amount);
    }
}

Here, the Strategy decides how payment is performed.

Example: Command

public class PayOrderCommand implements ActionCommand {
    private PaymentService paymentService;
    private long orderId;

    public PayOrderCommand(PaymentService paymentService, long orderId) {
        this.paymentService = paymentService;
        this.orderId = orderId;
    }

    @Override
    public void execute() {
        paymentService.payOrder(orderId);
    }
}

Here, the Command represents a request to perform the payment operation.

A command can also internally use a strategy to decide how the payment should be performed.

Command Pattern vs CQRS Command

Command is also a common term in distributed system architectures, it's important to distinguish the two concepts.

The GoF Command Pattern is an object-oriented behavioral design pattern. Its main concern is encapsulating an operation so that it can be invoked independently from its creator.

A CQRS command, on the other hand, expresses an intention to change application state.

For example:

public record CreateOrderCommand(long customerId, String productId, int quantity) {}

This is a data object carrying the information needed to request an order creation.

A command handler then processes it:

public class CreateOrderHandler {
    private OrderService orderService;

    public CreateOrderHandler(OrderService orderService) {
        this.orderService = orderService;
    }

    public void handle(CreateOrderCommand command) {
        orderService.createOrder(command.customerId(), command.productId(), command.quantity());
    }
}

CQRS commands often have no execute() method, and their processing logic lives in a separate handler.

The two ideas are related through the concept of representing operations explicitly, but CQRS is an architectural pattern that separates write operations from reads. The GoF Command pattern does not require that separation.

Advantages and Disadvantages

Advantages

  • Decouples request senders from the receivers that execute operations.
  • Supports undo/redo through command history and state management.
  • Makes deferred execution, scheduling, and queuing easier.
  • Allows individual commands to be combined into macro commands.
  • Encourages the Open/Closed Principle: a generic invoker can support new commands without modification.
  • Makes individual operations easier to test in isolation.

Disadvantages

  • Can introduce many small classes and additional abstraction.
  • Undo/redo can be complicated for operations with external side effects.
  • Command history may consume significant memory.
  • Mutable commands can cause problems when reused, retried, or accessed concurrently.
  • Queuing and logging commands require additional infrastructure for durability, security, and error handling.
When Should You Use the Command Pattern

The Command pattern is especially useful when an application needs to treat operations as independent objects rather than execute them immediately through direct method calls.

Typical scenarios include GUI button actions, text editor history, task schedulers, background job processors, workflow engines, transactional compensation, and macro automation.

However, if your application only needs a simple one-time method call, using the Command pattern may introduce unnecessary complexity.

For instance:

light.turnOn();

is perfectly fine if you have no requirement for undo, queuing, logging, dynamic dispatch, or other forms of command management.

The design pattern should solve a meaningful problem, not simply add additional layers.

Interview Summary

The Command Design Pattern is a behavioral design pattern that encapsulates a request or operation as an object, thereby decoupling the object that initiates the request from the object that performs it.

The pattern introduces a common Command interface, concrete command implementations, a receiver containing the actual business logic, and an invoker responsible for triggering command execution.

By encapsulating operations as objects, it becomes possible to store, queue, schedule, log, combine, undo, and redo operations without tightly coupling the invoker to the receiver.

Remember these three fundamental ideas:

  1. Command encapsulates an operation.
  2. Invoker triggers the operation without knowing its implementation.
  3. Receiver performs the actual work.

The most recognizable real-world applications are Undo/Redo in text editors, GUI actions, macro commands, and asynchronous task execution.

Real-world example
  • Runnable — each Runnable wraps an action as an object that an executor invokes later without knowing its details.
  • swing.Action — Swing binds an Action command to buttons, menu items, and key strokes as the invokers.
  • JdbcTemplate — StatementCallback and PreparedStatementCallback encapsulate a DB operation passed to the template.
  • java.util.concurrent Callable and Future — a Callable is a queued command whose result is retrieved through its Future.
  • Undo and redo in editors — each edit is stored as a command object so it can be reversed or replayed.
  • Restaurant orders — a waiter writes an order (command) that the kitchen (receiver) later executes, decoupling the two.
  • Task queues and job schedulers — jobs are captured as command objects that workers pull and execute asynchronously.
